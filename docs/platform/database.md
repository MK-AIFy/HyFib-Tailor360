# Database

One PostgreSQL database, one schema per module, one Entity Framework context per schema.

## Schemas

| Schema | Owner | Holds |
| --- | --- | --- |
| `platform` | Platform | outbox, inbox, idempotency keys, sequences, audit events, feature flags, job leases, worker heartbeats, Data Protection keys, print jobs |
| `identity` | Identity | users, roles, permissions, branch assignments, sessions |
| `customers` | Customers | customers, consent, preferences, measurement templates and versions |
| `catalog` | Catalog | categories, service types, design options, QC checklist templates |
| `media` | Media | media objects, derivatives, quarantine, retention holds |
| `orders` | Orders | estimates, orders, garment jobs, snapshots, workflow, QC, alterations |
| `custody` | Custody | barcode identities, labels, scans, custody transfers, delivery queue |
| `inventory` | Inventory | items, suppliers, locations, ledger, reservations, stocktakes |
| `billing` | Billing | price lists, invoices, payments, receipts, cashier sessions |
| `reporting` | Reporting | read models, projections, checkpoints, export jobs |
| `notifications` | Notifications | templates, intents, deliveries, customer links, feedback |
| `integration` | Integration | webhook subscriptions and deliveries, provider configuration |

No module reads or writes another module's schema. Where a module needs another's data it uses the
published read contract, which is an interface, not a table.

## Roles

Four roles rather than one, so that a defect or a stolen credential reaches less than the whole
database.

| Role | Rights | Used by |
| --- | --- | --- |
| `t360_migrator` | `CREATE`, `ALTER`, `DROP` on every schema | the `migrate` command only |
| `t360_app` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` on tables; no DDL; no `UPDATE` or `DELETE` on `platform.audit_events` | the web and worker hosts |
| `t360_reporting` | `SELECT` on reporting read models only | scheduled report and export jobs |
| `t360_backup` | `SELECT` plus replication | backup and restore tooling |

`migrate` refuses to run as `t360_app`. Revoking `UPDATE` and `DELETE` on the audit trail from
`t360_app` is the first defence for the append-only rule; the database trigger is the second, and chain
verification is the third, which is what makes tampering detectable even by someone who can disable a
trigger.

## Connection budget

Every pooled connection is a server slot. The budget is validated at startup rather than discovered
under load:

```
MaxPoolSize × ExpectedProcessCount ≤ ServerMaxConnections − ReservedConnections
```

The reserve keeps room for an operator session, `pg_dump` and monitoring during an incident, which is
exactly when the application is most likely to be holding its whole pool. A configuration that fails
this check refuses to start, with a message naming the two settings to change.

Defaults: `MaxPoolSize` 20, `ExpectedProcessCount` 2, `ServerMaxConnections` 100,
`ReservedConnections` 20.

## Conventions

- Table and column names are `snake_case`, applied by convention rather than by attribute.
- Every instant is `timestamptz` and stored in UTC. Business dates are evaluated in the branch's
  timezone, never in UTC.
- Money is `numeric(18,4)`. Binary floating point is never used for money.
- Primary keys are UUIDv7, generated by `IIdGenerator`, so they are time-ordered and keep indexes dense.
- Optimistic concurrency uses PostgreSQL's `xmin` system column, so a conflicting write is detected even
  when the competing change came from a migration or an operator statement.

## Audit trail

`platform.audit_events` is range-partitioned by month, append-only and hash-chained. Each row's hash
covers the previous row's hash and every meaningful field, so altering one row breaks verification for
it and for every row after it.

```sql
-- Empty result means the chain is intact.
SELECT * FROM platform.verify_audit_chain();

-- Provision a month ahead of time. The worker does this daily; the command line does it on demand.
SELECT platform.ensure_audit_partition(now() + interval '1 month');

-- Zero is the healthy state. Anything else means maintenance has stopped running.
SELECT platform.audit_default_partition_rows();
```

### Partition maintenance

Partitions cannot be created on demand by the insert that needs one: PostgreSQL routes a row to its
partition **before** any row-level trigger fires, so a row for an unprovisioned month is rejected
during routing and no trigger can rescue it. Because an audit entry is written in the same transaction
as the change it records, that rejection would fail the change too — running out of partitions would
stop every state change in the system.

Two things prevent that.

1. **A default partition.** A row for a month with no partition of its own lands in
   `platform.audit_events_default` instead of being rejected. Availability is never at risk.
2. **Maintenance.** The worker provisions the current month and three ahead, at start-up and daily,
   under a job lease so one instance does it when several are running. `init-reference-data` does the
   same on demand.

`platform.audit_default_partition_rows()` reports how many entries are in the default partition, and
the `audit-partitions` health check turns a non-zero count into a degraded status. That number is the
signal that maintenance has stopped: nothing is broken yet, but those rows must be moved out before
their month can be given a partition, and `ensure_audit_partition` will refuse with an explanatory
error until they are.
