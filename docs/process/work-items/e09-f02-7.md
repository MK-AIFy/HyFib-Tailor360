Sub-issue of #42. The parent's acceptance criterion "credit/debit corrections preserve links and complete audit
trail" is met server-side by #154, and the inventory of this parent records the matching gap on the client: there is
no credit/debit-note issue screen and no way to cancel a posted invoice from the application.
`grep -rn "cancel\|credit-notes\|debit-notes" clients/pwa/src/billing/billingApi.ts` returns nothing, and
`clients/pwa/src/billing/billingPermissions.ts` names neither `billing.cancel_invoice` nor
`billing.post_credit_note`. A posted invoice is immutable by database trigger, so a compensating document is the
**only** way to correct one — which makes this the one billing screen whose absence leaves a shop with no remedy at
all.

## What is already built (do not re-build)

- `src/Modules/Billing/Tailor360.Modules.Billing.Api/Invoicing/InvoiceEndpoints.cs` — three routes:
  - `CancelInvoice` — `POST /api/v1/billing/invoices/{invoiceId}/cancel`, body `{ "reason": "…" }`,
    `Idempotency-Key` required, **`.RequireStepUp()`**, and deliberately **no `If-Match`** (nothing on the invoice's
    row moves; the row is locked and re-read inside the transaction). It appends the cancellation **and** posts a
    credit note relieving the whole amount, in one transaction; the invoice keeps its number, its lines and its
    totals, and its garment jobs become free to invoice again.
  - `PostCreditNote` — `POST /api/v1/billing/invoices/{invoiceId}/credit-notes`, body
    `{ "lines": [ { "garmentJobId": …, "taxableValue": … } ], "reason": "…" }`, `Idempotency-Key`, no `If-Match`,
    answered `201` with `AdjustmentNotePayload`.
  - `PostDebitNote` — `POST /api/v1/billing/invoices/{invoiceId}/debit-notes`, the same body and the same
    permission, adding to what the customer owes.
- `src/Modules/Billing/Tailor360.Modules.Billing.Api/Payloads/InvoiceRequests.cs` —
  `PostAdjustmentNoteRequest(IReadOnlyList<AdjustmentNoteLineRequestPayload?>? Lines, string? Reason)` and
  `AdjustmentNoteLineRequestPayload(Guid? GarmentJobId, decimal? TaxableValue)`. **A note line is keyed by the
  garment job, not by the line number**, and `taxableValue` is the taxable value moved, positive, to the paisa —
  the server taxes it at that line's own rates and rounds once per component.
- `src/Modules/Billing/Tailor360.Modules.Billing.Api/Payloads/InvoicePayloads.cs` — `AdjustmentNotePayload`
  (`noteId`, `invoiceId`, `kind` = `Credit` | `Debit`, `number`, `reason`, `currency`, `lines`, `totals`,
  `postedAt`), `AdjustmentNoteLinePayload` and `InvoiceCancellationPayload`
  (`cancellationId`, `creditNoteId`, `reason`, `cancelledAt`).
- `src/Modules/Billing/Tailor360.Modules.Billing.Domain/Invoicing/Invoice.cs` — `RemainingTaxableValueOf(jobId)`,
  which is what bounds a credit note per line at the server. **It is not projected onto any payload**: it is
  `line.TaxableValue` less the sum of every *credit*-note line for the same `garmentJobId` (debit notes are not
  subtracted). The client has the inputs — `InvoicePayload.lines[].garmentJobId` / `.taxableValue` and
  `notes[].kind` / `.lines[].garmentJobId` / `.lines[].taxableValue` — but not the answer; see the next bullet for
  what that means. And
  `src/Modules/Billing/Tailor360.Modules.Billing.Domain/Invoicing/AdjustmentNote.cs` — `AdjustmentNoteKind`
  (`Credit = 0`, `Debit = 1`).
- `src/Modules/Billing/Tailor360.Modules.Billing.Domain/BillingErrors.cs` — the refusals to explain in words:
  `billing.invoice-not-posted`, `billing.invoice-already-cancelled`, `billing.cancellation-window-closed`,
  `billing.note-line-not-on-invoice`, `billing.note-exceeds-line`, `billing.note-value-not-well-formed`,
  `billing.reason-required`, `billing.reason-not-well-formed`.
- `docs/security/permission-matrix.md` section 5 rows 373 (cancel), 374 (credit note) and 375 (debit note), and
  section 3 lines 141 and 145 for the two permissions. No matrix change is needed.
- `tests/Tailor360.IntegrationTests/Billing/InvoicePostingTests.cs` — cancellation, the credit note it posts, and
  the database refusing every `UPDATE` on a posted row, already proven.
- `clients/pwa/src/billing/billingApi.ts` — `approveReconciliation()` and `approveDispatchException()` are the exact
  shape to copy for a step-up write: `challengeOnStepUp: true`, so `apiClient` raises the re-authentication dialogue
  on `403 security.step-up-required` and **replays the identical request with the same key**. A call site never
  answers a step-up refusal itself (`clients/pwa/CLAUDE.md` section 2).
- `clients/pwa/src/routes/billing/ReconciliationApprovalRoute.tsx` and `AllocateAdvanceRoute.tsx` — the house
  pattern for a reasoned, stepped-up write, including the reason hint
  (`billing.allocate.reason.hint`: "Required because this moves money against the automatic rule").
- `clients/pwa/src/components/dialogs/ConfirmDialog.tsx`, `confirmTiers.ts` (`reason` tier, mandatory typed reason,
  audited) and `clients/pwa/src/components/states/OfflineBlockedAction.tsx`.
- `clients/pwa/src/routes/billing/InvoiceDetailRoute.tsx` and the `Invoice`, `AdjustmentNote` and
  `InvoiceCancellation` types — **E09-F02-4**; the document view and per-note download — **E09-F02-5**.
- `clients/pwa/src/billing/denominationCount.ts` and its spec — **the precedent this slice needs.**
  `clients/pwa/src/billing/types.ts`'s own header says this module "never adds, multiplies or rounds" an amount,
  **with one named exception**: the denomination count sheet, which "totals what a cashier counted so the screen can
  show it before the server is asked; the server recomputes the same total from the same rows and is the only version
  that is ever stored." Read that module and its comment before writing any arithmetic here.

## What is missing

- No client call for cancel, credit note or debit note.
- No note-issuing screen: nothing lets a person choose the garment-job lines and the taxable value to relieve or add.
- `clients/pwa/src/billing/billingPermissions.ts` names neither key, so no screen can even filter on them.
- No message explains `billing.note-exceeds-line` — the one refusal a person meets by ordinary mistake (relieving
  more than a line still carries).
- **No sanctioned place to compute what a line still carries, or what the note will move.** Both are money
  arithmetic, which `clients/pwa/src/billing/types.ts` forbids outside its one named exception. The screen needs
  both; the rule must therefore be **extended deliberately and in the same words**, not quietly broken — see Scope.
