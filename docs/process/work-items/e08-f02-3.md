## Scope

- [ ] **`POST /api/v1/inventory/movements`** — one command for five types: `issue`, `consumption`, `return`,
      `wastage`, `adjustment`. Body: type, item, location, quantity with its unit, optional garment job and phase,
      optional reservation, reason code, optional `correctsEntryId`. Posts exactly one ledger entry through
      `ILedgerPoster`. `RequirePermission("inventory.record_movement", BranchScope.CurrentBranch)`,
      `RateLimitPolicyNames.Write`, `.Audited("inventory.movement.posted", reasonRequired: true)`,
      `.RequireIdempotency()`, `.TouchesNoBranchOwnedResource(reason, "#39")`, `RequestTimeoutPolicies.Command`.
      **`reasonRequired: true` because the permission is declared `RequiresReason: true`** —
      `AuthorisationProbeApplication.cs:721` pairs the two from the catalogue. It is metadata: nothing in `src/Hosts/`
      reads it, so the handler validates the reason code and writes it onto the audit entry through
      `IInventoryAuditWriter` itself (`AuditedEndpointMetadata.cs:5-6` — the filter is #21's, and #21 is open).
- [ ] **The per-type rules**, each a refusal with a stable `inventory.*` code and the field named, never a raw
      database error:
  - `issue` requires a garment job. Where a reservation is named it resolves it `Held → Consumed` **and that is the
    only posting that ever does** (`E08-F02-1`'s fold; `E08-F02-2`'s state machine), and it resolves it **in full
    whatever it issues**: `reserved` falls by the reservation's whole held quantity, not by the quantity issued, so
    issuing 4 against a hold of 10 releases all 10 and leaves no residual hold. There is no partial reservation state.
    A reservation already resolved, or for another item or location, or for another job, is refused with
    `inventory.reservation-not-drawable`. An `issue` with **no** reservation named is ordinary and moves `on_hand`
    only — it must not touch `reserved`, which would drive it negative and be refused by the poster's own guard.
  - `consumption` and `return` require a garment job, touch **no** reservation, and may not exceed what the job still
    holds of that item at that location — `held = Σ issue − Σ consumption − Σ return`, computed over the ledger for
    that `(job, item, location)`. Over-consuming is `inventory.nothing-issued-to-consume`. This is the guard that
    makes the fold honest: `Consumption` moves no balance component, so without it a job could "use" material that
    never left the shelf.
  - `wastage` requires a reason code; a garment job is optional, because cloth spoils on the shelf as well as on the
    table (T4).
  - `adjustment` requires a reason code; with reason `correction` it requires `correctsEntryId`, and the correcting
    entry must name the same item and location as the entry it corrects and carry the opposite sign. The corrected
    entry is **never** updated (INV-STK-01; the trigger refuses it anyway). An `adjustment` is subject to the
    negative-stock guard exactly like every other type, so it is not a way round it; a stocktake posting, which is the
    other thing an adjustment could be, is #40 and is refused no differently here.
- [ ] **The negative-stock policy** — `IFeatureFlags` key `inventory.allow_negative_stock`, evaluated per branch with
      `new OrganisationContext(organisationId, branchId)`. Off (the default for an unconfigured flag, and **FSR-05**'s
      default in force) means a movement that would take `on_hand` below zero is refused with
      `inventory.negative-stock-blocked`. That this is configuration rather than code is not a choice made here:
      `docs/prd/configurable-vs-fixed.md` line 71 reads "Negative-stock policy — block, or allow with approval | Yes,
      configuration | Owner or Admin | Audited", and a feature flag is the only per-branch configuration mechanism
      that exists today — it takes a branch override (`docs/platform/feature-flags.md`, "Evaluation"), it is changed
      only with a reason and is audited, and the existing surfaces are the `flags set` command of the command-line
      tool and `/api/v1/admin/feature-flags` (`IdentityRoutes.cs:40`, behind `admin.feature_flags`). **Name the
      tension for the reviewer rather than hiding it:** `docs/platform/feature-flags.md` also says a flag is
      temporary, and this one is a standing business policy, so record in the pull request that it is the interim
      mechanism under FSR-05 and that a durable branch setting is a follow-up if FSR-05 confirms the policy. Nothing
      is seeded here.
- [ ] **`POST /api/v1/inventory/movements/approved-negative`** — the same command, for the branch that has the flag on
      and the movement that needs authority. Declares `RequirePermission("inventory.approve_negative_stock",
      BranchScope.CurrentBranch)` and therefore `.RequireStepUp()` (ARCH-018), a mandatory reason,
      `RateLimitPolicyNames.Write`, `.Audited("inventory.movement.posted_negative", reasonRequired: true)`,
      `.RequireIdempotency()`. It is a **second route rather than a second permission on the first**, because a
      permission checked inside a handler cannot carry the step-up ARCH-018 enforces at the endpoint, and ARCH-022 and
      the contract tests read exactly one declared permission per route. With the flag off the route refuses with
      `inventory.negative-stock-blocked` as well, so turning the flag off is sufficient to close the path.
- [ ] **`GET /api/v1/inventory/movements/{entryId}`** — one posted entry with its type, base quantity, references,
      reason code, actor and the entry it corrects. `inventory.record_movement`, `RateLimitPolicyNames.DefaultUser`,
      `RequestTimeoutPolicies.Read`, `.ScopedToResource(InventoryResourceKinds.LedgerEntry, "entryId")`; another
      branch's entry reads as **404**. `unit_cost` is **not** on this payload: it is Confidential cost data and is
      read only under `inventory.view_valuation` in `E08-F02-7`.
- [ ] **`InventoryResourceKinds.LedgerEntry = "inventory.ledger_entry"`** and its `IResourceScopeResolver`.
- [ ] **`inventory.stock-consumed.v1`** — ledger entry id, item id, location id, base quantity, job id, phase code,
      branch code, exactly as `stock-reservation.md` section 5 fixes it, published on a `consumption` posting only.

- [ ] Matrix rows for the three routes in `docs/security/permission-matrix.md` section 5, the `identifier-editing`

## Acceptance criteria

- [ ] A caller holding `inventory.record_movement` issues material against a garment job over HTTP, then records a
      consumption and a return against the same job, and the three ledger entries and the resulting balance match the
      fold: `on_hand` falls by the issue and rises by the return, the consumption moves no balance component, and the
      named reservation ends `Consumed` **at the issue**. The balance and the reservation row are asserted through the
      `InventoryDbContext` in the test, not over HTTP: this child publishes no balance read, and `E08-F02-7`, which
      does, must not become a dependency of this child's criteria.
- [ ] **Traceability (the parent's fifth criterion):** every `issue`, `consumption` and `return` entry carries the
      garment job identifier, and `GET /api/v1/inventory/movements/{entryId}` answers with it, so consumption is
      traceable to the job that caused it without any module reading `orders.*`.
- [ ] **Correction (the parent's fourth criterion):** a correcting `adjustment` with reason `correction` posts a new
      entry carrying `correctsEntryId`; the corrected entry is byte-for-byte unchanged afterwards; an `adjustment`
      with reason `correction` and no link is refused, and a correcting entry with the same sign as the entry it
      corrects is refused.
- [ ] **Negative:** a consumption larger than the job holds is refused with `inventory.nothing-issued-to-consume` and
      posts nothing; a `wastage` with no reason code is refused naming the field; a caller without
      `inventory.record_movement` gets 403 and is audited; another branch's `{entryId}` reads 404; a replayed
      `Idempotency-Key` returns the first outcome and posts no second entry.
- [ ] **Negative-stock policy:** with the flag off, a movement that would take `on_hand` below zero is refused with
      `inventory.negative-stock-blocked` on **both** routes; with the flag on for that branch, the ordinary route
      still refuses and `movements/approved-negative` succeeds only for a caller holding
      `inventory.approve_negative_stock` with a fresh step-up and a reason. A caller holding the key **without**
      step-up gets `matrix.yaml`'s `step-up` answer — 403 `security.step-up-required` — and nothing is posted; a
      caller without the key gets `not-permitted`, 403 `security.forbidden`.
- [ ] Every route declares exactly one permission and one rate-limit policy, both commands carry the audit filter and
      idempotency, and the `{entryId}` route declares a resource scope (ARCH-007, ARCH-008, ARCH-017, ARCH-018,
      ARCH-022, ARCH-023).
- [ ] A refused movement of any kind leaves no ledger entry and no balance change.
