## The two readings this sub-issue has to settle, and the one it implements

Both are settled here, in the body, so no session has to decide mid-flight.

1. **Anonymous, not session-gated.** The #52 blueprint says "session-authenticated"; plan Section 4.4 line 276
   lists "telemetry ingest" among the "justified `[AllowAnonymous("reason")]` endpoints". **Implement the
   anonymous reading**, for two checkable reasons: the events worth having most are the ones from a client that
   could not start — the unsupported-configuration page of **[E12-F03-3]** renders before `SessionProvider` — and a
   batch flushed on page hide goes through `navigator.sendBeacon`, which cannot attach the anti-forgery header.
   The same-origin guarantee comes from `UseTailor360OriginChecks()`, not from the cookie. When a session does
   exist the cookie travels anyway and the handler may correlate with it; it never requires it. The justification
   string says all of this and cites `#52`.
   **And the anonymity is bounded by a per-endpoint origin requirement, not by the global middleware.** Because the
   route is anti-forgery-exempt, it declares its own filter refusing a request that carries neither `Origin` nor
   `Sec-Fetch-Site` — the same rule `RequireDeclaredOrigin` would apply globally, applied to this one route, reusing
   `OriginValidationMiddleware.ErrorCode` (`security.cross-site-request`) and `SecurityProblemDetails.WriteAsync`
   so there is one wire shape for "refused as cross-site" and not two. Without it the endpoint is an open,
   unauthenticated write surface and the threat-model entry below cannot be honestly closed.
2. **ARCH-008 without an architecture decision record.** The endpoint is a `POST`, so ARCH-008 fires, and its
   register says the rule admits **no** exception without an ADR. Do not seek one. Declare
   `.Audited("observability.client_telemetry_refused")` and have the handler write the row **only when a batch is
   refused** — outside the allowlist, over the size cap, or unparseable — at most one row per refusal reason per
   minute per route with a count, following the coalescing plan Section 4.4 already applies to `authz.denied`.
   An accepted batch changes no business state and writes no row. ARCH-008's own text allows this: it "asserts the
   declaration, not the effect", and "a pull request adding an `.Audited(…)` endpoint owes an integration test that
   the row appears" — which the refusal test provides. If a reviewer prefers a blanket exemption instead, that is
   an ADR and a rule amendment, and it is **not** something this session does on its own authority.

## Acceptance criteria

- [ ] A same-origin `POST /api/v1/telemetry/client` with a well-formed batch and **no session cookie** is answered
      `202` with an empty body, and each allowlisted event appears once as a structured log record carrying the
      request's correlation identifier.
- [ ] Every route this sub-issue adds declares a justified anonymous exposure (ARCH-007), exactly one rate-limit
      policy from the catalogue (ARCH-017), the audit filter (ARCH-008) and no permission alongside the
      justification (ARCH-022); it accepts exactly one authentication scheme (ARCH-019); and its payload types are
      declared in `Tailor360.Web` (ARCH-013). The contract tier proves all six.
- [ ] **Negative — cross-origin:** the same request with a foreign `Origin`, or with `Sec-Fetch-Site: cross-site`,
      is refused by `UseTailor360OriginChecks()` before the handler runs, as `security.cross-site-request` problem
      details, and nothing is logged as telemetry.
- [ ] **Negative — no declared origin at all:** a request carrying neither `Origin` nor `Sec-Fetch-Site` — a plain
      `curl -X POST` — is refused `403` with `security.cross-site-request` by this route's own filter, and nothing
      is logged as telemetry. This is the case the global middleware deliberately lets through
      (`RequireDeclaredOrigin` is `false`) because anti-forgery normally catches it, and this route is
      anti-forgery-exempt. Without this test the endpoint is open.
- [ ] **Negative — wrong content type:** a `text/plain` body is refused `415` with problem details, not with a
      framework error page, and the refusal is audited like any other.
- [ ] **Negative — redaction, with sentinel values:** a batch whose attributes carry a customer name, a phone
      number, a measurement value, a full stack trace, a URL with a query string and a route parameter value is
      accepted, and **none of the six sentinels appears in any log record, metric label, trace attribute or
      response**. The test asserts on the emitted records, not on the handler's return value, and it is the test
      `docs/nfr/data-classification.md` section 5.18 promises.
- [ ] **Negative — unknown event type:** a batch of events none of which is in the allowlist is refused as problem
      details, **one** audit row is written for that refusal reason in the minute however many times it is repeated
      — asserted at normal coalescer capacity, because `AuthorisationDenialCoalescer` deliberately records every
      refusal once its window is full and the test must not assert a guarantee the type does not give — and no
      event is emitted.
- [ ] **Negative — oversize:** a batch over the configured event count or body cap is refused with problem details
      and nothing partial is emitted.
- [ ] **Negative — rate limit:** requests above the `telemetry-ingest` policy are answered `429` with
      `Retry-After`, and the rejection is **not** audited — it is not one of `AuditedPolicies`, which is asserted.
- [ ] **Exception — ingest disabled:** with `ClientTelemetry:Enabled` false the route still answers `202` and emits
      nothing, so a client never changes behaviour because an operator turned ingestion off.
- [ ] `docs/api/openapi.v1.json` and `clients/pwa/src/api/schema.d.ts` are regenerated and committed;
      `OpenApiDocumentTests`, the Spectral lint and `generate:api:check` are all green.
