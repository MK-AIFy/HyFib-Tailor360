      `ReportingDbContext.SchemaName`; no handler calls `SaveChangesAsync`.
- [ ] **What each order-scoped event may and may not write, because this is where a projection quietly invents a
      product rule.** `OrderConfirmed` and `OrderRevised` both carry an **order-level** `DueDate` and a
      `RevisionNumber`; `OrderRevised` additionally carries `RevisedGarmentJobIds`. Neither carries a per-garment
      due date. Therefore `OrderRevised` writes `revision_number`, `order_number` and `last_event_at` on the
      garments it names and **nothing else** — it does **not** write `due_date`, `original_due_date` or
      `reschedule_count`. A garment's promised date moves on `GarmentJobRescheduled` alone, the only event carrying
      a per-garment `DueDate` **and** `PreviousDueDate`, and `reschedule_count` counts those events alone. Writing
      the order's date onto its garments would fabricate a rule no document states, and counting a revision as a
      reschedule would double-count every revision that also reschedules. `OrderCancelled` closes every garment
      found by `order_id` (it carries no garment list) unless a `GarmentJobCancelled` closed it first, and never
      overwrites an `exit_reason_code` that is already set.
- [ ] **Out-of-order and duplicate delivery are the normal case, not the exception.** A job row is created by
      whichever of `GarmentJobCreated` / `OrderConfirmed` / a phase event arrives first (`InvoiceScenes.cs`
      publishes the jobs before the confirmation on purpose for exactly this reason), and `last_event_at` plus the
      inbox row are what make a redelivery a no-op.

## Acceptance criteria

- [ ] A synthetic stream published through `IOrdersEventPublisher` and dispatched — confirm an order of three
      garments, start production, move two through phases, hold and resume one, reschedule another, cancel a third,
      pass one through the ready gate — leaves `projections_job_pipeline` with one row per garment carrying the
      phase it is in, the accumulated held seconds, the reschedule count and, for the cancelled garment,
      `lifecycle_state = Closed` with its reason code.
- [ ] `projections_job_phase_duration` elapsed time for a phase that was started, paused twice and completed
      equals the wall-clock span minus the paused spans, and `pause_count` is 2.
- [ ] **Rebuild equals live** (#45's fifth acceptance criterion): `rebuild-projection` over the same stream
      reproduces both tables row for row and field for field, including `held_seconds_total`.
- [ ] **Negative — redelivery:** dispatching the same stream twice changes no row and leaves the checkpoint
      unmoved on the second pass; the inbox row, not a guard in the projector, is what makes that true.
- [ ] **Negative — out of order:** a phase event, then `GarmentJobCreated`, then `OrderConfirmed` for the same
      garment produces the same row as the forward order, with no row created twice. `order_number` is the
      deliberate exception and the test says so: it is null until the order-scoped event arrives, because no
      garment event carries it, and the assertion is that `OrderConfirmed` back-fills it whichever side of the
      garment events that event lands on.
- [ ] **Exception — a revision after confirmation:** `OrderRevised` naming `RevisedGarmentJobIds` raises
      `revision_number` on exactly those garments and leaves `due_date`, `original_due_date` and
      `reschedule_count` **untouched**, because the event carries no per-garment date; a following
      `GarmentJobRescheduled` for one of them is what moves that garment's `due_date` and makes its
      `reschedule_count` 1. No history is deleted and no row is removed. A test asserts both halves, because
      writing the order's date onto its garments is the plausible wrong answer.
- [ ] No `reporting.*` table is read or written by any other module, and `ReportingDbContext` maps nothing outside
      `reporting` (ARCH-005); no Reporting project references `Orders.Infrastructure` or `Orders.Api` (ARCH-011).
