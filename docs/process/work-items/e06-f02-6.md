Sub-issue of #33. Assignment has two halves and they are separated on purpose: the record of **who may do what**,
and the act of **giving somebody a job**. This slice is the first half — the `assignee_capabilities` and
`assignments` tables that `docs/architecture/module-ownership.md` line 409 assigns to the `orders` schema
("Allotment with reason; capability and capacity used to validate it"), the domain types, and the three routes a
Tailor Master administers capabilities through. Neither table exists: the only Orders migration,
`20260911141153_InitialOrdersSchema`, creates twelve tables and neither is among them, and `grep -rn "Capability"
src/Modules/Orders` returns nothing.

## What is already built (do not re-build)

- `src/Modules/Identity/Tailor360.Modules.Identity.Contracts/Directory/IUserDirectory.cs` — `FindAsync`,
  `FindManyAsync`, `ListActiveInBranchAsync(branchId)` and a permission-holder count. Its own doc comment names this
  issue: "Orders validating that a job can be assigned to somebody (#33)". `ListActiveInBranchAsync` already returns
  **only** accounts that are active and assigned to the branch, because "offering either as an assignee would
  produce a job nobody can pick up" — so same-branch and active-user are answered by this contract and must not be
  re-derived from a local table.
- The same file states there is **no skills attribute** and why: "which skills exist, whether they are a seeded
  vocabulary or free text, and whether they gate assignment or merely rank it are product decisions with no source".
  A capability row here is therefore keyed on a **category code and a phase code**, which are both configuration this
  product already owns, and not on a skill name.
- `src/Modules/Orders/Tailor360.Modules.Orders.Infrastructure/Persistence/OrdersDbContext.cs` — `ModuleDbContext`
  conventions and the `UseRowVersion` helper.
- E06-F02-1's `WorkflowPhase.required_role_keys` — the role half of eligibility, which lives on the workflow version
  and is not duplicated here.
- E06-F02-4's `job_phases`, `OrdersResourceKinds.GarmentJob` and `GarmentJobScopeResolver`.
- `src/Platform/Tailor360.Platform.Abstractions/FeatureFlags/IFeatureFlags.cs` —
  `IsEnabledAsync(flagKey, OrganisationContext(OrganisationId, BranchId), ct)`, which is how a **branch-scoped**
  setting is read in this solution. Unknown flags evaluate **off**, and the file says so: "a missing flag never
  enables an unfinished feature".
- `src/Modules/Billing/Tailor360.Modules.Billing.Infrastructure/Payments/PaymentScopeResolver.cs` — the resource
  scope resolver shape to copy for the capability row.

## Out of scope

Assigning, reassigning and unassigning a job, the eligibility evaluation and the workload view (E06-F02-7).
**Teams**: plan Section 8 says assignment may be to a "Tailor Master/tailor/team" and `assignee_capabilities` is
"user or team" by category and phase, but there is no team anywhere in this solution. `IUserDirectory` has no team,
Identity has no team table, and no document defines who may create one or what a team's branch reach is.
Capabilities and assignments are **per-user** here, and the team question is recorded in Open decisions below
rather than invented. Daily capacity is
stored and is not yet enforced (E06-F02-7 uses it for the workload view; no document fixes what happens when it is
exceeded). The Team screen is E06-F02-13.

## Acceptance criteria

- [ ] A Tailor Master grants a capability over HTTP (branch, user, category code, phase code, a valid-from date and a
      reason), reads it back in the branch list, end-dates it with a reason, and the end-dated row is still returned
      by the history read with both its grant and its revocation reason — no row was updated in place and none was
      deleted.
- [ ] Every route this issue adds declares a permission, exactly one rate-limit policy, an audit action on each write
      and a resource scope where it takes an identifier (ARCH-007, ARCH-008, ARCH-017, ARCH-023), with a matching row
      in section 5 of `docs/security/permission-matrix.md`.
- [ ] **Negative:** granting a capability to a user who is not active in the caller's branch is refused with a named
      problem detail and no row is written — and the check goes through `IUserDirectory`, proven by a test that
      suspends the account and repeats the call.
- [ ] **Negative:** a caller in another branch reading or revoking a capability by its identifier receives `404`, not
      `403`; a caller without `orders.assign` receives `403` `security.forbidden` and the denial is audited.
- [ ] **Negative:** an `UPDATE` or `DELETE` against `orders.assignments` as the application role is rejected by the
      database trigger, asserted by an integration test that attempts both.
- [ ] **Exception:** re-granting the same capability on the same `valid_from` is refused by the unique index and
      surfaces as a named result, not a raw `PostgresException`. Re-granting after a revocation succeeds and creates
      a second row, so a capability can be restored without rewriting history.
- [ ] `migrate --dry-run` then `migrate` apply cleanly and `Down` has been executed once.

whose examples list "assignee capabilities" and "workload and throughput figures attributable to a named tailor"
explicitly.
