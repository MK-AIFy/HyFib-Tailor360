Sub-issue of #33. E06-F02-6 records who may do what; this slice gives somebody a job. It is the other half of
`docs/prd/state-transitions.md` line 220 — "Assign or reassign a phase — **REASON** … Same branch, active user,
role permitted for the phase, and a capability row for the job's category and phase unless
`Workflow:RequireCapabilityMatch=false` … New `assignments` row; `JobAssigned` or `JobReassigned` … Reassignment
is a new row, never an update: earlier completions stay attributed to the previous assignee. An ineligible assignee
is rejected with the failing eligibility reason." Nothing implements it: there is no assignment handler, no route, and
no `orders.job-assigned.v1` event in `src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Events/`, whose ten
existing events cover estimates, confirmation, revision, cancellation, creation, production entry, holds, reschedules
and readiness and not assignment.

## Acceptance criteria

- [ ] A Tailor Master assigns the Cutting phase of a job to an eligible tailor over HTTP with a reason, reassigns it
      to a second tailor with a reason, and then unassigns it — and the assignment history read back shows **three**
      rows with the first two superseded and their original assignees, reasons and instants intact. This is the
      parent's fourth acceptance criterion: "Reassignment preserves complete history and does not change prior work
      ownership."
- [ ] A phase already completed by the first assignee still names that assignee after the reassignment, asserted by
      reading the completed `job_phases` row's `transitioned_by` and the superseded assignment together.
- [ ] Both routes this issue adds declare a permission, exactly one rate-limit policy, an audit action and a
      resource scope for `{jobId}` (ARCH-007, ARCH-008, ARCH-017, ARCH-023), with a matching row in section 5 of
      `docs/security/permission-matrix.md`.
- [ ] **Negative, and this is half the parent's second acceptance criterion:** each of the five eligibility rules is
      refused server-side with its own reason code — a tailor from another branch, a suspended account, a role the
      pinned phase does not permit, no capability row for the job's category and phase, and a job on hold. Each
      refusal is a `422`-class problem detail naming the failing rule, and **no** `assignments` row is written.
- [ ] **Negative:** with `workflow.capability-match-not-required` on for the branch, the capability rule alone stops
      refusing and the other four still refuse. Proven by toggling the flag in the test, not by reading the code.
- [ ] **Negative:** a caller without `orders.assign` receives `403` `security.forbidden` and the denial is audited; a
      `{jobId}` from another branch returns `404`.
- [ ] **Negative:** two concurrent assignments of one phase to two different tailors produce exactly one current
      assignment — the partial unique index on `(garment_job_id, job_phase_id) WHERE superseded_at IS NULL` refuses
      the loser, which surfaces as `409` with `OrdersErrors.ConcurrentChange`, never as a raw `PostgresException`.
- [ ] **Exception:** unassigning a phase that has no current assignment is refused with a named problem detail rather
      than silently succeeding, and reassigning to the same person is refused as a no-op with its own reason code
      rather than writing a second identical row.
- [ ] The assignment write stays inside the command objective as an **indicative** measurement: paste the wall-clock
      for 50 sequential assignments at the peak-day volume of `docs/nfr/capacity-and-performance.md` section 2 (346
      garment jobs). It is indicative and not a gate: `docs/nfr/traceability.md` NFR-LT-02 is "proposed, to be
      confirmed; proof scheduled (#52, #58)", its named proof is a k6 scenario, and `tests/load` does not exist in
      this repository. The binding measurement is E06-F02-14's.
