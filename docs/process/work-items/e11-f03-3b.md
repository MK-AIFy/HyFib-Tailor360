## Scope

- [ ] `GET /api/v1/notifications/feedback/metrics` — the aggregate for the caller's branch and a date range:
      count and mean per dimension (overall, fit, stitching quality, design match, timeliness) plus the 1–5
      distribution of each; response rate (responses ÷ feedback tokens issued in the window); alteration-request
      rate; contact-request rate; cases opened and cases closed in the window; and median and 90th-percentile time
      to closure. `RequirePermission(NotificationsPermissions.ReadFeedback, BranchScope.AssignedBranches)`,
      `TouchesNoBranchOwnedResource("the window is aggregated over the caller's own assigned branches and the route
      takes no resource identifier", "#49")`, `RateLimitPolicyNames.DefaultUser`,
      `RequestTimeoutPolicies.Report`. No audit filter: the payload carries no customer reference and no free text,
      so there is nothing sensitive about the read (contrast the two detail reads of [E11-F03-3], which do carry
      `.Audited(…)` for exactly that reason).
- [ ] **No free text in the response and no text analysis anywhere.** The parent's "fit/quality themes" are the
      per-dimension distributions and the alteration rate — the words never leave the row they are stored on.
      Say that in the route's own `WithDescription`, so the next person does not add a word cloud.
- [ ] The entry kinds `notifications.feedback.received`, `notifications.service_recovery.opened` and
      `notifications.service_recovery.closed` on **#212's** `NotificationsTimelineSource`, each with
      `ExpandPermission = NotificationsPermissions.ReadFeedback`, `ReferenceType`/`ReferenceId` naming the response
      or the case, `BranchId` set so the composer can scope it, `ActorDisplayName` null for the received entry
      (the customer is not an actor and must not be named there) and the staff owner's name for the case entries,
      and a `Title`/`Detail` that is operational prose and a configured code only — never the comment, never the
      contact note, never the `reason` a member of staff typed. `Reason`/`ReasonPermission` stay null: the
      case's reason text is audit-trail material, and `ITimelineSource` line 131 forbids freehand staff text here
      as flatly as it forbids the customer's.
- [ ] `docs/reports/feedback-metrics.md` — the directory's first file. One entry per metric above: formula, source
      rows and columns, denominator, exclusions (cancelled orders, responses outside the window, tokens issued but
      never resolved) and the statement that no metric carries free text. Every entry is marked **proposed,
      awaiting owner sign-off**, and **no threshold, target or benchmark is written**, because none is sourced —
      plan #45 requires "owner sign-off recorded" for its own dictionary and that sign-off has not happened for
      either. When #45 creates `docs/reports/metrics.md` it links to this file rather than restating it; say so in
      this file's own first paragraph so #45 inherits the instruction.

## Acceptance criteria

- [ ] A Branch Manager reads the metrics for their own branch over a seeded window and every number equals one
      computed by hand in the test from the same fixture — the counts, the five means, the five distributions, the
      response rate, both rates and both closure percentiles.
- [ ] Rule-level: the route declares `feedback.read` with a branch scope (ARCH-007), exactly one rate-limit policy
      (ARCH-017), and `TouchesNoBranchOwnedResource` with a justification because it takes no route parameter
      (ARCH-023). It declares no permission and an anonymous justification together (ARCH-022) and accepts one
      authentication scheme (ARCH-019). A row is added to the `<!-- matrix:endpoints -->` block of
      `docs/security/permission-matrix.md` (lines 311–512).
- [ ] Negative: a caller holding no `feedback.read` gets `403 security.forbidden`; an unauthenticated caller gets
      `401 security.authentication-required` — the answers named in
      `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`'s `answers` block.
- [ ] Negative: a window whose end precedes its start, and a window longer than the maximum the route accepts, are
      both refused with RFC 9457 field errors on the query parameters — never silently swapped and never clamped.
- [ ] Negative: the payload contains no customer identifier, no order identifier and no comment. A test asserts the
      serialised body against the seeded comment string and against the seeded customer's identifier.
- [ ] Exception: a window with no responses answers `200` with zero counts, **null** means and null percentiles —
      not `404`, not zeros masquerading as measurements, and not a division error. The response-rate denominator
      being zero is the defined case and is answered as null, not as 0%.
- [ ] Exception: a window in which tokens were issued but none resolved gives a response rate of 0 (a real zero,
      because the denominator is non-zero) — the test distinguishes this from the null case above, since confusing
      the two is how a branch comes to look as though nobody ever answers.
- [ ] A feedback response, a case opening and a case closure each produce exactly one timeline entry, composed by
      the host alongside Customers' source, and none of the three carries the comment, the contact note or a
      staff-typed reason. Asserted over the composed timeline payload, not over the source in isolation.
- [ ] Negative: a caller without `feedback.read` sees the three entries' `ExpandPermission` withheld exactly as
      Customers' entries are, and no entry body leaks through the composer.
