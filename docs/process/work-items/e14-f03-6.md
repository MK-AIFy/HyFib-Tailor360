## What is missing

- A document stating, per operation, its semantics and therefore its policy. Without one, "bounded retry" is decided per
  call site, which is how a retry comes to duplicate a payment.
- A bulkhead and a circuit breaker on the one external dependency that exists today, object storage.
- A non-essential health check for object storage, so `failure-modes.md` section 5's "Storage reports **Degraded** on
  `/health/detail`" is true.
- The in-process liveness watchdog on both hosts.

      existing file or document; no new threshold invented except the two this issue introduces, which are named as
      **proposed, to be confirmed** and listed in the open-decisions table below.
- [ ] **`ResilientObjectStorage`** in `src/Modules/Integration/Tailor360.Modules.Integration.Infrastructure/Storage/`,
      decorating whichever `IObjectStorage` the existing factory selects: a **bulkhead** bounding concurrent calls, a
      **circuit breaker** that opens after a configured number of consecutive failures and half-opens after a configured
      break, and a per-call timeout. When the breaker is open the call fails fast with a distinguishable result so a
      caller can answer `503 media.unavailable` rather than hanging — it never silently succeeds (principle 3).
- [ ] **`ObjectStorageOptions`** extended with the bulkhead, breaker and timeout settings, validated by the existing
      `ObjectStorageOptionsValidator.cs` pattern (there is already a contract test for it at
      `tests/Tailor360.ContractTests/Adapters/ObjectStorageOptionsValidatorTests.cs` — extend it).
- [ ] **`ObjectStorageHealthCheck`** registered with `tags: [HealthCheckTags.NonEssential]`, reporting `Degraded` when
      the breaker is open or a probe fails, and **never** `Unhealthy` and never on the readiness tag. Registering it
      needs the health-check abstractions on `Tailor360.Modules.Integration.Infrastructure.csproj`. **Check first
      whether they already resolve transitively**: that project references `Tailor360.Platform.Persistence`, which calls
      `AddHealthChecks()`, so the types may already be in scope and an extra `PackageReference` would be noise. If one
      is needed, `Microsoft.Extensions.Diagnostics.HealthChecks` is already pinned in `Directory.Packages.props` at line
      24 (10.0.11) and `…HealthChecks.Abstractions` at line 25, so only the reference is added and
      `Directory.Packages.props` itself is **not** touched — which removes this issue's contention on that file unless a
      resilience package is chosen. Note also that `IntegrationModuleServiceCollectionExtensions` does not call
      `AddHealthChecks()` today; adding the check means adding that call beside the existing
      `TryAddSingleton<IObjectStorage>` factory at lines 41-53.
- [ ] **The liveness watchdog** in both hosts: a hosted service that runs `HealthCheckService.CheckHealthAsync` over
      the `HealthCheckTags.Live` predicate on an interval **with its own timeout**, and after three consecutive failures
      exits with code 70, so `restart: unless-stopped` recovers a container that Compose will not restart itself. This
      is specified, not invented — `docs/architecture/container.md` lines 176-177 and
      `docs/architecture/failure-modes.md` section 2. Its interval and failure count are configuration. **Read this
      before designing it.** Today the only `Live`-tagged check on either host is `self`, which is `() =>
      HealthCheckResult.Healthy()` — `src/Hosts/Tailor360.Web/Program.cs:94-97` and
      `src/Hosts/Tailor360.Worker/Program.cs:86`. It cannot return anything but Healthy, so a watchdog that only reads
      its *status* can never fire, and the feature would be untestable and useless. Two consequences: (a) the watchdog
      must treat **its own timeout or an exception** as a failure, which is what actually catches thread pool starvation
      and a deadlocked process — the condition `container.md` is describing; (b) ADR-0010 line 241 and `container.md`
      line 170 say the **worker's** liveness additionally means "the dispatcher loop is still ticking", and no check
      asserts that. Add a `Live`-tagged dispatcher-tick check on the worker — `OutboxDispatcherService` already has the
      loop and `HeartbeatService`/`IHeartbeatMonitor` the precedent for exposing in-process state to a check — or record
      in the pull request why the watchdog ships without it and which issue owes it. Do not ship a watchdog whose only
      input is a constant.
- [ ] **Record what is deliberately not changed**: `QueueLimit = 0` on every rate-limit policy (shed immediately rather
      than queue, because a queued request still holds a connection), the single-runner job lease as the scheduling
      bulkhead, and the outbox's existing retry bound. Each gets a row in the catalogue with its file reference, so a
      later reader does not add a second mechanism for a problem already solved.

## Acceptance criteria

- [ ] Every operation class in `docs/architecture/resilience-policies.md` names its semantics and its policy, and every
      policy it claims is implemented is traceable to a file in `src/` — asserted by a test over the document's file
      references, not by reading.
- [ ] With object storage stopped, a document-rendering call fails fast once the breaker opens instead of waiting for
      the per-call timeout on every attempt; `/health/detail` reports the storage check `Degraded`; `/health/ready`
      stays 200 and the host stays in rotation; and posting an invoice and recording a payment both still succeed,
      because `failure-modes.md` section 5 makes the financial record independent of the file.
- [ ] With storage restored, the breaker half-opens and closes, and the backlog drains with no operator action.
- [ ] **Negative:** the bulkhead refuses rather than queues without bound — with concurrent calls above the limit, the
      excess calls are rejected with the distinguishable fast-fail result and the host's memory stays inside the
      envelope of `docs/nfr/capacity-and-performance.md` section 4. A rejected call is never reported as a successful
      write.
- [ ] **Negative:** an open breaker never turns a failed write into a success, and never causes a caller to record an
      artefact row for an object that was not stored — the `failure-modes.md` section 5 rule that "the artefact row is
      written only once the object is stored with its checksum" still holds.
- [ ] **Exception:** the watchdog exits with code 70 after exactly three consecutive liveness failures and **not** after
      two, and does not exit when the failures are non-consecutive; and a host whose *database* is unreachable is
      **not** restarted by it, because liveness performs no dependency call (`HealthCheckTags.Live`) and restarting
      would turn a shared-dependency outage into a restart loop.
