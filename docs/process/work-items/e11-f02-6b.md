routing rule, one template in two languages, and the render-time call that pulls the code out of Custody exactly once.
It is separate from [E11-F02-6] for one reason — it depends on **[E11-F02-3b]**'s event and read contract, and the four
delivery-outcome messages must not wait behind that design.

## Scope

- [ ] **One routing rule**, `Notifications/Routing/DeliveryConfirmationCodeRule.cs`, an `IOutboxMessageHandler` over
      `custody.delivery-confirmation-code-issued.v1` with its own `HandlerName` and
      `Schema = NotificationsDbContext.SchemaName`. It raises exactly one intent through #209's mechanism and sends
      nothing itself.
- [ ] **`Templates/delivery.confirmation-code`** in **`en-IN` and `ta-IN`**, whose declared variable allowlist is the
      minimum that works: the code, the order display number and the expiry in minutes. **No recipient name, no amount,
      no link, no staff name, no garment description.** Seeded through `init-reference-data` beside the
      `Templates/delivery.*` set [E11-F02-6] already added.
- [ ] **The code is pulled at render time, not at intent time.** The rule raises the intent carrying no code; the
      renderer calls `IDeliveryConfirmationCodeReader.TakeAsync` while rendering the body for the chosen channel. **A
      null answer is not an error to retry** — it means the code was already taken, has expired, or the authorisation is
      spent — so the intent is **suppressed with its reason** and no body is rendered. That is the behaviour #209
      already defines for a refusal, and it is what stops a retry from burning a code nobody receives.
- [ ] **Quiet hours cannot defer this message.** A code valid ten minutes cannot be queued to the next open window, so
      the purpose is flagged **transactional** in #209's per-purpose table, exactly as #209's own acceptance criterion
      describes ("a transactional purpose … bypasses the optional/marketing consent gate but never the quiet-hours or
      allowed-channel gate") — and because quiet hours would still defer it, the rule treats a deferral as a
      **suppression with a reason** rather than a delayed send, so the delivery staff member sees no code arrive and
      asks for another at a workable time. Record this as the one place a documented gate and a ten-minute credential
      genuinely conflict, and let the suppression be visible rather than silent.
- [ ] **No change to #47's service, adapters or existing templates, and none to [E11-F02-6]'s four rules** — plan
      Section 6.2 note 4, quoted in the pull-request description. The second pull request of the W4 Notifications group
      to merge rebases and re-runs #47's routing tests.

## Acceptance criteria

- [ ] A published `custody.delivery-confirmation-code-issued.v1` produces exactly one notification intent for the
      order's customer, carrying the `delivery.confirmation-code` template version and the customer's locale, with the
      inbox row committed in the same transaction — and the rendered body contains the six digits that `TakeAsync`
      returned.
- [ ] Both languages have a published version; a missing `ta-IN` is a failing test, not a runtime fallback to English.
- [ ] **Negative:** a redelivered event produces **no** second intent and **does not call `TakeAsync` a second time**.
      This is the criterion that matters most: a second call would return null on a code that was already delivered, and
      a retry that re-rendered would send an empty body or suppress a perfectly good code.
- [ ] **Negative:** a null `TakeAsync` answer suppresses the intent with its reason and renders no body. No message is
      sent with a blank code, and nothing throws into the dispatcher's retry loop.
- [ ] **Negative:** a customer with no consented channel for the transactional purpose produces a suppression with its
      reason and no send (#209's behaviour, exercised here, not re-implemented).
- [ ] **Negative:** the code, the rendered body and the recipient address appear in no log line, trace attribute, metric
      or audit payload. The prohibition list is `docs/nfr/data-classification.md` **section 8** — "rendered notification
      bodies and template variable values", "recipient addresses" — and the code is a credential besides (section 6.2,
      row "Delivery one-time passwords"). Asserted by a test over captured output.
- [ ] **Exception:** the template refuses an undeclared variable (#208's safe-mode behaviour, exercised), so a later
      edit cannot quietly add the recipient's name to the body.
- [ ] Hand-off meets `docs/nfr/slo.md` section 5 rows "Notification hand-off (S10)", `p95 < 60 s`, and outbox lag (S7),
      `p95 < 30 s` — which together are what make a ten-minute code workable. Both figures are cited, not set here.
