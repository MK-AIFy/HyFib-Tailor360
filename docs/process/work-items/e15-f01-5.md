Sub-issue of #59. Two of #59's requirements are about the database and nothing else: the acceptance criterion
"Supported old/new application components coexist during migration window", and the Required verification item
"Failed migration and failed health-check rehearsal". The *mechanism* for the first already exists and is good —
`MigrationRunner.GetStateAsync` compares the two sets one-directionally and its own doc comment says why ("that is
the state during a rollback to release N while the database is still at N+1, and refusing to start then would turn a
rollback into an outage"), `MigrationState.DatabaseIsAhead` exposes it, and `MigrationStateHealthCheck` reports
`Degraded` rather than `Unhealthy` for it. What is missing is the **proof**: nothing anywhere starts release N
against a database at N+1, so the property is asserted by a comment and a unit-level shape, never by a run. The
second requirement has nothing at all — there is no deliberate failed-migration rehearsal, so "the advisory lock is
released and nothing is half-applied" is also untested. And the plan's #59 blueprint asks for one thing the runner
does not do: record "the latest backup label and `pg_current_wal_lsn()` recorded before `migrate` as the PITR target
(not a new full backup per deploy)". `grep -rn "pg_current_wal_lsn\|pg_stat_archiver\|pgbackrest" src/ infra/
scripts/` matches nothing but one sentence of `infra/README.md`.

## What is missing

- Any run in which release N serves against a database at N+1. `grep -rn "DatabaseIsAhead" tests/` returns nothing,
  so even the degraded-startup path has no test.
- Any preflight. `migrate` goes straight from `CliHost.Build()` to the lock; nothing records a recovery target, and
  nothing reports what it is about to do in a form a release record can carry (checklist item 11 of
  `docs/process/release-gates.md` section 6 asks for "the migration dry-run output, the rollback note and the
  recorded recovery target").
- Any deliberate failure. Nothing proves the lock is released after an exception, and nothing proves that a failure
  in module *k* leaves modules 1…k−1 applied and k+1…n untouched — which is what `MigrateAsync`'s per-context loop
  actually does, and which an operator must know before they choose between roll-forward and restore.

## Scope

- [ ] A `preflight` read-only step, exposed as `migrate --preflight` (an option on the existing command, so there is
      one command an operator learns) that prints, and writes as a small text record an automation can attach: the
      pending migrations per schema from `GetStateAsync`, whether the database is ahead, the server version,
      `pg_current_wal_lsn()`, and the `pg_stat_archiver` row (`last_archived_wal`, `last_archived_time`,
      `failed_count`). It **applies nothing** and exits `ExitCodes.Success` even when there is nothing to apply.
- [ ] When write-ahead-log archiving is off — which it is today, because pgBackRest arrives with **#60** — the record
      says so in one line and the step **still succeeds**. A preflight that fails on an absent backup system would
      block every deployment until #60 merges, and a preflight that silently prints an empty recovery target would be
      worse. The **backup label** is deliberately not collected: there is no backup system to read it from yet, and
      `docs/dev/migrations.md` gains a row saying which issue adds it.
- [ ] `migrate` calls the same preflight collection before acquiring the lock and emits it into its own output, so a
      deployment that runs `migrate` gets the recovery target without a second command and without a second
      connection policy.
- [ ] Structured log events for the preflight through the existing `PersistenceLog` pattern (beside
      `MigrationLockAcquired` / `MigrationLockReleased`), carrying the write-ahead-log position and the pending
      counts and **nothing about data**. No connection string, no host, no user — `PlatformHealthChecks` already
      drops a connection exception's message for exactly that reason, and the preflight must be no more talkative.
- [ ] Integration tests for the coexistence property, in `tests/Tailor360.IntegrationTests/Platform/`: migrate a
      scratch database to the full set, remove the newest migration from what the build *knows* (the existing
      per-module migration tests show how a scratch database is driven), and assert `CanServe` is true,
      `DatabaseIsAhead` is true, and `MigrationStateHealthCheck` reports **`Degraded`, not `Unhealthy`**.
- [ ] An integration test for the converse: a build with an unapplied migration reports `Unhealthy` from
      `/health/startup` and the message names the schema, so an orchestrator holds the instance back rather than
      restarting it in a loop.
- [ ] A failed-migration integration test: a migration that throws part-way leaves the advisory lock released — proved
      by a second `MigrateAsync` on another connection succeeding rather than blocking — and leaves the already-applied
      modules applied and the later ones untouched, asserted per schema against `__ef_migrations_history`.
- [ ] A new step in the `migration-check` job of `.github/workflows/ci.yml` that runs the real **N/N+1 rehearsal over
      HTTP**: migrate the database with the head build, then start the web host from an **earlier** source and assert
      `/health/startup` answers degraded-but-serving and one read endpoint answers. This is the only form of AC3 that
      is not a unit-level claim.
      **Which earlier source, precisely, because there is no released tag yet** (`git tag` is empty, and the release
      workflow arrives with **E15-F01-2**): the newest commit before `HEAD` that added a migration **anywhere**. There
      are six migration directories, not one — `src/Platform/Tailor360.Platform.Persistence/Migrations/` plus
      `src/Modules/{Identity,Catalog,Customers,Orders,Billing}/Tailor360.Modules.*.Infrastructure/Migrations/` — so the
      job resolves it over all six:

      ```bash
      git log -1 --format=%H HEAD~1 -- \
        'src/Platform/Tailor360.Platform.Persistence/Migrations' \
        'src/Modules/*/Tailor360.Modules.*.Infrastructure/Migrations'
      ```

      Pinning it to the platform directory alone, as an earlier draft of this issue did, would pick a commit that is
      not behind the database at all for a release whose only migration was in a module — and the rehearsal would then
      prove nothing while passing. Write the resolution in the job's comment, print the resolved commit in the log, and
      **fail the step when it resolves to nothing** rather than silently rehearsing `HEAD` against `HEAD`. When the
      release workflow exists, the same step prefers the previous released tag and the comment says so.
- [ ] `docs/dev/migrations.md`: a row in the per-migration register is **not** added, because this issue adds no
      migration — say so in one line, because the register's evidence column is the first place a reviewer looks. And
      a "Preflight and the recovery target" section naming the command, what it records,
      what it does not record yet and which issue adds it; and the rollback paragraph updated to say that the
      recovery target is the write-ahead-log position recorded **before** `migrate`, not a fresh full backup per
      deploy, citing the plan's #59 blueprint.
- [ ] `docs/process/branch-protection.md` section 3's table if and only if a **new job** is added. Prefer extending
      `migration-check`, which is already a required check named `Database migrations`, so no table change is needed —
      and say so in one line, because section 3.1 makes the check compulsory either way.

## Acceptance criteria

- [ ] `dotnet run --project src/Tools/Tailor360.Cli -- migrate --preflight` against a migrated database prints a
      record naming: zero pending migrations per schema, whether the database is ahead, the PostgreSQL version, the
      current write-ahead-log position, and the archiver state — and exits `0`.
- [ ] The same command against an **empty** database lists what would be applied, per schema, and exits `0` without
      applying anything. `__ef_migrations_history` does not exist afterwards, or exists empty.
- [ ] `migrate` prints the same preflight record before it acquires the lock, so one deployment command produces
      checklist item 11's recovery target without a second invocation.
- [ ] **Positive, the headline:** release N's web host, started against a database migrated by release N+1, answers
      `/health/startup` as degraded-with-a-reason and serves a read endpoint over HTTP. Asserted in CI, not described.
- [ ] **Negative:** a build with an unapplied migration answers `/health/startup` unhealthy, and the message names the
      schema — so the instance is held back at startup rather than flapping on readiness.
- [ ] **Negative:** a migration that throws mid-run releases the advisory lock, and the next `migrate` from a separate
      connection proceeds rather than blocking. Proved by the second call succeeding, with a timeout on the assertion
      so a hung lock fails the test rather than hanging the tier.
- [ ] **Negative:** after that failure, the schemas migrated before the failing one are at their new state and the
      schemas after it are untouched — asserted per schema, so the operator's choice between roll-forward and restore
      rests on a tested fact.
- [ ] **Negative:** with archiving off, the preflight record says the recovery target is unavailable and names the
      issue that adds it, and the command still exits `0`. It does not print an empty or zero position as if it were
      one.
- [ ] **Exception:** `migrate --preflight --dry-run` is either accepted as a synonym for `--preflight` or refused with
      a message saying which to use. It must not silently apply migrations, which is the one unrecoverable surprise in
      this command's surface.
- [ ] ARCH-014 stays green: the preflight takes any timestamp of its own from `IClock`
      (`src/Platform/Tailor360.Platform.Abstractions/Time/IClock.cs`, implemented by `SystemClock.cs`, which is the one
      file ARCH-014's `sanctioned` array names), never from `DateTime.UtcNow`, and the architecture tier proves it.
      `Tailor360.Platform.Persistence` already has the project reference to `Tailor360.Platform.Abstractions`, so no
      reference is added and ARCH-001/ARCH-002 are untouched. `last_archived_time` comes **from PostgreSQL** and is not
      a clock read — say so, so a reviewer does not look for an injection that should not be there.

## Migration and rollback

**This issue adds no table and no column, deliberately**, even though it is about migrations. Recording the recovery
target in a table would mean a migration whose own application needed a recovery target — so the record is text the
caller captures, and that is a constraint on the implementation, not an omission. What proves it: `dotnet ef
migrations has-pending-model-changes` reports none and `migrate --dry-run` reports "The database is up to date with
this build.", both already steps of the `migration-check` job. The failed-migration test creates its failure in a
scratch database through the test fixture, never through a committed migration.

Rollback of this pull request is `git revert`; the preflight is additive and a build without it migrates exactly as
today.
