Sub-issue of #57. The parent's third acceptance criterion is "every critical mutation has a searchable audit event
linked by correlation ID", and the plan spells out how it is to be proved: "a completeness review generated from
OpenAPI (every state-changing operation has a test asserting its audit event and correlation id)"
(`docs/IMPLEMENTATION_PLAN.md` Section 8, #57). Its fourth criterion adds "audit and general logs contain no
passwords, tokens, full payment credentials or image content", whose **audit** half is the same machinery: read the
stored `before`/`after` snapshot and assert what is not in it. This child is both halves and nothing else. **It adds
no production code, no table, no migration, no endpoint and no permission** — it is a test-tier child, which is what
makes it a session.

It is separate from `[E14-F02-5]` for a measured reason. The composed route table carries **121 state-changing
routes** — counted from the `<!-- matrix:endpoints -->` block of `docs/security/permission-matrix.md`, which holds 198
endpoint rows in total. Driving each of them to a *successful* call needs request bodies, a branch, a customer, a
catalogue version, a price list and in some cases a posted invoice; the existing authorisation probe drives every
route to a **`403`**, which is a different and far cheaper thing. Putting this inside the anchoring child would either
exhaust a session's context or collapse into an exemption list with almost every route on it.

## What is missing

- Nothing asserts at run time that an audited endpoint's entry actually **carries a correlation id**. ARCH-008 proves
  the filter is declared; it cannot prove the entry was written, and it cannot prove the correlation propagated.
- Nothing asserts that a stored `before`/`after` snapshot is free of values under a redacted property name. The
  interceptor serialises whatever the entity carried.
- There is no register of which state-changing routes are covered and which are not, so "audit completeness" is an
  opinion.

## Scope

- [ ] **`AuditCompletenessHarness`** in `tests/Tailor360.IntegrationTests/Auditing/`: enumerate every state-changing
      route from the composed route table, and for each one either drive it to a **2xx** through the probe
      application with the fixtures that already exist and assert that `platform.audit_events` holds an entry whose
      `correlation_id` equals the `Correlation-Id` the response carried and whose `action` equals the route's
      `AuditedEndpointMetadata`, or record it as exempt.
- [ ] **An exemption register that is read, not hidden.** A new
      `tests/Tailor360.IntegrationTests/Auditing/audit-completeness.yaml`, in the spirit of `matrix.yaml`: one row per
      exempt route with the reason and the issue that will cover it. The harness **fails** when a route is neither
      driven nor listed, and **fails** when a listed route has become drivable — so the register shrinks by itself
      rather than rotting. A reason is one of a fixed, documented set: `needs-fixture` (with the issue),
      `needs-hardware` (printer or scanner), `needs-provider` (payment or messaging), `destructive-in-test`, or
      `covered-elsewhere` (with the test).
- [ ] **A stated coverage floor, so the pull request can be judged.** The harness prints the driven count, the exempt
      count and the total, and the pull request records all three. **The floor for this issue is every state-changing
      route in Identity, Customers and Catalog**, which is the surface whose fixtures `MatrixFixtures.cs` already
      builds; every other module's routes may be exempt with `needs-fixture` and the module's own issue named. That is
      a deliberately modest floor: the value here is the harness and the register, and the register is what makes the
      remaining work countable instead of invisible.
- [ ] **Audit payload redaction assertion**: for every route the harness drives, assert that the stored `before` and
      `after` JSON contains **no property** whose name normalises to a `LogRedaction` entry, and no value equal to a
      sentinel planted in the request. A leak found here is a defect fixed in this same pull request, by adding the
      property name to `LogRedaction` **and** by whatever the interceptor needs so the snapshot never carried it —
      masking the log is not a fix for a value written into the evidence store.
- [ ] **No new `ARCH-…` identifier is proposed.** This adds no rule over the source text: ARCH-008 already asserts the
      declaration, and this asserts the behaviour, the way `DenialAuditTests` asserts the denial behaviour without an
      identifier of its own. **If the reviewer judges the "neither driven nor listed" failure to be a new mechanical
      rule, it takes an `ARCH-…` row in `docs/architecture/architecture-rules.md` in this same pull request**
      (CLAUDE.md section 3) — say which way it was decided, in the pull request, either way.
- [ ] **Documentation**: record in `docs/nfr/traceability.md` that **NFR-AU-01** (line 171, "Every state-changing

## Out of scope

The anchors table, the verification job, the head-disagreement detection, the correlation-id **filter** and the
`/api/v1/admin/audit/chain` read are `[E14-F02-5]`. **This child adds no query parameter and no route**, and it does
not need the filter: it reads `platform.audit_events` directly in the test tier, which is what the existing
`AuditTrailTests` does. The **log** half of the parent's fourth criterion — a sentinel that never reaches a log, a
problem detail, a health response or the OpenAPI document — is the sixth child. Sensitive-**read** audit review
(measurement sheet, media stream, export download) is explicitly **not** here: media streaming does not exist (#188),
and the two reads that are audited today are already asserted by their own module's tests. Fixtures for Orders,
Custody, Inventory, Billing, Reporting, Notifications and Integration routes belong to those modules' issues and are
named in the exemption register rather than written here.

## Acceptance criteria

- [ ] The harness runs in the integration tier and prints three numbers — driven, exempt, total — and the total equals
      the count of state-changing routes in the composed route table, so no route is silently absent from both sides.
- [ ] Every state-changing route in Identity, Customers and Catalog is **driven**, and for each one the audit entry's
      `correlation_id` equals the response's `Correlation-Id` header and its `action` equals the route's declared audit
      action.
- [ ] A state-changing call followed by `GET /api/v1/admin/audit/?correlationId=<id>` joins the mutation to its entry
      — **only if `[E14-F02-5]` has merged**. If it has not, the same join is asserted through `IAuditReader` in the
      test tier and the HTTP form is the criterion to defer, recording all six deferral fields of
      `docs/process/definition-of-ready.md` section 5.
- [ ] **Negative — the failure the harness exists to catch**: a deliberately introduced route that declares
      `.Audited(...)` but whose handler bypasses the interceptor is reported as a completeness failure naming the
      route, proved by a negative control in the same shape as
      `tests/Tailor360.IntegrationTests/Authorization/AuthorisationMatrixTests.cs` line 333 ("ARCH-018, proved to
      detect").
- [ ] **Negative**: a route removed from the register while still undrivable fails the harness; a route added to the
      register that the harness can in fact drive **also** fails it. Both are proved, so the register cannot be used
      to hide a gap or to keep a stale excuse.
- [ ] **Negative**: a planted sentinel value in a request body does not appear in the stored `before` or `after` JSON
      for any driven route, and a property name added to `LogRedaction` is honoured in the snapshot on the next run.
- [ ] **Exception**: a route whose successful call is genuinely impossible in this environment — a printed label, a
      hardware scan, a gateway callback — is exempt with `needs-hardware` or `needs-provider` and the issue that owns
      the evidence, and the harness says so in its output rather than passing quietly. **No coding session is blocked
      on hardware it cannot have**, and the exemption reason is how that is recorded.
- [ ] **Exception**: the harness is order-independent and leaves no row behind — run twice in one session it produces
      the same three numbers, which `CLAUDE.md` section 5 ("run the suite twice") requires anyway.
