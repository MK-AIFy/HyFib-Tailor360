Sub-issue of #58. #58's fourth implementation step asks for "role-appropriate dashboards", and there is no dashboard of
any kind in the repository: `ls infra/observability` returns only `otel-collector-config.yaml`, and `grep -rn "grafana"
infra/` finds nothing. `docs/nfr/slo.md` section 11 makes the dashboards the evidence for three whole target classes —
"Availability, error rate, burn rate | Dashboards and alert rules as code (#58) | Monthly SLO report in the release
train record", "Outbox, projection and notification lag | Worker metrics and the alert rules of
#58", "Latency budgets | … measured percentiles against the targets" — so the monthly SLO report has no source until
this lands. This slice is the **operator's service-health dashboard**, the provisioning mechanism, the lint test and the
panel-to-SLI README — and nothing else. The background-integrity and capacity dashboards are **child 4b**, which builds
on the provisioning, the lint test and the README this issue establishes; the stack they are provisioned into is child
3; the alert rules that share their queries are children 5 and 5b. The split is a size judgement, not a taste one: a
Grafana panel with its targets, `fieldConfig` and thresholds is 60 to 90 lines of JSON, so three twelve-panel dashboards
in one pull request is about 1,700 lines of JSON before the provisioning file, the README and the test — over the
`CLAUDE.md` section 6 target and well past what one session can review.

## What is already built (do not re-build)

- `docs/nfr/slo.md` section 4 — the SLI catalogue **S1 to S14**, each row naming its definition, what it is measured
  from and what it excludes. Every panel must be traceable to one of these rows or to a budget row of
  `docs/nfr/capacity-and-performance.md` section 3.3. Do not invent a panel with no row behind it.
- `docs/nfr/slo.md` section 5 — the objective table (read p95 < 400 ms, command p95 < 800 ms, error rate ≤ 0.5% and
  commands ≤ 0.2%, outbox lag p95 < 30 s, dead-letter rate ≤ 0.1%, projection lag p95 < 5 min, notification hand-off p95
  < 60 s, revocation ≤ 60 s, flag propagation ≤ 30 s). These are the threshold lines a panel draws. **Cite the row;
  never retype a number into a dashboard as a literal without the row beside it in the panel description.**
- `docs/nfr/slo.md` section 3.1 and section 10 — the error budget: 0.5% of a 12-hour service window, 108 minutes in a
  30-day month. The burn-down panel reads from this, not from a new calculation.
- `docs/nfr/slo.md` section 5.1 — the diagram of where each objective is measured, and the explicit statement that
  report, media, export and sequence-allocation routes have **their own** budgets in
  `docs/nfr/capacity-and-performance.md` and are excluded from S2 and S3. A dashboard that folds them together is wrong,
  and the document says why.
- `docs/nfr/capacity-and-performance.md` section 3.3 — the budget table; section 4 — the server resource envelope, which
  is what a saturation panel is measured against.
- `src/Platform/Tailor360.Platform.Abstractions/Diagnostics/SignalNames.cs` and `docs/platform/observability.md`, both
  from #58 child 1 — the only legitimate source of a metric name. A panel that names a metric not in that catalogue is a
  defect in the panel.
- The built-in instrumentation already registered in
  `src/Platform/Tailor360.Platform.Observability/Telemetry/ObservabilityServiceCollectionExtensions.cs` —
  `AddAspNetCoreInstrumentation`, `AddHttpClientInstrumentation`, `AddRuntimeInstrumentation`. The golden-signal panels
  read `http.server.request.duration` and the runtime series from these, not from anything new.
- `docs/prd/raci.md` — who is accountable for what operationally. Row 28 and the **OD-15** note at line 216 are the
  basis for "role-appropriate": the audiences are the **operator** named under OD-15, the **technical reviewer** who
  reports the error budget monthly (`docs/nfr/slo.md` section 10), and the **Owner**, who decides on a waiver. They are
  not the twelve application roles of `docs/security/permission-matrix.md`, and saying so in the README prevents the
  next reader from building a "Cashier dashboard".

## Acceptance criteria

- [ ] With the `observability` profile up and a host exporting, the service-health dashboard loads in Grafana with
      every panel rendering data — no "No data" panel, and no panel whose query errors. Every panel on this dashboard
      reads `http.server.request.duration` and the runtime series from `AddAspNetCoreInstrumentation` /
      `AddRuntimeInstrumentation`, which are merged and producing today, so "No data" here means a broken query rather
      than an absent producer. (That is also why this dashboard is first: it is the one that *can* be fully green.)
- [ ] Every panel's description names the `docs/nfr/slo.md` SLI row or the `capacity-and-performance.md` budget row it
      serves, and the README table lists all of them with no row missing on either side.
- [ ] The error-budget burn-down panel agrees with a hand calculation from `docs/nfr/slo.md` section 3.1 for one
      synthetic month of data — 108 minutes in a 30-day, 12-hour-window month — so the panel is checked rather than
      believed.
- [ ] **Negative:** no panel query groups by a high-cardinality or personal attribute. A panel that groups request
      latency by customer identifier, order identifier, media identifier or route **parameter value** fails the lint
      test; route **template** is what may be grouped on (`docs/nfr/data-classification.md` section 5.18, "In logs" row,
      and section 8's "what a log line should contain instead").
- [ ] **Negative:** the lint test fails when a panel names a metric absent from `SignalNames` and the allowed
      instrumentation list — proved by a negative control, not by inspection.
- [ ] **Exception:** a signal whose producer has not been built yet is **not** put on a panel at all. It goes in the
      README's no-producer backlog table with its owning issue, and child 4b renders those rows on screen. An empty
      graph and a broken exporter must never look alike — the same distinction child 1's gauges make by reporting no
      measurement rather than zero.
