Sub-issue of #58, and the second half of child 7. Child 7 builds the fault-injection fixture, `docs/qa/retry-safety.md`
and the coverage test, and proves singularity for the three **invoice-side** protected commands. This issue proves the
same for the three **payment-side** commands and adds the two **handler-side** redelivery scenarios, which is where
at-least-once delivery meets inbox de-duplication. It adds no production code.

The split is a size judgement with the calibration in the repository:
`tests/Tailor360.IntegrationTests/Billing/PaymentEndpointTests.cs` is **421 lines** and
`CashierSessionEndpointTests.cs` **198** for the happy and refusal paths alone, so nine fault-injection scenarios over
the payment commands plus the handler side is a session's worth on its own.

## What is missing

No scenario proves that a retried payment leaves one payment row, that a retried reversal leaves one compensating
record, or that a retried cashier close leaves one variance record. Nothing proves that a redelivered outbox message
produces one consumer-side effect: `OutboxTests.cs` proves the dispatcher's own behaviour, not that a handler which
wrote outside the de-duplication record's transaction would be caught. That last case is the defect class this suite
exists for, and nothing in the repository would catch it today.

## Scope

- [ ] **Three commands, three failures each — nine scenarios**, each verified present in the working copy:
      - `POST /api/v1/billing/payments` — `PaymentEndpoints.cs:67`, permission `payments.record`
        (`BillingPermissions.cs:51`). **The vocabulary is `payments.`, not `billing.`**, even though the Billing module
        declares the key; grep the constant rather than inferring it from the module name. Effect asserted: **one**
        payment row with **one** allocation set, oldest posted invoice first (INV-PAY-04), the remainder held as an
        advance (INV-PAY-05) — and no second advance.
      - `POST /api/v1/billing/payments/{paymentId:guid}/reversal` — `RefundEndpoints.cs:25`, permission
        `payments.reverse` (`BillingPermissions.cs:66`), **step-up and a reason required**. Effect asserted: **one**
        compensating record, the original row untouched, paid status recomputed from rows (INV-PAY-01, INV-PAY-06), and
        a second reversal of the same payment refused with **409** rather than creating a second compensating record.
      - `POST /api/v1/billing/cashier-sessions/{sessionId:guid}/close` — `CashierSessionEndpoints.cs:142`, permission
        `payments.session` (`BillingPermissions.cs:69`). Effect asserted: **one** closed session with **one** variance
        record; a second close is a **409** because the close is a conditional update and the row is the guard
        (INV-CSH-05).
      The three failures, as child 7 defined them: retry with the **same** `Idempotency-Key` after a timeout; retry
      after a mid-transaction failure; and the worker restarted while the resulting outbox message is in flight.
- [ ] **The handler side — redelivery after lease expiry.** For `OrderFactHandlers` and
      `CatalogReconciliationHandlers`: stage a message through `InvoiceScenes.PublishAsync`, let the dispatcher claim
      it, stop the dispatcher so the lease expires, restart it, and assert **exactly one** consumer-side effect **and
      exactly one** `InboxMessage` row for that `(MessageId, HandlerName)` pair. Assert on the de-duplication record,
      not only on a row count: a handler that wrote its row outside the transaction the record is written in would pass
      a row count on the first run and fail on the second, which is the defect this asserts away. If there is room, add
      the same for `Payments/AdvanceApplicationHandlers.cs`, which moves money; if not, make it a coverage-table row
      with this issue's number and say so.
- [ ] **Complete the coverage table in `docs/qa/retry-safety.md`**: the three payment commands move from "owned by this
      issue" to "covered", and every remaining protected command keeps its owning issue. No new index and no second
      document.
- [ ] **Extend child 7's coverage test** so a handler with no redelivery scenario is a failure too, not only a command
      with no scenario — with a negative control that adds a handler and fails.

## Acceptance criteria

- [ ] For each of the three commands, a client that times out and retries with the same `Idempotency-Key` observes the
      **first** outcome and the database holds exactly one effect, as itemised per command in Scope above.
- [ ] For each command, a mid-transaction failure leaves **no** partial effect: no payment without its allocation, no
      reversal without its recomputed paid status, no closed session without its variance record, and no audit event
      describing a change that did not commit.
- [ ] Redelivering a message after lease expiry leaves exactly **one** consumer-side effect and exactly **one**
      `InboxMessage` row per `(MessageId, HandlerName)`, for both handlers.
- [ ] **Negative:** the same `Idempotency-Key` with a **different** body is refused with the code
      `docs/platform/idempotency-and-concurrency.md` specifies, and writes no effect; a duplicate arriving **while the
      first is in flight** is refused rather than queued or executed.
- [ ] **Negative:** a second reversal of the same payment is a **409** and creates no second compensating record; a
      second close of the same session is a **409** and creates no second variance record. Neither is allowed to be
      absorbed silently as an idempotent replay of a *different* key — a 409 and a replay are different answers and a
      test that accepts either proves nothing.
- [ ] **Negative:** a payment recorded **without** an open cashier session is refused (INV-CSH-02) and the refusal is
      not retried into existence by a repeated `Idempotency-Key`.
- [ ] **Exception:** a timed-out command's claim is left standing, so an immediate retry is refused as in-flight and the
      caller is told to wait rather than being allowed to run the command again — the behaviour
      `src/Platform/Tailor360.Platform.Security/Endpoints/RequestTimeoutPolicies.cs`' own remarks state. For a
      **payment** this is the criterion that matters most: the safe answer to "try again" is "wait for the lease", never
      "take the money again".
- [ ] The extended coverage test fails when a handler is added with no redelivery scenario, proved by a negative
      control.

## Modules, contracts and events

No `src/` project is changed. The suite lives in `tests/Tailor360.IntegrationTests/` and reads through each module's own
harness and `InvoiceScenes`; it writes no SQL against another module's schema. Events exercised: the `orders.*` facts
consumed by Billing's `OrderFactHandlers` and the catalogue reconciliation events consumed by Catalog's
`CatalogReconciliationHandlers`, both through the outbox — the sanctioned **versioned integration event through the
transactional outbox** mechanism of `CLAUDE.md` section 3. Threat-model coverage: a duplicate financial effect under
retry is a payment-tampering concern; batch 1's **E14-F01b-3** covers the *authorisation* half and this suite the
*idempotency* half, and the two must cite each other so neither is assumed to cover the other.

`TAILOR360_TEST_DATABASE_URL`, so `./scripts/dev doctor` reports the integration tier as SKIPPED and
`DatabaseAvailability.cs` makes the skip visible. Run `doctor` **first** (DOR-16) and then either point

already provides a `postgres:16-alpine` service. `CI=true` turns the skip into a failure — which for this issue is the
whole point, because a skipped fault-injection suite is indistinguishable from a passing one. Say which route was used.
