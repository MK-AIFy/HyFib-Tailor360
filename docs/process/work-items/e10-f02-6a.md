Sub-issue of #45. One of the parent's five acceptance criteria is "dashboard counts reconcile to source jobs for
selected cutoff/filter", and it cannot be built by the slices that fill the projections, because reconciliation needs
a **source** count that does not exist.
`src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Orders/IOrderSnapshotQuery.cs`
says so in its own remarks at lines 81 to 83: "Four methods, all by identity, and deliberately no branch-wide query.
Reporting #45's reconciliation wants an aggregate read over a cut-off and a filter that no document specifies;
inventing its shape here would be inventing reporting surface. **It lands with #45 as an additive method**". This
slice is that method, its implementation, and the comparison that uses it. The schedule, the alerts and the
production-volume proof are E10-F02-6b and E10-F02-6c.

**Read this before you start, because it is the one place in #45 that touches a second module's implementation.**
The one-session rule is "at most one other module touched, and then only through its `Contracts` project". This slice
breaks the letter of that and is allowed to, narrowly and for a reason the contract itself records: you cannot add a
method to a published interface without implementing it, or the solution does not compile. The Orders change is
therefore capped at **exactly two files** — a trailing method and two records on `IOrderSnapshotQuery.cs`, and its
implementation in `OrderSnapshotQuery.cs` — with **no behaviour change to any existing Orders method, no new Orders
table, no new Orders endpoint and no Orders migration**. Anything beyond those two files is out of scope and becomes
a new issue. ARCH-003, ARCH-004, ARCH-010 and ARCH-011 all still hold: Reporting references only `Orders.Contracts`,
and the implementation lives inside the module that owns the table.

## Scope

- [ ] **One additive method on `IOrderSnapshotQuery`**, counts only and no rows:
      `Task<IReadOnlyList<JobStateCount>> CountJobStatesAsync(JobStateCountQuery query, CancellationToken
      cancellationToken = default)`, with `JobStateCountQuery(Guid OrganisationId, IReadOnlyCollection<Guid>
      BranchIds, DateTimeOffset AsOf)` and `JobStateCount(Guid BranchId, string CategoryKey, GarmentJobState State,
      int Count)`. It is a **trailing** addition, so no existing signature moves and no consumer recompiles
      (`conventions.md` section 5.5). Counts and codes carry no personal data, which keeps the contract's
      no-personal-data property intact.
- [ ] **Its implementation in `OrderSnapshotQuery.cs`**, against `orders.garment_jobs` **inside Orders**, where that
      table belongs. Grouped in the database rather than in memory, so a branch with 36,000 garments a year does not
      stream rows to count them.
- [ ] **Pipeline reconciliation in Reporting**: for a cut-off and a branch set, compare the counts of
      `reporting.projections_job_pipeline` against `CountJobStatesAsync` at the same instant; write one
      `reconciliation_runs` row per report code (`pipeline`) with source total, projected total, delta, status and the
      instant used, and one `reconciliation_findings` row per disagreeing `(branch, category, state)` cell. **It
      reports; it never corrects** (NFR-BG-06). A cell present on one side and absent on the other is a finding with
      the missing side recorded as zero, not a skipped comparison.
- [ ] **The cut-off is evaluated per branch**, in that branch's own IANA zone from `IBranchDirectory`, and the run row
      records the instant it used — so two branches in different zones reconcile against different instants for the
      same business date and a reader can see which.
- [ ] **Invoked directly, not scheduled.** This slice exposes the comparison as an application service the
      integration tests call; **E10-F02-6b** is what puts it on a timer in the worker. No worker job, no hosted
      service and no change to `src/Hosts/Tailor360.Worker/Program.cs` here, which is what keeps this slice to one
      session and off a file every issue edits.
- [ ] **No event is published here.** `reporting.report-reconciliation-mismatch.v1` and
      `reporting.report-freshness-breached.v1` are the only two events Reporting may ever publish
      (`module-ownership.md` section 5.9) and **#184's scope already claims both** ("Raise
      `reporting.report-reconciliation-mismatch.v1` / `reporting.report-freshness-breached.v1` on a mismatch or a
      stale projection"). E10-F02-6b is where #45 either extends what #184 landed or introduces them if #184 has not
      merged. A non-zero delta here is visible in the run and finding rows.
- [ ] **No endpoint.** The run history is read through #186's `GET /api/v1/reporting/status?report=…` and the
      existing reconciliation tables; a second status route would be a second answer to one question.
- [ ] **Metric dictionary**: a `docs/reports/metrics.md` entry for the reconciliation itself — what is compared, at
      what cut-off, what a delta means, and the explicit statement that a projection is never authoritative
      (`module-ownership.md` section 5.9).
- [ ] **No migration**, unless the comparison needs a column `reconciliation_runs` or `reconciliation_findings` lacks.
      If it does, add it as an expand-only migration named `PipelineReconciliationFields` with a working `Down`, say
      so in the pull request, and **widen no table outside `reporting`**.

## Acceptance criteria

- [ ] With a projection and its source in agreement, a reconciliation run records a zero delta with status `matched`
      for the chosen cut-off and branch set, writes no finding, and publishes nothing.
- [ ] **Negative — a seeded mismatch:** deleting or altering a `projections_job_pipeline` row behind the runner's back
      makes the next run record a non-zero delta and a finding naming the `(branch, category, state)` cell, and **the
      projection is not corrected** by the run — asserted by reading the row back after the run.
- [ ] **Negative — a cell on one side only:** a category present in the source and absent from the projection
      produces a finding with the projected count recorded as zero, rather than the cell being skipped and the totals
      appearing to agree.
- [ ] **Negative — a branch the caller's scope does not reach:** the comparison is driven by an explicit branch set
      and never by "all branches" by default; a run for branch A reads and writes nothing about branch B.
- [ ] **Exception — a cut-off in the middle of the day:** the run evaluates the cut-off in each branch's own timezone,
      so two branches in different zones reconcile against different instants for the same business date, and the run
      row records the instant it used for each.
- [ ] `CountJobStatesAsync` answers with counts only: a test asserts the returned types expose no customer
      identifier, no amount, no measurement and no free text, so the contract's no-personal-data property still holds.
- [ ] **Rule-level:** no Reporting project references `Orders.Infrastructure` or `Orders.Api` and no Billing project
      references any Orders project (ARCH-010, ARCH-011), and the architecture tier proves it with the new method in
      place. The Orders diff touches exactly two files.
- [ ] The new method is **trailing**: a test or the diff shows no existing signature moved and no existing caller
      changed.
