## Acceptance criteria

- [ ] An Owner restricts a customer over HTTP with a reason; `GET /api/v1/customers/{customerId}` then shows the
      restriction with its instant and actor; `ICommunicationPreferenceQuery` for that customer answers
      `ProcessingRestricted = true`. Lifting it with a reason returns the flag to false and keeps both audit entries.
- [ ] Both routes declare a permission (ARCH-007), exactly one rate-limit policy (ARCH-017) and the audit filter
      with a mandatory reason (ARCH-008). They also declare
      `.TouchesNoBranchOwnedResource(NoBranchResource, Review)` as `MapExport` does two screens up in the same file —
      **not because ARCH-023 compels it**, since that rule's allowed-exceptions row
      (`docs/architecture/architecture-rules.md` line 346) puts organisation-scoped routes outside it and
      `EndpointAuthorisationInspector.UnscopedIdentifierComplaints` yields nothing for `BranchScope.Organisation`,
      but so the matrix's `Resource` cell reads `—` the way line 497 does for the export.
- [ ] Pseudonymising a customer over the participant leaves `CustomerNumber` unchanged and leaves every posted
      financial record, scan event and audit event byte-identical, proved by comparing row hashes before and after.
- [ ] After pseudonymisation the customer is not findable by the old name or the old phone number through
      `GET /api/v1/customers?...`, and is still findable by `customer_number`.
- [ ] **Negative**: correcting a restricted customer does not lift the restriction — asserted in a unit test on the
      aggregate and in an integration test over `PUT /api/v1/customers/{customerId}`.
- [ ] **Negative**: a caller holding `customers.update` but not `customers.restrict` is refused both routes with the
      `403` answer already defined in `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`; a restrict call
      with a stale `If-Match` is refused `409` carrying the current version; a replayed `Idempotency-Key` returns the
      first outcome and records no second audit entry.
- [ ] **Negative**: the participant run against a customer in another organisation erases nothing and reports the
      subject as not found, with the same answer an unknown identifier produces.
- [ ] **Exception**: the participant is idempotent — a second run changes no row and writes no audit event, asserted
      by comparing the audit chain sequence before and after.
- [ ] **Exception**: the participant attempts to change `customer_merges` beyond clearing `reason` and the database
      refuses it — a test drives that refusal deliberately, so the trigger's protection is proved rather than
      assumed.
- [ ] **Exception**: `consent_records` survive pseudonymisation and are reported as retained for an evidentiary
      reason, not as skipped by a hold.

One expand-only migration, EF name `AddProcessingRestriction`, adding three nullable columns, one partial index and

and nothing in release N reads them. Rollback is redeploying the previous tag with the columns unread; `Down` drops

none. Per `docs/dev/migrations.md`, with the register row and the live-database evidence that the check constraint
bites. **Pseudonymisation is not reversible and is not a migration** — it is a command, gated by an approved request
in the fourth child, and the backup treatment of `docs/nfr/data-classification.md` section 7 applies: the data
survives in backups until those expire, and a restore replays the requests executed after the restore point (#60).
