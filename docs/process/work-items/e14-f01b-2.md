Sub-issue of #56. Plan Section 8 gives the W5 half of this parent an "automated security regression suite (IDOR,
escalation, workflow bypass via direct API, barcode replay, invoice/payment tampering, stock manipulation, malicious
upload, export leakage, SSRF, credential abuse, DoS limits, no-PII-in-barcodes …)" and "business-state authorisation
checks (no client-driven state)". That is eleven abuse-case families over nine flows, plus a
cross-cutting rule, and it is six sub-issues rather than one. **This sub-issue takes the two authorisation families
— `ABF-01` insecure direct object reference and `ABF-02` privilege escalation — and builds the coverage-enumeration
mechanism every sibling suite then reuses.** Its sibling takes `ABF-03` workflow bypass, `ABF-04` barcode replay and
the no-client-driven-state rule; three more take `ABF-05`, then `ABF-06` with `ABF-08`, then `ABF-07`, `ABF-09` and
`ABF-10` with `ABF-11`.

The split is at the line where the fixtures change. `ABF-01` and `ABF-02` are **pure authorisation**: they reuse
`tests/Tailor360.IntegrationTests/Authorization/` wholesale, need no business scene beyond an existing record, and
can be written against any surface that exists. `ABF-03` and `ABF-04` need a *sequence of business state* — an
estimate that was never accepted, a job in a prior phase, a label already dispatched — which is a different fixture
problem and a different body of domain reading. Putting them in one session meant one session reading Identity,
Orders, Custody and the whole published inventory at once.

**This sub-issue owns the folder and the shared machinery**, because it is the first of the seven to be taken:
`tests/Tailor360.IntegrationTests/Security/AbuseCases/`, the family trait, the shared probe helper, and the
enumeration harness that makes coverage a build failure rather than a claim. Every sibling suite depends on this one
for those four things and adds only its own test classes. That is what makes the other six parallel-safe after this one
merges, and it is why this one must be taken first.

The gap is checkable today: `ls tests/Tailor360.IntegrationTests/Security` returns
`ContentSecurityPolicyTests.cs`, `CrossSiteDefenceTests.cs`, `ErrorLeakTests.cs`, `ForwardedHeaderTests.cs` and
`ResourceScopePipelineTests.cs` — five files, none of which tests a **sequence**. What exists proves per-request
rules; what is missing is the attacker's multi-step plan.

## What is already built (do not re-build)

- `tests/Tailor360.IntegrationTests/Authorization/` — the authorisation matrix and its machinery:
  `matrix.yaml` (the expectations), `AuthorisationMatrix.cs`, `AuthorisationMatrixTests.cs`, `RoleMatrixTests.cs`,
  `MatrixFixtures.cs`, `AuthorisationProbeApplication.cs`, `EndpointInventory.cs`, `DenialAuditTests.cs`,
  `IdentifierEditingTests.cs`. The matrix **already** fails when a published endpoint has no entry, and it already
  covers role × own-branch × other-branch per endpoint (`NFR-SE-02`). **This suite is not a second matrix.** It
  proves what the matrix cannot: that a sequence of individually-permitted requests cannot reach a state no single
  request may reach.
- `tests/Tailor360.IntegrationTests/Security/ResourceScopePipelineTests.cs` — the resource-scope pipeline and its
  fail-closed behaviour: a host that omits `UseTailor360ResourceScope()` refuses every request rather than skipping
  the check. Reuse this; it is the foundation `ABF-01` rests on.
- The two controls `docs/security/README.md` section 3.2 records as already decided and tested for the authorisation
  flow: **a foreign resource and a missing one are both answered `404 security.resource-not-found`**, and the
  resource pipeline fails closed. Every `ABF-01` assertion must check the *indistinguishability*, not merely the
  refusal.

  database-availability rule. Integration tests use `TAILOR360_TEST_DATABASE_URL` when set, otherwise a container,

- `docs/architecture/invariants.md` sections 4.5 to 4.8 and section 6, and `docs/prd/state-transitions.md` — the

## What is missing

- No test anywhere performs a **sequence**: confirm an order whose estimate was never accepted; advance a phase twice
  from the same prior state; scan a label that another branch already dispatched; re-present an invalidated label;
  send a state field the client should not be allowed to choose and see whether the server trusts it.
- Nothing asserts the **no-client-driven-state** rule as a rule. It is stated in plan Section 8 and enforced nowhere.
- Nothing groups the existing negative tests by abuse-case family, so the parent's acceptance criterion cannot be
  evidenced without reading eight files.

## Acceptance criteria

- [ ] `./scripts/dev test integration` runs `InsecureDirectObjectReferenceTests` and `PrivilegeEscalationTests`, and
      either can be run alone by its family trait. Every test carries `[Trait("Category", "Integration")]`.
- [ ] For every route in the published endpoint inventory that carries a resource identifier, an `ABF-01` case exists;
      `AbuseCaseCoverage` **fails when a new such route has no case**, the way `matrix.yaml` already fails for a
      missing matrix entry, and the failure message lists the uncovered routes by name. Coverage is enforced, not
      asserted.
- [ ] For every `RequiresStepUp` or `RequiresMfa` permission and every irreversible or money-moving permission, an
      `ABF-02` case exists, under the same enumeration rule.
- [ ] **The shared machinery is usable by a sibling without modification.** `AbuseCaseTraits` declares all eleven
      families; `AbuseCaseProbes` declares the five probe principals by the names above; `AbuseCaseCoverage` takes a
      new family predicate as **one new file and no edit to any existing file**. The pull request demonstrates this by
      adding a throwaway `Abf03Coverage.cs` on a scratch commit, showing the harness picks it up with no other change,
      and removing it again — and by showing that a family with no predicate file is reported as **not-yet-owned**
      rather than failing the build, so a sibling can land its predicate and its tests together without this
      sub-issue having to guess its content.
- [ ] **Negative case** (the whole sub-issue is negative cases, so this criterion is about their shape): every
      refusal is asserted on the **exact** response — status, problem type, and the absence of any detail that
      distinguishes "forbidden" from "not found" — and on the audit row it produced. A test that asserts only
      "not 200" does not count.
- [ ] **Negative case, indistinguishability**: at least one `ABF-01` test asserts that the other-branch and the
      non-existent answers do not differ measurably in time, in the manner `authentication.md`'s
      `AWrongPasswordAndAnUnknownAccountTakeTheSameTimeToAnswer` already does for sign-in.
- [ ] **Exception case**: each sanctioned way out is tested as *working*, not only as refused — a caller **with** the
      branch reach reads the same resource successfully; a caller holding a `RequiresStepUp` permission with a
      **fresh** strong authentication succeeds; a caller with an enrolled factor reaches a `RequiresMfa` action. A
      suite that only proves refusals would pass against a system that refuses everything, and this criterion is what
      stops that.
- [ ] The suite is **stable**: it passes twice in a row in different orders (CLAUDE.md section 5), and it runs inside
      the pull-request pipeline budget — plan Section 8 fixes that at 15 minutes wall clock, so the pull request
      reports the tier's duration before and after.
- [ ] Every new test names the `ABF-nn` family and the flow model's `AB-nn`/`CTL-nn` identifier it proves, and
      `docs/security/abuse-cases.md` names the test class in return, in the `ABF-01` and `ABF-02` rows only. A
      reviewer can go from a family to a test and back.
- [ ] Any finding is either fixed here, or an open issue number appears in a skip reason. Nothing is silently
      removed.
- [ ] `dotnet format --verify-no-changes` is clean and the other tiers still pass.
