## Scope

- [ ] **`inventory.purchase_receipts`** — `id` (UUIDv7), `organisation_id`, `branch_id`, `supplier_id`,
      `purchase_order_id` nullable, `receiving_location_id`, `supplier_document_reference` (the supplier's own invoice
      or delivery-note number, a reference and never a lookup key), `received_at`, `received_by_user_id`,
      `evidence_media_id uuid` nullable **with no foreign key** — Media owns its objects and Inventory owns no storage
      prefix (`module-ownership.md` section 5.7: "Owned object-storage prefix. None. Purchase-receipt evidence images
      are Media objects") — `client_request_key`, `notes_code` nullable.
- [ ] **`inventory.purchase_receipt_lines`** — `id`, `purchase_receipt_id`, `purchase_order_line_id` nullable,
      `item_id`, `received_quantity numeric(18,4)` with `received_unit_code` and the base-unit equivalent computed at
      entry, `unit_cost numeric(18,4)` **required**, `lot_reference` nullable, `hsn_code` and `tax_code_reference`
      copied at entry, `ledger_entry_id` (the entry this line posted), `line_index`, unique on `(purchase_receipt_id,
      line_index)`.
- [ ] **One transaction, one posting** — the receipt header, every line, one `PurchaseReceipt` ledger entry per line
      through a **single** `ILedgerPoster` call, the balance updates, the audit entry and the outbox row all inside
      the same unit of work. No second `SaveChangesAsync`, no outbox-driven balance update (INV-STK-03 forbids it in
      terms: the balance is updated in the same database transaction as the ledger insert, never via the outbox).
- [ ] **Validation** — the supplier must be `active` (`inventory.supplier-not-selectable`); every item must be
      `active`; the receiving location must belong to the caller's branch; at least one line; a non-positive quantity
      or a negative unit cost is refused naming the field; an item whose tracking method is lot/batch **must** carry a
      `lot_reference` and an untracked item **must not** (`inventory.lot-reference-required` and
      `inventory.lot-reference-not-applicable`); where a `purchase_order_id` is given, every line's purchase-order
      line must belong to that order, the order must be `Placed` and of the same supplier, and the received quantity
      may not exceed the line's outstanding ordered quantity (`inventory.receipt-exceeds-order`) — no over-delivery
      tolerance is invented, because none has a source.
- [ ] **Closing the order** — when every line of a named purchase order is fully received, the order moves `Placed →
      Closed` in the same transaction. A partially received order stays `Placed` and a second receipt against it is
      accepted.
- [ ] **Endpoints** — `POST /api/v1/inventory/purchase-receipts` (`inventory.record_movement`,
      `RateLimitPolicyNames.Write`, `.Audited("inventory.purchase_receipt.posted", reasonRequired: true)` — the key is
      declared `RequiresReason: true`, so the pair must match the catalogue (`AuthorisationProbeApplication.cs:721`),
      and the handler validates the reason and writes it onto the audit entry itself because no filter does
      (`AuditedEndpointMetadata.cs:5-6`) —, `.RequireIdempotency()`, `.TouchesNoBranchOwnedResource(reason, "#39")`,
      `RequestTimeoutPolicies.Command`); `GET /api/v1/inventory/purchase-receipts/{purchaseReceiptId}` with its lines
      and their ledger entry identifiers (`inventory.record_movement`, `DefaultUser`, `RequestTimeoutPolicies.Read`,
      `.ScopedToResource(InventoryResourceKinds.PurchaseReceipt, "purchaseReceiptId")`, another branch's reads
      **404**); `GET /api/v1/inventory/purchase-receipts` with the collection shape `docs/api/conventions.md` section
      4.2 fixes — `items`, opaque `nextCursor`, `hasMore`, no `totalCount`, `limit` clamped not refused — and
      `filter[supplierId]`, `filter[purchaseOrderId]` and `filter[receivedAfter]`; an undeclared filter is **400**,
      never ignored.
- [ ] **`unit_cost` is never on a response payload this child publishes.** Cost is Confidential
      (`docs/nfr/data-classification.md` section 5.9) and is read under `inventory.view_valuation` through the
      response view `E08-F02-7` adds. The receipt read answers quantities, lots, locations and references; a reviewer
      can check that by reading the payload type.
- [ ] **`inventory.purchase-received.v1`** — the **eight** fields `stock-reservation.md` section 5 fixes, and no
      others: receipt id, supplier id, item ids, quantities, unit costs, lot references, location, branch code. It is
      the one published event that legitimately carries cost, because section 5 names the accounting export as its
      consumer. Add `docs/integration/events/inventory.purchase-received.v1.schema.json` and its `.example.json`.
- [ ] `InventoryResourceKinds.PurchaseReceipt = "inventory.purchase_receipt"` and its `IResourceScopeResolver`. One
      migration, `PurchaseReceipts`, with its `docs/dev/migrations.md` register row. Matrix rows for the three routes,
      the `{purchaseReceiptId}` `identifier-editing` entry in `matrix.yaml`, and the regenerated
      `docs/api/openapi.v1.json`.

## Acceptance criteria

- [ ] An Inventory Clerk holding `inventory.record_movement` posts a three-line receipt against a placed purchase
      order over HTTP; three `PurchaseReceipt` ledger entries exist, each balance rises by its line's base-unit
      quantity, each line records the `ledger_entry_id` it posted, and the order is `Closed` because the receipt
      covered it.
- [ ] **No half-post (the parent's third acceptance criterion):** a receipt whose **third** line fails validation — an
      unknown unit, a retired item, a missing lot reference — leaves **no** receipt row, **no** receipt line, **no**
      ledger entry and **every** balance unchanged. Proved for a failure in the first, middle and last line.
- [ ] **No half-post under a database failure:** the same assertion when the posting fails at the database rather than
      in validation (for example by provoking the append-only trigger on a deliberately malformed second posting in
      the same transaction) — the transaction boundary, not the validation order, is what guarantees it.
- [ ] A receipt posted without a purchase order succeeds and leaves no order touched; a receipt whose lines exceed the
      outstanding ordered quantity is refused with `inventory.receipt-exceeds-order`; a partially received order stays
      `Placed` and accepts a second receipt which then closes it.
- [ ] Lot discipline: a lot-tracked item without a lot reference is refused, an untracked item **with** one is
      refused, and both refusals name the field.
- [ ] **Negative:** a caller without `inventory.record_movement` is refused 403 and audited; another branch's receipt
      reads 404; a replayed `Idempotency-Key` returns the first receipt and posts no second set of ledger entries; a
      suspended supplier cannot be selected while a receipt that already names it still reads in full.
- [ ] `inventory.purchase-received.v1` is published exactly once per receipt, in the same transaction as the rows (the
      outbox row is committed with them), carries the **eight** fields section 5 names and no others, and has its
      schema and example committed.
- [ ] Every route declares exactly one permission and one rate-limit policy, the command carries the audit filter and
      idempotency, and the single read declares a resource scope (ARCH-007, ARCH-008, ARCH-017, ARCH-023). No response
      payload carries `unit_cost`.
