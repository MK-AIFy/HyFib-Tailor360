Sub-issue of #46. Seventh of thirteen, and the part of this issue a reviewer will read first: the **governed export**
of the stock and profitability reports — field-level column policies so a caller receives only the columns permitted
to their role and branch, the export audit record, the Confidential classification on the file itself, and the proof
that an expired export is unusable. It adds **no export service**: #186 owns `export_jobs`, the worker generation, the
download route and the retention job, and the plan says #46 "uses the #44 export service".

This is the slice where a mistake leaks money figures out of the building, so it is deliberately small and entirely
about governance rather than about new reports.

- #186 — `[E10-F01-4]`: `export_jobs` (requester, report, filters, format, classification, row count, status, storage
  key under the Reporting-owned `exports/` prefix, `expires_at`), the worker that generates the encrypted file, `GET
  /api/v1/reporting/exports/{id}/download` re-authorised per request and audited, the retention job that deletes an
  expired file, and the synchronous-versus-asynchronous split behind a row limit.
- `src/Platform/Tailor360.Platform.Abstractions/Ports/IObjectStorage.cs` — a put, `OpenReadAsync` and `ExistsAsync`,
  and **deliberately no delete and no listing**: line 5 of that file says so in as many words, and that "no URL to an
  object is ever handed out: every read goes through an endpoint that re-authorises the caller" (CLAUDE.md section 4
  rule 9, ADR-0005). Know this before writing an expiry test: what this child proves is that the **download refuses**,
  and what the retention job can delete is #186's question, not a reason to add a delete to a platform port here.
- `docs/adr/0011-reporting-read-models.md` section 4.4 — the export controls, verbatim and already decided: the
  `exports/` prefix, the expiring authorised download, the injection rule ("every cell beginning `=`, `+`, `-`, `@`,
  tab or carriage return is prefixed with an apostrophe and quoted; UTF-8 with a byte-order mark; rows capped (default
  50,000, larger exports paginated into an archive)"), and "`reports.export` permission, branch scope enforced, and an
  explicit audit entry for the sensitive read".
- `src/Platform/Tailor360.Platform.Security/FieldVisibility/` plus the views `e10-f03-3` and `e10-f03-6` declared —
  `IFieldVisibilityPolicy` computes the mask from the caller's permissions. **The export column set is that same mask,
  applied to a file instead of to a payload.** Re-deriving the rule in an export writer is exactly what
  `docs/security/field-visibility.md` section 2 argues against.
- `src/Platform/Tailor360.Platform.Security/Background/WorkerJobAttribute.cs` — `ActsForRequester` with
  `IWorkerScopeFactory.CreateScopeForAsync`, which "rebuilds the requester's authority from the database before the
  job runs". That is the mechanism that makes an asynchronous export obey the requester's live permissions rather than
  a copy taken at request time.
- `docs/security/permission-matrix.md` — `reports.export` already exists (line 245): branch scope, **MFA required**,
  reason required, granted to `owner`, `branch_manager`, `auditor`. The note on that row says the row threshold is
  "#46's separate control"; that control is `e10-f03-8`.
- The audited-read precedent: `POST /api/v1/admin/audit/export`, audited as `platform.audit.exported` — "audited
  although it changes nothing, because taking a copy out of the system *is* the act".

## What is missing

- Nothing registers a report with the export service: there is no report-definition registry, so no column set, no
  classification and no ordered header exist for any report in this issue.
- No test anywhere proves that an export cannot carry a column the requester's screen withholds, which is the parent's
  third acceptance criterion ("exports cannot bypass screen-level branch/field restrictions").

## Scope

- [ ] **A report-definition registry in Reporting** — one definition per report this issue has actually shipped by the
      time this child runs: stock position and aging, stock movements, stocktake variance, stock trends,
      profitability, profitability trends. **The wastage report is deliberately absent**: it arrives with
      `e10-f03-2b`, which is blocked on an additive Inventory event and adds its own definition to this registry when
      it lands. Each definition names naming: the projection it reads, the `ReportingResponseViews` view that governs
      its columns, the ordered column list with each column's `FieldClassification`, the classification label that
      goes in the file header (**Confidential** for every report here, per `data-classification.md` section 5.9 and
      5.10), the metric dictionary entries behind its figures, and the filters it accepts. Configuration-shaped and
      versioned in source (DOR-11), not rows an operator edits.
- [ ] **Column policy applied to the file**: the generator asks `IFieldVisibilityPolicy` for the mask the
      **requester** holds — rebuilt by `IWorkerScopeFactory.CreateScopeForAsync` for an asynchronous run, not copied
      from the request — and emits exactly the permitted columns. A withheld column is **absent from the header**, not
      blank and not zero, so a file cannot imply a figure it does not carry.
- [ ] **Branch scope applied to the rows**: the same branch-reach evaluation the read routes perform, re-evaluated at
      generation time, so a permission lost between request and generation narrows or refuses the file rather than
      honouring a stale claim (CLAUDE.md section 4 rule 2: branch scope is evaluated, never inferred).
- [ ] **The export audit record**, per the parent's seventh implementation step: actor reference, report, filters, row
      count, classification, status, and a separate entry on each download — recorded through the platform audit
      mechanism with an action name per event (for example `reporting.report.exported` and
      `reporting.report.downloaded`). The filters are recorded as the **filter values**, which are identifiers, codes
      and dates; no exported row, no amount and no customer name is recorded (CLAUDE.md section 4 rule 7).
- [ ] **The file header block** on every generated file: report name, generated-at, data-as-of read from #183's
      `projection_checkpoints` through the seam that child publishes — the same source #186's status route reads, so
      the two cannot disagree; not recomputed, and not fetched by calling #186's HTTP route from the worker — the
      reconciliation status and delta at that cut-off, the classification label, the costing assumption version and
      valuation run where the report carries cost or margin, and the estimated-and-incomplete label where any
      component is unavailable.
- [ ] **Injection safety and encoding** are #186's writer's; this child adds its reports to that writer's **injection
      corpus test** so every new column is covered (`docs/nfr/traceability.md` NFR-FI-07 names the corpus test for
      "every export path").
- [ ] **No route is added here, and that is decided rather than left open.** The request and download routes are
      #186's generic ones — expected to be `POST /api/v1/reporting/exports` and
      `GET /api/v1/reporting/exports/{id}/download`, but **read #186's merged `ReportingEndpoints` and
      `docs/api/openapi.v1.json` for the real paths rather than assuming these**, because #186 is open and has not
      fixed them yet — and a per-report request route would duplicate the governance this child exists to centralise.
      So `docs/security/permission-matrix.md` section 5 and
      `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml` gain **no new endpoint row**; they gain only the
      per-caller column-parity and expiry cases under `tests/Tailor360.IntegrationTests/Authorization/`. If a reviewer
      wants a per-report route it is a follow-up issue, not a late addition here.

## Acceptance criteria

- [ ] An Owner requests a stock-position export and receives a file whose header carries the report name,
      generated-at, data-as-of, reconciliation status, the Confidential label and the valuation run; its columns are
      exactly the view's columns for that caller.
- [ ] **Negative — the parent's third criterion:** a caller holding `reports.export` and `reports.read` but **not**
      the cost and margin gate receives a file with every cost, value and margin column **absent from the header**;
      the test compares the file's columns with that caller's on-screen payload and asserts they agree, which is what
      "exports cannot bypass screen-level restrictions" means operationally.
- [ ] **Negative:** a caller assigned to branch A who names branch B in an export filter is refused, and a file
      generated for a requester whose branch assignment was removed between request and generation contains no
      branch-B row — the authority is rebuilt at generation time.
- [ ] **Negative:** a download after `expires_at` is refused by the route rather than serving stale content (#186's
      route behaviour, asserted here for these reports), and the refusal is indistinguishable from "not found" for a
      caller who was never entitled to it.
- [ ] **Exception:** an export whose generation fails leaves an `export_jobs` row in a failed state with a reason, no
      partial file offered for download, and an audit entry saying so — a failed export is visible, not silent.
- [ ] Every export and every download writes its audit entry, and a test asserts the entry contains **no amount and no
      customer name** (CLAUDE.md section 4 rule 7; `data-classification.md` section 5.9 forbids cost figures in logs).
- [ ] The injection corpus test covers every column of every report defined here.

## Modules, contracts and events

Reporting only. `exports/` is Reporting's own object-storage prefix (`module-ownership.md` section 5.9), reached
through the platform port `IObjectStorage` — a **platform port**, the fifth of the five sanctioned mechanisms in
CLAUDE.md section 3. No other module's table is read (ARCH-005) and no other module's `Infrastructure` or `Api` is
referenced (ARCH-011). No integration event is published: Reporting publishes only its two operational events. DOR-05:
this is the export surface the "Reports and exports" row of `docs/security/README.md` section 3.2 names, covered by
**#56a** (the plan's label for a not-yet-filed W2 child of open **#56**) with **ADR-0011 section 4.4** standing in —
the abuse cases are column bypass, branch-filter inference, link sharing and an expired file still being served, and
each has a negative test above.
