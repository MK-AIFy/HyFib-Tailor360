## Scope

- [ ] `docs/runbooks/README.md` — the index and the rules: one document per situation; every document begins with
      **when to use this and when not to**; every step is numbered, has an expected result and says what to do when
      the result differs; every document names a primary and an alternate owner **by role**, never by person
      (**OD-15** is open); and every document ends with "what this run must record" so the evidence is produced
      during the recovery rather than reconstructed after it. The index table carries, per runbook: the situation,
      the severity it usually is (from `docs/nfr/security-operations-targets.md` section 5), the expected duration

- [ ] `docs/runbooks/_template.md` — the skeleton the ten runbooks share, in the spirit of
      `docs/templates/threat-model.md`: situation; when not to use this; severity and who to tell; **preserve
      evidence first**; preconditions and access needed; the numbered steps; decision points, each with the roles
      that may take it; verification; reopening the environment; what to record; related runbooks.
- [ ] `docs/runbooks/restore.md` — the full database restore. The stages of `docs/nfr/slo.md` section 6.1 in order,
      each with the command and the expected output; `infra/backup/restore-drill.sh` named as the automated form and
      the manual form given for when the script cannot be used; the invariant queries run **before** the environment

      executed after the restore point before the environment is opened**. That table does not exist yet (it arrives

      omitted — an omitted step is how a restore quietly reinstates data a customer asked to have deleted
      (`docs/nfr/data-classification.md` section 7).
- [ ] `docs/runbooks/point-in-time-recovery.md` — recovering to a chosen timestamp rather than to the latest backup:
      how the target is chosen and who approves it, how the preflight record of a deployment is used as the target
      (the "latest backup label and `pg_current_wal_lsn()` recorded before `migrate`" of plan #59), what is lost
      between the target and now and how that loss is communicated, and the refusal case — a target the repository
      cannot satisfy, which the drill reports as `indeterminate`.
- [ ] `docs/runbooks/accidental-deletion.md` — a wrong `DELETE`, a wrong administrative action, a wrong bulk change.
      The first decision is the one people get wrong: **recover the rows, not the cluster**, wherever possible —
      restore into the isolated project of `infra/compose/docker-compose.restore.yml` and copy the affected rows
      forward, because a whole-cluster rollback discards every other branch's work since. Includes the audit trail as
      the evidence of what was deleted (`platform.audit_events`' `before`/`after` columns), and the explicit rule
      that audit rows are never deleted or re-written to tidy the record.
- [ ] `docs/runbooks/bad-migration.md` — the three-step order of `docs/dev/migrations.md` "Rolling back", in that
      order, with the preconditions of each; how the expand–migrate–contract shape decides whether the previous
      application version can simply be redeployed; and the case the plan's #59 preflight exists for — the recorded
      backup label and WAL position as the recovery target. States plainly that editing an applied migration is
      never a recovery step.
- [ ] `docs/runbooks/database-corruption.md` — `--data-checksums` is on
      (`infra/compose/docker-compose.yml:57`, `POSTGRES_INITDB_ARGS: "--data-checksums"`), so corruption surfaces as
      a checksum failure rather than as a mystery; what to capture before touching anything; why the response is
      restore-and-verify rather than `REINDEX`-and-hope; and the audit-chain case of
      `docs/nfr/security-operations-targets.md` section 6.4 — compare against the anchored chain head, **never
      truncate or repair the chain**.
- [ ] `docs/runbooks/lost-object.md` — an object deleted or overwritten in the media, documents or exports bucket:

      that may take it — with a line in the index recording that **OD-15** is open, so the roles are named and the

## Migration and rollback

No schema change and no migration: this slice adds only markdown. `migrate --dry-run` printing "The database is up to
date with this build." is the proof, and CI's `migration-check` job confirms no model change.

Rollback is a revert of the documents, which is safe precisely because nothing depends on them mechanically **yet**:
after #58 points a `runbook_url` at one of these files, reverting it breaks an alert's link, so the document must say
so at the top of `docs/runbooks/README.md` — a runbook that alerts reference is no longer free to delete, and the
replacement comes in the same pull request as the removal.
