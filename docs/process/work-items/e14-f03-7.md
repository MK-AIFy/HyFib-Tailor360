Sub-issue of #58. #58's third acceptance criterion is "retry policies cannot create duplicate protected business
effects", and the plan's blueprint names the test it wants: a "**retry-safety test**: fault injection retries every
protected command (confirm, scan, invoice post, payment, webhook delivery, payment callback) under timeouts and worker
restarts and asserts exactly one business effect". The mechanism that makes this true is built and well tested in
isolation — `src/Platform/Tailor360.Platform.Persistence/Idempotency/IdempotencyStore.cs` over
`platform.idempotency_keys` with the in-flight lease from `Migrations/20260906170048_IdempotencyInFlightLease.cs`, wired
by `src/Platform/Tailor360.Platform.Security/Endpoints/IdempotencyEndpointFilter.cs`, and declared on **95** endpoints
(`grep -rn RequireIdempotency src/ --include=*.cs | wc -l`). What does not exist is a suite that proves the *business
effect* is singular when the failure arrives in the worst place: mid-transaction, at the timeout boundary, or while a
worker restarts. This slice is the **fixture and the invoice-side half** of that suite, and it adds no production code.
**Child 7b** is the payment-side half and the handler-side redelivery scenarios. The split is a size judgement and the
calibration is in the repository: `tests/Tailor360.IntegrationTests/Billing/InvoicePostingTests.cs` is **454 lines** and
`PaymentEndpointTests.cs` is **421** for the happy and refusal paths alone, so eighteen fault-injection scenarios over
six commands plus the fixture is 2,000 test lines or more. "No production code" does not make it one session — the
context a session spends reading harnesses and writing assertions is what runs out.

## Acceptance criteria

- [ ] For each of the three commands, a client that times out and retries with the same `Idempotency-Key` observes the
      **first** outcome and the database holds exactly one effect: one invoice in `Posted` with one document number and
      no sequence gap other than a recorded cancellation; one cancellation with one credit note for the whole amount;
      one outbox replay with one audit entry and one delivery.
- [ ] For each command, a mid-transaction failure leaves **no** partial effect: no invoice row without its document
      number, no payment without its allocation, no audit event describing a change that did not commit.
- [ ] Restarting the worker while a message is in flight redelivers it after the lease expires and the consumer's effect
      remains singular, proved through the inbox de-duplication record rather than by counting rows alone.
- [ ] **Negative:** the same `Idempotency-Key` with a **different** body is refused with the code
      `docs/platform/idempotency-and-concurrency.md` specifies, and the refusal writes no effect; and a duplicate
      arriving **while the first is in flight** is refused rather than queued or executed.
- [ ] **Negative:** a retry **without** an `Idempotency-Key` on a protected command is refused by the filter rather than
      executed twice — the absence of a key is never treated as a fresh command on a protected route.
- [ ] **Exception:** a timed-out command's claim is left standing, so an immediate retry is refused as in-flight and the
      caller is told to wait rather than being allowed to run the command again. This is the behaviour
      `RequestTimeoutPolicies`' own remarks state, and proving it is the point: "the safe answer to 'try again' is 'wait
      for the lease', not 'run it again'".
- [ ] The coverage test lists every protected command with either a scenario or an owning issue, and fails when a new
      protected command is added to the catalogue with neither.
