Sub-issue of #40. The stocktake half of #40 is four separable things — opening and counting, closing and holding the
location, approving what the count found, and the screens — and the blueprint paragraph in
`docs/IMPLEMENTATION_PLAN.md` Section 9 (`### #40`, "**Stocktake**") names all of them in one sentence. This child is
the **opening and counting** part only: the session, the count sheet with its frozen expected quantities, the first
count and the recount.

**Closing counting, abandoning a session and the movement freeze are `E08-F03-4b`.** An earlier decomposition put
them here and listed "six endpoints, which is the cap this slice accepts" — but its own scope and acceptance criteria
also required an **abandon** route, which was not among the six, so the real count was seven and the slice was over
the two-to-six bar with the only cross-sibling edit in the parent (the freeze call site inside #39's movement command)
buried in it. Splitting puts that single call site in a child that can be reviewed for it. Checked today: `grep -rn
"stocktake\|Stocktake" src/` returns nothing at all;
the only stocktake artefact in the repository is the accessibility prototype
`clients/pwa/src/stories/journeys/InventoryStockEntry.tsx` (492 lines, over
`clients/pwa/src/stories/fixtures/inventory.ts`, 240 lines), which has no backend behind it.

## Scope

- [ ] **`Stocktake` aggregate** in `…Inventory.Domain/Stocktakes/` — one session per `(branch, location)`, states
      `Counting → CountingClosed → Posted | Abandoned`, the actor who opened it, the opening instant, and **at most
      one session in `Counting` per location**, enforced by a partial unique index rather than by a read-then-write
      check. The **whole** state enumeration is declared here so the migration's check constraint and the payload's
      union are complete from the start; but this child implements only `Open`, `RecordCount` and `RecordRecount`.
      `CloseCounting` and `Abandon` are `E08-F03-4b`'s, `Posted` is `E08-F03-5`'s.
- [ ] **`StocktakeCount` entity** — one row per counted `(item, location)` line, carrying the **expected quantity
      frozen at open** (read from #39's balances in the opening transaction), the first count with its actor and
      instant, and the recount with its actor, instant and reason, all in the item's base unit (INV-STK-02: no
      conversion in a report or an evaluation). The first count is never overwritten — the prototype's "It is kept."
      is a data rule, not a screen rule.
- [ ] **No freeze here.** The freeze — a movement **out of** a `Counting` location being refused — is `E08-F03-4b`'s,
      because it is the one edit in the whole of #40 that lands inside another issue's handler (#39's movement
      command) and it deserves a pull request a reviewer can read for exactly that. This child stores the state the
      freeze is computed from and nothing more; it must **not** add a half-port or a disabled guard, because a guard
      that is present and not wired reads in review as a guard that works.
- [ ] **One migration**, `InventoryStocktakes`, creating `inventory.stocktakes` and `inventory.stocktake_counts`
      only, with the partial unique index above and an append-only trigger on `stocktake_counts`
      (counts are evidence: a correction is a recount row, not an edit — the pattern
      `billing.financial_records_are_append_only()` already uses, verified in
      `src/Modules/Billing/…/Migrations/20260912160123_Receipts.cs:84`, G-4). Expand-only; ledger row added to
      `docs/dev/migrations.md` in the shape of the `20260912180307_ReconciliationBatches` row at line 121.
      `E08-F03-4b` adds **no** migration, so this is the only schema change in the counting half.
- [ ] **Five endpoints**:
      `POST /api/v1/inventory/stocktakes` (open; `Idempotency-Key`; refuses a second open session for the location),
      `GET /api/v1/inventory/stocktakes` (cursor-paged, filter by state and location),
      `GET /api/v1/inventory/stocktakes/{stocktakeId}` (the count sheet, with an `ETag` through
      `context.Response.SetEntityTag(...)` — `ConcurrencyEndpoints.cs:39`, used the same way at
      `ReconciliationEndpoints.cs:58`), `POST …/{stocktakeId}/counts`, `POST …/{stocktakeId}/recounts`.
      All five: `RequirePermission(InventoryPermissions.Stocktake, BranchScope.CurrentBranch)`, exactly one
      rate-limit policy (`DefaultUser` for the two reads, `Write` for the three commands), exactly one request
      timeout (`RequestTimeoutPolicies.Read` / `.Command`), `.Audited(…)` on every command (ARCH-008),
      `.ScopedToResource(InventoryResourceKinds.Stocktake, "stocktakeId")` on every `{stocktakeId}` route
      (ARCH-023), `.RequireIdempotency()` on every command, and **no** `.RequireStepUp()` — `inventory.stocktake` is
      not flagged for step-up and `AuthorisationMatrix.Reconcile` fails an endpoint that declares step-up for an
      unflagged key (`DetectsStepUpDeclaredForAPermissionThatIsNotFlaggedForIt`, ARCH-018). The two reads take no
      `If-Match` and the commands take none either: the row's state is the guard, the form the matrix note for
      `POST /api/v1/billing/cashier-sessions/{sessionId}/close` (line 386) already records.
- [ ] **Where the reason is demanded, and where it is not.** The permission is flagged `RequiresReason`
      (`InventoryPermissions.cs`: `new(Stocktake, …, RequiresReason: true)`), and this child spends that flag where it
      means something: `.Audited("inventory.stocktake.recounted", reasonRequired: true)`, while opening a session and
      recording a **first** count are audited without one. Demanding a typed reason per counted line would make the
      clerk's job undoable; say so in the matrix note so the decision is reviewed once. (`E08-F03-4b` spends it again
      on abandon, and deliberately not on close-counting.)
- [ ] **Payload types in the `Api` project** (ARCH-013); `InventoryResourceKinds` gains `Stocktake` and a
      `StocktakeScopeResolver` is registered (the `CashierSessionScopeResolver` shape).
- [ ] **Matrix and fixtures**: five endpoint rows in section 5 of `docs/security/permission-matrix.md` (inside the
      `<!-- matrix:endpoints -->` markers, which the tests parse) and one `identifier-editing` entry in
      `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml` for `{stocktakeId}`, in that file's own
      `route:` / `identifier:` / `because:` shape, whose answer is `out-of-reach` (`404`,
      `security.resource-not-found`).

## Acceptance criteria

- [ ] An Inventory Clerk opens a session for a location, reads the count sheet with its expected quantities, records
      a first count for three lines and records a recount with a reason for one of them — entirely over HTTP, with
      the first count still readable afterwards and the count sheet's `ETag` changing between reads.
- [ ] The expected quantity on every line is the balance **as at the opening instant**, read inside the opening
      transaction, and does not move when the balance moves afterwards — asserted by posting a movement after the
      open and re-reading the sheet.
- [ ] **Negative:** a second `POST /stocktakes` for a location that already has a session in `Counting` is refused
      `409` by the index, not by a read-then-write check — proved by two concurrent opens in one test.
- [ ] **Negative:** a caller at another branch pasting this branch's `{stocktakeId}` gets `matrix.yaml`'s
      `out-of-reach` answer — `404` with `security.resource-not-found`; a caller without `inventory.stocktake` gets
      `not-permitted` — `403` with `security.forbidden`.
- [ ] **Negative:** an `UPDATE` or `DELETE` against `stocktake_counts` is refused by the database trigger even for the
      application role, and a second count for a line that already has one is **appended as a new row** rather than
      overwriting — the prototype's "It is kept." is a data rule, so the test reads both rows back.
- [ ] **Exception:** a count recorded for a line that is not on the sheet, or for an item with no balance at the
      location, is refused with an RFC 9457 problem detail naming the field — not silently accepted as a new line,
      because a line that was never expected has no expected quantity and therefore no computable variance.
- [ ] Every one of the five routes declares exactly one permission, exactly one rate-limit policy, one request
      timeout, a resource scope where it takes an identifier, and an audit action on every command;
      `AuthorisationMatrixTests` passes with the new rows.
