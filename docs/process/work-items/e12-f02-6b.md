Sub-issue of #51. **Evidence only. This is not a coding session: it cannot be completed without a real Android phone, a
real iPhone or iPad, and a real desktop browser.** It produces the install, installed-mode, offline-reload, update and
rollback records that `docs/nfr/support-matrix.md` section 9 requires per Tier 1 device class, and it is the one child
of #51 that may legitimately report a **gap** instead of a pass.

It is carved out deliberately. `docs/process/definition-of-ready.md` DOR-16 treats "a device or printer for a physical
rehearsal" as its own environment requirement, and its exemption table says the hardware criterion applies to
"#35, #36, #37, #48 and #61c always; others rarely". #51 is one of the rare others, and mixing a device walkthrough into
a code pull request is how a coding session ends up blocked on hardware it cannot have. Everything automatable in this
feature is in #E12-F02-1 to #E12-F02-6a; what is left is here.

## Scope

- [ ] **Per Tier 1 device class, a recorded walkthrough** of the five steps, in a browser tab **and** in installed
      mode, with the device, operating-system and browser versions logged as section 9 requires:
      1. **Install** from the browser — Android through `beforeinstallprompt`, iOS through Safari's Share → Add to Home
         Screen, desktop through the address-bar install control. On iOS in a **non-Safari** browser, record that the
         Install screen detects it and says to open the same URL in Safari (section 4.1), which is a pass, not a fail.
      2. **Confirm installed mode** — `installPlatform.ts`'s display-mode probe reports standalone.
      3. **Go offline and reload** — the shell renders, the offline banner is on screen, and the catalogue shows the
         staleness marker rather than an error.
      4. **Take an update** — a second build deployed, the prompt appears without a manual reload, consent reloads
         once, and the footer shows the new build.
      5. **Roll back** — the previous asset build republished with the same minimum client; the device is prompted
         again, takes it, and lands on the older build with the older cache names and no stranded `required` latch.
- [ ] **The evidence table**, appended to `docs/pwa/offline-and-resilience.md`: one row per device class, with columns
      for device, operating system, browser, install result, installed-mode confirmation, offline-reload result, update
      result and rollback result. Cache names observed before and after each activation.
- [ ] **The print-station class needs no separate install record**, because section 3 defines it as "a counter tablet or
      desktop with the thermal label printer and the A4 printer attached" — the same browser on the same class of
      device. Say that in the document in one line, with the citation, rather than leaving a blank row a reviewer has
      to ask about. **No printing is exercised by this child at all**: labels, receipts and the print queue are #35's
      and #E07-F01's, and no thermal printer is required here.
- [ ] **`docs/nfr/traceability.md` NFR-CB-05** → `Proven` **only if** every Tier 1 class in section 3 was actually
      recorded. If any class was unavailable, the status stays `Proof scheduled (#50, #51)` with the gap named, or
      moves to `Evidence only` if that is the honest reading of section 2.3's vocabulary — and the choice is argued in
      one sentence in the pull request. Do not invent a fifth status. Edit this row and no other: #E12-F02-6a owns
      NFR-CL-04, NFR-CU-05 and NFR-CB-06.
- [ ] **Where a device class is unavailable, name it as a gap.** Say which class, why it was unavailable, and what is
      consequently unproven, in the pull request and in the document's table. Do **not** quietly test fewer classes and
      do **not** write a waiver: `docs/process/waivers.md` is for a gate that cannot be met, not for hardware that was
      not on the desk, and a waiver written for an absent device would be the wrong instrument recorded in the wrong
      register. A named gap against NFR-CB-05 is the correct artefact, and it is exactly what
      `docs/nfr/a11y-checklist.md` section 3.7 does for a state that cannot be forced.

      prompted, takes the older build, and its cache names carry the older build's version. No device is left unable to
      save.

      reason, the pull request says what is unproven because of it, and NFR-CB-05's status reflects that honestly. No
      waiver is written.

      e-mail address, device label and account name is redacted before it is attached.
