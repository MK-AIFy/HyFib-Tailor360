## What is already built (do not re-build)

- `src/Platform/Tailor360.Platform.Abstractions/Barcodes/BarcodePayload.cs` — the payload already exists and is
  already the one generator and validator for all four namespaces: `Alphabet` (Crockford base32), `GarmentJob`,
  `StockItem`, `Invoice` and `Receipt` namespaces, `BodyLength = 11`, `Length = 14`, `EntropyBits = 55`, `Mint(ns)`
  and `TryParse`. Its own documentation records that the payload "carries no display number and no personal data
  (`INV-BID-04`)". The policy document describes this; it does not redefine it, and no sheet hand-crafts a payload.
- `src/Platform/Tailor360.Platform.Abstractions/Ports/IBarcodeRenderer.cs` with `RenderPngAsync(payload, symbology,
  widthPixels, heightPixels)`, implemented by
  `src/Modules/Integration/Tailor360.Modules.Integration.Infrastructure/Documents/Code128BarcodeRenderer.cs`
  (ZXing.Net, Apache 2.0, per ADR-0014 section 2), and `IPdfRenderer` implemented by `QuestPdfRenderer` with the
  Noto Sans and Noto Sans Tamil embedded fonts in `Documents/DocumentFonts.cs`.
- **Both renderers are registered by `AddIntegrationModule`** —
  `IntegrationModuleServiceCollectionExtensions.cs` lines 54 and 55, `TryAddSingleton` — **and `CliHost` does not
  call it.** `src/Tools/Tailor360.Cli/CliHost.cs` composes Identity, Customers, Catalog, Media, Orders and Billing
  and nothing else, so a new command cannot resolve `IBarcodeRenderer` or `IPdfRenderer` until this issue adds
  `AddIntegrationModule(builder.Configuration)` beside them, and `AddCustodyModule(...)` for #191's templates. The
  project references for both are already in `Tailor360.Cli.csproj` (lines 19 and 22), so this is two lines and a
  comment, not a reference change — but it is the single most likely place to lose an hour, which is why it is
  written here. Integration owns no `DbContext`, so adding it puts no new migration in front of the runner; Custody
  does after #190, and that is a correction rather than a side effect — the `20260911141153_InitialOrdersSchema` row
  of `docs/dev/migrations.md` (line 112) records what the same omission cost last time. If #190 already added the
  Custody line, leave it alone.
- `src/Tools/Tailor360.Cli/Program.cs` — `RootCommand` composing `MigrateCommand.Create()`,
  `InitReferenceDataCommand`, `SeedSyntheticCommand`, `ReplayOutboxCommand` and `FlagsCommand` with
  `System.CommandLine`, and `Commands/EnvironmentGuard.cs` for the commands that must refuse Production.
- `docs/adr/0014-document-rendering-and-object-storage.md` — the libraries, the licence position and, at item 2, the
  fact that "the barcode is drawn, not rasterised into the PDF". Cite it; do not restate the choice.
- `docs/nfr/data-classification.md` section 9 (line 650) — the label content rule, already written and binding: "A
  **label** carries an opaque payload, a job number, a category cue, a due cue and a branch code — **no personal
  data at all**." The policy document is the operational form of this sentence, not a new rule.
- `docs/architecture/invariants.md` lines 328–330 — `INV-BID-04` (no personal data, no display number),
  `INV-BID-05` and `INV-BID-06`, which the policy cites rather than paraphrases.
- `docs/nfr/a11y-checklist.md` section 3.7 — the run kit already requires "a printed synthetic label sheet carrying
  one pre-made payload per rule — wrong namespace, bad check character, unknown identity, wrong branch, wrong
  custodian", and says in terms that "the check-character payload is generated by the seed tool, never hand-crafted:
  the checksum is a Damm-style check character over the Crockford base32 alphabet and cannot be guessed at a desk".
  **That is the requirement this command exists to satisfy**, and its five cases are the five the invalid sheet must
  carry — not four.
- `docs/nfr/support-matrix.md` section 7.2 and section 10 (**SM-04** scanner models, **SM-05** printer models, label
  size, QR). This issue produces the instrument those rows need; E07-F01-9 produces the readings.
- `docs/dev/commands.md` — the reference a new command is listed in, beside `init-reference-data` and
  `seed-synthetic` (lines 122–123).
- **From #191**: the label templates themselves (thermal 50 × 30 mm, 40 × 25 mm optional, A4 sheet), the quiet-zone
  and resolution validation, and the renderer's own unit tests. This issue renders **through** them and adds no

- [ ] **A repeatable test-sheet command.** `dotnet run --project src/Tools/Tailor360.Cli -- label-sheet --template
      <name> --out <dir> [--payloads <file>]` following the `System.CommandLine` shape of `MigrateCommand.Create()`,
      rendering, for every template #191 ships: a sheet of valid synthetic payloads minted by
      `BarcodePayload.Mint('G')`, a sheet at each supported size and orientation, and **a sheet of the deliberately

      allocated to nothing. It touches **no database** and reads no customer data, so it runs on a laptop and in CI;
      `EnvironmentGuard` is therefore not used and the command's help text says why. One sheet carries a synthetic
      **Tamil** category cue, so that **NFR-LO-05** has something to be proved with.
- [ ] **`--payloads <file>` and determinism.** Given a fixed list of payloads the command's output is
      byte-identical run to run, which is what lets a record say "this sheet came from these payloads" and a
      reviewer reproduce it. Nothing about the output may depend on the clock or on `Guid.NewGuid()` — ARCH-014 and
      ARCH-015 are source scans over `src/` and `Tailor360.Cli` is in `src/`.
- [ ] Add the command's row to `docs/dev/commands.md`, in the one-liner table, not the verb table — it is not
      wrapped by `./scripts/dev`.
- [ ] **`docs/custody/label-tests/README.md` — the method and the index.** How a run is set up, which combinations
      must be covered (one row per template × printer × label stock), how each sheet is printed, photographed and
      scanned, the rule that **every payload on every sheet is synthetic** (CLAUDE.md section 4 item 10 and
      section 5), and an index table with one row per combination and its state: `recorded`, `pending` or

- [ ] **The record template**, `docs/custody/label-tests/TEMPLATE.md`, carrying the empty shape E07-F01-9 fills:

      **iPhone or iPad camera** (Safari, and in installed mode, per `docs/nfr/support-matrix.md` section 9) and a

## Acceptance criteria

- [ ] `dotnet run --project src/Tools/Tailor360.Cli -- label-sheet --template thermal-50x30 --out <dir>` produces the
      sheets on a machine with **no database and no compose stack running**, and with `--payloads` produces
      byte-identical output for a fixed payload set, so a reviewer can reproduce any committed sheet.
- [ ] `docs/custody/labels.md` states, for every field a label can carry, whether it appears and why, with each
      prohibition citing `docs/nfr/data-classification.md` section 9 or an `INV-BID-…` identifier — and a reader can
      tell from it alone whether a proposed addition to the template is allowed.
- [ ] `docs/architecture/identifiers.md` links to it, so #190's forward reference resolves and `./scripts/dev docs`
      passes with no broken relative link in either direction.
- [ ] The invalid-payload sheet carries **all five** cases of `docs/nfr/a11y-checklist.md` section 3.7, and a unit
      test asserts each one through `BarcodePayload.TryParse` — a bad check character fails parsing, each wrong
      namespace parses and classifies as the wrong namespace, the malformed string fails, each confusable
      substitution decodes to the payload it is a confusable of, and the unallocated payload is well-formed. Asserted
      in code, never by eye.
- [ ] **Negative:** no sheet and no committed artefact contains a real customer name, telephone number or
      measurement, and no label on any sheet carries a name, a price or a contact detail. A reviewer checks this by
      reading the sheets, which is why they are committed rather than described.
- [ ] **Negative:** the command refuses an unknown `--template` with a message naming the templates it has, and
      refuses to write outside `--out`; it never touches a database, and a unit test proves it resolves without a
      connection string.
- [ ] **Exception:** a template #191 ships that this command cannot render — because its geometry needs an option
      the command does not pass — is named in the README index as `deferred — <reason>` rather than silently absent.
- [ ] The README index exists with one row per intended combination, every row `pending`, and says in terms that a
      `pending` row is not evidence of anything.

## Permissions and roles

No permission is added, changed or granted, and no endpoint is published. The command runs as an operator on a
machine, not as a session, and resolves no `ICurrentUser`. The printing the policy describes happens through
`custody.print_label` (matrix line 174) and `print.station` (proposed in E07-F01-5b); neither is touched here.
**OD-13 is open**, and this issue asserts no grant.

## Modules, contracts and events

One new command in `src/Tools/Tailor360.Cli`, two registration lines in `CliHost`, and documentation. No module
boundary is crossed: the command resolves the renderers and #191's templates through each module's own registration
extension, which is what ARCH-006 asks of a host, and reads no table of any module. No schema, no endpoint, no
integration event, no contract. ARCH-020 is satisfied by construction — the command-line host is one of the two
permitted to reach `IWorkerScopeFactory`, and this command needs no scope at all because it touches no database.
ARCH-014 and ARCH-015 apply to this code like any other in `src/`.

**DOR-05:** the abuse case this evidence speaks to is **label forgery** in the `barcode-custody` threat model — the
#56a backlog row in `docs/security/README.md` line 74, not yet written, scheduled W2. The interim control this issue
contributes is the invalid-payload sheet: a label the product must refuse can be produced deliberately, repeatably
and without a database, so the refusal can be field-tested rather than assumed.
