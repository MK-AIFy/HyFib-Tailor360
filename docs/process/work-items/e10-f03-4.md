Sub-issue of #46. Fourth of thirteen, and the configuration this issue's profitability figures are computed from:
`reporting.costing_assumption_versions` — the labour rate per category or service, the overhead percentage, the
allocation basis and the effective dates, as a draft → published → retired version chain the Owner edits without a
deployment. It is split out ahead of the profitability projection because the plan's seam order puts "schema,
migration and masters" first, and because a version chain with immutability invariants is a session on its own:
`src/Modules/Reporting` holds no entity of any kind today (twelve files, all scaffolding) and `grep -rn "costing"
src/` returns nothing.

## Scope

- [ ] **`reporting.costing_assumption_versions`** — version number, status (`draft`, `published`, `retired`),
      effective-from and effective-to dates, allocation basis (an enumerated code), the overhead percentage, and the
      per-category / per-service / per-phase labour rates as rows of an owned child table (`costing_assumption_rates`:
      category key, service-type key or phase code, rate, unit). Plus actor, reason and the created/updated pairs
      `src/Modules/CLAUDE.md` section 5 asks of an editable row.
- [ ] **Domain invariants**, unit-tested, and each given an `INV-` identifier in the pull request: a published version
      is immutable (enforced by an append-only/immutability trigger in the migration, in the shape of
      `billing.financial_records_are_append_only()`); effective windows of published versions never overlap; a draft
      cannot be published with no rate and no overhead percentage; retiring a version never deletes it; a figure
      already computed against a version keeps naming that version for ever.
- [ ] **Five routes**, in the existing `/api/v1/reporting` group: `GET /costing-assumptions` (list with status and
      window — `reports.read`, `RateLimitPolicyNames.DefaultUser`, `RequestTimeoutPolicies.Read`), `GET
      /costing-assumptions/{versionId}` (one version with its rates, setting the entity tag an edit is made against),
      `POST /costing-assumptions` (create a draft — `.RequireIdempotency()`,
      `.Audited("reporting.costing_assumption.drafted")`, `RateLimitPolicyNames.Write`), `PUT
      /costing-assumptions/{versionId}` (edit a draft — `.RequireIfMatch()`,
      `.Audited("reporting.costing_assumption.edited")`), `POST /costing-assumptions/{versionId}/publish` (publish
      with a mandatory reason — `.RequireIdempotency()`, `.Audited("reporting.costing_assumption.published")`,
      `RateLimitPolicyNames.Write`, `RequestTimeoutPolicies.Command`). **Exactly five routes: there is no `/retire`
      route.** Retirement is what publishing a superseding version does to its predecessor, which is how
      `PriceListVersion` and `TaxConfigurationVersion` already behave; adding a separate retire route would let a shop
      have **no** version in force on purpose, and that is a product decision nobody has asked for. If a reviewer
      wants one it is a follow-up issue, not a sixth route bolted on here.
- [ ] **ARCH-023 needs nothing here, and this is verified rather than argued.** The rule applies only to a
      **branch-scoped** permissioned endpoint with a route parameter: `EndpointAuthorisationInspector` (the type
      behind `tests/Tailor360.ContractTests/EndpointResourceScopeTests.cs`) exempts a declaration where
      `permission.Scope == BranchScope.Organisation` or `route.RoutePattern.Parameters.Count == 0`, and its own
      comment says "organisation-scoped routes are outside the rule: their reach is decided by a permission rather
      than by a row". `PriceListEndpoints.cs` ships `{priceListId:guid}` and `{versionId:guid}` under
      `BranchScope.Organisation` with no resource scope and is green. So: **declare no `ScopedToResource` and no
      `TouchesNoBranchOwnedResource`**, leave the matrix row's `resource` column as `—`, and do not coin a
      `ReportingResourceKinds` entry. Assumptions are organisation-wide, full stop — a per-branch assumption would be
      a different product decision and is not proposed here.
- [ ] **A new permission key** `reports.manage_costing_assumptions`, added to `ReportingPermissions.All` as
      `new(ManageCostingAssumptions, "…", PermissionModules.Reporting, PermissionScope.Organisation, RequiresReason:
      true)`. Note the type: the catalogue entry takes **`PermissionScope.Organisation`** (from
      `src/Platform/Tailor360.Platform.Security/Permissions/Permission.cs`), while the **endpoint** declares
      **`BranchScope.Organisation`** (from `Platform.Abstractions.Multitenancy`) — two different enumerations, and
      mixing them will not compile. `RequiresMfa` and `RequiresStepUp` are both **false**: that is the decided default
      and the reason is in **Permissions and roles** below. Then the section 4 row in
      `docs/security/permission-matrix.md`, the five section 5 endpoint rows, the `SystemRoles.cs` grant to `owner`
      (whose reach is `organisation`, matrix line 102 — an organisation-scoped key may only be granted to an
      organisation-reach role, and the matrix test says so), and the per-caller answers in
      `tests/Tailor360.IntegrationTests/Authorization/`. **No `identifier-editing` entry is owed**: that block is for
      routes whose identifier a caller could edit to reach another branch's row, and an assumption version belongs to
      no branch — matrix.yaml's own header says to add an entry only "if the route takes an identifier a caller could
      type instead of follow" and answer differently for.
- [ ] **A new open-decision row, `docs/prd/assumptions-and-open-decisions.md` — take OD-26** for the labour rate,
      overhead percentage and allocation basis. OD-24 is the highest identifier in the register today (verified), and
      `e10-f03-2` takes **OD-25** for the stock-aging buckets; if that sibling has not merged, **OD-26 is still
      yours** so the two numbers cannot collide, and the sibling renumbers if it merges second. Written in the
      register's own format, with the default in force stated as below. **No rate, percentage or basis value is
      committed, seeded or written into a migration.**
- [ ] **One expand-only migration**, `CostingAssumptionVersions`, with the immutability trigger as hand-written
      `migrationBuilder.Sql(...)` carrying a comment saying why, per `docs/dev/migrations.md`; plus its ledger row.
- [ ] Regenerate `docs/api/openapi.v1.json` and `clients/pwa/src/api/schema.d.ts`.

## Acceptance criteria

- [ ] An Owner creates a draft, adds a labour rate for one category and an overhead percentage, publishes it with a
      reason, and reads it back — all over HTTP, with no direct database access.
- [ ] Every route declares exactly one permission and one rate-limit policy, every state-changing route carries
      `.Audited(...)` (ARCH-008), the three parameterised routes satisfy ARCH-023 explicitly, and each has exactly one
      row in permission-matrix section 5.
- [ ] **Negative:** an edit to a **published** version is refused by the endpoint and, independently, by the database
      trigger — the test asserts both, because the trigger is what protects a figure already computed.
- [ ] **Negative:** a `PUT` with a stale `If-Match` is refused `412` with the current entity tag
      (`ConcurrencyEndpoints.VersionConflict`), and a `PUT` with no `If-Match` at all is refused `428`
      (`PreconditionMissing`); neither writes anything.
- [ ] **Negative:** publishing a version whose effective window overlaps an already-published version is refused
      naming the conflicting version; publishing a draft with no rate and no overhead percentage is refused naming the
      missing field.
- [ ] **Negative:** a caller holding `reports.read` but not `reports.manage_costing_assumptions` is refused `403
      security.forbidden` on all three write routes.
- [ ] **Exception:** retiring or superseding a version leaves it readable for ever and leaves every figure that names
      it answering identically; a replayed `Idempotency-Key` on publish returns the first outcome rather than
      publishing twice.
