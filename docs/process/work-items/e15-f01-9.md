Sub-issue of #59. One of #59's obligations is recorded not in the parent's body but in the waiver register, and it is
the only application-code gap the parent still owes. `docs/process/waivers.md` section 4.2, in the table of "Known gaps
that will need a row here at the first release", carries this row: "The ASP.NET Core Data Protection key ring is
persisted to `platform.data_protection_keys` **unencrypted** — nothing calls `ProtectKeysWith…`, because no
key-encryption certificate is provisioned. The ring wraps every stored TOTP shared secret", recorded as **RR-04** in
`docs/security/threat-models/authentication.md`, accepted by the technical reviewer on 2026-09-05, with the corrective
issue named as "**#59** (environments, secrets and certificate provisioning)" and the gate it would be waived against
as "**RG-10** (secrets and key management) at the first release that has one". No other child of #59 touches it. This
slice closes it.

Two facts about the current state, because the repository's own documents disagree about them and an earlier draft of
**E15-F01-7** repeated the wrong one:

- the ring **is** already persisted in the database. `src/Hosts/Tailor360.Web/Program.cs` line 82 calls
  `AddTailor360DataProtection`, which calls `PersistKeysToDbContext<PlatformDbContext>()`, and migration
  `20260905162158_DataProtectionKeyRing` created `platform.data_protection_keys`.
- `docs/dev/staging.md` section 12 item 4 says the opposite — "nothing binds it yet", "each container holds an
  ephemeral ring". That is **stale** and is corrected here, in the same pull request, because leaving it is what made
  two children of #59 push this work at #23.

What is genuinely missing is the **key-encryption key**: `grep -rn "ProtectKeysWith" --include=*.cs src/` returns
nothing, so anybody who can read `platform.data_protection_keys` can decrypt every enrolled TOTP secret, which is
exactly what threat `AS-05` in the authentication threat model says.

## What is already built (do not re-build)

- `src/Platform/Tailor360.Platform.Persistence/DataProtection/DataProtectionServiceCollectionExtensions.cs` —
  `AddTailor360DataProtection(IServiceCollection, IConfiguration)`: binds and validates the options, calls
  `AddDataProtection()`, `SetApplicationName`, `SetDefaultKeyLifetime` and `PersistKeysToDbContext<PlatformDbContext>`,
  and registers the `data-protection` startup health check. **The builder chain this issue extends is here and nowhere
  else.** Adding the call in a host's `Program.cs` instead would split the configuration across two places.
- `src/Platform/Tailor360.Platform.Persistence/DataProtection/DataProtectionOptions.cs` — section
  `Security:DataProtection`, `ApplicationName` (required, 3-100) and `KeyLifetime` (7-365 days, default 90), with a
  remark explaining why the ring's **location** is deliberately not configurable. The new setting is about the
  key-encryption key, not the location, and the remark stays true.
- `src/Platform/Tailor360.Platform.Persistence/DataProtection/DataProtectionKeyRingHealthCheck.cs` — the startup check
  that refuses to serve when the ring cannot be read. **It is the right place for the new failure to surface**: a ring
  that cannot be unwrapped is a ring that cannot be read.
- `docs/nfr/data-classification.md` section 6.2 already carries the register row and its design: "Ring in
  `platform.data_protection_keys`; the key-encryption key supplied as a secret **from a certificate or key-management
  service**", "Startup fails if the ring is on the local file system outside development", ring rotation "every **90
  days**", and the compromise procedure. **The design is decided. Implement the row; do not redesign it, and do not
  add a second row.**
- `docs/platform/secrets.md` section "Data Protection key ring" — the same rule in prose: "The ring itself is
  encrypted with a certificate or a key-management service, so a database backup does not carry usable keys." Cite it.
- `infra/compose/docker-compose.staging.yml` lines 464-478 — the `secrets:` block. Every entry is a `file:` under
  `${TAILOR360_STAGING_SECRETS_DIR}` whose **file name is the configuration key** with `__` as the section separator
  (`Database__ConnectionString`, `ObjectStorage__AccessKey`). The new secret follows that convention exactly, and the
  web service's `secrets:` list gains it.
- `infra/compose/.env.example` and `infra/compose/docker-compose.yml` — the development stack, which must keep working
  with **no** certificate, because CLAUDE.md section 4 rule 6 forbids a committed secret value and a development
  machine has no key store.
- `tests/Tailor360.IntegrationTests/Platform/PlatformServiceTests.cs` and `PlatformDatabaseFixture.cs` — where a
  platform service's composed behaviour is already asserted against a real database. Extend; do not add a fixture.

## What is missing

- Any call to `ProtectKeysWith…`. `grep -rn "ProtectKeysWith" --include=*.cs src/` returns nothing.
- Any configuration for it. `DataProtectionOptions` has two properties and neither names a key-encryption key.
- Any secret file for it. The staging `secrets:` block has six entries and none is a certificate.
- Any refusal. A deployment with no certificate starts silently and stores the ring in clear, which is the state the
  waiver row describes.

## Acceptance criteria

- [ ] With the certificate configured, the web host starts, `/health/startup` reports the `data-protection` check
      healthy, and a newly created key row in `platform.data_protection_keys` is **encrypted** — asserted by reading
      the stored XML and showing it carries an encrypted-key element rather than a plaintext key, not by trusting the
      configuration.
- [ ] An anti-forgery token issued before a restart is still accepted after it, with the same certificate — the
      property the ring exists for, and the one a wrong `ProtectKeysWith…` call silently breaks.
- [ ] A TOTP secret enrolled before the change is still readable after it, because old unencrypted keys stay in the
      ring and keep decrypting what they protected. **This is the upgrade path and it must be tested**: a ring that
      starts encrypting new keys must not orphan the old ones.
- [ ] **Negative:** a Staging or Production host with no certificate configured **fails to start**, with a message
      naming the configuration key and the expected file path and nothing else. It does not start with an unencrypted
      ring and it does not log the file's contents.
- [ ] **Negative:** a configured path that does not exist, or a file that is not a usable certificate, fails at start
      with a message that distinguishes the two. "Missing" and "unreadable" are different operator actions.
- [ ] **Negative:** a second host with a **different** certificate cannot read the first's keys — demonstrated, because
      it is the failure an operator will cause by regenerating rather than escrowing, and the message must make that
      diagnosable.
- [ ] **Exception:** Development and every test tier start with **no** certificate and an unencrypted ring, and nothing
      warns in a way that trains people to ignore warnings. The environment rule is asserted, not assumed.
- [ ] `./scripts/dev docs` passes over the five changed documents, and `dotnet format --verify-no-changes` is clean.

## Migration and rollback

No table and no column. `platform.data_protection_keys` already exists
(`20260905162158_DataProtectionKeyRing`) and its shape does not change — the **contents** of the XML column change for
newly written rows, which is not a schema change and needs no migration. What proves it: `dotnet ef migrations
has-pending-model-changes` reports none and `migrate --dry-run` reports "The database is up to date with this build.",
both already steps of the `Database migrations` job of `.github/workflows/ci.yml`.

Rollback of this pull request is `git revert` **plus one operational caveat a reviewer must see**: reverting removes
the ability to decrypt the keys written while it was in force, so any host that ran with the certificate must keep it
available, and the pull request says that in the rollback note rather than implying a clean revert. Rows written before
the change stay readable either way.
