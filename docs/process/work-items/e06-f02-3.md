Sub-issue of #33. E06-F02-2 lets an Owner draft and edit a workflow version and deliberately cannot make one live.
This slice closes that: the validation report, publish, retire, the Orders-side `ICatalogDependencyValidator` that
stops a catalogue version being published against a workflow definition with nothing published, and the default
workflow drafted by `init-reference-data`. None of it exists.
`src/Tools/Tailor360.Cli/Commands/InitReferenceDataCommand.cs` seeds Identity roles, consent purposes, the
catalogue, the design catalogue, measurement templates and Billing reference data, and names no workflow; and
`grep -rn "ICatalogDependencyValidator" src/Modules/Orders` returns nothing.

## What is already built (do not re-build)

- `src/Modules/Catalog/Tailor360.Modules.Catalog.Contracts/Catalogue/ICatalogDependencyValidator.cs` — the
  registration point, with `ValidatePublicationAsync` and `ValidateRetirementAsync` both defaulting to "found
  nothing", and `CatalogFinding.Error/Warning(code, message, target)`. Its own doc comment says a module implements
  only the direction it cares about. **Read the whole remark before writing the class:** it currently says "A
  module that only holds work in progress, such as Orders, implements only `ValidateRetirementAsync`", which is
  the opposite of what this slice needs and is stale — a workflow *definition* is published configuration, not
  work in progress, and the harm named in plan Section 8 is a catalogue version published against a definition
  with nothing published. **Correct that one sentence in the same pull request** and say why in the description.
  It is an XML comment in a `Contracts` project Orders already references, so ARCH-004 is not engaged; leaving it
  wrong would make the next reader believe this validator is a boundary breach. Study the three existing
  implementations first — `MeasurementTemplateCatalogValidator` (Customers, both directions),
  `PriceListCatalogValidator` (Billing) and `DesignRuleValidator` (Catalog's own).
- `src/Modules/Catalog/Tailor360.Modules.Catalog.Contracts/Catalogue/CatalogPublicationCandidate.cs` — already
  carries `CatalogServiceTypeView.WorkflowDefinitionId` (line 113, commented "Link 2 — a workflow definition
  (#33)") and `AllowIncomplete`. **No change to the Catalog module is needed**: the candidate already hands Orders
  every workflow reference it must check.
- `src/Tools/Tailor360.Cli/Commands/InitReferenceDataCommand.cs` — the `I…ReferenceDataSeeder` pattern, each seeder

## Scope

- [ ] `Api/Workflows/WorkflowLifecycleEndpoints.cs` with exactly three routes on the E06-F02-2 group:
      `GET /api/v1/orders/workflow-definitions/{definitionId}/versions/{versionId}/validation` —
      `catalog.workflows.edit`, `DefaultUser`, no audit (a read that is not sensitive);
      `POST .../versions/{versionId}/publish` — `catalog.workflows.publish`, `.RequireStepUp()` (ARCH-018, because
      the permission is catalogued as requiring step-up), a mandatory reason, `If-Match`, `Write`, audited
      `orders.workflow_version_published`;
      `POST .../versions/{versionId}/retire` — `catalog.workflows.publish`, `.RequireStepUp()`, mandatory reason,
      `If-Match`, `Write`, audited `orders.workflow_version_retired`.
- [ ] Publish refuses while the graph report holds any `Error` finding, and the refusal body is the same report the
      `GET …/validation` route returns, so the editor never has to ask twice.
- [ ] Publish is atomic with retiring the outgoing published version of the same definition, under the partial
      unique index E06-F02-1 created — one transaction, so a definition is never momentarily without a published
      version and never briefly has two.
- [ ] **The retire rule, stated precisely.** Plan Section 8 (#33) says retirement is "refused while a published
      catalog version maps a category to the definition unless a successor is published". Orders cannot see the
      catalogue's tables (MO-2) and Catalog publishes no "is this definition referenced" query, so this slice
      implements the stronger, locally decidable half: **retiring the published version of a definition is refused
      unless a successor version of that definition is already published.** Combined with the validator below, a
      category can never map to a definition with nothing published, which is the harm the plan names. Record this
      reading in the pull request; do not add a method to `Catalog.Contracts` to reach the weaker rule.
- [ ] `Infrastructure/Workflows/WorkflowCatalogDependencyValidator.cs` implementing
      `ICatalogDependencyValidator.ValidatePublicationAsync`: for every `CatalogServiceTypeView` with a non-null
      `WorkflowDefinitionId`, an `Error` finding `orders.workflow-definition-not-published` targeted at
      `serviceTypes[<code>].workflowDefinitionId` when no published version resolves, and a `Warning` when
      `AllowIncomplete` is set and the link is null. Registered with `AddScoped` in
      `OrdersModuleServiceCollectionExtensions.cs` so it joins the list rather than replacing another module's —
      the same reason `ITimelineSource` is registered that way, which that file already explains.
- [ ] `Application/Workflows/SeededWorkflow.cs` and `IWorkflowReferenceDataSeeder` +
      `Infrastructure/Workflows/WorkflowReferenceDataSeeder.cs`, wired into `InitReferenceDataCommand`: one
      definition, `WF_STITCH_STANDARD`, one **draft** version whose phases are exactly **six** — Cutting,
      Specialist work (optional), Stitching, Finishing, QC and Ready for delivery, in that order — from
      `docs/prd/workflows/blouse.md` section 2.1, with `required_role_keys` taken from the document's Actor column
      (`tailor` for Cutting, Stitching, Finishing; `tailor_master` for QC) and no duration or SLA value, because the
      document fixes none. Idempotent: a second run reports "already exists; nothing was changed".
- [ ] **A deliberate divergence from the plan, to be flagged in the pull request.** Plan Section 8 says the default
      workflow is "published by `init-reference-data`". It is seeded as a **draft** instead, because publishing
      demands `catalog.workflows.publish` with MFA, step-up and a stated reason (`permission-matrix.md` line 165) and
      a command-line tool has none of those — exactly the reasoning `InitReferenceDataCommand` already prints for
      the catalogue. The command prints the same sentence for the workflow, naming what the shop cannot do until an
      Owner publishes it.
- [ ] Three rows in the `<!-- matrix:endpoints -->` block of `docs/security/permission-matrix.md`, and the
      `step-up` dimension in `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml` if the two publish routes
      need one that is not already defined. Regenerate `docs/api/openapi.v1.json` and
      `clients/pwa/src/api/schema.d.ts`.

**A third deliberate divergence from the plan, to be flagged in the pull request.** Plan Section 8 lists the
seeded default as seven phases by prefixing **Intake**. A job phase is instantiated at start-production, which
happens after confirmation, so an Intake phase would be created already complete and could never be worked —
and `docs/prd/workflows/blouse.md` section 2.1 attributes "Intake and measurement" to Customers/Measurements,
not to Orders/Workflow. The seed therefore carries the **six** Orders/Workflow phases, and the pull request
says so in one line so a reviewer comparing against the plan finds the reason rather than a contradiction.

## Out of scope

Cloning a draft and editing a graph (E06-F02-2). Pinning a version onto a job (E06-F02-4). Any reverse dependency
check that would need a new `Catalog.Contracts` method — explicitly not built, and the reason is recorded above.
Retiring a whole definition rather than a version. Publishing the seeded workflow: an Owner does that through the
screen in E06-F02-12, and this issue must not do it for them.

## Acceptance criteria

- [ ] An Owner with a second factor publishes a valid draft over HTTP; the previous published version of the same
      definition is retired in the same transaction; `FindPublishedVersionAsync` then resolves the new one.
- [ ] **Negative:** publishing a draft whose graph has an unreachable phase is refused, the body is the validation
      report with that phase code, and no row changed status — asserted by re-reading both versions.
- [ ] **Negative:** a caller holding `catalog.workflows.edit` but not `catalog.workflows.publish` is refused `403`
      with `security.forbidden`; a caller who holds the publishing key but has not re-authenticated recently is
      refused with the step-up answer `matrix.yaml` defines, and the refusal is audited (NFR-AU-04).
- [ ] **Negative:** retiring the only published version of a definition is refused with a named conflict, and the
      version stays published.
- [ ] **Exception:** a retired version stays readable and stays resolvable by identity for ever, because a garment
      job may be pinned to it (INV-JOB-02); only `FindPublishedVersionAsync` stops returning it.
- [ ] Catalog publication is refused with `orders.workflow-definition-not-published` when a service type references
      a definition with no published version, and the finding names `serviceTypes[<code>].workflowDefinitionId` —
      demonstrated through Catalog's own publish route, not by calling the validator directly.
- [ ] `dotnet run --project src/Tools/Tailor360.Cli -- init-reference-data` run twice prints the workflow summary
      both times and creates exactly one definition and one draft version.
