Sub-issue of #33. `GarmentJob.StartProduction` and `Order.StartProduction` are fully written and unit-tested
(`src/Modules/Orders/Tailor360.Modules.Orders.Domain/Jobs/GarmentJob.cs:501`,
`.../Orders/Order.cs:689` — it even sorts the `finish_before` prerequisites so a refusal names the same one every
time), and `Orders.Contracts.Events.GarmentJobEnteredProduction` exists with its wire name
`orders.job-entered-production.v1`. Nothing calls any of it: the Application project holds only port interfaces, no
route exists, and there is no `job_phases` table — which is the other half of what start-production is supposed to
create. #201 records this explicitly in its own Out of scope: "production start and workflow-version pinning … issue
#33". This slice is that one transition and the phase rows it creates.

## Acceptance criteria

- [ ] A Tailor Master starts production on a confirmed garment job over HTTP; the response shows the pinned workflow
      version and the ordered phase list; `GET .../phases` returns the same rows; `garment_jobs.workflow_version_id`
      is set and the job's status is `InProduction` — all through the API, with no direct database access.
- [ ] The `GarmentJobEnteredProduction` outbox row exists in `orders.outbox_messages` in the same transaction as the
      phase rows: a forced failure after the pin and before the phase insert leaves **no** pin, no phases and no
      outbox row.
- [ ] Every route this issue adds declares a permission, exactly one rate-limit policy, a resource scope for its
      `{jobId}` parameter and the audit filter on the write (ARCH-007, ARCH-008, ARCH-017, ARCH-023), with a matching
      row in section 5 of `docs/security/permission-matrix.md`.
- [ ] **Negative:** a Tailor Master in another branch receives `404`, not `403` — the answer `matrix.yaml` defines
      for a foreign identifier, so editing the `{jobId}` in the URL reveals nothing. A caller without
      `orders.start_production` receives `403` `security.forbidden`, and the denial is audited.
- [ ] **Negative:** starting production twice, with two different `Idempotency-Key` values, is refused the second
      time with `OrdersErrors.WorkflowVersionAlreadyPinned` and **one** set of phase rows exists. With the *same*
      key, the first outcome is replayed and still one set exists.
- [ ] **Negative:** starting production on a job whose `finish_before` prerequisite is unfinished is refused and
      names the prerequisite's job number; no phases are created.
- [ ] **Exception:** when the job's workflow definition has no published version, the refusal is a named problem
      detail saying so — not a `500`, and not a silently skipped pin. The job stays `Confirmed` and can be started
      after an Owner publishes a version.
