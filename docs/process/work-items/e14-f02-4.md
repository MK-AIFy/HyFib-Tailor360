Sub-issue of #57. **A hold is the one control that stops an erasure, and nothing in this repository can place one.**
`grep -rn "retention_holds\|RetentionRun" src/` returns nothing. `docs/nfr/data-classification.md` section 7 item 4
states the requirement in one line — "the retention job is idempotent, audited and honours holds. Every skipped record
appears in an exception report; a silent skip is a defect" — and the flowchart above it makes the hold the **first**
branch, before the statutory-retention branch and before anything is deleted. This child builds the two tables the
hold and the exception report live in, the port that answers "is this pair held", and the four administration routes
over them. **It runs nothing.** The worker that sweeps and executes is the next child (`[E14-F02-4b]`), which is split
out because this child is already a full table-plus-endpoints slice by the repository's own calibration and because a
hold register that cannot be read is useless whether or not the sweep exists.

## What is missing

- No hold of any kind, anywhere. Nothing can stop a sweep from deleting a record that is under legal or business
  hold, which is the single most consequential gap in the privacy lifecycle.
- No place for an exception report to live, so a skipped record is invisible — which
  `docs/nfr/data-classification.md` section 7 item 4 calls a **defect** rather than a limitation.
- No way to ask "is this `(subject, data class)` pair held", which the executor needs before it offers anything to a
  participant.

## Acceptance criteria

- [ ] An Owner places a legal hold on a customer subject over HTTP with a reason; `GET /api/v1/admin/privacy/holds`
      lists it as open with its kind, reason, actor and instant; releasing it with a reason and the current `If-Match`
      shows it as released with both reasons and both actors still readable. No direct database access in the test.
- [ ] `IRetentionHolds` answers **true** for a pair whose class is held, **true** for every class of a subject whose
      hold has a null `data_class`, **false** for a different subject, **false** for a different organisation, and
      **false** once the hold is released — five unit assertions, which is the whole of the rule the next child
      depends on.
- [ ] Every route declares a permission (ARCH-007), exactly one rate-limit policy (ARCH-017), and each `POST`
      carries `.Audited(...)` with a mandatory reason (ARCH-008). **No route declares `.RequireStepUp()`**, because
      `admin.privacy.hold` is catalogued `RequiresStepUp: false` and `AuthorisationMatrix.cs` line 197 checks
      ARCH-018 both ways. Each route declares `.TouchesNoBranchOwnedResource(NoBranchResource, Review)` as
      `FeatureFlagAdminEndpoints` does — **not because ARCH-023 compels it**, since that rule's allowed-exceptions row
      (`docs/architecture/architecture-rules.md` line 346) puts organisation-scoped routes outside it, but so that the
      matrix's `Resource` cell reads `—`.
- [ ] **Negative**: a caller holding `admin.privacy.read` but not `admin.privacy.hold` is refused both `POST`s with
      the `403` answer `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml` already defines for a missing
      permission — not a bespoke message.
- [ ] **Negative**: a `holdId` belonging to another organisation answers **exactly** as an unknown one does, asserted
      through the `identifier-editing` block the way `IdentifierEditingTests.cs` already asserts it for other routes.
- [ ] **Negative**: placing a hold with no reason is refused `422` with a field error on `reason`; a reason longer
      than `AdminRequests.MaximumReasonLength` is refused the same way, with the key named and the value absent.
- [ ] **Negative**: releasing an already-released hold is refused with a named code and changes neither
      `released_at` nor `release_reason`; releasing with a stale `If-Match` returns `409` carrying the current
      version, per `ConcurrencyResults.VersionConflict`.
- [ ] **Negative**: a replayed `Idempotency-Key` on either `POST` returns the first outcome and writes no second row
      and no second audit entry; the same key with a different body is refused `422 idempotency.key-reused`.
- [ ] **Exception**: the check constraint refuses a half-populated release — `released_at` without `released_by`, and
      `release_reason` without `released_at` — proved against the live database.
- [ ] **Exception**: `platform.retention_runs` refuses an `UPDATE` once `finished_at` is set and refuses `DELETE`
      outright, proved against the live database. A row inserted with `finished_at` null may still be completed once,
      which is the single update the next child's job performs.
- [ ] `GET /api/v1/admin/privacy/runs` on an empty table answers an empty page rather than a 404, and its payload
      shape is the one the next child writes into — fixed here so that child adds no endpoint.

## Modules, contracts and events

Platform owns both tables and all four ports; the endpoints live in `Identity.Api` by the precedent of
`AuditAdminEndpoints.cs` and `FeatureFlagAdminEndpoints.cs`. **No module is referenced, and no module's schema is
read or written.** ARCH-005 holds with no exception: both tables are in `platform` and are mapped only by
`PlatformDbContext`. No integration event is published — a hold is configuration read on demand, and an event would
be a second copy of it that can disagree.

Threat-model coverage: the abuse case is "a hold used to keep data for ever". The controls are the hold's mandatory
reason, its visibility in the register and in **every** run of the exception report, and the access-review cadence of
`docs/nfr/security-operations-targets.md` section 5. **#192 builds its own `media_retention_holds` table for media
objects, and that is not a duplicate of this one** — a media object is not a data subject, the two hold different
things at different granularity, and the relationship is stated in `module-ownership.md` by this pull request: the
privacy lifecycle's hold check never reads `media_retention_holds`, and a media object held by #192's table is
reported to the platform run by Media's own participant as a skip with reason `hold`.
