## Acceptance criteria

- [ ] The job takes its lease, runs one bounded pass, releases the lease, and a second instance started in the same
      window takes no lease and does no work — asserted over at least two passes.
- [ ] With a projection and its source in agreement, a scheduled run records a zero delta and **publishes nothing**.
- [ ] **Negative — a seeded mismatch:** the next scheduled run publishes **exactly one**
      `reporting.report-reconciliation-mismatch.v1` for that report, cut-off and condition, and the projection is not
      corrected.
- [ ] **Negative — a stale projection:** holding the dispatcher so the checkpoint falls behind the configured
      threshold raises **exactly one** `reporting.report-freshness-breached.v1`; running the pass again while it is
      still breached raises none; the condition clearing is recorded in the run history.
- [ ] **Negative — no threshold configured:** with `Reporting:Reconciliation:LagThresholdSeconds` unset the job uses
      the S9 row as its documented default and says so in the alert; it does not silently disable the check.
- [ ] **Exception — a cut-off in the middle of the day:** the scheduled pass evaluates the cut-off in each branch's
      own timezone, so two branches in different zones are reconciled against different instants for the same
      business date.
- [ ] **Rule-level:** the job declares `[WorkerJob]` with its name and branch scope (ARCH-021), takes its scope
      through `IWorkerScopeFactory` (ARCH-020), does **not** declare `ActsForRequester`, and no project except the
      worker and command-line hosts references `IWorkerScopeFactory`. The architecture tier proves all of it.
- [ ] If this slice is the first to publish either event, `IntegrationEventTests` passes with the two schemas and
      examples under `docs/integration/events/` and the rows in `IntegrationEventInventory.cs`; if #184 published them
      first, the test output shows **no new event** and the pull request names the commit that introduced them.
