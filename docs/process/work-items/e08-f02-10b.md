Sub-issue of #39. The second half of the plan's last Lane B screen for #39 — the **purchase receipt** entry form, with
its lines, their per-line conversion, the conditional lot reference and the single all-or-nothing posting
(`docs/IMPLEMENTATION_PLAN.md` Section 9, `### #39`). It is its own child rather than a third screen on `E08-F02-10`
because a multi-line entry form with a per-line unit conversion is a session's work on its own:
`clients/pwa/src/routes/catalog/CatalogVersionEditorRoute.tsx` is **994 lines** by `wc -l` for one comparable editor,
and the parallel batch estimates two comparable screens (`E08-F01-6`, the item list and editor) at 1,350 lines. It is
also the only screen in #39 whose single request must be all or nothing, which is its own reviewable claim.

## Scope

- [ ] **`clients/pwa/src/routes/inventory/PurchaseReceiptRoute.tsx`** at `/inventory/purchase-receipts/new` — the
      header (supplier, receiving location, the supplier's own document reference, the received date) and the lines:
      item, received quantity with its unit and **the conversion sentence**, unit cost, and a lot reference field that
      appears **only** for an item whose tracking method is lot/batch and is required there. Optionally started from a
      placed purchase order, which pre-fills the lines with the outstanding quantities.
- [ ] **One posting, one key** — the whole receipt is **one** request with one `Idempotency-Key`, minted when the
      person commits and unchanged across a retry, matching the server's all-or-nothing posting. There is **no
      per-line save and no partial submit**, because a half-posted receipt is precisely what `E08-F02-5` exists to
      prevent. A test asserts there is exactly one request for a three-line receipt.
- [ ] **`clients/pwa/src/routes/inventory/PurchaseReceiptDetailRoute.tsx`** at
      `/inventory/purchase-receipts/:purchaseReceiptId` — the posted receipt read back: header, lines with quantities,
      units, lot references and the ledger entry identifier each line posted. **No cost column**, because the API
      sends none; render no placeholder for it either.
- [ ] **Refusals against the line or field they concern** — `inventory.receipt-exceeds-order` names the offending line
      rather than the whole receipt; `inventory.lot-reference-required` and `inventory.lot-reference-not-applicable`
      render against the line's lot field (the second is reachable only from a stale form, since the field is
      conditional, and must still render rather than appearing as a broken button);
      `inventory.supplier-not-selectable` renders against the supplier field and keeps the input. Through
      `plainLanguageDetail`; no second problem-rendering path.
- [ ] **Online-only** — `OfflineBlockedAction` on the single submit: blocked with words, never queued

- [ ] **Messages** added to `clients/pwa/src/i18n/messages/inventory.ts` in both `inventoryEn` and `inventoryTa`,

## Acceptance criteria

- [ ] An Inventory Clerk holding `inventory.record_movement` starts a receipt from a placed purchase order, sees the
      outstanding quantities pre-filled and each line's conversion **in words**, posts it as **one** request, and sees
      the order become `Closed`; re-opening the receipt shows each line's posted ledger entry identifier and **no cost
      column**.
- [ ] A receipt posted with **no** purchase order succeeds and the screen says no order was affected.
- [ ] **Lot discipline on screen:** the lot reference field appears only for a lot-tracked item and is required there;
      for an untracked item it is absent, so `inventory.lot-reference-not-applicable` is reachable only from a stale
      form — and a test drives exactly that case and asserts it renders as a sentence naming the line.
- [ ] **One key, one posting:** a failed submit retried from the screen carries the same `Idempotency-Key`; a success
      replaces it; a three-line receipt makes exactly one request, asserted on the transport stub.
- [ ] **Negative:** a caller without `inventory.record_movement` sees the `RequirePermission` empty state
      (`admin.forbidden.title` / `admin.forbidden.body`) on both routes and is **not** redirected; a suspended
      supplier is refused with a sentence and the form keeps the input; `inventory.receipt-exceeds-order` names the
      offending line rather than the whole receipt.
- [ ] **Offline:** the submit is refused through `OfflineBlockedAction`, posts nothing and queues nothing.
- [ ] **Accessibility:** every field has a persistent visible label; the confirmation reads supplier, location, each
      line's item, quantity-with-unit and conversion, and the line count, before committing, which is `A11Y-RJ-05`
      step 1 ("Receive a purchase, hearing supplier, item, quantity, unit and any conversion") — walk it and fill its
      row in `docs/nfr/a11y-checklist.md` section 6.8, because **this is the screen that step is about**; the error
      summary moves focus to the first invalid line; `expectNoAccessibilityViolations` passes in each state and
      `expectNoHorizontalOverflow` at all its default widths, including the line table at 320 px.
- [ ] **Localisation:** every string is in both `inventoryEn` and `inventoryTa`; the conversion sentence is the shared
      parameterised message; money renders through `formatters.formatMoney` and typed decimals parse through
      `parseDecimal`.
- [ ] `pnpm --dir clients/pwa lint`, `typecheck`, `test`, `format:check` and `build` pass, and `generate:api:check` is
      clean — the schema was regenerated by `E08-F02-5`, not here.
