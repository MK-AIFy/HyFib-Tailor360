Sub-issue of #37. The parent's third implementation step — "Integrate start/complete phase, QC,
ready-for-delivery, delivery-team receipt and dispatch scans with the production state machine" — is the one seam
between Custody and Orders, and it is deliberately the only slice that touches Orders. E07-F03-1 ships the
participant hook **with no participant registered**, so a phase scan today records custody and moves no phase.
#33's own E06-F02-5 says the same from the other side: "The scan that triggers a transition and its offline replay
(#36, #37): this slice publishes the route those will call", and E06-F02-4 records `Workflow:AutoStartOnFirstScan`
as "Not a decision — a branch setting this slice does not read. Start-production happens only through the route.
**The scan path is #37's**." This slice is that path.

## Scope

- [ ] **`Orders.Infrastructure/Production/JobPhaseScanParticipant.cs`** implementing
      `IConfirmationParticipant<Custody.Contracts.Scans.ScanRecorded>` — **check which interface actually exists
      before you write the declaration**: `rg -n "IConfirmationParticipant" src/` returns **nothing today**, and
      plan Section 6.2 note 10 assigns `Platform.Abstractions.IConfirmationParticipant<TEvent>` to **#32a**
      (delivered through #199/#201), not to this slice. If E07-F03-1 had to fall back to its own
      `Custody.Contracts/Scans/IScanParticipant.cs`, implement that instead and say so in the pull request; the
      mapping and the tests are identical either way. Orders.Infrastructure referencing
      `Custody.Contracts` is the only boundary crossing, and it is the one ARCH-004 allows. Registered in
      `OrdersModuleServiceCollectionExtensions` so Custody's T1 picks it up by composition, never by Custody
      knowing Orders exists.
- [ ] **The mapping, and nothing wider.** `ScanAction.PhaseStart` → `PhaseTransitionHandler` `start` on the phase
      the scan names; `PhasePause` → `pause`; `PhaseResume` → `resume`; `PhaseComplete` → `complete`. A **QC scan
      needs no special arm**: the seeded default workflow makes QC a phase (plan line 1563, "Intake → Cutting →
      Specialist work → Stitching → Finishing → **QC** → Ready for delivery"), so scanning into QC is `PhaseStart`
      against the QC phase code and E07-F03-1 declares no `QcIn`/`QcOut` member to map. A QC **result** is never
      recorded by a scan — #34's E06-F03-2 owns `qc_results` — and a `ReadyForDelivery` scan does not exist either,
      because section 3.2 line 238 makes Ready "the gate alone (system)". The actions that reach the participant
      and change **no** phase are `IntakeReceived`, `TransferOut`, `Receive` and `Correction` — a no-op arm with a
      test each, so a new action cannot silently acquire a phase effect.
- [ ] **Auto start-production on the first phase scan**, gated on `Workflow:AutoStartOnFirstScan` (E06-F02-4's
      branch setting, default **false** — unchanged here): when the setting is on and the job has no pinned
      workflow version, call `StartProductionHandler` first, in the same transaction, then apply the transition.
      With the setting off, a phase scan against a job not yet in production **fails the participant**, which
      rolls the scan back with `custody.job-not-in-production` — the refusal being the point: a garment cannot be
      half-started.
- [ ] **Actor and permission.** The participant runs inside the scanning caller's request, so `ICurrentUser` is
      the scanner. It demands `OrdersPermissions.PhaseTransition` (`orders.phase_transition`) through
      `ICurrentUser.HasPermission` and refuses without it, because `raci.md` rows 9-12 require both keys and a
      scan may not launder a transition the caller could not make on Orders' own route (`CLAUDE.md` section 4 rule
      1). The refusal rolls the scan back and is audited.
- [ ] **Idempotency and concurrency.** The participant takes no second lock and mints no second key: it runs
      inside T1, whose `SELECT … FOR UPDATE` on the custody row already serialises, and the phase handler's own
      job-token check still applies. A replayed scan never reaches the participant, because E07-F03-1 replays the
      stored outcome before T1 opens. A `complete` on an already-complete phase is a **refusal from the phase
      handler**, surfaced as the scan's problem details, never a silent success.
- [ ] **Close FBH-01 in the same pull request**: amend `docs/architecture/sequences/barcode-handoff.md` section
      8's FBH-01 row to decided, with the reason and the pull-request reference, per that document's own section
      10 ("Amended in the same pull request that changes a scan action"). If the reviewer instead chooses the
      asynchronous arm, this slice becomes an `IOutboxMessageHandler` for `custody.scan-recorded.v1` in the
      **same** files, with the same mapping, and the same document amendment recording the other answer — the
      precedent being `Billing.Infrastructure/Invoicing/OrderFactHandlers.cs` with its registrations at
      `BillingModuleServiceCollectionExtensions.cs:114-118`. Decide it, record it, do not leave it open.
- [ ] **No new endpoint, no migration, no payload.** The surface is unchanged: `docs/api/openapi.v1.json` and
      `clients/pwa/src/api/schema.d.ts` must come out of this slice **byte-identical**, which is itself an
      acceptance criterion.

## Acceptance criteria

- [ ] A Tailor holding `custody.scan` **and** `orders.phase_transition` submits a `PhaseComplete` scan for a job
      in production: one `scan_events` row, one `job_phases` row moved to complete, one `custody.scan-recorded.v1`
      and one `orders.job-phase-changed.v1` in the outbox — **all committed together**, so a forced failure in the
      phase handler leaves **no** scan event (the atomicity test shape
      `tests/Tailor360.IntegrationTests/Orders/OrderConfirmationRetryTests.cs` and E06-F02-4's
      `StartProductionAtomicityTests` already use).
- [ ] **Negative — missing the Orders permission.** The same scan from a caller holding only `custody.scan` is
      refused, writes **no** scan event and **no** phase row, and is audited; the refusal names the missing
      permission without leaking the job's contents.
- [ ] **Negative — not in production.** With `Workflow:AutoStartOnFirstScan = false`, a phase scan against a job
      with no pinned workflow version is refused `custody.job-not-in-production` and nothing is written. With the
      setting **on**, the same scan starts production and applies the transition in one transaction.
- [ ] **Negative — repeat.** A second `PhaseComplete` scan of a completed phase is refused by the phase handler's
      own rule and surfaced as the scan's problem details; the first completion is unchanged and no second event
      exists. A replayed `Idempotency-Key` returns the first outcome and the participant does not run twice.
- [ ] **Exception — a no-effect action.** An `IntakeReceived`, `TransferOut`, `Receive` or `Correction` scan runs
      the participant and changes **no** phase — four tests, one per action, rather than one test for the group.
- [ ] The published API is unchanged: `generate:api:check` is clean and the OpenAPI difference report is empty.
- [ ] ARCH-003, ARCH-004 and ARCH-005 hold: Orders references `Custody.Contracts` only, and writes only
      `orders.*`.
