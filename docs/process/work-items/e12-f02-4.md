## Scope

- [ ] **`clients/pwa/src/offline/queueOperations.ts`** — the single typed constant. One exported type
      `QueuedOperation` = `{ id, method: 'POST', path, permission, labelMessageId, conflictCodes }` and one exported
      `OFFLINE_OPERATIONS: Readonly<Record<string, QueuedOperation>>`, **empty at merge**, with a comment naming the
      only two permitted additions (#37's scan submissions under `custody.scan`, and the doorstep confirmation under
      `custody.confirm_delivery`, per plan Section 8 for #51 and `docs/nfr/support-matrix.md` section 7.4). A
      registration helper is **not** provided: an entry is a source edit in this file, reviewed as one.
- [ ] **`clients/pwa/src/offline/queueOperations.test.ts`** — the guard. Every entry's `method` is `POST`, its `path`
      starts with `/api/v1/custody/`, and its `permission` is one of the two constants above; anything else fails.
      The test runs over both `OFFLINE_OPERATIONS` and a fixture table, so it proves the rule rather than merely
      passing on an empty set.
- [ ] **`clients/pwa/src/offline/queue.ts`** — the store. `enqueue(operation, payload, { user, jobNumber })` writes
      `{ entryId, operationId, path, payload, idempotencyKey, clientEventUuid, binding, queuedAt, sequence, attempts,
      lastProblem }` through `deviceStore` under purpose `offline-queue`; `list()`, `count()`, `summary()`,
      `remove(entryId)`, `quarantined()`. The **idempotency key and the client event UUID are minted once, at
      enqueue**, with `crypto.randomUUID()`, and are never regenerated — that is the whole guarantee.
- [ ] **Bounds, refusing rather than evicting.** At `OFFLINE_BOUNDS.maximumEntries` — which is 200 in production and
      whatever `VITE_OFFLINE_MAX_ENTRIES` lowered it to on a test environment, so that **A11Y-OF-04** is reachable by
      hand at all (`docs/nfr/a11y-checklist.md` section 3.7 names this fixture and names its owner as "Technical
      reviewer, **with #51**") — a further `enqueue` is **refused** and the caller is told the queue is full; the
      oldest entry is never discarded
      (`docs/nfr/support-matrix.md` section 7.4: "refuses further queuing rather than discarding the oldest entry").
      An entry older than `OFFLINE_BOUNDS.maximumAgeHours` is not replayed; it moves to the visible **cannot send**
      list with the reason `too-old` and is never silently dropped.
- [ ] **`clients/pwa/src/offline/replay.ts`** — the drain. Strictly sequential in `(queuedAt, sequence)` order; each
      entry goes through `apiRequest` with its stored `idempotencyKey`; on success the entry is removed. It **pauses
      on the first `409` or `422`**, keeps the entry, stores the server's problem details and stops the drain — a
      conflict is resolved by a person, never by a retry loop. `429` is honoured through `retryAfterSeconds`, and the
      drain paces itself below the `scan-burst` ceiling of 240 requests a minute per account. A transport failure is
      not a conflict: the entry stays, `attempts` increments, the drain stops and waits for the next trigger.
- [ ] **Binding and quarantine.** Before replaying, compare the entry's binding with the signed-in user and branch.
      A mismatch moves the entry to the cannot-send list with the reason `other-user` or `other-branch` and it is
      **never** sent and **never** deleted. Entries bound to the *same* user replay after re-authentication, which is
      why the queue key is not shredded on sign-out.
- [ ] **How the queue survives sign-out, mechanically.** Add the string `offline-queue` to
      `SURVIVES_SIGN_OUT` in `clients/pwa/src/offline/onSignOut.ts` — the set #E12-F02-3a deliberately shipped
      **empty**, so that every exception to "a sign-out destroys everything on this device" is a reviewed one-line
      source edit rather than a behaviour nobody voted for. That one line is the security judgement of this issue;
      #E12-F02-3a's own test asserts the set is empty, so **that test changes in this pull request too**, and a
      reviewer sees both halves in one diff. State the trade-off in the module comment: it is the one place this
      design departs from "clear everything on sign-out", and the reason is plan Section 8 for #51 — entries are
      "bound to `(user_id, branch_id)`, **not to the session**".
- [ ] **Resume triggers** — the `online` event, `visibilitychange` to visible, and application start, all through one
      `startQueueReplay()` with a single-flight guard so two triggers cannot drain concurrently. No timer and no
      `BackgroundSync` registration: background sync is not available on the WebKit engines of
      `docs/nfr/support-matrix.md` section 4.1, so a foreground drain is the behaviour on every supported platform
      and a second mechanism would be untested on half the fleet.
- [ ] **`clients/pwa/src/offline/queueMirror.ts`** — the metadata mirror in `localStorage`, holding **only**
      `{ userKey, branchId, count, operationIds, jobNumbers, firstQueuedAt }` so that a device whose IndexedDB has
      been evicted can still say what was lost. No payload, no recipient name, no measurement, no identifier beyond
      the hashed `userKey` from #E12-F02-3a's `binding.ts`. It is updated on every enqueue and drain and cleared when
      the queue empties.
- [ ] **`clients/pwa/src/offline/queueState.ts`** — the observable the user interface subscribes to:
      `{ pending, sending, paused, conflict, cannotSend, full, lastDrain }`, published through a module-level
      snapshot and `subscribe` in the shape of `useNetworkState`'s external store, so #E12-F02-5a can render it with
      `useSyncExternalStore` and no cascading effect.
      **`lastDrain: { sent, conflicted, failed, finishedAt } | null` is not optional.**
      `docs/nfr/a11y-checklist.md` **A11Y-OF-06** asks: "On reconnect, is the outcome announced — how many actions
      replayed, how many conflicted?", and its reason is that "otherwise the person cannot know whether their
      morning's scans landed". A queue that renders only a live count cannot answer it, because by the time the drain
      finishes the count is zero and nothing was ever said. So the drain records its own outcome here and
      #E12-F02-5a announces it. Clear `lastDrain` when a new drain starts, never on a timer.
- [ ] Messages for the queue's own sentences added to `clients/pwa/src/i18n/messages/offline.ts` (created by
      **#E12-F02-1**, extended by #E12-F02-3a) in **both** languages, untranslated Tamil carrying the English text
      and the `// not translated — awaiting native-speaker review` comment as the rules at the top of
      `clients/pwa/src/i18n/messages/shell.ts` require. Counts use ICU plurals; nothing is concatenated, because word
      order differs in Tamil.

## Acceptance criteria

- [ ] With a fixture operation registered in a test, an action taken offline is queued, survives a reload, and is
      sent exactly once when the connection returns, carrying the **same** `Idempotency-Key` and client event UUID it
      was queued with.
- [ ] Two entries queued in order are replayed in that order, and the second is not attempted until the first
      succeeds.
- [ ] **Negative — the allowlist is the boundary:** `enqueue` called with an operation that is not in
      `OFFLINE_OPERATIONS` throws and queues nothing, and the guard test refuses an entry whose path is outside
      `/api/v1/custody/` or whose permission is neither `custody.scan` nor `custody.confirm_delivery`.
- [ ] **Negative — a conflict stops the queue:** a `409` (for example the `custody.event-conflict` shape plan
      Section 4.4 describes for a client event UUID seen under another actor) or a `422`
      (`idempotency.key-reused`) pauses the drain, keeps the entry, and exposes the server's problem details through
      `queueState`. The remaining entries are untouched and nothing is retried automatically.
- [ ] **Negative — another user:** an entry queued by one user is not sent after a different user signs in on the same
      device; it appears in `cannotSend` with `other-user` and is still there afterwards. The same for a different
      branch.
- [ ] **Negative — the bound:** the 201st enqueue is refused with the queue-full outcome and the 200 stored entries
      are all still present; an entry older than 24 hours is not sent and is listed as `too-old`.
- [ ] **Negative — replay does not mint keys:** a test asserts the `Idempotency-Key` header on the replayed request
      equals the one stored at enqueue, and that a second drain of an already-sent entry does not happen because the
      entry was removed on success.
- [ ] **Exception — re-authentication by the same user:** after signing out and back in as the same user in the same
      branch, the queue is intact and drains in order. The draft store, by contrast, is gone — that asymmetry is
      deliberate and is recorded in the module comment and in the pull request.
- [ ] **Exception — eviction:** with the IndexedDB database deleted by hand, `queueMirror` still reports the count,
      the operations and the job numbers of what was lost, and contains no payload and no personal data.
- [ ] `429` is respected: a drain that receives one waits `retryAfterSeconds` before the next attempt, and a drain of
      more than 240 entries cannot exceed the `scan-burst` ceiling — asserted with a fake clock, not a real wait.
- [ ] **The drain reports its own outcome.** After a drain, `queueState.lastDrain` carries how many were sent, how
      many conflicted and how many failed, so that **A11Y-OF-06** can be answered by #E12-F02-5a rather than
      discovered to be unanswerable late. A named test asserts the counts for a mixed drain: two sent, one paused on
      a `409`, the rest untouched.
- [ ] **Each quarantined and conflicted entry can be named.** Every entry exposed through `cannotSend` and `conflict`
      carries its operation label message id **and its job number**, because **A11Y-OF-07** requires each conflict to
      be "named by what it was and which job it belongs to" — "a conflict named 'error 409' is not resolvable at a
      counter". The data has to be on the entry for the screen of #E12-F02-5b to render it; a test asserts both
      fields are present on a quarantined entry.
