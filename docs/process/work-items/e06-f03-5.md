## Acceptance criteria

- [ ] A garment whose pinned workflow is complete, whose latest QC result is a pass with no open rework, whose
      required evidence is recorded, which has no open hold and which is bound to nothing becomes ready through the
      service alone: `is_ready_for_delivery` is true, `ready_state_computed_at` is the clock's instant,
      `ready_state_blocks` is empty, and `orders.job-ready-for-delivery.v1` is on the outbox in the same
      transaction.
- [ ] **#34's acceptance criterion "A failed-QC garment cannot enter ready-for-delivery state"**: with a failing
      latest QC result, the verdict is blocked, the block's predicate is `QcPassed`, its reference is the failed
      result, and `is_ready_for_delivery` stays false. The same for an open rework, an open hold, an incomplete
      phase and missing evidence — five distinct reason codes, each naming its own reference.
- [ ] **#34's "Ready-for-delivery is derived from explicit gates, not a client-only status change"**: no HTTP route
      in the whole application can set `is_ready_for_delivery`. Demonstrated by the endpoint inventory showing no
      such route and by `garment_jobs_ready_is_gate_only` refusing an insert that claims it (INV-JOB-07,
      `docs/prd/raci.md` row 16).
- [ ] A `deliver_together` parcel of two is evaluated in one pass and promoted together; a recomputation triggered
      for one member that would leave the other standing is refused with `orders.ready-gate-parcel-split` rather
      than promoting half of it.
- [ ] **Negative, fail-closed**: with `Custody:GateEnabled = true` and the placeholder answering `Unknown`, the
      verdict is blocked with the `CustodyReconciled` predicate; with the default `false` the predicate is not asked
      and the garment can reach ready. Both are asserted, because the default is what W3 runs on and the true case
      is what #37 turns on.
- [ ] **Exception**: a recomputation over a parcel containing a **cancelled** garment applies no verdict to it and
      does not fail (SQ-08, interim); asked about that garment on its own it answers
      `orders.job-status-transition-not-allowed`. A hold taken on a garment already ready closes its own ready
      state and leaves its partner's alone (`orders.job-held.v1.schema.json`'s own statement of SQ-09).
- [ ] Recomputation is idempotent: running it twice with unchanged facts produces one state and does **not** publish
      a second `orders.job-ready-for-delivery.v1`.
