Sub-issue of #59. A release needs one version before anything can be built once and promoted, and this repository
has two that can disagree: `clients/pwa/package.json` declares `"version": "0.1.0"` and compiles it into the bundle
as `__CLIENT_VERSION__` (`clients/pwa/vite.config.ts` lines 17-21), while the .NET half has no version at all —
`Directory.Build.props` sets `LangVersion` and `ManagePackageVersionsCentrally` and no `VersionPrefix`, so
`BuildInformation.Version` falls back to the assembly default unless `infra/docker/Dockerfile.web` is handed
`--build-arg VERSION=` by hand (its default is `0.0.0`). Nothing states the semantic-versioning policy, nothing
records the compatibility matrix the plan's #59 blueprint requires, and `docs/process/release-gates.md` section 6
item 14 names "the release notes" as produced by #59 with no template to produce them from. This slice fixes the
version and writes the policy; every other child of #59 builds, signs, promotes and deploys *that* version.

## Acceptance criteria

- [ ] `dotnet build HyFib.Tailor360.slnx --configuration Release` with no build argument produces a web host whose
      `GET /api/version` reports `current` equal to the contents of `VERSION`, asserted over the composed host by
      extending `WebPipelineTests.VersionEndpointDescribesTheBuildTheSchemaAndTheSupportedClientRange`.
- [ ] **The proviso, and it is load-bearing:** the SDK appends `+$(SourceRevisionId)` to
      `AssemblyInformationalVersion` when a revision is supplied, and `BuildInformation.Version` returns that whole
      string. So `current` equals `VERSION` exactly **when no `SourceRevisionId` is supplied** — which is every
      `dotnet build` and every test run, including in CI — and equals `<VERSION>+<revision>` when
      `infra/docker/Dockerfile.web` or `Dockerfile.worker` supplies one. The assertion is written to that rule (equal,
      or equal up to the first `+`), and the pull request states both readings with the command that produced each.
      An acceptance criterion that claims plain equality in a container build is wrong, and would be discovered by
      whoever builds the image in **E15-F01-2**.
- [ ] Changing `VERSION` and nothing else changes the `current` value the endpoint reports, and changes no other
      field of the response — in particular not `api` and not `schemaVersion`.
- [ ] **Negative:** a pull request that changes `VERSION` without changing `clients/pwa/package.json` fails the
      architecture tier with a message naming both files and both values. The converse fails the same way.
- [ ] **Negative:** a `VERSION` file whose contents are not a semantic version (`1.2`, `v1.2.3`, empty, two lines)
      fails the same check with a message that says what the expected shape is. The check does not "helpfully"
      normalise it.
- [ ] **Exception:** a pre-release version (`1.2.0-rc.1`) is accepted by both the check and the build, and reaches
      `/api/version` unchanged, because a release candidate is built from the same source as the release. It is not
      silently truncated to `1.2.0`.
- [ ] `docs/process/versioning.md` states, for every component, who may raise which part of its version and what the
      consequence is for the other three; a reviewer can decide from it alone whether a given change needs a major.
- [ ] `./scripts/dev docs` passes: every relative link in the new and changed documents resolves.
