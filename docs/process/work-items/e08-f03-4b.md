Sub-issue of #40. `E08-F03-4` opens a stocktake session and records counts and recounts. Two things are still
missing before a variance can be approved: a way to say **the counting is finished**, and the behaviour that makes a
count mean anything at all — **the location is held while it is being counted**. This child is both, plus the
abandon path that releases a session nobody finished.

It is separate from `E08-F03-4` for one reason that is worth stating plainly: the freeze is the **only** change in
the whole of #40 that adds a call site inside another issue's command handler (#39's stock-movement command). A
reviewer should be able to read one small pull request for that, rather than find it on page four of a
1,300-line one. The earlier decomposition also listed "six endpoints" for the counting slice while its own
acceptance criteria required a seventh (abandon), which is how the slice quietly went over the bar.

Checked in this working copy today: `grep -rn "stocktake\|Stocktake" src/` returns nothing, and
`grep -rn "location-frozen\|IStocktakeFreeze" src/` returns nothing, so neither the transitions nor the guard exists.

## What is missing

- No way to finish counting, so `E08-F03-5` has no `CountingClosed` session to compute variances from and the whole
  approval half is unreachable.
- No freeze, so stock can be issued out of a location **while it is being counted** — which makes every count
  unreliable and every variance unexplainable, and is the single most important behaviour in #40's stocktake
  paragraph ("sessions per branch/location with **freeze**/snapshot policy").
- No way to release a location from a session somebody opened by mistake.

## Scope

- [ ] **Two transitions on `Stocktake`** — `CloseCounting(actor, at)` and `Abandon(actor, reason, at)` — each
      returning `Result` and each refusing every illegal move: closing a session that is not `Counting`, closing one
      with no count rows at all, abandoning one that is already `CountingClosed`, `Posted` or `Abandoned`, and
      abandoning without a reason. The shape is `ReconciliationBatch.Approve`'s
      (`src/Modules/Billing/…/Payments/ReconciliationBatch.cs:159`).
- [ ] **`IStocktakeFreezeQuery`** (or whatever `E08-F03-4`'s store shape makes natural) in
      `…Inventory.Application/Stocktakes/` — given an `(organisation, branch, location)`, does a session in
      `Counting` exist. One method, no I/O in the `Domain` project, implemented in `Inventory.Infrastructure` over
      the partial unique index `E08-F03-4` created, so the answer is a single indexed lookup and not a scan.
- [ ] **One call site in #39's stock-movement command handler**, and nothing else in #39's code: a movement whose
      **source** location has a session in `Counting` is refused with
      `InventoryErrors.LocationFrozenForStocktake` = `Error.Conflict("inventory.location-frozen-for-stocktake", …)`,
      whose message says the count must be posted or abandoned before stock can leave the location. **Which
      movements the freeze applies to is a decision, so make it explicitly and write it down:** it blocks every
      movement *out of* the counting location — issue, consumption, wastage and the source half of a transfer — and
      it does **not** block a **receipt into** the location, because refusing a supplier delivery because somebody
      is counting would stop the shop, and a receipt recorded during the count appears on the ledger with its own
      instant and is therefore reconcilable against the count's own frozen expected quantity. Reservations are
      #39's own concern and are not a movement; say in the pull request what #39's entry types actually are and
      which of them the guard refuses, from the list #39 publishes rather than from this paragraph.
- [ ] **Two endpoints**: `POST /api/v1/inventory/stocktakes/{stocktakeId}/close-counting` and
      `POST /api/v1/inventory/stocktakes/{stocktakeId}/abandon`. Both
      `RequirePermission(InventoryPermissions.Stocktake, BranchScope.CurrentBranch)`,
      `RateLimitPolicyNames.Write`, `.WithRequestTimeout(RequestTimeoutPolicies.Command)`,
      `.ScopedToResource(InventoryResourceKinds.Stocktake, "stocktakeId")` (ARCH-023), `.RequireIdempotency()`, no
      `If-Match` (the row's state is the guard, matrix line 386's recorded form), and **no** `.RequireStepUp()` —
      `inventory.stocktake` is not flagged for it and `AuthorisationMatrix.Reconcile` fails an endpoint that declares
      step-up for an unflagged key (ARCH-018).
- [ ] **The reason, spent where it means something.** `.Audited("inventory.stocktake.counting_closed")` **without**
      a reason — finishing a count is the ordinary path — and
      `.Audited("inventory.stocktake.abandoned", reasonRequired: true)`, because an abandoned count is a count whose
      result nobody will ever see and the audit trail is the only record of why. Put that sentence in the matrix
      note so the asymmetry is reviewed once rather than questioned in every review.
- [ ] **No migration.** `E08-F03-4` created both tables with every column these transitions write
      (`closed_at`/`closed_by`, `abandoned_at`/`abandoned_by`, `abandon_reason`). Prove it with a `migrate --dry-run`
      showing no outstanding migration and `dotnet ef migrations has-pending-model-changes` reporting none. If
      `E08-F03-4` did **not** include those columns, this child adds exactly one expand-only migration,
      `InventoryStocktakeClosure`, with its ledger row — and never edits `E08-F03-4`'s
      (`src/Modules/CLAUDE.md` section 6 forbids editing an applied migration).
- [ ] **Matrix and fixtures**: two endpoint rows in section 5 of `docs/security/permission-matrix.md` inside the
      `<!-- matrix:endpoints -->` markers. No new `identifier-editing` entry is needed — `E08-F03-4` already added
      the one for `{stocktakeId}` — and say so explicitly in the pull request rather than leaving the omission
      unexplained.

## Acceptance criteria

- [ ] While a session is `Counting`, an attempt to **issue stock out of** that location is refused with
      `inventory.location-frozen-for-stocktake`, and the message says the count must be posted or abandoned first;
      movements at **other** locations of the same branch, and a **receipt into** the counting location, are
      unaffected. Three assertions, not one.
- [ ] An Inventory Clerk closes counting on a session with count rows, and the session reads back as
      `CountingClosed` over HTTP; `E08-F03-5` can then compute its variances.
- [ ] **Negative:** closing a session twice is refused `409` with a stable code (the conditional-update form, matrix
      line 386), and a replayed `Idempotency-Key` returns the first outcome rather than refusing.
- [ ] **Negative:** closing a session with **no** count rows at all is refused with a code that says so — a session
      closed without a single count would compute a variance equal to the whole expected quantity of every line and
      post the branch's entire stock away as a shortfall, which is the worst failure this child can prevent.
- [ ] **Negative:** a caller at another branch pasting this branch's `{stocktakeId}` gets `matrix.yaml`'s
      `out-of-reach` answer — `404` with `security.resource-not-found`; a caller without `inventory.stocktake` gets
      `not-permitted` — `403` with `security.forbidden`; an abandon with no reason is refused by the audit filter's
      `reasonRequired` before it reaches the domain.
- [ ] **Exception:** abandoning a session **releases the location** — a movement out of it succeeds immediately
      afterwards — writes the audit event with its reason, and leaves **every count row in place as history**.
      Nothing is deleted, and a new session may be opened for the location, which the partial unique index permits
      because the abandoned session is no longer `Counting`.
- [ ] **Exception:** a session in `CountingClosed` also leaves the location **frozen** until it is posted or
      abandoned — the prototype's wording is "nothing can be issued from it until the count is posted", not "until
      counting is closed" — so the freeze predicate is "a session exists that is neither `Posted` nor `Abandoned`",
      and a test asserts a movement is still refused after close-counting. **This is the detail most likely to be
      got wrong**: naming the predicate after `Counting` alone would let stock leave between the count and the
      posting, and every approved variance would then be wrong by that movement.

## Migration and rollback

**No schema change expected** — see the scope item above for the one condition under which a migration is added and
what it would be named. Rollback is redeploying the previous tag: the two routes disappear and, more importantly,
**the freeze stops being enforced**, so a session left in `Counting` across a rollback no longer holds its location.
Say that in the rollback note, because it is the one behaviour an operator needs to know: finish or abandon open
sessions before rolling back.
