Sub-issue of #41. What a counter may take off a line, and what nobody may exceed: the discount rules of a draft
price-list version, authored on the screen rather than in the database. #146 built the three routes and closed;
E09-F01-7 renders whatever rules a version already holds **read-only**, with a sentence saying the editor arrives
here. This is that editor.

It is a slice of its own rather than a section bolted onto E09-F01-7 because the bounds it authors are the bounds the
engine enforces — `billing.discount-above-maximum` and `billing.approval-required` are decided against
`maximumWithoutApproval` and `maximum` — so the screen that writes them deserves its own negatives and its own
evidence. It is also what keeps E09-F01-7 and E09-F01-8b each inside one session: the preview in E09-F01-8b cites a
rule by code, and a rule has to be authorable before that citation means anything.

## Scope

- [ ] **Transport**, appended to `clients/pwa/src/billing/priceListApi.ts`: `addDiscountRule`, `editDiscountRule`,
      `removeDiscountRule`. Each takes the caller's `Idempotency-Key` and the `If-Match` tag **from the previous
      response**, including after a `204` removal, and returns `VersionedResponse<…>` (`VersionedResponse<void>` for
      the removal) so the version's new tag is carried forward rather than re-fetched.
- [ ] **Types**, appended to `clients/pwa/src/billing/priceListTypes.ts`: `DiscountRule`, `DiscountRuleRequest`. Both
      bounds are `number | string` and **no arithmetic is done on either** — including the comparison that would
      "helpfully" warn before the server does. The ordering rule is the server's
      (`billing.discount-bounds-not-ordered`), and a client-side comparison of two values that may be strings is how
      a second, disagreeing rule grows.
- [ ] **The rules section** on `clients/pwa/src/routes/pricing/PriceListVersionEditorRoute.tsx`, replacing the
      read-only list and the sentence E09-F01-7 left there: a table of the draft's rules with add, edit and remove,
      beside the items rather than behind a tab, because an administrator setting up a version does both in one
      sitting. A published or retired version keeps the read-only list and offers no control, because the server
      refuses every write to one (`billing.version-not-editable`).
- [ ] **The rule form** `clients/pwa/src/routes/pricing/DiscountRuleForm.tsx`: code, description, kind
      (`Percentage` or `Amount` — a radio group with **no pre-selected default**), the maximum a counter may give on
      its own authority, the hard maximum, and active (an explicit choice, because the server refuses an omitted
      flag). **Both bounds are required and neither is pre-filled**: a discount boundary is the owner's decision
      with the accountant, and a number this product suggested would be a number nobody signed. The unit of each
      bound follows the kind — a percentage through `formatPercent` and `parseNumber`, an amount through
      `formatMoney` and `parseNumber` — and the label says which, so "10" is never ambiguous between ten per cent and
      ten rupees.
- [ ] **Refusals in words**, appended to `CODE_MESSAGES` in `clients/pwa/src/billing/billingProblems.ts`:
      `billing.discount-bounds-not-ordered`, `billing.discount-rule-not-found`. The others this screen can meet
      (`billing.code-not-unique`, `billing.code-not-well-formed`, `billing.amount-not-well-formed`,
      `billing.value-required`, `billing.version-not-editable`, `billing.version-changed`) are already in the map
      from E09-F01-6 and E09-F01-7 — append only what is missing.
      The sentence for `billing.discount-bounds-not-ordered` says which way round they go, in the shop's words, not
      "bounds not ordered".
- [ ] **States and stories**: the rules section's four states plus the pseudo-locale story, appended to
      `clients/pwa/src/routes/pricing/pricingScreens.stories.tsx`.
- [ ] **Fixtures**, appended to `clients/pwa/src/billing/testing/priceListFixtures.ts`: `aDiscountRule`. Every code
      and bound is synthetic.
- [ ] **Conformance assertions** in `clients/pwa/src/api/contract.ts` for `DiscountRule` and the `AddDiscountRule`
      request body.

## Acceptance criteria

- [ ] An Owner opens a draft version, adds a `Percentage` rule with a counter bound and a hard maximum, edits it,
      removes a second one, and reads all three facts back after a reload — no deployment, no database access.
- [ ] The label of each bound says its unit, and a `Percentage` rule's bounds render through `formatPercent` while an
      `Amount` rule's render through `formatMoney`, so the same typed "10" cannot be read two ways.
- [ ] **Negative, the bounds the wrong way round:** a hard maximum below the counter bound is refused with
      `billing.discount-bounds-not-ordered` rendered as a sentence that says which way round they go, attached to
      the field it concerns; the typed values stay on screen and a retry reuses the **same** `Idempotency-Key`. The
      client does **not** pre-empt this with its own comparison — the test asserts the request was actually sent.
- [ ] **Negative, an omitted bound or flag:** submitting without either bound, or without the active choice, is
      refused and the message names the field; the test asserts the request body carried no value the person did not
      type.
- [ ] **Negative, duplicate code:** a second rule taking an existing code is refused with `billing.code-not-unique`
      against the code field.
- [ ] **Negative, concurrency:** a write against a tag the screen no longer holds answers `billing.version-changed`,
      and the screen offers a re-read and a retry with the **same** `Idempotency-Key`; the tag carried into the next
      write is the one the previous response returned, **including after a `204` removal**. Because the rules and the
      items share one version tag, the test also covers an item write followed by a rule write.
- [ ] **Negative, authorisation:** a caller without `billing.manage_price_lists` meets `RequirePermission`'s
      `EmptyState`, never a redirect; the test also asserts the screen handles the **server's** refusal of a write.
- [ ] **Exception path:** a published or retired version shows its rules **read-only** with their bounds visible and
      offers no control, and the screen says a change is a clone into a new draft. A rule is never deleted from a
      published version — there is no route that could.
- [ ] **Offline:** every rule control renders `OfflineBlockedAction` — "Needs connection — this will not be queued",
      word for word.
- [ ] No bound is pre-filled, no bound is suggested, and no comparison of the two bounds happens in the client.

## Data and classification

Nothing is persisted client-side: component state only, no `localStorage`, no service-worker cache, and **no bound in
any telemetry attribute**.

| Item | Class | Purpose | Retention | Who may read it | Logs, telemetry, export |
| --- | --- | --- | --- | --- | --- |
| `DiscountRule.maximumWithoutApproval`, `maximum` | **Confidential** | The discount a counter may give alone, and the most anybody may give | None client-side | Holders of `billing.manage_price_lists`; `owner` today | "Price-list rates and discounts" is the Confidential row of `docs/nfr/data-classification.md` line 52: never on a shop-floor screen, never in a log line, never in telemetry, never exported from this screen |
| `DiscountRule.code`, `description`, `kind`, `active` | **Internal** | To name the rule a line's discount cites | None client-side | As above | Price-list structure, the Internal row (line 51). The code may appear in a correlated server log line; the client logs nothing |
| The reason typed on a rule write or removal | **Internal** — evidentiary | The audit trail of a configuration change | Server-side, per `docs/nfr/data-classification.md` section 5.16 | `auditor`, `owner` | Sent in the body, stored on the audit event; the client keeps it only until the request succeeds |

No new field is unclassified and no retention period is invented.

`billing.override_price` (line 144, branch scope, granted to `owner` and `branch_manager`) is **named here only to
say this screen never asks for it**: it is the key a *counter* needs to exceed the bounds this screen writes, and the
engine consults it server-side (`PricingService.cs` line 194). Authoring a bound and exceeding it are different acts
by different people, which is exactly why the bound is organisation-scoped configuration and the exceedance is a
branch-scoped, step-up permission. **OD-13** is open, so the grant above is proposed rather than approved. No
integration authorisation-matrix fixture changes — no endpoint is added.

give is the defect the whole feature exists to prevent.
