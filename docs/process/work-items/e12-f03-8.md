Sub-issue of #52. **This is an evidence sub-issue: it writes documents and no code, and a coding session may not
sign a manual run.** The parent's last implementation step — "Run real-device testing; treat emulation as
supplementary" — and the two Required-verification lines no automated gate can answer: "Manual screen-reader/
keyboard/zoom testing" and real-device profiling.

Read this before anything else. `docs/nfr/a11y-checklist.md` section 2.5 rule 1 is that "**a record written from
memory is not evidence**", and section 2.2 says who runs a pass: a person, at a device, for a measured number of
minutes per screen. A coding agent in a container has no Android phone, no iPhone, no iPad and no Windows machine; it
also has no human to press Tab and say what the screen reader announced. So this sub-issue **builds the instruments
and records the deferral**, and every pass — keyboard, environment and screen-reader alike — is owed by a named
human afterwards. Filling a record in from what the code appears to do would be the worst outcome available: a signed
artefact that a release gate trusts and nobody ran. The automated equivalents of the keyboard and reflow passes
already exist and belong to **[E12-F03-2]**; this sub-issue does not duplicate or pre-empt them. The documents that
define this work are already written and have
no instruments: `docs/nfr/a11y-checklist.md` is 1,525 lines whose section 8 says the runner must not have to
"hand-build the sheet, because what gets built is only the rows they already suspect" — and there is no sheet in the
repository to copy, no `docs/nfr/a11y-records/` directory, and nothing under `docs/` that records a device. Three of
that document's own open decisions are scheduled **"Before #52"** — **A11Y-OD-01** (which pairing a pull request
runs on), **A11Y-OD-05** (the barrier-versus-friction test) and **A11Y-OD-06** (where a completed record lives) —
and lines 119 to 122 say plainly that "the NVDA leg of the rotation begins at #52". This sub-issue stands those
instruments up and records every pass as a deferral with all six fields rather than as a claim nobody can check.

  cannot be met, not for an approval that has not been sought, so no waiver is written here.

## Screens and states

No screen is added or changed. Which screens are walked, and in which pass, is fixed by `a11y-checklist.md`: the
core checklist of section 4 is answered **once per screen** on the DOR-14 screen list, and section 4.12 requires the
**five screen states** — loading, empty, error, offline and forbidden — to be reached on each. Section 3.7 names the
fixtures and forced states a run needs; the forced states for the screens that exist come from the story harnesses
that already exist, which for an admin or billing screen is
`clients/pwa/src/admin/testing/storyTransport.tsx` (`storyJson`, `storyProblem`, `storyPending`, `withAdminApi`,
`STORY_USER`, `StoryRoutes`). Two facts about that harness the runner must know and not fight: there are
deliberately **no offline Storybook stories for admin screens** — `catalogScreens.stories.tsx` records why — so the
offline state of an admin screen is reached in the running application with the network disabled, not in a story;
and `JourneyFrame` (`clients/pwa/src/stories/journeys/JourneyFrame.tsx`, used by
`journeys.stories.tsx`) brings its own `MemoryRouter` and therefore cannot be combined with
`withAdminApi` or `StoryRoutes`, so a runner picks one.
