- [ ] **The record**, written as `artifacts/backup/restore-<utc-timestamp>.json` plus a markdown summary on stdout:
      `{startedAt, finishedAt, repository, backupLabel, restoreTargetTime, recoveredToTime, measuredRpoSeconds,
      measuredRtoSeconds, migrationState, invariants: [{name, rows, passed}], informational: {inheritedOutboxLeases,
      artifactsChecked, artifactsSampled}, verdict}`, where `invariants` carries exactly `audit-chain`,
      `invoice-sequence`, `outbox` and `media-objects` (the last being `head.sh`'s verdict over the feed, which is why
      the feed itself is not an entry). `measuredRpoSeconds` is
      `recoveredToTime` subtracted from the newest archived WAL time, not from "now" — the difference is the whole
      point of the measurement and a comment says so. `artifacts/` is already git-ignored, so the record is pasted
      into the pull request rather than committed; the **filed** records are child [E15-F02-7]'s.
- [ ] `infra/backup/verify/` — one `.sql` file per invariant, each returning **rows only on failure** so the drill's
      rule is uniform.

      **Read this before writing a single query, because it decides which queries are worth writing.** A pgBackRest
      point-in-time restore replays write-ahead log and is **transactionally consistent**: it cannot produce a
      database in which a `CHECK` constraint is violated, a unique index has a duplicate, or one half of a committed
      transaction is missing. So an "invariant" that merely restates a constraint the schema already enforces can
      never return a row, and a drill built from four of those is a drill that cannot fail. The checks with teeth are
      exactly the three kinds the database does **not** enforce for itself:
      (i) a **recomputation** — a hash chain whose arithmetic is checked rather than asserted;
      (ii) a **cross-relation** agreement no foreign key or constraint covers, especially across two module schemas;
      (iii) a **cross-system** agreement, between a row and an object in a bucket.
      Write those three, and say in `docs/platform/backups.md` that you deliberately did not write the fourth kind.

      - `audit-chain.sql` — kind (i) and (ii). `SELECT * FROM platform.verify_audit_chain()`
        (`src/Platform/Tailor360.Platform.Persistence/Migrations/20260904185927_AuditTrailStructure.cs:176`,
        signature `(from_sequence bigint DEFAULT 0)` returning `TABLE (broken_sequence bigint, broken_id uuid,
        reason text)`), which recomputes every `sha256` from `previous_hash` and the row's material — no constraint
        does that. Plus the head agreement: `platform.audit_chain_head.last_sequence` equals `max(sequence)` and
        `last_hash` equals that row's `hash`. `audit_chain_head` is a separate one-row table maintained by a trigger,
        so its agreement with `audit_events` is kind (ii) and is genuinely falsifiable.
      - `invoice-sequence.sql` — kind (ii), and the reason it has teeth is that it spans two schemas: the allocated
        high-water mark lives in `platform.sequences` and the numbers live in `billing.invoices`, and **nothing in the
        database relates them.** Per `(organisation_id, branch, financial_year)` scope over **posted** invoices
        (`status = 1`; the check constraint `ck_invoices_lifecycle_is_consistent` makes `invoice_number` non-null
        exactly then, and a cancellation is a separate `billing.invoice_cancellations` row so a cancelled invoice
        keeps its number): the six-digit suffixes are contiguous from 1, and the count equals
        `platform.sequences.next_value - 1` for the matching `sequence_key` and scope. The scope string is
        `DocumentNumbers.SequenceScope` = `"{organisationId:N}:{branchCode}-{FY}"` and the four keys are exactly
        `invoice`, `receipt`, `credit-note` and `debit-note` (`DocumentNumbers.InvoiceSequence`, `ReceiptSequence`,
        `CreditNoteSequence`, `DebitNoteSequence`). Do **not** assert no-duplicates:
        `ux_invoices_organisation_invoice_number`
        already forbids that, so it is the fourth kind.
      - `document-artifacts.sql` — **not an invariant; a feed.** `ck_document_artifacts_completed_is_whole` already
        forces `object_key`, `sha256`, `size_bytes` **and `completed_at`** non-null exactly when `status = 1`, and
        `ux_document_artifacts_object_key` already forbids a duplicate `object_key`, so asserting either is the fourth
        kind and can never fire. This file instead **selects** `(id, object_key, sha256, size_bytes)` for every row
        with `status = 1`, for `head.sh` to check against the bucket — which is kind (iii) and is the real check. It
        returns rows on success by design, so the drill treats it as a feed and not as a pass/fail query; say so in
        the file's header comment, because the uniform "rows mean failure" rule does not apply to it.
      - `outbox.sql` — **the obvious query here is wrong and would make every drill red.** A restored database does
        inherit the leases held at the moment of the backup, but a lease is *reclaimable by design*:
        `OutboxDispatcher` claims a row with
        `AND (m.lease_expires_at IS NULL OR m.lease_expires_at < now())`
        (`src/Platform/Tailor360.Platform.Persistence/Outbox/OutboxDispatcher.cs:160` and `:174`), so an inherited
        lease simply expires and is picked up. "A row is leased by a dispatcher that no longer exists" is therefore
        **expected, harmless and self-healing**, and asserting against it would fail the drill on every single run.
        Report inherited leases as an informational count in the record and assert only the two states that are
        genuinely stuck and that no constraint forbids: no row has **both** `processed_at` and `dead_lettered_at`
        set, and no row has `lease_owner IS NOT NULL` with `lease_expires_at IS NULL` — a lease with no expiry that
        no dispatcher can ever reclaim.
        `outbox_messages` exists in **six** schemas, and the session must not guess the list: `platform`, `identity`,
        `customers`, `catalog`, `orders` and `billing` (created by `20260904185922_InitialPlatformSchema`,
        `20260908022906_ModuleOutbox`, `20260908022913_ModuleOutbox`, `20260909054521_InitialCatalogSchema`,
        `20260911141153_InitialOrdersSchema` and `20260912061752_InitialBillingSchema`). The query unions all six and
        names the schema in each row it returns; a new module's outbox must be added here, and the file says so.
      - `media-references.sql.owed` — **not** a query: a short file naming what cannot be checked yet and which
        issue owes it, so the omission is visible in the tree rather than implied. See "Out of scope".
- [ ] `infra/backup/verify/head.sh` — the object-reference half, which is not SQL and is the only **cross-system**
      check in the set: for each `(object_key, sha256, size_bytes)` the `document-artifacts.sql` feed emits, a `HEAD`
      against the **documents** bucket (`tailor360-documents`, not the media bucket — `media_objects` does not exist;
      see "Out of scope") through `mc stat`, reporting every key the bucket does not hold and every key whose reported
      size disagrees with `size_bytes`. Bounded and sampled when the row count exceeds the configured sample size,
      with the sample size and the sampling rule printed in the record so the evidence says what it proved rather than
      implying it proved everything. Its comparison is a shell function over `(feed line, mc stat output)` so that the
      integration test can drive it with fixture text and no bucket — the same `--self-test` shape child [E15-F02-1]
      defines.
- [ ] `docs/platform/backups.md` — the restore-drill section: what the drill does, what it proves, what it does
      **not** prove, how to run it by hand, what each invariant means and what a failure of each implies, and the
      record's shape. It names the cadence by citing `docs/nfr/slo.md` section 6 and `docs/process/release-gates.md`
      RG-13's freshness rule rather than restating either.
- [ ] `tests/Tailor360.IntegrationTests/Platform/RestoreInvariantQueryTests.cs` —
      `[Trait("Category", "Integration")]`. Each pass/fail `.sql` file is executed against the test database and must
      return **no rows** on a consistent database, and **rows** on a deliberately broken one. This is the negative
      control the queries would otherwise never get, and it is the part of this slice that runs in CI on every pull
      request rather than only on a VM.

      **How to break each one, stated exactly, because the schema actively resists all three and a session that
      guesses will spend its context on a wall.** Every corruption happens inside a transaction the test rolls back.
      1. **The audit chain.** `platform.audit_events` carries trigger `audit_events_no_update`, `BEFORE UPDATE OR
         DELETE ... EXECUTE FUNCTION platform.audit_events_append_only()`, which raises with `ERRCODE =
         'restrict_violation'` — so a plain `UPDATE ... SET hash = ...` **fails**, and the failure is not the test
         passing. Disable the trigger first (`ALTER TABLE platform.audit_events DISABLE TRIGGER
         audit_events_no_update;`), overwrite one row's `hash`, re-enable it, then run the query and assert
         `verify_audit_chain()` names that row's `sequence` in `broken_sequence`. The test connection owns the table,
         so the `ALTER` succeeds; the rollback restores both the row and the trigger state.
      2. **The invoice sequence.** Post two invoices in one scope, then `UPDATE billing.invoices SET invoice_number =
         <suffix + 1>` on the second so the run skips a number — the unique index still holds, which is the point:
         the gap is invisible to every constraint and visible only to this query's comparison against
         `platform.sequences.next_value`.
      3. **The document artefact.** `ck_document_artifacts_completed_is_whole` is a `CHECK` constraint, and **a
         `CHECK` constraint cannot be deferred in PostgreSQL** — `SET CONSTRAINTS ... DEFERRED` applies only to
         foreign keys and unique/primary-key constraints, so "inserted with the constraint deferred" is impossible.
         Because this file is a feed rather than a pass/fail query (see above), its negative control is not a broken
         row at all: it is `head.sh`'s missing-object case, asserted against a fake `mc stat` that reports one key
         absent. Write that control as a unit-level assertion over `head.sh`'s comparison function, and state in the
         pull request that the intra-row wholeness needs no control because the database enforces it.

Versioned configuration, not code (DOR-11): the compose project, the SQL files and the sample size are versioned;
the restore credential is a mounted secret that exists only in the restore environment.

## Migration and rollback

No schema change: no table, column, index, trigger or EF Core migration. The new SQL files are read by a script and
by a test; they create nothing. Proof: `migrate --dry-run` prints "The database is up to date with this build." and
the `migration-check` job reports no model change.

Two rollback notes belong in `docs/platform/backups.md`:

1. **Reverting this pull request** removes the drill, not any data; no environment changes state.
2. **The drill's own failure is not a rollback.** A failed drill means the *backup* is suspect, so the documented
   response is to keep the repository untouched, raise a `release-blocker` corrective issue (the mechanism is child
   [E15-F02-7]'s) and re-run against an earlier backup label — never to re-create the stanza, never to take a fresh
   backup to make the drill pass, which would destroy the evidence of what failed.
