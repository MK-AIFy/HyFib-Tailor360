Sub-issue of #59. `docs/process/release-gates.md` section 2.3 asserts a cadence this repository cannot run: a
**Nightly** row reading "RG-05 across the full browser and device matrix, RG-06 and RG-07 across all journeys, RG-11
against the deployed digests". Nothing fires on a schedule. `grep -n "^on:" -A6 .github/workflows/*.yml` shows
`ci.yml` triggered by `pull_request` and `push` to `main`, and `pr-policy.yml` by pull-request events — there is no
`schedule:` key anywhere in the repository. `docs/nfr/security-operations-targets.md` line 129 names the other half:
base and third-party images are to be rebuilt **weekly**, "pinned to exact patch releases", by "**the scheduled
rebuild of #59, followed by a Trivy re-scan**", and section 2.1 sets the clocks that rebuild is meant to keep —
critical within 7 calendar days, high within 30, medium within 90, low by the next scheduled release, with the clock
stopping only "when the fix is **deployed to production** and verified". This slice adds the schedule, rebuilds and
re-scans what is actually deployed, and makes a breached patching clock a release gate instead of a paragraph.

- [ ] **Make the jobs runnable without the schedule, because the schedule cannot be proved before this merges.** Both
      `schedule:` and `workflow_dispatch` only take effect for a workflow file on the **default branch** — a scheduled
      run cannot be triggered from a feature branch at all, and the dispatch button does not appear until the file is on
      `main`. So structure the workflow so the same jobs are reachable another way for the pull request's evidence: a
      `push:` trigger limited to this branch and this path, or a `workflow_call` the reviewer can invoke, removed or
      narrowed in the same pull request once the real evidence is captured — say which was done. **The first genuinely
      scheduled run is an Owner confirmation after merge**, recorded as such.
- [ ] The nightly arm that can run today: **RG-11 against the deployed digests.** Read the digests from
      **E15-F01-4**'s promotion record, verify each with `scripts/verify-artefact.py` (a deployed digest that no
      longer verifies is the most serious thing this run can find), Trivy-scan each image by digest, and gate through
      `scripts/sarif-gate.py` at the severity RG-11 names — critical and high in a shipped layer are S1, medium is S2.
- [ ] The weekly arm: rebuild the three release images **from the same commit** on their current pinned bases, compare
      the resulting digests against the deployed ones, and report when a rebuild would change a layer — which is how a
      base-image patch becomes visible without waiting for a feature release. The rebuild **publishes nothing by
      itself**: a new digest reaches an environment only through **E15-F01-4**'s promotion, so "production cannot
      deploy an unapproved artifact" still holds.
- [ ] `scripts/patch-clock.py` — reads the findings of the nightly run together with
      `.github/sarif-accepted.json`, and fails when any finding's age exceeds the clock for its severity in
      `docs/nfr/security-operations-targets.md` section 2.1. It **reads the figures from the document or from a small
      committed table that cites it**; it does not hard-code 7, 30 and 90 in a way that can drift from the document.
      With a `--self-test`, in the idiom of `scripts/sarif-gate.py`.
- [ ] **Decide and write down where a finding's age comes from, because nothing in this repository records it today.**
      Section 2.1 says the clock starts "when the finding first appears in a scanner run", and a single SARIF report
      from tonight's run carries no first-seen date — so an age cannot be computed from the scan alone. There are two
      honest sources and this pull request picks one and says why:
      (a) **GitHub code-scanning alerts**, whose `created_at` is exactly "when it first appeared", read through
      `gh api repos/{owner}/{repo}/code-scanning/alerts`. The catch is already written down in `ci.yml` lines 73-81 and
      887-897: uploads are opt-in behind the `CODE_SCANNING_ENABLED` repository variable, and when it is off the alerts
      page is unavailable. So this path needs the same fallback the existing jobs use, and the clock must fail loudly
      rather than report "age 0" when it cannot read an alert.
      (b) **a committed first-seen register** — a small JSON file the nightly run appends to, which makes the clock
      self-contained and makes the run a committer.
      Prefer (a), because `NFR-SE-07`'s evidence is "the vulnerability register with due dates" and
      `docs/security/vulnerability-management.md` (**`E14-F01a-7`**) is the document that defines that register — a
      second register invented here would be the thing that document then has to reconcile. Whichever is chosen, the
      `--self-test` feeds the clock a **synthetic first-seen date**, so none of this waits on a calendar.

      blueprint says ("patching SLAs from #19 enforced as a release gate"): add it to **E15-F01-4**'s

- [ ] The expedited path for an emergency patch, documented where `docs/nfr/security-operations-targets.md` line 136
