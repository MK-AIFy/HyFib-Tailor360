Sub-issue of #41. The second half of the tax configuration editor: the publication checks read **before** a publish,
and the publish itself — step-up, a reason, and the race two administrators lose. E09-F01-5 ships the editor up to
the last save and deliberately carries no validate control and no publish control; this issue adds them, and builds
the one shared component both the tax editor and the price-list editor render a finding with.

It is split from E09-F01-5 because one session cannot carry both under the 1,500-line target of CLAUDE.md section 6:
the closest analogue, `clients/pwa/src/routes/catalog/CatalogVersionEditorRoute.tsx`, is 978 lines before its two
forms, and the publish path is where the second permission key, the step-up renewal, the mandatory reason and two
conflict codes all live. Splitting it also makes the authorisation negatives first-class rather than a tail.

## Scope

- [ ] **The shared findings list** `clients/pwa/src/billing/BillingFindingsList.tsx` — one presentational component
      taking `readonly findings: readonly BillingFinding[]` and rendering **errors separated from warnings**, each
      finding naming its severity, its target and the server's own sentence. Severity comes from the payload's
      `severity` field, never from a client-side list of codes, so a severity the server changes changes here for
      free. The list is an `Alert live="polite"` region so a validation run announces its result, and severity is
      carried by an icon **and** a word, never colour alone (NFR-AC-05). It has its own component test and its own
      story, and **E09-F01-7b reuses it unchanged** — this is the reason that issue depends on this one.
      A warning does not refuse a publish and an administrator must be able to see which is which; that
      distinction is exactly what **OD-19** turns on for the price list's own checks.
- [ ] **The findings reader** `findingsOf(failure: unknown): readonly BillingFinding[]`, appended to
      `clients/pwa/src/billing/pricingAdminTypes.ts` (or a small sibling module) — takes the `findings` extension
      off an `ApiError`'s `problem`, validates each element's shape, and answers an empty array for anything else.
      Typed here rather than trusted, because `ApiProblem` does not declare it.
- [ ] **Transport**, appended to `clients/pwa/src/billing/pricingConfigApi.ts`: `validateTaxConfigurationVersion`
      (a read) and `publishTaxConfigurationVersion` (`POST`, `Idempotency-Key`, `If-Match` from the previous
      response, a mandatory reason in the body, returning `VersionedResponse<TaxConfigurationPublication>`).
- [ ] **Types**, appended to `pricingAdminTypes.ts`: `TaxConfigurationPublication`.
- [ ] **The validate control and the report** on `clients/pwa/src/routes/pricing/TaxConfigurationEditorRoute.tsx`,
      replacing the sentence E09-F01-5 left in its place. The report is stale once a write has happened since it
      was run, and says so rather than showing a figure that is no longer true — the catalogue's
      `catalog.check.stale` alert is the precedent.
- [ ] **Publish**, on `BILLING_PERMISSIONS.publishPriceList` only: a `ConfirmDialog` with `tier="reason"` and
      `irreversible`. The control is **hidden, not disabled with an explanation**, for somebody holding only the
      drafting key — exactly as the catalogue editor hides its publish control — and a `Forbidden` region naming
      who may publish is shown in its place, with `action` in words, `allowedRoles` and a keyboard-reachable
      `onBack` (A11Y-89). After a successful publish the screen shows the version it superseded **and every warning
      the publication returned**.
- [ ] **Refusals in words**, appended to `CODE_MESSAGES` in `clients/pwa/src/billing/billingProblems.ts`:
      `billing.version-not-publishable`, `billing.publish-validation-failed`, `billing.publish-conflict`,

- [ ] **States and stories**: the report and the publish dialog added to the editor's existing stories, plus a

## Acceptance criteria

- [ ] An Owner opens a draft with a tax code carrying a CGST + SGST pair, runs the validation, sees it report
      nothing to fix, publishes with a reason, and sees the version move to `Published` with the one it superseded
      named — no deployment, no database access.
- [ ] **Negative, the publication check:** a draft whose code carries a CGST without its SGST is refused at publish,
      and the screen lists **every** finding from the `findings` extension against the code it concerns — not the
      first one, and not a bare `billing.publish-validation-failed`.
- [ ] **Negative, severity is not flattened:** a warning returned by a **successful** publish is shown as a warning
      beside the published version, not as a failure and not silently dropped. (The tax configuration's own checks
      are all errors today; the test drives this through a stubbed warning, because the component is the one
      E09-F01-7b reuses where warnings are real.)
- [ ] **Negative, authorisation:** a holder of `billing.manage_price_lists` without `billing.publish_price_list`
      sees no publish control and a `Forbidden` region naming who may publish; a holder of neither key meets
      `RequirePermission`'s `EmptyState` and never a redirect. The test also asserts the screen handles the
      **server's** refusal of a publish, because the claim list from `GET /me` can be minutes old.
- [ ] **Exception path, step-up:** when the publish answers `403 security.step-up-required`, the transport renews
      the proof of identity in place and replays the identical request with the **same** `Idempotency-Key`; the
      screen shows no challenge of its own and no duplicate publication results. Driven through
      `setSessionChallengeHandler`.
- [ ] **Negative, the reason:** a publish submitted with no reason is refused with `billing.reason-required` as a
      field error on the reason field, and the dialog stays open with the typed reason intact.
- [ ] **Negative, the concurrent publish:** when a second administrator has already published, the publish answers
      `billing.publish-conflict` as a `409`; the screen says so in words, re-reads the version and shows its new
      status rather than leaving a stale `Draft` on screen. This is the client half of the parent's "concurrent
      effective-version publish" verification, whose server half is
      `RefusesASecondDraftThatTookTheSameVersionNumber`.
- [ ] **Negative, the stale report:** a write made after a validation run marks the report stale and says so; the
      publish control does not read a stale report as permission to publish.
- [ ] **Offline:** the validate and publish controls render `OfflineBlockedAction` — "Needs connection — this will
      not be queued", word for word.

## Data and classification

Nothing is persisted client-side: component state only, no `localStorage`, no service-worker cache, no telemetry
attribute carrying a rate, a code or a reason.

| Item | Class | Purpose | Retention | Who may read it | Logs, telemetry, export |
| --- | --- | --- | --- | --- | --- |
| `BillingValidationReport` and each `BillingFinding` — severity, code, message, target | **Internal** | To say why a publication would be refused, and what it warned about | None client-side | Holders of `billing.manage_price_lists`; `owner` today | The server's sentence is rendered; the code is never shown to a person and never logged by the client. A finding encodes no rate |
| `TaxConfigurationPublication` — the published version, the superseded version, the findings | **Internal** | To show what was published and what it replaced | None client-side | As above | Identifiers are safe in a correlated server log line |
| The publish **reason** the administrator types | **Internal** — evidentiary | The audit trail of a publication that changes what every future order is quoted at | Server-side, per `docs/nfr/data-classification.md` section 5.16 | `auditor`, `owner` | Sent in the body, stored on the audit event by `.Audited(..., reasonRequired: true)`. The client keeps it only until the request succeeds, and **never** in `localStorage` — a reason surviving a reload would survive the person who typed it |

No new field is left unclassified and no retention period is invented: nothing in this slice is retained on the
device, and the audit event's retention is the row already written in section 5.16.
