Sub-issue of #46. Ninth of thirteen, and the **first client child**: the reporting feature area, the two shared report
controls every later report screen reuses — the freshness status strip and the export-request-and-download action —
and the **first** stock screen, stock position and aging. The other two stock screens are `e10-f03-9b`.

It is split from the endpoints because appending "and the screens for it" to a backend slice reliably makes two
sessions, and it is split from `e10-f03-9b` for a number rather than a feeling:
`clients/pwa/src/routes/catalog/CatalogVersionEditorRoute.tsx` is **994 lines in the file for one route**, before its
entry components, its API module, its messages and its stories. Three report screens plus a new API module plus two
new shared components plus a two-language message family does not fit under the 1,500-line ceiling of CLAUDE.md
section 6. One screen plus the foundation does.

There is no reporting screen in the client today: `clients/pwa/src/routes/` holds `auth`, `measurements`, `billing`,
`admin`, `catalog` and the unguarded shell routes, and `ls clients/pwa/src/reporting` finds nothing.

  `clients/pwa/src/billing/{billingApi.ts,billingPermissions.ts,types.ts,testing/}` is the model (325, 40 and 2xx

## Out-of-band note on drill-through

A figure drills through to the **owning module's** own authorised screen — an Inventory ledger or receipt screen, a
Billing invoice screen — using the source references the payload carries. `Inventory.Contracts` publishes no ledger
read contract (`docs/architecture/module-ownership.md` section 5.7), so where the target screen does not exist yet the
control is shown **disabled with a reason**, never linked to a route that 404s. `e10-f03-3` records the same reduction
on the server side.
