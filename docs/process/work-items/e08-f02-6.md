Sub-issue of #39. T6 of `docs/architecture/sequences/stock-reservation.md` section 4 — "A balanced pair of
`transfer_out` and `transfer_in` entries in one transaction … Neither leg is posted; a half transfer cannot exist" — and
the second half of the parent's third acceptance criterion ("purchase receipt or **transfer** failure cannot leave a
half-posted balance"). Nothing exists: the Inventory module has no `DbContext` today, and
`docs/architecture/module-ownership.md` section 5.7 lists **no `transfers` table**, which is the design this child

## Scope

- [ ] **`POST /api/v1/inventory/transfers`** — **a route of its own, and that is a deliberate deviation from the
      plan.** `docs/IMPLEMENTATION_PLAN.md` Section 9 `### #39` lists `transfer` as one of the types on
      `POST /api/v1/inventory/movements`. It cannot be: that route posts **exactly one** ledger entry, and a transfer is
      a balanced **pair** in one transaction (T6), with two locations, two balance rows and an allowed-destination rule
      that no other movement type has. Folding it in would make one request body mean two different things and one
      response mean either one entry or two. State the deviation and this reason in the pull request so a reviewer
      reading the plan beside the diff is not surprised. Body: item, source location, destination location, quantity
      with its unit, reason code. Mints one `transfer_group_id` from `IIdGenerator` and posts **one**
      `ILedgerPoster` call carrying exactly two lines: a `TransferOut` at the source (negative) and a `TransferIn` at
      the destination (positive), both with the same base quantity, the same group identifier and the same reason code.
      `RequirePermission("inventory.record_movement", BranchScope.CurrentBranch)`, `RateLimitPolicyNames.Write`,
      `.Audited("inventory.transfer.posted", reasonRequired: true)` — the key is declared `RequiresReason: true`, and
      the handler validates the reason code and writes it onto the audit entry itself, because no filter does
      (`AuditedEndpointMetadata.cs:5-6`) —, `.RequireIdempotency()`,
      `.TouchesNoBranchOwnedResource(reason, "#39")`, `RequestTimeoutPolicies.Command`.
- [ ] **Validation** — source and destination must differ; both must be active and belong to the caller's branch; the
      destination must be in the source location's allowed-destination set
      (`inventory.transfer-destination-not-allowed`); the item must be `active`; the quantity must be positive; the
      source's `available` must cover it, so a transfer cannot oversubscribe reserved stock any more than a reservation
      can (`inventory.insufficient-stock`, and the row lock is the serialisation point). The `reserved` component is
      untouched by either leg: `E08-F02-1`'s fold moves `reserved` only on a `Reservation`, a `Release` and an `Issue`
      that names a reservation, so a transfer of reserved stock is refused rather than quietly moving the claim.
- [ ] **No transfer approval, and no refusal code for one.** An earlier draft of this issue refused with
      `inventory.transfer-approval-required` against an approval-required flag on the destination location. **That flag
      does not exist** — see above — so there is nothing to read and nothing to refuse, and a refusal code for an
      invented field would be a false contract the client (`E08-F02-9b`) would then render. A transfer is allowed
      exactly when the destination is in the source's allowed-destination set. If a shop later wants a second pair of
      eyes on a transfer, that is one new permission key, one route and one grant, and it is a product decision under
      **OD-13** rather than a silent flag here.
- [ ] **`in_transit` stays zero** — a one-transaction transfer is never in transit, by construction: both legs commit
      together. The column exists (`E08-F02-1`) because the ownership document names it, and a two-step
      dispatch-then-receive transfer, which is the only thing that could populate it, is **not** in the plan's #39
      blueprint and is not invented here. State that in the `Balance` type's documentation so the zero is a decision a
      reader can find.
- [ ] **`GET /api/v1/inventory/transfers/{transferGroupId}`** — the pair as one object: item, both locations, the base
      quantity, the reason code, the actor, the instant, and both ledger entry identifiers. Answered by reading the two
      entries, with no third record to keep in step. `inventory.record_movement`, `RateLimitPolicyNames.DefaultUser`,
      `RequestTimeoutPolicies.Read`, `.ScopedToResource(InventoryResourceKinds.TransferGroup, "transferGroupId")`;
      another branch's transfer reads **404**. `unit_cost` is not on this payload (it is not on a transfer entry at
      all).
- [ ] **`InventoryResourceKinds.TransferGroup = "inventory.transfer_group"`** and an `IResourceScopeResolver` answering
      the branch from either leg — they always share it, and a check constraint is not available for a cross-row rule,
      so the poster asserts it.
- [ ] Matrix rows for the two routes in `docs/security/permission-matrix.md` section 5, the `{transferGroupId}`
      `identifier-editing` entry in `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`, and the regenerated
      `docs/api/openapi.v1.json` (`TAILOR360_WRITE_OPENAPI=1 dotnet test --project
      tests/Tailor360.ContractTests/Tailor360.ContractTests.csproj`).
- [ ] Amend the T6 row of `docs/architecture/sequences/stock-reservation.md` section 4 with the group-identifier design
      and the `in_transit` note, under that file's section 10 maintenance rule.
- [ ] **No migration.** `transfer_group_id` is already a column; there is no transfer table by design.

## Out of scope

Cross-branch transfers. `module-ownership.md` section 5.7 scopes a location to a branch and #193 validates destinations
within it; a transfer between branches is a custody and an ownership question (`docs/IMPLEMENTATION_PLAN.md` Section 8,
`### #37`, gives cross-branch movement its own `from_branch_id`/`to_branch_id` model and a transfer-scoped
authorisation), and inventing one here would be inventing a control. A two-step dispatch-then-receive transfer and
anything that would populate `in_transit`. Any approval of a transfer — there is no field and no key for one, as above.
The transfer screen is `E08-F02-9b`. Stocktake adjustments are #40.

## Acceptance criteria

- [ ] An Inventory Clerk holding `inventory.record_movement` transfers a quantity between two locations of the branch
      over HTTP; exactly two ledger entries exist with the same `transfer_group_id`, equal and opposite base quantities,
      the source balance falls by it, the destination rises by it, the branch total is unchanged, and `in_transit` is
      zero on both rows.
- [ ] **No half transfer (the parent's third acceptance criterion):** a transfer whose destination leg fails — a retired
      destination location, a destination outside the allowed set, a destination in another branch — leaves **no**
      ledger entry at all and **both** balances unchanged. Proved for a validation failure and for a database-level
      failure inside the same transaction.
- [ ] `BalanceRebuild` folds the two entries back to exactly the two balances afterwards, so a transfer cannot drift the
      cache (INV-STK-03).
- [ ] **Negative:** a destination not in the source's allowed set is refused with
      `inventory.transfer-destination-not-allowed`; the same source and destination is refused; a quantity greater than
      the source's `available` is refused with `inventory.insufficient-stock` and posts nothing, including when the
      shortfall is caused by a reservation rather than by `on_hand`; a caller without `inventory.record_movement` is
      refused 403 and audited; another branch's `{transferGroupId}` reads 404; a replayed `Idempotency-Key` returns the
      first transfer and posts no second pair.
- [ ] **Exception:** a destination that was in the allowed set when the form was loaded and has since been retired, or
      removed from the set, is refused at post time with `inventory.transfer-destination-not-allowed` and nothing is
      posted — the server is the authority and a stale client set does not become one.
- [ ] Concurrency: two simultaneous transfers of the same item between the same two locations in opposite directions
      both complete or refuse cleanly, with no deadlock and with the two balances consistent afterwards — the
      deterministic lock order is what makes that true.
- [ ] Both routes declare exactly one permission and one rate-limit policy, the command carries the audit filter and
      idempotency, and the read declares a resource scope (ARCH-007, ARCH-008, ARCH-017, ARCH-023). `dotnet ef
      migrations has-pending-model-changes` reports nothing pending.

`docs/nfr/data-classification.md` section 5.9 — **Confidential**. This child adds no table and no column; the new items

## Migration and rollback

**No migration**, and that is a design claim rather than an omission: a transfer is the balanced pair of ledger entries
sharing `transfer_group_id`, and `module-ownership.md` section 5.7 lists no transfer table. The evidence is `dotnet ef
migrations has-pending-model-changes` reporting nothing pending for the Inventory context and `migrate --dry-run`
reporting no change. Rollback is therefore code-only: the previous tag serves the previous routes and the ledger rows
the new routes wrote remain valid entries of types the previous release already understood.
