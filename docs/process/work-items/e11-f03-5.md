Sub-issue of #49. Two edges of the feedback loop are unbuilt and have no home in any sibling: the invitation that
goes out when a delivery is confirmed, and the closure confirmation the customer gets when the case is shut. Both are
named in `docs/prd/exceptions.md` section 4.4 — "Closing it emits `ServiceRecoveryClosed`, which becomes a closure
confirmation to the customer on their preferred consented channel; where no consented channel exists, the send is
suppressed and audited rather than skipped invisibly" — and in `docs/prd/state-transitions.md` line 132, where
`DeliveryConfirmed` produces "customer notification; feedback invitation on the consented channel". The third piece is
the clock: #213 ships the escalation *operation* and its per-rung idempotency but nothing that calls it, and
`src/Hosts/Tailor360.Worker/Jobs/` has no feedback job. This slice is those three: two outbox handlers and one
worker job. It adds no HTTP route and no table.

## What is already built (do not re-build)

- `src/Platform/Tailor360.Platform.Persistence/Outbox/IOutboxMessageHandler.cs` — the consumer mechanism:
  `EventType`, `HandlerName`, `Schema` and `HandleAsync(OutboxDelivery, ct)`. Its contract is binding and easy to
  get wrong — **stage writes, never call `SaveChangesAsync`**: the dispatcher opens the transaction, calls the
  handler, adds the inbox row and saves both together, which is what makes a redelivery a no-op. `Schema` must be
  `notifications`, the schema the writes land in.
- `src/Modules/Catalog/Tailor360.Modules.Catalog.Infrastructure/Reconciliation/CatalogReconciliationHandlers.cs` —
  the worked example of a module consuming another module's events: one handler per event type, each with its own
  `HandlerName` because the inbox de-duplicates on it, and the payload read as JSON rather than through the
  publisher's record where only a field or two is needed.
- `src/Hosts/Tailor360.Worker/Jobs/DispatchExceptionExpiryService.cs` — **copy this shape exactly**:

## What is missing

- No handler consumes `custody.delivery-confirmed.v1`, so no invitation is ever raised.
- No handler consumes `notifications.service-recovery-closed.v1`, so the closure confirmation EX-11 promises the

  the escalation ladder exists to prevent.

## Scope

- [ ] `Infrastructure/Feedback/FeedbackInvitationHandler.cs` — `EventType = "custody.delivery-confirmed.v1"`,
      `HandlerName = "notifications.feedback_invitation"`, `Schema = notifications`. Reads the order identifier from
      the payload, resolves the customer and the branch through `IOrderSnapshotQuery`, then: checks
      `feedback_requests` consent and the allowed channels and language through #209's gate, issues the feedback
      token through **#213's issue operation**, and raises one `notification_intents` row against the invitation
      template. **The token's time-to-live is an open decision, recorded below** — do not read it from
      `service_recovery_policies` unless #213 actually put a field there: plan line 2098 lists that row's fields as
      "rating threshold, automatic case on explicit alteration request, owner role, due time in business hours,
      escalation ladder", and a time-to-live is not among them. Every refusal — no consent, no
      allowed channel, quiet hours, already invited — is a `suppressions` row with its reason, never a silent drop.
- [ ] **One invitation per order, not per garment — and that is a deviation from a product document which this
      pull request corrects rather than leaves to disagree.** `docs/prd/state-transitions.md` line 132 (the
      whole-order doorstep row) **and** line 133 (the per-garment row, which leaves the order at `in_production`)
      *both* list "customer notification; **feedback invitation on the consented channel**" among their effects, so
      read literally the document asks for an invitation per garment handover. That cannot be what is wanted:
      `docs/prd/glossary.md:242` defines Feedback as "the customer's rating and comments on **a delivered order** —
      overall, fit, stitching quality, design match, timeliness — captured through a one-time feedback link with a
      single edit window", which is one response per order across five dimensions and not one per garment; and
      `docs/prd/walkthroughs.md` line 493 shows a three-garment order receiving exactly one invitation.
      **Default in force**: raise the invitation only when `OrderSnapshot.DeliveredAt` is set — the whole order has
      been handed over — with the order identifier as the de-duplication key, so a five-garment order handed over in
      five visits invites the customer once. **Amend line 133 of `docs/prd/state-transitions.md` in this pull
      request** so the invitation follows the order's delivery rather than the garment's, citing the glossary as the
      reason. That is the route `CLAUDE.md` section 8 prescribes — correct the document, never work around it — and
      it is a one-line documentation fix rather than an architecture decision record, because no decision changes:
      the row was describing the event's effects, not choosing an invitation policy. The question is also recorded
      below in case the owner does want a per-garment invitation.
- [ ] `Infrastructure/Feedback/ServiceRecoveryClosureHandler.cs` — `EventType =
      "notifications.service-recovery-closed.v1"`, `HandlerName = "notifications.service_recovery_closure"`. Raises
      one closure-confirmation intent on the customer's preferred consented channel, against the closure template.
      The variables are the order display number and the **configured resolution code's display text** — never the
      words the customer wrote, which plan line 1613 and `IAlterationRequests`' own remarks both forbid crossing any
      boundary. No consented channel means a `suppressions` row plus an audit event, per `exceptions.md` 4.4.
- [ ] `src/Hosts/Tailor360.Worker/Jobs/ServiceRecoveryEscalationService.cs` —
      `[WorkerJob("notifications.service_recovery_escalation", WorkerBranchScope.Organisation)]` (it sweeps every
      branch's overdue cases, which `WorkerBranchScope.None` would not describe), under a lease, bounded by a batch
      size, calling #213's escalation operation for each case whose current rung is due. **`Organisation` is valid
      for a system job and does give cross-branch reach — verified, so do not downgrade it to `None` out of

      `BatchSize = 200` — which are implementation sizing and not product decisions; the rung due times are the

- [ ] One line in `src/Hosts/Tailor360.Worker/Program.cs` registering the hosted service, and the handler

## Acceptance criteria

- [ ] A `custody.delivery-confirmed.v1` message for a fully delivered order whose customer has granted
      `feedback_requests` consent leaves exactly one `notification_intents` row against the invitation template,
      carrying a resolvable `feedback` link — asserted by publishing the outbox row and running a dispatcher cycle,
      not by calling the handler directly.
- [ ] The same message redelivered leaves the intent count at one (the inbox row), and a second
      `DeliveryConfirmed` for another garment of the same order adds none (the de-duplication key).
- [ ] Negative: a customer whose `feedback_requests` consent is `NeverAsked`, `Declined` or `Withdrawn` gets no
      intent and exactly one `suppressions` row naming the reason — the three of the four `ConsentStatus` values for
      which `ConsentState.IsGranted` is false. The test covers all three separately, because `Withdrawn` "stays
      separate from `Declined` across the boundary" in the contract and a gate that collapsed them would be
      untestable. A fourth case: `CommunicationPreference.HasBeenRecorded` false — consent granted but no channel
      ever recorded — is also a suppression with its own reason, since 5.14's "necessary to perform the service"
      does not extend to a channel nobody chose.
- [ ] Negative: a `DeliveryConfirmed` for one garment of an order still `in_production` raises no invitation and no
      suppression, because nothing was refused — the order has not been delivered yet.
- [ ] A `notifications.service-recovery-closed.v1` message raises one closure-confirmation intent whose rendered
      variables contain the resolution code's display text and **not** the customer's comment — asserted over the
      rendered body.
- [ ] Exception: a closure for a customer with no consented channel writes a `suppressions` row and an audit event
      and no intent; the case stays closed, because the confirmation is not what closes it.
- [ ] The escalation job, run twice in the same window, raises the rung's notification once: the job is the clock
      and #213 owns the idempotency, and the test proves the pair behave.
- [ ] The job declares `[WorkerJob(...)]` with its branch scope and the permissions it exercises (ARCH-021), takes
      its lease (ARCH-020 — only the worker and command-line hosts may use `IWorkerScopeFactory`), and a second
      instance running concurrently performs no duplicate work.
- [ ] This slice adds no route: the contract tier's endpoint inventory and `docs/api/openapi.v1.json` are unchanged.

Notifications owns every row written. Events **consumed**: `custody.delivery-confirmed.v1` (#48) and

sanctioned mechanisms. Events **published**: none. Other modules touched: `Orders.Contracts.IOrderSnapshotQuery`

ARCH-004). The worker host references the module's `Infrastructure` and `Application`, which ARCH-006 permits and
ARCH-012 confines to a host. No table outside `notifications` is read or written (ARCH-005, MO-2).
Threat model: the new surface is an outbound message containing a credential (the link). The controls are #211's
hashing and redaction and #209's consent gate; nothing new is introduced, and that is worth stating in the pull
request rather than claiming a new model.

## Migration and rollback

No table and no column. The two template rows are **seed data**, applied by `init-reference-data`, not schema.
`migrate --dry-run` reporting no change is the evidence. Rollback is a redeploy of the previous tag: the handlers
disappear, the inbox rows they wrote stay, and a redelivered message finds no handler — which
`IOutboxMessageHandler`'s own remarks call normal ("an event with no handler is not an error").
