Sub-issue of #57, **and the gap the first draft of this decomposition missed entirely.** The parent's blueprint
(`docs/IMPLEMENTATION_PLAN.md` Section 8, #57) requires that an approved erasure "**clears** `garment_jobs.
measurement_snapshot`, design notes and media links on jobs whose statutory retention (delivery + configured period)
has elapsed, records the cleared classes on the request". Nothing in #57's other children touches Orders: the
Customers participant deletes `customers.measurement_versions` and `measurement_version_values`, and explicitly leaves
the frozen job-level copies alone. **Those copies are Sensitive Personal data** —
`docs/nfr/data-classification.md` section 5.1 classifies 5.4 "Measurements — drafts, versions, snapshots, sheets" as
**Sensitive Personal**, owned by "Customers/Measurements, **Orders/Workflow**" — so without this child the privacy
lifecycle demonstrably does not erase a person's measurements: it erases one of the two places they are held.

The Orders schema is built and present in this working copy: `20260911141153_InitialOrdersSchema.cs` creates
`orders.garment_jobs`, `orders.measurement_snapshots` and `orders.design_snapshots`, and
`orders.job_snapshots_are_immutable()` refuses every `UPDATE` to a snapshot once its job has left `Confirmed`. **That
trigger is why this is its own child**: clearing a snapshot on a delivered job needs one expand-only migration in the
`orders` schema to add the erasure arm, and the repository already has the exact precedent for that arm in
`customers.customer_merges_no_rewrite`.

order-workflow threat model that owns this area is scheduled by **#56**'s `[E14-F01a-4]` child

## Migration and rollback

One expand-only migration, EF name `AddSnapshotErasureArm`, in the **`orders`** schema — which is why it cannot be
folded into `[E14-F02-3]`, whose one migration is in `customers`. It changes **no table, no column, no index and no
constraint**: it replaces one trigger function with `CREATE OR REPLACE FUNCTION`, widening what it accepts. The
previous release therefore tolerates it completely — release N never performs the newly permitted update, so the wider
arm is simply unused. `Down` restores the previous function body verbatim, which the migration must carry in full
rather than reconstructing; re-applying must be clean with `dotnet ef migrations has-pending-model-changes` reporting
none. Per `docs/dev/migrations.md`, with the register row and **two** live-database transcripts: the permitted
redaction accepted on a delivered job, and an ordinary `UPDATE` on the same row still refused.

**The clearing itself is not reversible and is not a migration.** It is a command, gated by an approved request, and the
backup treatment of `docs/nfr/data-classification.md` section 7 applies: the data survives in backups until those
expire, and a restore replays the requests executed after the restore point (**#60**).
