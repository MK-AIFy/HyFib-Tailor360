## Acceptance criteria

- [ ] An Owner creates a definition over HTTP, starts a draft version, `PUT`s the **six**-phase graph taken from
      `docs/prd/workflows/blouse.md` section 2.1 (Cutting, Specialist work, Stitching, Finishing, QC, Ready — the
      count E06-F02-1 settles, and not plan Section 8's seven, which prefixes an Intake phase that cannot be a job
      phase), reads it back and receives the same graph — end to end through the
      API, with no direct database access.
- [ ] A second `POST .../versions` with the same `Idempotency-Key` replays the first draft rather than creating a
      second one, and a `PUT` with a stale `If-Match` is refused with `409` and leaves the stored draft untouched.
- [ ] Every route this issue adds declares a permission, exactly one rate-limit policy, an audit action on each
      write, and either a resource scope or a recorded reason for naming none (ARCH-007, ARCH-008, ARCH-017,
      ARCH-023), and has a matching row in section 5 of `docs/security/permission-matrix.md`.
- [ ] **Negative:** a caller holding `catalog.edit` but not `catalog.workflows.edit` is refused `403` with
      `security.forbidden`; an unauthenticated caller receives `401` with `security.authentication-required` — the
      answers `matrix.yaml` already defines, not new ones.
- [ ] **Negative:** a `PUT` whose graph has an unreachable phase and a phase with no permitted role comes back as a
      single RFC 9457 document listing both findings with their phase codes, and the draft is **not** saved.
- [ ] **Exception:** a `PUT` against a version that is already published is refused with a conflict naming the
      status, not a `404` and not a silent no-op; the published row is byte-identical afterwards.
