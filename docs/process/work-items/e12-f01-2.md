Sub-issue of #50. The client half of the blueprint's promise that display preferences are "stored server-side in
`identity.user_preferences` and applied at login so shared devices do not leak or lose settings". It is not built,
and the code says so in its own comments: `clients/pwa/src/app/preferences.ts` lines 15-35 declare the
`DisplayPreferencesStore` interface and state that "the only implementation today is the local stub below", and
`clients/pwa/src/main.tsx` wraps the application in `DisplayPreferencesProvider` with no `store` prop, so the stub
is what runs — even though `clients/pwa/src/auth/types.ts:101-108` already types `AccountPreferences` and
`GET /api/v1/me` already returns it. The consequence on a shared counter tablet is the one the blueprint names: a
Tailor who sets 150% text hands the next person that screen, and loses it on the next device.

**This slice is the four document-level display preferences only — theme, text size, density and reduced motion.**
The account **locale** reaching `AppIntlProvider` and `<html lang>` is **e12-f01-2b**, which depends on this one:
that is a different subsystem (`src/i18n/`), it is the one piece with a real provider-composition design decision,
and bundling it here is what would make this session overrun. Everything below is written on that split.

## What is already built (do not re-build)

- `clients/pwa/src/app/preferences.ts` — the `DisplayPreferencesStore` interface (`read()`, `write()`, both
  asynchronous precisely so a network store can replace the stub), `DISPLAY_PREFERENCES_STORAGE_KEY`, the parser that
  rejects unrecognised values, and `createLocalDisplayPreferencesStore()`. Unit-tested. The interface is the contract
  this slice implements against; do not change its shape.
- `clients/pwa/src/app/DisplayPreferencesProvider.tsx` — applies the preferences to `<html>`, takes a `store` prop
  documented as the drop-in point, updates the document first and writes afterwards, and swallows a failed write on
  purpose. `clients/pwa/src/app/displayPreferencesContext.ts` carries the context.
- `clients/pwa/src/design-system/foundations/displayPreferences.ts` — `DisplayPreferences` is
  `{ theme, textSize, density }`; `applyDisplayPreferences` writes `data-theme`, `data-text-size` and `data-density`,
  and removes `data-theme` for `system`. `foundations/types.ts` holds `THEME_PREFERENCES`
  (`system | light | dark | contrast`), `TEXT_SIZE_PREFERENCES` (`100 | 125 | 150`) and `DENSITIES`.
  `src/styles/themes.css` already keys every palette and scale on those attributes — there is no styling work here.
- `clients/pwa/src/components/layout/DisplayPreferencesPanel.tsx` with its test and story, and the
  `/settings/display` route in `clients/pwa/src/app/router.tsx:168`, deliberately outside `RequireSession` because
  somebody needs the high-contrast theme *in order to read the sign-in screen*.
- `clients/pwa/src/auth/SessionProvider.tsx`, `sessionContext.ts` and `useSession.ts` — `useSession()` gives
  `status` (`loading | anonymous | active | unavailable`) and `user`; `useCurrentUser()` throws outside a session.
  `clients/pwa/src/auth/types.ts` types `AccountPreferences` as `locale`, `timeZoneId`, `theme`, `density`,
  `reducedMotion`, `landingRoute`.
- `clients/pwa/src/auth/apiClient.ts` — `apiRequest`, the `X-Correlation-Id`, `X-Client-Version` and anti-forgery
  header injection, the problem-details reader and the session-challenge path. Every call in this slice goes through
  it; `clients/pwa/CLAUDE.md` section 6 forbids a second data-fetching path.
- `clients/pwa/src/components/layout/DisplayPreferencesPanel.tsx` uses **`RadioGroup`** from
  `clients/pwa/src/design-system/components/forms/RadioGroup.tsx` with `ChoiceOption` from
  `forms/controlTypes.ts` — three groups, built from `THEME_PREFERENCES`, `TEXT_SIZE_PREFERENCES` and
  `DENSITIES`, with the message ids `layout.display.theme.*`, `layout.display.textSize.*` and
  `layout.display.density.*`. It does **not** use `SegmentedControl`. The reduced-motion control added here is
  `forms/Switch.tsx`, which already implements `FieldProps`.
- `clients/pwa/src/components/states/` — `RetryableError.tsx`, `OfflineBlockedAction.tsx`, `EmptyState.tsx`,
  `useNetworkState.ts` and `problemDetails.ts`, each with a test and a story. Use them as they are.
- Test harness: `clients/pwa/src/auth/testing/fixtures.ts` exports `stubFetch`, `jsonResponse`,
  `problemResponse`, `noContent`, `aCurrentUser`, `aSessionExpiry` — the pattern to copy is
  `clients/pwa/src/auth/RequireSession.test.tsx`, which renders `AppIntlProvider` + `MemoryRouter` +
  `SessionProvider` over a stubbed `fetch` and calls `forgetAntiforgeryToken()` and
  `setSessionChallengeHandler(null)` in `beforeEach`/`afterEach`. Note that
  `clients/pwa/src/design-system/testing/renderWithProviders.tsx` supplies **only** `AppIntlProvider` and display
  preferences — no session and no router — so it cannot render anything in this slice that reads the session. The
  admin harness `clients/pwa/src/admin/testing/storyTransport.tsx` is **not** the right one either: this is not an
  admin screen.

## What is missing

- A server-backed `DisplayPreferencesStore`. Nothing in `clients/pwa/src` calls a preferences endpoint.
- Any connection between the session and the applied preferences: the provider sits **outside**
  `SessionProvider` in `main.tsx`, reads the device stub once on mount, and never re-reads when a different person
  signs in on the same device.
- Any honouring of `AccountPreferences.reducedMotion`: `src/styles/global.css:87` and `src/styles/themes.css:307`
  respond to the operating system's `prefers-reduced-motion` only, so a person whose device cannot express it has no
  way to ask. `DisplayPreferences` in `design-system/foundations/displayPreferences.ts:19-30` has three members —
  `theme`, `textSize`, `density` — and no fourth.

## Scope

- [ ] `createServerDisplayPreferencesStore()` in `clients/pwa/src/app/preferences.ts`, implementing the existing
      two-method interface against `GET /api/v1/me` and `PUT /api/v1/me/preferences` through `apiRequest` from
      `clients/pwa/src/auth/apiClient.ts` — read from the session's already-loaded user rather than issuing a
      second `GET`.
- [ ] **The write is a full replacement and must send all seven members**, because that is what
      `PUT /api/v1/me/preferences` accepts (e12-f01-1; `docs/api/conventions.md` section 2.1). Four of them are
      this slice's: `theme`, `textSize`, `density`, `reducedMotion`. The other three — `locale`, `timeZoneId`,
      `landingRoute` — are sent back **unchanged, exactly as `GET /api/v1/me` returned them**. Changing the
      applied locale is e12-f01-2b; `landingRoute` is read by e12-f01-3 and written by #25. Dropping or
      defaulting any of the three would silently reset a person's language or landing screen, which is the one
      way this slice can do real harm.
- [ ] The two mapping tables, in one place, with the server vocabulary on one side and the document attributes on
      the other: theme `System|Light|Dark|HighContrast` ↔ `system|light|dark|contrast`; text size
      `Standard|Large|Larger` ↔ `100|125|150`; density `Comfortable|Compact` ↔ `comfortable|compact`. An
      unrecognised value from the server falls back to the default rather than throwing, the way the existing
      parser does.
- [ ] Provider composition in `clients/pwa/src/main.tsx` so that a signed-in account's preferences are applied and
      an anonymous device still has a working panel. The order in `main.tsx` today is
      `AppIntlProvider` → `DisplayPreferencesProvider` → `SessionProvider` → `RouterProvider`, and the display
      provider therefore cannot call `useSession()`. **Swap the two inner providers** —
      `AppIntlProvider` → `SessionProvider` → `DisplayPreferencesProvider` → `RouterProvider` — which is the
      smallest change that lets the display provider read the session, keeps `SessionProvider` inside
      `AppIntlProvider` (it renders `ReauthenticationDialog` with `FormattedMessage`, so it must stay there), and
      leaves exactly one `IntlProvider` in the tree. `SessionProvider` must not depend on display preferences, and
      does not. Update `clients/pwa/src/App.test.tsx:37`, which composes the same providers, in the same change.
- [ ] Re-read on identity change: when `useSession().user?.userId` changes, the applied preferences are replaced,
      and when the session becomes `anonymous` they revert to `DEFAULT_DISPLAY_PREFERENCES`. Nothing of the
      previous person's choice survives their sign-out. While `status` is `loading` the defaults are applied and
      the panel's controls are disabled, so the first paint is never the previous person's theme.
- [ ] Stop persisting a signed-in person's display preferences on the device: `createLocalDisplayPreferencesStore`
      remains the **anonymous** store only, and the signed-in path neither reads nor writes
      `DISPLAY_PREFERENCES_STORAGE_KEY`. The locale's storage key is e12-f01-2b's to deal with; leave
      `clients/pwa/src/i18n/locales.ts` alone here.
- [ ] The two stale comments naming #25 as the owner of the server store
      (`clients/pwa/src/app/preferences.ts` lines 26-29 and `clients/pwa/src/main.tsx`) are corrected by
      **e12-f01-1**, which merges first. If they are still there, correct them here and say so.
- [ ] `DisplayPreferencesPanel` saves a change for a signed-in person and says what happened: a failed save is a
      `RetryableError` with a Retry that keeps the choice applied for this session, never a discarded change and
      never a toast (`clients/pwa/CLAUDE.md` section 4 and plan Section 4.6 both forbid a toast for an actionable
      error). Offline, saving is an `OfflineBlockedAction` — a preference is not a queued command.
- [ ] Reduced motion as a fourth member of `DisplayPreferences`: `reducedMotion: boolean` on the interface, a
      `REDUCED_MOTION_ATTRIBUTE = 'data-reduced-motion'` written by `applyDisplayPreferences` and read back by
      `readDisplayPreferences`, a default of `false` in `DEFAULT_DISPLAY_PREFERENCES`, the parser in
      `preferences.ts` accepting and rejecting it like the other three, the CSS honoured next to the existing
      `prefers-reduced-motion` blocks at `src/styles/global.css:87` and `src/styles/themes.css:307`, a `Switch`
      control in the panel, and the value carried in the `PUT`. The operating-system preference still wins when it
      is set: the attribute adds a way to ask, it never takes one away. Adding the member changes every
      construction of `DisplayPreferences` —
      `rg -n "DEFAULT_DISPLAY_PREFERENCES|createInMemoryDisplayPreferencesStore\(" clients/pwa/src` lists them,
      and `AppShell.test.tsx`, `DisplayPreferencesPanel.test.tsx`, `App.test.tsx`, the three stories and
      `JourneyFrame.tsx` are the call sites to expect.
- [ ] **The save outcome is announced by the panel itself, not through the shell.**
      `useShellStatus()` (`clients/pwa/src/components/layout/useShellStatus.ts`) **throws** outside a
      `ShellStatusProvider`, and the panel is rendered standalone by `DisplayPreferencesPanel.test.tsx` and
      `DisplayPreferencesPanel.stories.tsx` and is reachable anonymously at `/settings/display`. So the panel owns
      a `role="status"` region of its own for "Saved" / "Not saved", and nothing in this slice calls
      `announceAutosave`. Wiring the panel to the shell channel would break two existing files and an anonymous
      route; do not do it.
- [ ] Stories for the panel in each state — saved, saving, failed, offline, anonymous — plus the pseudo-locale
      story every component owes (`.storybook/preview.tsx` documents why), and the `ta-IN` toolbar entry left
      alone. These are ordinary component stories in
      `clients/pwa/src/components/layout/DisplayPreferencesPanel.stories.tsx`, driven by an injected store and a
      forced network state; they are **not** admin screens, so the deliberate no-offline-story rule recorded in
      `clients/pwa/src/routes/admin/catalogScreens.stories.tsx` does not apply and neither does
      `storyTransport.tsx`. `JourneyFrame` cannot be combined with them — it brings its own `MemoryRouter`.

## Out of scope

The endpoint and the `text_size` column are **e12-f01-1**, which must merge first. **The account locale, the intl
provider and `<html lang>` are e12-f01-2b** — this slice sends the stored locale back unchanged and renders in
whatever locale `AppIntlProvider` already resolves. A **language picker** is built by neither: `ta-IN` becomes a
selectable interface language only when the eight criteria of the Tamil enablement gate in
`docs/nfr/accessibility-localisation.md` section 10.3 pass, and today `clients/pwa/src/i18n/ta-IN.ts` says in its
own header that the catalogue awaits native-speaker review. Administering somebody else's preferences is #25. The
shell's navigation is **e12-f01-3**; the home launcher is **e12-f01-3b**.

## Acceptance criteria

- [ ] A Tailor whose account stores the high-contrast theme, 150% text and compact density signs in on a counter
      tablet and gets those three applied as soon as the session resolves and before any screen behind
      `RequireSession` paints — asserted through the rendered
      `<html>` attributes, not by reading the provider's state.
- [ ] The same person signs out; the document reverts to the defaults, and the next person to sign in on that
      device gets their own stored preferences and never the previous person's. This is the criterion the slice
      exists for.
- [ ] A change made in the panel is applied on the next frame and persisted to the account; reloading the page
      keeps it, and signing in on a second device shows it.
- [ ] A save sends all seven members and the three it does not own are byte-for-byte what `GET /api/v1/me`
      returned: asserted on the recorded request body from `stubFetch`, because a dropped `locale` would reset a
      person's language and nothing on screen would show it.
- [ ] Negative: the `PUT` fails with a 500-class problem — the choice stays applied for this session, a
      `RetryableError` names what did not save and offers Retry, no typed state is lost, and nothing is written to
      `localStorage` for the signed-in person.
- [ ] Negative: the device is offline — the panel shows the `OfflineBlockedAction` wording
      ("Needs connection — this will not be queued") rather than appearing to save.
- [ ] Negative: `GET /me` answers preferences containing `"theme": "Sepia"` and `"textSize": "175"` — the shell
      applies the default for each unrecognised value and renders, rather than throwing or blanking; the next save
      sends the defaults it actually applied, not the values it could not read.
- [ ] Exception: an anonymous person sets the high-contrast theme at `/settings/display` in order to read the
      sign-in screen, then signs in to an account that stores `system` — the account wins, and the device-local
      choice does not survive into the session. The behaviour is deliberate and is asserted, because the opposite
      reading is defensible and must not be introduced by accident later.
- [ ] Every new or changed component keeps its axe assertion green through
      `clients/pwa/src/design-system/testing/axe.ts`, and the panel's stories render in the pseudo-locale without
      clipping.

## Modules, contracts and events

Client only. It consumes two Identity routes over HTTP — `GET /api/v1/me` and `PUT /api/v1/me/preferences` — and no
other module's surface. The generated types come from `clients/pwa/src/api/schema.d.ts`, which **e12-f01-1**
regenerates from `docs/api/openapi.v1.json` when it publishes the operation; this slice runs `pnpm --dir clients/pwa
generate:api:check` and expects no change. If it does report drift, regenerate here and say so in the pull request —
that file is shared with every other client lane in flight, so an unexplained diff in it is a merge problem for
somebody else. No module boundary is crossed in `src/` (ARCH-003, ARCH-004 are not engaged by client code).
