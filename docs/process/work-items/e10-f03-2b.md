## Why this is blocked, and what unblocks it

`docs/architecture/module-ownership.md` section 5.7 lists exactly seven published Inventory events:
`inventory.stock-reserved.v1`, `inventory.stock-released.v1`, `inventory.stock-consumed.v1`,
`inventory.purchase-received.v1`, `inventory.low-stock-raised.v1`, `inventory.low-stock-cleared.v1`,
`inventory.stocktake-posted.v1`. The plan's #39 blueprint gives `ledger_entries` eleven movement types — `opening`,
`purchase_receipt`, `reservation`, `release`, `issue`, `consumption`, `return`, `transfer_out`, `transfer_in`,
`wastage`, `adjustment` — and its **Events** line publishes only `StockReserved/Released/Consumed` and
`PurchaseReceived`. **No published event carries a wastage, return, issue, adjustment or transfer movement.**
Reporting may not read `inventory.ledger_entries` (ARCH-005, ARCH-011, module-ownership section 5.7, rule MO-2), and
`Inventory.Contracts` publishes only `IStockBalanceQuery` and `IValuationQuery`.

So this child needs Inventory to publish an **additive** event, and that is a dependency on #39 rather than something
to work around here. The shape it needs, so that #39's own decomposition can include it rather than this child
inventing it:

> One event per posted ledger entry, carrying the entry identifier, the organisation, the branch, the item, the >
location, the movement type (the eleven-member vocabulary above), the signed base quantity, the reason code, the >
garment job and phase where one is named, the purchase or stocktake reference where one is named, >
`corrects_entry_id` for a compensating entry, and the instant — and **no unit cost**, which stays Confidential >
behind `IValuationQuery` exactly as `inventory.stock-consumed.v1` does. Additive, a new event type, never a > breaking
change to an existing `v1` (`docs/architecture/conventions.md` section 5.5), with its JSON Schema and > example under
`docs/integration/events/`.

**Do not start this child until that event exists.** The remedy if #39 merges without it is an Inventory follow-up
issue carrying exactly the paragraph above — **never** a cross-schema read, never a guessed field name, and never a
second Inventory subscription invented inside Reporting. Nothing else in this decomposition depends on this child:
`e10-f03-5` reports its wastage component as unavailable with reason `no_wastage_movement_published` until this
merges, and `e10-f03-2`'s aging metric records the same exclusion in its dictionary entry.
