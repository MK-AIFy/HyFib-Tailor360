Sub-issue of #33. E06-F02-4 creates the `job_phases` rows and leaves every one of them `NotStarted`; this slice is
the everyday shop-floor action that moves them. `docs/prd/state-transitions.md` lines 186 to 212 give the phase state
machine and line 221 gives the rule in one row — "Phase start, pause, resume, complete … job version concurrency
token matches … Two concurrent scans cannot double-complete a phase; the loser sees a conflict with the current
state. An out-of-order transition is rejected against the pinned version's transition graph". None of that exists:
there is no `JobPhase` transition method, no route and no `orders.job-phase-changed.v1` event — and
`Contracts/Events/GarmentJobEnteredProduction.cs` says so in prose: "Phase state is issue #33's, and
`orders.job-phase-changed.v1` is not declared here, because the repository's rule is that an event lands with the
issue that raises it."

## Acceptance criteria

- [ ] A Tailor starts, pauses, resumes and completes the Cutting phase over HTTP; each response carries the
      server-stamped instant and the new status; `GET .../phases` shows the timings; one
      `orders.job-phase-changed.v1` outbox row exists per accepted transition, each naming the previous status.
- [ ] Completing the last non-skippable phase leaves the job `InProduction` and **not** `Ready`, because readiness is
      the gate's verdict and the gate needs QC, evidence, hold and custody facts this slice does not have (INV-JOB-07).
      A test asserts that `garment_jobs.is_ready_for_delivery` is unchanged and that no code path in this slice writes
      `GarmentJobStatus.Ready`. Where #34's `IReadyGateRecomputation` is registered, the handler calls it exactly once
      per completing transition — asserted with a test double that counts calls.
- [ ] **Negative, and this is the parent's third acceptance criterion:** two simultaneous `complete` requests on one
      phase produce exactly one completion. The loser receives `409` with `OrdersErrors.ConcurrentChange` and a body
      naming the phase's **current** state, and exactly one outbox row exists. Proven with two genuinely concurrent
      requests, not two sequential ones.
- [ ] **Negative:** replaying an accepted transition with the same `Idempotency-Key` returns the first outcome and
      produces no second outbox row; the same key with a different body is refused per the platform's idempotency
      contract.
- [ ] **Negative:** starting Finishing while Stitching is `NotStarted` is refused against the pinned graph, and the
      problem detail names Stitching. Starting a phase of a job in another branch returns `404`; a caller without
      `orders.phase_transition` receives `403` `security.forbidden` and the denial is audited.
- [ ] **Exception:** `pause` requires a reason and `skip` is refused on a phase whose copied `is_skippable` is false;
      a `resume` on a phase that is `InProgress` rather than `Paused` is refused with the current state, not silently
      accepted.
- [ ] The route declares a permission, exactly one rate-limit policy, a resource scope and the audit filter
      (ARCH-007, ARCH-008, ARCH-017, ARCH-023), with a matching row in section 5 of the permission matrix.
