Sub-issue of #49. The second half of the client surface, split out of [E11-F03-6] during review: the case detail
route and the three commands that make a service-recovery case movable. [E11-F03-6] ships the feature folder, the
read API module, the message family, the navigation entry and the queue; this slice adds one route to that
foundation and the writes.

**Why the split.** One session at this repository's measured rate cannot carry both routes.
`clients/pwa/src/routes/catalog/CatalogVersionEditorRoute.tsx` is 994 production lines for one route and
`CatalogDesignRoute.tsx` is 1,269; commit `5f99c6a`, which shipped the catalogue design screens, added 3,192
production lines across 21 files. A queue with two tabs, filters and a metrics strip plus a case detail with a
timeline and three command dialogs, plus the API module, types, problems, a two-locale message family and a
stylesheet, estimates at 1,750–2,100 production lines against CLAUDE.md section 6's target of about 1,500. This
route alone, with its three dialogs and their forms, is roughly 700–900.

## Acceptance criteria

- [ ] A Branch Manager opens a case from the queue, assigns it to a colleague, records two contact attempts and
      closes it with a resolution; the screen afterwards shows the owner, both attempts, the resolution and the
      closing instant — walked in a Vitest journey against stubbed HTTP, with no `fetch` called from a screen and no
      direct database access.
- [ ] **Negative, and this is the one that proves the matrix**: a user holding `feedback.read` but **not**
      `feedback.manage_cases` — the Owner — sees the case in full, including the comment, and **no** assign, contact
      or close affordance. Asserted by query, not by screenshot.
- [ ] Negative: a command submitted with an empty reason is refused by the form before it is sent, with the error on
      the `reason` field and focus moved to it through `FormErrorSummary` — and the server's own
      `reason`-field error is rendered the same way if it arrives anyway.
- [ ] Negative: a `409` or `422` problem from a command renders through the feature's problem alert with the
      server's field errors mapped onto `FormErrorSummary`. **The raw `failure.message` is never rendered**, and no
      correlation identifier or exception text reaches the screen (`CLAUDE.md` security rule 3).
- [ ] Negative: with the browser offline, each of the three commands shows `OfflineBlockedAction` and sends nothing;
      the read shows `NetworkStatusBanner` and keeps the last value on screen.
- [ ] Negative: a `caseId` that answers `404` renders the not-found state, not an error — a case of another branch
      answers `404` by [E11-F03-4]'s design, so this is the same path and must read as "not yours" rather than as a
      fault.
- [ ] Negative: a command retried after a transport failure reuses the same `Idempotency-Key`, so the server replays
      the first outcome and the timeline does not gain a second contact attempt. A different user intent gets a
      different key. Asserted over the stubbed request headers.
- [ ] Exception: closing with an accepted alteration while the Orders hand-off is unregistered shows
      [E11-F03-4]'s `notifications.alteration-hand-off-unavailable` refusal as an **explained** alert saying the
      case stays open and the alteration was not recorded — not a generic failure, and not a success.
- [ ] Exception: a `PUT` of the policy refused for a stale `If-Match` is explained as "somebody changed this since
      you opened it", with a reload offered — distinct from the missing-precondition refusal, which is a defect in
      the client and should never reach a user.
- [ ] The comment is rendered on this route and nowhere else, matching the payload [E11-F03-3] returns
      (`data-classification.md` 5.14: "Free text is never shown on a public screen or a shop-floor dashboard" — a
      case detail held by the person acting on it is neither).
- [ ] `expectNoHorizontalOverflow` passes at its five default widths and at 200% zoom with no focused control
      obscured, including **with a dialog open**, which is where a bottom sheet on a 320 px viewport usually fails.
- [ ] Every date, rating and number goes through `getFormatters(locale)`; ratings render as "4 of 5" through the
      message family, never as a bare glyph. No currency appears.
- [ ] `pnpm --dir clients/pwa typecheck`, `lint`, `test`, `format:check`, `build` and `generate:api:check` all clean.
