## Scope

- [ ] **`LowStockAlert` aggregate** in `…Inventory.Domain/Alerts/` — the state machine
      `Raised → Acknowledged | Snoozed → Escalated → Cleared`, keyed for de-duplication on
      `(organisation_id, branch_id, item_id, location_id)` with **at most one open alert** per key, plus the
      verdict it was raised on, the shortfall at that moment, the quantities it was computed from, and the
      timestamps of each transition. Transitions are methods returning `Result`, refusing an illegal move — the
      shape `ReconciliationBatch.Approve` uses in
      `src/Modules/Billing/Tailor360.Modules.Billing.Domain/Payments/ReconciliationBatch.cs`. This child implements
      only `Raise`, `Refresh` (the shortfall moved while the alert stayed open) and `Clear`.
- [ ] **One migration**, `InventoryLowStockAlerts`, creating `inventory.low_stock_alerts` with a **partial unique
      index** over `(organisation_id, branch_id, item_id, location_id) WHERE state <> cleared` — which is what makes
      "fires once per meaningful state change" true under concurrency rather than by convention — **and**
      `inventory.low_stock_evaluation_state` (one row per branch: the ledger watermark, and the instant of the last
      completed evaluation, which is also the freshness field `E08-F03-6` reports). Two tables, one migration, one
      schema; expand-only; ledger row added to `docs/dev/migrations.md` in the shape of the
      `20260912180307_ReconciliationBatches` row at line 121.
- [ ] **`LowStockEvaluationService`** in `src/Hosts/Tailor360.Worker/Jobs/`, declared
      `[WorkerJob("inventory.low_stock_evaluation", WorkerBranchScope.Organisation, InventoryPermissions.ViewReports)]`
      — `DocumentRenderService.cs:19` is the precedent for `Organisation` *with* a permission ceiling and
      `OutboxDispatcherService.cs:26` for `Organisation` with none — under a lease, bounded by a batch size, and
      running on a fixed `RunInterval` engineering constant (the `DispatchExceptionExpiryService` precedent:
      `JobName`, `BatchSize = 200`, `LeaseDuration`, `RunInterval`, `PeriodicTimer`, `TryAcquireAsync` …
      `ReleaseAsync`). Per branch it reads the branch's policy, the reorder rules (#196) and the balances (#39),
      calls the evaluator, and raises, refreshes or clears — **writing nothing when the verdict has not changed**.
      Clearing happens on replenishment automatically, because a cleared verdict is just another evaluation
      (`configurable-vs-fixed.md` line 69: "Alerts already raised keep their state machine and clear on
      replenishment").
- [ ] **Evaluate on ledger movement as well as on the cadence. This is half of #40's first implementation step and
      the earlier decomposition of this parent left it out.** The blueprint
      (`docs/IMPLEMENTATION_PLAN.md` Section 9, `### #40`) reads "Worker evaluates **on ledger events and** on the
      configured cadence", so a cadence-only pass does not satisfy it: with a cadence of an hour, a replenishment
      leaves a false alert standing for an hour and an emptying bin unwarned for an hour. Implement it as a
      **watermark, not a second queue**: the pass records, per branch, the highest `ledger_entries` sequence it has
      already evaluated, in a small `inventory.low_stock_evaluation_state` row created by this child's migration
      (not a column on `alert_policies`, which is configuration a person edits). A branch whose ledger has moved
      past its watermark is evaluated on the **next pass regardless of its cadence**; a branch whose ledger has not
      moved is skipped until its cadence elapses; and only the `(item, location)` pairs the new entries name are
      re-evaluated, which is what keeps the pass inside its batch bound at the recorded steady state of 110,000
      entries a year (`docs/nfr/capacity-and-performance.md` line 159). If #39 exposes no monotonic sequence or
      timestamp on `ledger_entries` to watermark against, that is a defect raised on #39 — do not substitute a full
      re-scan of every branch on every pass.
- [ ] **Two integration events** — `inventory.low-stock-raised.v1` and `inventory.low-stock-cleared.v1` — in
      `…Inventory.Contracts/Events/`, published in the same save as the alert row, carrying identifiers, codes,
      quantities, the verdict, the branch code **and the alert policy's `targetRoles`**, and nothing else (no item
      description, no supplier, no cost: `docs/nfr/data-classification.md` section 5.9 forbids unit costs in logs,
      and `tests/Tailor360.ContractTests/IntegrationEventInventory.cs` screens payload field names for personal
      data). Add the four `docs/integration/events/` files — `<name>.schema.json` and `<name>.example.json` for
      each, the paths `IntegrationEventInventory.cs:227,231` compute.
      **`targetRoles` is on the payload for a boundary reason, not a convenience one:** the Notifications routing
      rule (`E08-F03-3b`) has to know which staff roles to address, the answer lives in `inventory.alert_policies`,
      and **no module reads another module's tables** (ARCH-005; `CLAUDE.md` section 3 — only a read contract, a
      versioned event, a confirmation-participant hook, host composition or a platform port crosses a boundary).
      Role keys are low-cardinality configuration vocabulary and **Internal**, never personal data, so they are safe
      on the wire and pass the personal-data screen. Carrying them here is what lets the routing child exist without
      inventing a second crossing mechanism or a read contract nobody else needs.
- [ ] **One endpoint**: `GET /api/v1/inventory/alerts` — the branch's open alerts, cursor-paged, filterable by
      state and by location, ordered by severity then age. `RequirePermission(InventoryPermissions.ViewReports,

- [ ] **`InventoryDbContext`** gains the new `DbSet` and its configuration; the module registration gains the

## Acceptance criteria

- [ ] A branch whose item falls below its reorder point has exactly **one** open alert after three consecutive
      worker passes with no further movement — proved by an integration test that runs the pass three times and
      counts rows, not by reading the code.
- [ ] A replenishing movement that takes available back above the reorder point plus the policy's hysteresis margin
      clears the alert on the next pass and publishes `inventory.low-stock-cleared.v1` exactly once; a movement that
      lands inside the hysteresis band leaves the alert open and publishes nothing.
- [ ] **A branch whose ledger has moved is evaluated on the next pass even though its cadence has not elapsed, and a
      branch whose ledger has not moved is skipped** — two tests: one posts a movement and runs the pass
      immediately, one runs the pass twice with no movement and counts the branches evaluated. This is the "on
      ledger events" half of #40's first implementation step.
- [ ] `inventory.low-stock-raised.v1` carries the policy's `targetRoles`, so nothing downstream ever needs to read
      `inventory.alert_policies` — asserted against the published schema file, not by inspection.
- [ ] **Negative:** two worker instances running a pass concurrently produce one alert, not two — the partial unique
      index refuses the second insert and the pass treats that refusal as "already raised", not as an error to
      retry. A test asserts it with two concurrent passes against the same branch.
- [ ] **Negative:** a caller at another branch reading `GET /api/v1/inventory/alerts` sees none of this branch's
      alerts; a caller without `inventory.view_reports` is refused `403` `security.forbidden`.
- [ ] **Exception:** a branch with **no** alert policy row is skipped with a recorded diagnostic and raises nothing
      — the policy's numbers are an open decision (`E08-F03-1`), so an unconfigured branch must not be evaluated
      against a guessed default.
- [ ] **Exception:** an item with no reorder rule at a location is never evaluated there (#196's own rule: "an item
      with no rule at a location is simply never evaluated for low stock there").
- [ ] Every published event validates against its schema file, and `IntegrationEventTests` passes with no
      personal-data field.
