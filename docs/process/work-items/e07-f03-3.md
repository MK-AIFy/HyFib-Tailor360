Sub-issue of #37. Two earlier slices refuse a contradicting scan and a rejected transfer and leave the garment with
nobody accountable for putting it right. `docs/architecture/invariants.md` INV-CDY-03 says a scan that contradicts
current custody "is recorded and **opens a reconciliation case**; it never silently succeeds and never silently
fails", and `docs/prd/exceptions.md` **EX-13** names the six case types and the repair: "a new `scan_events` row with
`action = CORRECTION` linked to the corrected event and the case". None of it exists — `grep -rn "reconciliation_case"
src/` returns nothing — and `custody.open_case`, `custody.reconcile` and `custody.approve_reconciliation` are three
permissions with matrix rows, role grants and no code. **This slice is the case: the tables, the four arms that open
one, and the reads.** The compensating `CORRECTION` event and the second approver are **E07-F03-3b**, because a case
that opens, is read and is withdrawn is already a whole feature and adding the repair to it puts two tables, two
triggers, an options class, five routes and a second state machine in one pull request.

## Acceptance criteria

- [ ] A Tailor Master scans a garment the records say somebody else holds: the scan is refused
      `custody.custodian-mismatch`, the event is persisted as evidence, **and** a `mismatch` case now exists for
      that job with the refused event linked — the behaviour INV-CDY-03 requires and E07-F03-1 deliberately left
      short.
- [ ] A Branch Manager reads `GET /custody/cases?type=mismatch&status=open`, opens the case detail and sees the
      refused event, the expected and the recorded custodian, the opener and the reason code — enough to decide
      what to do, without the repair, which is E07-F03-3b's.
- [ ] Every route declares one permission, one rate-limit policy, the audit filter on the two writes, and a
      resource scope on the two routes that carry `{caseId}` (ARCH-007, ARCH-008, ARCH-017, ARCH-023). **No route
      here declares step-up** — the step-up route is E07-F03-3b's approval — so ARCH-018 has nothing to assert
      about this slice beyond what it already asserts.
- [ ] **Negative — no reason.** Opening or withdrawing a case without a reason is refused and writes nothing
      (`custody.open_case` and `custody.reconcile` are both `RequiresReason: true` in
      `CustodyPermissions.All`).
- [ ] **Negative — other branch.** A case of another branch answers exactly as a case that does not exist, for the
      read, the correction and the approval.
- [ ] **Negative — duplicate cases.** Five refused scans of the same job and kind produce **one** open case,
      enforced by the partial unique index as well as the handler.
- [ ] **Exception — withdrawal.** A case opened in error is withdrawn with a reason; the withdrawal deletes no
      scan event and no case row, and a withdrawn case never moves custody.
- [ ] **Negative — the case cannot repair anything yet.** There is no correction route in this slice, and the pull
      request says so against #37's seventh implementation step, naming E07-F03-3b. A half-built repair is worse
      than a recorded gap.
