Sub-issue of #56. Plan Section 8 closes the W5 half of this parent with "ASVS traceability **audit**, independent
penetration test before production and after material auth/payment/upload changes, verified remediation".
**This sub-issue is the audit half, and only the audit half.** The engagement — the pack, the environment, the
assessor, the remediation register and the release wiring — is the immediately following sibling.

The split is not a preference; it is the difference between work a session can finish and work it cannot. The audit is
a closed, verifiable piece of desk work: read every row of the sheet, check the control exists, check the named test
was run, downgrade what cannot be evidenced, raise what it finds. It starts and ends inside one pull request. The
engagement cannot: **engaging an assessor and providing them a seeded instance are owner actions**, the issue stays
open across the engagement and the remediation, and no coding session can carry it to a green pull request. Keeping the
two in one issue would have produced a child that can never be closed by the session that opens it, which fails the
"one session, one branch, one green pull request" rule outright.

So this sub-issue is the **last of this parent's children that a session can finish**, and its output is the thing the
engagement needs most: a traceability sheet that states facts rather than intentions, so the assessor is testing
claims the project actually makes.

The row it exists to evidence is `docs/nfr/traceability.md` `NFR-SE-12` — "ASVS baseline coverage, with a traceability
record and a penetration test whose findings are remediated … Evidence only; scheduled (#56a, #56b)". This sub-issue
delivers the record half and leaves the penetration-test half named and scheduled.

## Out of scope

**The penetration test, in every respect** — the engagement pack `docs/security/penetration-test.md`, the environment
and its accounts, the rules of engagement, the re-test trigger, the remediation register, and the release wiring for
the report. That is the immediately following sibling sub-issue, and it is separated because an assessor engagement is
an owner action that no session can finish. This sub-issue writes no part of that document.

Writing the models, the catalogue, the ASVS skeleton, the vulnerability process or the exception register — all from
the W2 half of this parent. Writing the regression suites or the policy hardening — the eight sibling sub-issues of the
W5 half. **Fixing what the audit finds**: each finding is its own issue, scoped, reviewed and merged on its own branch,
because a remediation pull request that fixes eleven findings across six modules is unreviewable and breaks CLAUDE.md
section 6. No source file, no test and no configuration change in this pull request — **with one exception, stated so a
reviewer can hold it**: if a `covered` row's named test does not run, the audit **runs the tier and records the
result**; it does not edit the test to make it pass.

## Migration and rollback

No table, no column, no migration; `dotnet run --project src/Tools/Tailor360.Cli -- migrate --dry-run` reports no
outstanding change and that output is the evidence. Rollback is a revert, and it is **dangerous in one specific way**:
reverting restores a sheet full of unaudited `covered` rows, which reads as stronger than the audited version. The pull
request therefore records the count of downgrades, so a revert is visibly a loss. Any `exceptions.md` row the audit
added is the durable artefact and must survive a revert of the sheet.
