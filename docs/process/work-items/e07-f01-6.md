## What is already built (do not re-build)

- `clients/pwa/src/app/router.tsx` — the data router, with `RequireSession` and per-screen
  `RequirePermission` (`clients/pwa/src/admin/RequirePermission.tsx`, which renders an `EmptyState` rather than
  redirecting on a stale claim). Add one route; change nothing else.
- `clients/pwa/src/auth/apiClient.ts` — the one transport. `apiRequest<T>(path, { method, body, idempotencyKey,
  challengeOnStepUp })` adds `X-Correlation-Id`, `X-Client-Version` and the anti-forgery header, re-authenticates in
  place on a 401 and replays the identical request. **The caller holds the idempotency key** — see the
  `printKey`/`fingerprint` pattern in `ReceiptPanel.tsx`, which is the shape to copy. Do not write a second fetch
  wrapper (`clients/pwa/CLAUDE.md` section 2).
- `clients/pwa/src/components/states/` — `LoadingState`, `EmptyState`, `ErrorState`, `Forbidden`,
  `OfflineBlockedAction`, `RetryableError`, `NetworkStatusBanner`, `StateRegion`, `useNetworkState` and
  `problemDetails.ts`, all exported from `index.ts` and all with Storybook stories. The five states are assembled
  from these, never hand-rolled.
- `clients/pwa/src/components/primitives/` — `DataTable`, `StatusBadge` (icon **and** word, never colour alone),
  `Button`, `ButtonGroup`, `Alert`, `Card`, `Icon` with the `icons.ts` allowlist.

  `billingPermissions.ts` (keys named once), `types.ts`, `testing/fixtures.ts`. `clients/pwa/src/api/contract.ts`
  pins every hand-written payload type against the generated `schema.d.ts` with `Conforms<…>`; see

## What is missing

- No `/print-station` route, no `clients/pwa/src/printing/` area, no message family for printing.
- No way to print anything from the client at all: `ReceiptPanel.tsx` queues and stops there, and nothing drains

- No **Verify** step, so a badly printed label cannot be caught before it is attached to a garment —
  `docs/prd/state-transitions.md` line 283 requires exactly that step at the station.

## Acceptance criteria

- [ ] A Cashier holding `print.station` opens `/print-station`, sees the receipt job a payment queued,
      prints it through the browser dialog, marks it printed, and the row leaves the queue — done entirely through
      the screen, with the transport stubbed at `fetch`, never by calling the API module directly.
- [ ] A caller **without** `print.station` sees the forbidden state and no controls, and the screen makes
      no request for the queue at all.
- [ ] **Negative:** the queue request failing renders `RetryableError` with the problem's plain-language text and a
      Retry that reuses the same request; the device being offline renders `OfflineBlockedAction` on **Printed** and
      **Mark failed** with "Needs connection — this will not be queued", and no command is sent; a `403
      security.step-up-required` is answered by `apiClient`, not by this screen.
- [ ] **Negative:** **Mark failed** with an empty reason cannot be submitted, and the field's error is text
      associated with the field and summarised at the top of the dialog.
- [ ] **Exception:** a job another station has already resolved answers `print_job.already_resolved`; the row says
      so in words, the list refreshes, and nothing is printed twice. A Retry after a timeout replays the same
      `Idempotency-Key` and does not produce a second resolution.
- [ ] **Exception:** the Verify field is given a payload that does not match the printed label; the screen says the
      label does not match, does not mark it verified, and offers reprint. `docs/prd/state-transitions.md` line 283:
      "An unverifiable print is reprinted before the label is attached, so a bad label never enters the workshop".
- [ ] axe reports no violations at the phone, tablet and desktop profiles, at 200% zoom and at 320 px, with no
      horizontal page scroll and focus never obscured; the primary actions meet the 56 × 56 CSS px shop-floor
      target of AL-03 (`clients/pwa/CLAUDE.md` section 4).
- [ ] Every user-visible string resolves from `printingEn`, and the pseudo-locale story shows no clipping at 40%

## Modules, contracts and events

Client only. It consumes the host's `/api/v1/print-station/**` routes (E07-F01-5b) and Custody's
`custody.verify_label` route (#191) through the generated contract: `pnpm --dir clients/pwa generate:api` regenerates
`src/api/schema.d.ts` from `docs/api/openapi.v1.json`, and every hand-written type is pinned in
`src/api/contract.ts`, so a server-side change to either route fails `pnpm typecheck` rather than failing at a
counter. No .NET project is touched, so ARCH-003, ARCH-004 and ARCH-011 are not engaged.

**DOR-05:** the station is where a forged or mis-matched label would enter the workshop, which is the "label
forgery" abuse case of the `barcode-custody` threat model — the #56a backlog row in `docs/security/README.md` line
74, not yet written. The control this screen carries is the Verify step and its refusal to mark an unmatched print
verified.
