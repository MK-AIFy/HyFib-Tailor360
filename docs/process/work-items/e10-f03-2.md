Sub-issue of #46. Second of thirteen: the **loss and value** half of the stock reports that can actually be built from
Inventory's published contract set today — posted stocktake variance, stock aging, reorder status, and the valued side
of every figure with its valuation run stamped on it — plus the value reconciliation against `IValuationQuery`. It is
split from `e10-f03-1` because it consumes a different set of events, needs `Inventory.Contracts.IValuationQuery`
rather than `IStockBalanceQuery`, and handles Confidential **cost** figures that the quantity projections deliberately
do not.

**Wastage, supplier returns and adjustments are NOT in this child, and the reason matters.**
`docs/architecture/module-ownership.md` section 5.7 lists exactly seven published Inventory events:
`inventory.stock-reserved.v1`, `inventory.stock-released.v1`, `inventory.stock-consumed.v1`,
`inventory.purchase-received.v1`, `inventory.low-stock-raised.v1`, `inventory.low-stock-cleared.v1`,
`inventory.stocktake-posted.v1`. The plan's #39 blueprint gives the ledger eleven movement types including `wastage`,
`return`, `transfer_out`, `transfer_in` and `adjustment`, and its **Events** line publishes only
`StockReserved/Released/Consumed` and `PurchaseReceived` — so **none of the seven carries a wastage, return or
adjustment movement**, and ARCH-005 and ARCH-011 forbid reading `inventory.ledger_entries`. Those three metrics are
therefore `e10-f03-2b`, which is explicitly blocked on an additive Inventory movement event. **This child is not
blocked on anything**: everything in its scope is reachable from the seven published events plus `IValuationQuery` and
`IStockBalanceQuery`. Do not pull wastage forward into it, do not invent an event name, and do not add a cross-schema
read.

## Scope

- [ ] **`projections_stocktake_variance`** — one row per posted stocktake variance from
      `inventory.stocktake-posted.v1`: stocktake reference, location, item, counted and expected base quantities,
      variance quantity, its valued amount and the run that valued it, approval actor reference, and the branch-local
      date.
- [ ] **`projections_stock_aging`** — per organisation × branch × location × item × branch-local date, the on-hand
      quantity split into age buckets. The attribution rule is the projection's own and must be written into the
      metric dictionary: **the oldest unconsumed receipt first**, applied inside the projection over
      `projections_stock_movements`. The dictionary entry must say in terms a reader can check that this attribution
      is the projection's, that it is **not** Inventory's valuation method (**OD-05**, default weighted average), and
      that the figure is therefore labelled estimated. It must also record the one exclusion this child cannot avoid:
      until `e10-f03-2b` merges, the movement population behind the attribution is receipts and consumptions only, so
      a wastage or a return is not yet subtracted from the oldest layer. The bucket boundaries are **not** invented
      here: they are configuration (`Reporting:Aging:Buckets`) and the set is recorded as **OD-25** below.
- [ ] **`projections_stock_reorder_status`** — the current and historical reorder state per item × location, built
      from `inventory.low-stock-raised.v1` and `inventory.low-stock-cleared.v1` only. Inventory owns the thresholds;
      this child stores **no** threshold of its own and derives no "should reorder" judgement that Inventory has not
      already published.
- [ ] **The value side** — each valued figure stores the amount as a `Money`, the valuation method and configuration
      version, and the `valuation_run` identifier `IValuationQuery` named, so a figure whose provenance cannot be
      named is never stored. A cut-off with no completed valuation run stores the quantity with the value left null
      and a reason code, never a zero and never a locally computed cost.
- [ ] **One value reconciliation** registered against #183's `reconciliation_runs`/`reconciliation_findings`:
      projected value per item × location at a cut-off compared with `IValuationQuery` at the same cut-off, raising
      `reporting.report-reconciliation-mismatch.v1` on a delta, and recording "no valuation run at or before the
      cut-off" as a **finding** rather than a failure. No new table — #183 owns both.
- [ ] **Metric-dictionary entries** in `docs/reports/metrics.md` for stocktake variance quantity and value, the aging
      buckets and reorder status — each with its source event, its cut-off and timezone rule, its exclusions
      (including the wastage exclusion above), and the limitation it carries.
- [ ] **One expand-only migration**, `StockVarianceAgingAndValuationProjections`, plus its row in the `## Register`
      table of `docs/dev/migrations.md` (`Migration | Schema | Phase | Issue | Applied and verified`).
- [ ] Register the handlers, the projector and the reconciliation pass in
      `ReportingModuleServiceCollectionExtensions`, and the worker job in `src/Hosts/Tailor360.Worker`.

## Acceptance criteria

- [ ] A posted stocktake with a variance is projected with its valued amount and the valuation run that produced it,
      and `rebuild-projection` reproduces every row byte-identically.
- [ ] Aging buckets at a cut-off sum exactly to the on-hand quantity `IStockBalanceQuery` reports for that item and
      location at the same cut-off, over a fixture containing receipts and consumptions only; a mismatch is a test
      failure, not a rounding allowance.
- [ ] Reorder status reflects the latest of `inventory.low-stock-raised.v1`/`cleared.v1` per item and location, and a
      cleared-then-raised sequence delivered out of order does not leave the status inverted.
- [ ] Delivering any consumed event twice writes one row: the inbox row committed with the handler's writes is what
      makes the second delivery a no-op, and the test asserts the row count and the unchanged checkpoint.
- [ ] **Negative:** a cut-off with no completed valuation run leaves the valued amount null with its reason code,
      records a reconciliation finding, and the report does not present a zero value as if it were a known one.
- [ ] **Negative:** a caller-independent check that no cost or valuation figure reaches a log, trace or metric —
      `docs/nfr/data-classification.md` section 5.9 forbids it explicitly ("unit costs, valuations and supplier terms
      may not" appear in logs).
- [ ] **Negative:** a reconciliation whose projected value differs from `IValuationQuery` records a finding with the
      delta and raises `reporting.report-reconciliation-mismatch.v1`; it does **not** correct the projection
      (`docs/adr/0011-reporting-read-models.md` section 4.2: hand-correcting projection rows is never permitted — the
      fix is a rebuild).
- [ ] **Exception:** a compensating correction in Inventory produces a second projected row and edits none; a
      stocktake whose variance is later re-approved keeps both rows, because the projection follows Inventory's
      compensating-entry model rather than editing history.
- [ ] ARCH-005 and ARCH-011 hold; no `inventory.*` table is read, and
      `Arch011_ReportingReferencesOnlyContractsOfOtherModules` in
      `tests/Tailor360.ArchitectureTests/ModuleBoundaryTests.cs` (line 132) is green.
