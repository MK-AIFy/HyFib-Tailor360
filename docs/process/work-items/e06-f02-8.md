Sub-issue of #33. Four slices have built the write side: versions, phases, transitions and assignment. Nothing can
**read** the shop floor. The parent's fifth acceptance criterion is "Queues reconcile to source workflow state and
meet response targets", and today there is no queue endpoint at all — `OrdersEndpoints.cs` maps an empty group, and
the only Orders read that will exist is #201's single order and job card. This slice publishes the three reads every
workboard screen needs — the flat queue, the grouped planning board and the per-assignee workload — the due and aging
arithmetic they display, computed in the branch timezone, and the response-view declarations that decide which fields
may reach a shop-floor surface at all.

## What is already built (do not re-build)

- `src/Platform/Tailor360.Platform.Security/FieldVisibility/OrdersResponseViews.cs` — `OrdersResponseViews.WorkQueue`
  (`"orders.work_queue"`) exists and declares **exactly nine** fields in this order: `jobNumber`, `categoryLabel`,
  `dueDate`, `priority`, `currentPhase`, `holdState`, `assignedTo`, `customerName`, `assigneeThroughput`. It withholds
  `SurfaceRules.ForbiddenOnAWorkshopSurface` and requires `OrdersPermissions.Read`.
  **Read this next paragraph before writing any payload type — it is the single thing most likely to stop this slice
  mid-flight.** A field that is not on a view cannot reach a response: `MaskedPayload.Set` throws at run time on an
  undeclared name, and `tests/Tailor360.ContractTests/ResponseViewPayloadTests.cs` holds a typed payload's property
  names **and their order** equal to the view's declared fields. The rows this slice must return carry
  `orderNumber`, `serviceLabel`, `phaseId`, `phaseStatus`, `daysUntilDue`, `isOverdue`, `ageInDays` and `blockedBy`,
  none of which the view declares. So **extending the view is in scope and is not optional**, and extending it means
  four edits in one pull request:
  (1) the `ViewField` rows in `OrdersResponseViews.cs`, each with its `FieldClassification` and any gating permission;
  (2) the `<!-- matrix:views -->`, `<!-- matrix:fields -->` and `<!-- matrix:role-fields -->` blocks of
  `docs/security/field-visibility.md`, all three of which
  `tests/Tailor360.UnitTests/Security/FieldVisibilityDocumentTests.cs`
  holds equal to the code — including the role table, which is derived from the code and the seeded grants;
  (3) the new entry in `ResponseViewPayloadTests.ServedViews`, which today maps only the three Customers views; and
  (4) nothing else — there is no second masking rule to write.
- `src/Platform/Tailor360.Platform.Abstractions/Time/IClock.cs` — `TodayIn(TimeZoneInfo branchTimeZone)`. Business
  dates are evaluated in the branch timezone, never in UTC (`src/Modules/CLAUDE.md` section 7, plan decision D11).

## Scope

- [ ] `Application/Queues/WorkQueueQuery.cs` and `Infrastructure/Queues/WorkQueueQuery.cs` — one read over
      `garment_jobs`, `job_phases` and the current `assignments` row, all in the `orders` schema (ARCH-005, MO-2),
      returning one row per **open phase** with: job number, order number, category label, service label, due date,
      priority, current phase code and status, hold state, assignee identifier and display name, and the computed
      indicators below.
- [ ] `Application/Queues/DueIndicator.cs` — the arithmetic, in one place and unit-testable without a database:
      `daysUntilDue` from the job's `DueDate` against `IClock.TodayIn(branchZone)`; `isOverdue` when the due date is
      strictly before the branch's today; `ageInDays` of the current phase from its `started_at`, also in branch
      days. **No due-soon threshold is chosen here:** the row carries `daysUntilDue` and the caller decides, because
      the due-soon window is branch configuration and no document fixes a number (see Open decisions).
- [ ] **Three** routes, all `DefaultUser` rate-limit policy and no audit action — none is a sensitive read, because
      no measurement snapshot is on any response and the views withhold the four workshop-forbidden classes:
      `GET /api/v1/orders/work-queue` — `OrdersPermissions.Read`, `BranchScope.CurrentBranch`, the flat shop-floor
      list, keyset-paged, with the filter set `filter[assignment]=mine|assigned|unassigned`,
      `filter[state]=overdue|blocked|held`, `filter[priority]=`, `filter[phase]=`, and `filter[dueWithinDays]=<n>`
      which the **caller** supplies;
      `GET /api/v1/orders/planning-board` — `OrdersPermissions.Read`, `BranchScope.CurrentBranch`, the same rows
      grouped by phase code and then by assignee, for the desktop planning surface, with the same filters and the same
      row projection;
      `GET /api/v1/orders/workload?filter[branchId]=&filter[on]=` — **`OrdersPermissions.Assign`, not
      `orders.read`**, because every field on it is staff data under `docs/nfr/data-classification.md` section 5.15
      and DC-11 restricts it to the Tailor Master, the Branch Manager and the Owner, which is exactly who holds
      `orders.assign`. One row per assignee of the branch: the count of open phases by phase code, the assignee's
      `daily_capacity` where one is stated and an explicit "no stated capacity" where it is null, and the unassigned
      count as its own row. Moved here from E06-F02-7 so that one child makes one masking decision and owns one
      performance fixture.
- [ ] **Three response views, not one.** `orders.work_queue` is **extended** with the eight fields named above.
      `orders.planning_board` and `orders.workload` are **new** `ResponseView` declarations in
      `OrdersResponseViews.cs`, because a grouped board and a per-assignee workload are different field sets and
      `ResponseView` refuses a workshop view that withholds less than `SurfaceRules.ForbiddenOnAWorkshopSurface`.
      `orders.workload` requires `OrdersPermissions.Assign` and carries no customer field at all — a workload row is
      about a member of staff, and putting a customer's name on it would widen 5.15 and 5.3 at once. All three views
      land in the same pull request as their rows in the three generated blocks of `docs/security/field-visibility.md`
      and their entries in `ResponseViewPayloadTests.ServedViews`.
- [ ] `blocked` is defined and not guessed: a phase is blocked when the pinned version's graph has an inbound
      transition from a phase that is neither complete nor skipped, **or** the job has an unfinished `finish_before`
      prerequisite sibling. The response names which of the two, and which phase or job number, so the screen can say
      why rather than showing a grey pill.
- [ ] Indexes: add to the existing `job_phases` and `garment_jobs` mappings only the indexes these two queries
      actually use, in one expand-only migration `33_work_queue_indexes` — at minimum `(branch_id, status)` on
      `job_phases` and `(branch_id, due_date)` on `garment_jobs`, each justified by an `EXPLAIN` in the pull request.
      `OrdersDbContext.cs` already calls an index with no query "a guess"; do not add a speculative one.
- [ ] No route accepts a `branchId` the caller could edit: each reads the caller's own branch reach, which is why
      none declares a resource scope and each records that reason (ARCH-023 engages only on a route **parameter**, and
      a query filter is not one). A caller with organisation reach may pass `filter[branchId]=` and it is checked
      against `admin.organisation.read_all_branches` server-side.
- [ ] Three rows in the `<!-- matrix:endpoints -->` block of `docs/security/permission-matrix.md`, each with a blank
      `Resource` cell and the recorded reason for it; regenerate `docs/api/openapi.v1.json` and
      `clients/pwa/src/api/schema.d.ts`.

## Acceptance criteria

- [ ] A Tailor reads `GET /api/v1/orders/work-queue` and receives only their own branch's open phases, one row per
      phase, carrying exactly the fields the **extended** `orders.work_queue` view declares, in the view's declaration
      order, and no others — `ResponseViewPayloadTests` is what proves it; `filter[assignment]=mine` narrows it to the
      phases currently assigned to them.
- [ ] **Reconciliation, which is the parent's fifth acceptance criterion:** for a scripted history — confirm, start
      production, assign, start a phase, complete it, reassign, hold, resume — the queue's counts per state equal the
      counts derived directly from `job_phases`, `assignments` and `garment_jobs`. Asserted by a test that computes
      both sides, not by a fixture that states the expected numbers.
- [ ] Due and aging are computed in the **branch** timezone: a job due today in `Asia/Kolkata` is not overdue at
      23:00 IST and is not overdue at 18:00 UTC on the same calendar day; the test asserts both sides of midnight.
- [ ] **What this slice proves about latency, and what it does not.** Each of the three reads is a bounded number of
      round trips — assert the query count with an EF Core interceptor, so an N+1 over assignees or phases fails the
      build — and each has an `EXPLAIN (ANALYZE, BUFFERS)` in the pull request at the peak-day volume of
      `docs/nfr/capacity-and-performance.md` section 2 (346 garment jobs) showing the index it uses. A wall-clock p95
      is pasted as **indicative**. It is **not** a gate here: `docs/nfr/slo.md` is "Draft — proposed targets; nothing
      here is binding until section 13 is signed", NFR-LT-01 is "proposed, to be confirmed; proof scheduled (#52,
      #58)", its named proof is a k6 scenario and `tests/load` does not exist in this repository. The binding
      measurement against S2 is E06-F02-14's, which is an evidence issue and not a coding session.
- [ ] All three routes declare a permission, exactly one rate-limit policy and a recorded reason for naming no
      resource scope (ARCH-007, ARCH-017, ARCH-023), with a matching row in section 5 of the permission matrix. None
      declares an audit action, and each matrix row's `Audited as` cell says so.
- [ ] **Negative:** a caller whose reach is one branch and who passes another branch's `filter[branchId]` receives
      their **own** branch's rows or a `403` — never the other branch's rows; the test asserts which and the matrix
      row states it. A caller without `orders.read` receives `403` `security.forbidden`.
- [ ] **Negative:** a Tailor's queue response carries no `assigneeThroughput` field at all (the view gates it on
      `reporting.read`), and carries no customer phone number, address, price or measurement — asserted by a
      field-level test over the serialised body, not by inspecting the projection code.
- [ ] **Negative:** a Tailor holding `orders.read` and not `orders.assign` is refused `403` `security.forbidden` on
      `GET /api/v1/orders/workload`, and the refusal is the reason the workload read is a separate route rather than a
      block on the queue response.
- [ ] **Negative:** the workload rows reconcile to the `assignments` and `job_phases` rows they are derived from, and
      an assignee with `daily_capacity` null renders as "no stated capacity" and never as `0` — a zero would read as
      "may take no work".
- [ ] **Exception:** a job whose pinned workflow version has been retired still appears with its phases intact,
      because the version is pinned and retired versions stay readable (INV-JOB-02). A cancelled job does not appear
      in the queue and is still readable through #201's order read.
