## Scope

- [ ] **`clients/pwa/src/offline/deviceStore.ts`** — the **only** module in the application allowed to name
      `indexedDB`. One database (`tailor360`) with object stores `records` (drafts now, queue entries later) and
      `keys`. Every value is written as `{ iv, ciphertext, binding, purpose, writtenAt, expiresAt }`: AES-GCM with a
      fresh 12-byte initialisation vector per record, so no plaintext ever reaches disk. Exports `put`, `get`,
      `listByPurpose`, `remove`, `clearPurpose` and `sweepExpired`, all async and all taking the binding.
- [ ] **`clients/pwa/src/offline/deviceKeys.ts`** — `getOrCreateKey(purpose, binding)` generating a
      **non-extractable** 256-bit AES-GCM `CryptoKey` through `crypto.subtle.generateKey` and storing the key object
      itself in the `keys` store (a `CryptoKey` is structured-cloneable, so the raw bytes never exist in script);
      `shredKey(purpose, binding)` deleting it. Document the property honestly in the module comment: this protects
      the records against someone reading the browser profile off the device, **not** against same-origin script,
      which can always ask the key to decrypt. Overstating it would mislead the security reviewer, and the pull
      request asks for their sign-off on this exact sentence.
- [ ] **`clients/pwa/src/offline/binding.ts`** — `bindingFor(user: CurrentUser)` returning `{ userKey, branchId }`
      where `userKey` is the base64url SHA-256 of `user.userId`, plus `isSameBinding`. The hash is what lets a record
      be matched to its owner without a staff identifier sitting in device storage (CLAUDE.md section 4 rule 8:
      personal data is never an identifier).
- [ ] **`clients/pwa/src/offline/bounds.ts`** — one exported `OFFLINE_BOUNDS = { maximumAgeHours: 24,

## Acceptance criteria

- [ ] A record written under a purpose and a binding is read back intact through the same binding, across a close and
      reopen of the database.
- [ ] **At rest, the record is ciphertext.** A test reads the raw stored value out of IndexedDB and asserts it
      contains none of the plaintext fragments it was given — using distinctive synthetic sentinels in the style of
      `browserStorage.test.ts`'s `SESSION_MATERIAL`.
- [ ] **Negative — sign-out:** after `clearOfflineStateOnSignOut()`, every key is gone and every record is gone, and
      a read by the same accessor returns nothing rather than throwing. With `SURVIVES_SIGN_OUT` empty, **nothing**
      survives, and a test asserts that by enumerating the stores rather than by checking one purpose.
- [ ] **Negative — another user, or another branch:** a record whose binding does not match is **never** decrypted
      and never returned. A record written with `branchId: null` does not match a record written with a branch.
- [ ] **Negative — expiry:** a record written more than `OFFLINE_BOUNDS.maximumAgeHours` ago is not returned by a
      read even when the sweep has not run, and is deleted by the sweep.
- [ ] **Negative — the key is the only thing that opens it:** after `shredKey`, the ciphertext is still in the
      database and is unreadable; the read fails as "no key" rather than as a decode exception reaching the caller.
- [ ] **Negative — the depth override cannot widen the bound:** `VITE_OFFLINE_MAX_ENTRIES=5000` is ignored and the
      bound stays 200; `VITE_OFFLINE_MAX_ENTRIES=3` lowers it to 3; a non-numeric value is ignored. A named test per
      case.
- [ ] **Exception — storage full:** `isQuotaExceeded` recognises a `QuotaExceededError` `DOMException` and the write
      rejects rather than resolving. Nothing is silently dropped and no record is half-written.
- [ ] **Exception — the capability is absent:** a browser with no `navigator.storage`, no `persist`, no
      `crypto.subtle` or no `indexedDB` leaves the application fully usable. Every entry point returns a defined
      "not available" outcome, logs nothing personal, shows the user nothing, and never throws into a render.
- [ ] No part of the application outside `src/offline/deviceStore.ts` names `indexedDB` — the guard test fails if it
      does, with its negative control proving the guard can fail.

## Migration and rollback

No database change in PostgreSQL: no table, no column, no migration.
`dotnet run --project src/Tools/Tailor360.Cli -- migrate --dry-run` reporting nothing outstanding is the proof. The
device store has its own schema version in the IndexedDB `onupgradeneeded` handler. The rollback for a bad store
shape is to bump the version and **delete** the old object stores rather than migrate them — a local draft is a
convenience, never a record, so discarding one is always safe. State that in the module comment, **and state its one
exception in the same comment**: a queued entry is not a convenience, so when #E12-F02-4 lands, an incompatible shape
change must read the old queue records and rewrite them, or refuse to open. Writing both halves now is what stops the
next person reading "discarding is always safe" and losing somebody's scans.
