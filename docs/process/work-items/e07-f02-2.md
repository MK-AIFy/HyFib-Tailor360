## Scope

Target: about 700 production lines plus tests, all of it under `clients/pwa/src/scanning/camera/` plus two
configuration files. **No route, no React screen, no message id and no edit to `clients/pwa/src/app/router.tsx` or

- [ ] **`clients/pwa/src/scanning/camera/cameraCapability.ts`** — feature detection that answers **without
      prompting for permission**: is this a secure context, does `navigator.mediaDevices.getUserMedia` exist, is a
      `videoinput` device enumerable, and is `window.BarcodeDetector` present with a `getSupportedFormats()`
      including `code_128` and `qr_code`. Returns a descriptor the screens branch on, with the `support-matrix.md`
      section 6 row per class quoted in the doc comment.
- [ ] **`clients/pwa/src/scanning/camera/cameraPermission.ts`** — the permission state machine
      `unknown | prompt | granted | denied | unavailable`, read from the Permissions API where it exists and
      inferred from the `getUserMedia` rejection name where it does not: `NotAllowedError` → `denied`,
      `NotFoundError` → `unavailable`, `NotReadableError` → `granted` but **in use by another application**,
      `OverconstrainedError` → the constraints could not be met. Each terminal state carries a **reason code from a
      closed enumeration exported here** and a denial records `permission.denied` through E07-F02-1's sink exactly
      once, not once per frame. **No message id and no copy**: the reason-code-to-`scanning.*`-id mapping belongs to
      E07-F02-2b, and the platform-specific re-enable instructions belong to **E07-F02-5**. This module classifies.
- [ ] **`clients/pwa/src/scanning/camera/decoders.ts`** — two adapters behind one interface: a `BarcodeDetector`
      adapter used when detection says it is present, and a `@zxing/browser` adapter otherwise, both `import()`-ed
      dynamically so neither is in the initial bundle. A native adapter that throws falls through to ZXing **once**
      and records `decode.failure`; the product never depends solely on `BarcodeDetector` (plan D2).
- [ ] **`@zxing/browser` added to `clients/pwa/package.json`** dependencies, pinned the way the file already pins
      (`qrcode-generator` is exact), plus a `vendor-zxing` branch in `manualChunks` in `clients/pwa/vite.config.ts`
      **before** the generic `vendor` return. Record the resolved version and the `pnpm-lock.yaml` diff in the pull
      request. A bundle-size budget is **#52's** gate (NFR-CL-02, "with the scanner, camera, PDF and dashboard
      bundles split out"); what this issue owes is that the chunk is separate and lazily loaded.
- [ ] **`clients/pwa/src/scanning/camera/CameraSource.ts`** — a `ScannerSource` with `source: 'camera'`. Opens a
      stream with `facingMode: { ideal: 'environment' }`; applies `zoom` and `torch` through
      `track.applyConstraints()` **only where `track.getCapabilities()` reports them**; runs the decoder on a
      bounded frame cadence inside the scan region; pipes every result through E07-F02-1's debounce; records
      `decode.latency` per successful decode. `stop()` calls `track.stop()` on **every** track, and the source also
      stops on `visibilitychange` to hidden and on unmount, so the camera light goes out when the operator navigates
      away. **No frame is retained, copied, serialised or transmitted** — the decode call is the only consumer.
- [ ] **Cadence and constraints as named constants** (DOR-11) in `clients/pwa/src/scanning/camera/`, not literals at
      call sites, each with the figure it is derived from quoted: the decode allowance of 400 ms on Blink and 900 ms
      on WebKit from `capacity-and-performance.md` section 3.2. **No new latency target is created here**; the
      constants are a cadence, and the objective stays S4 in `slo.md`.
- [ ] **`clients/pwa/src/scanning/camera/testing/fakeCamera.ts`** — a fake `MediaStreamTrack` recording `stop()`,
      `getCapabilities()` and `applyConstraints()`, a fake `getUserMedia` that can reject with each of the four
      names, a fake `BarcodeDetector`, and a scripted fake decoder. Every payload it emits is synthetic.

## Acceptance criteria

- [ ] On a profile where `window.BarcodeDetector` is present and reports `code_128`, the native adapter decodes and
      the ZXing module is **never imported** — asserted on a dynamic-import spy, not by eye. On a profile where it
      is absent, ZXing decodes. Both produce an identical `ScanResult` for the same synthetic payload.
- [ ] **Negative:** `getUserMedia` rejecting `NotAllowedError` yields state `denied` with its reason code, records
      `permission.denied` **once**, starts no retry loop and leaves no unhandled rejection.
- [ ] **Negative:** with no `videoinput` device enumerable, the camera rung reports `unavailable` **before any
      prompt is raised**, so a desktop without a webcam is never asked for camera permission at all
      (`support-matrix.md` section 6, desktop row).
- [ ] **Negative:** a `getCapabilities()` reporting neither `torch` nor `zoom` still completes a decode, and neither
      constraint is applied — the controls are absent rather than present-and-broken (**A11Y-SC-10**, answered on a
      real device in E07-F02-6).
- [ ] **Exception:** `NotReadableError` — the camera held by another application, the common case on a shared
      counter tablet — is its own state with its own reason code, distinct from a denial, because the remedy
      differs.
- [ ] **Exception:** a native adapter that throws mid-session falls through to ZXing once, records one
      `decode.failure`, and keeps decoding; it does not ping-pong between adapters.
- [ ] `stop()`, unmount and `visibilitychange` to hidden each stop **every** track — asserted on the fake track.
- [ ] No telemetry event, log line or error message produced anywhere in this issue contains a decoded payload, a
      frame, a `deviceId` or a camera label — asserted by a test over the sink.
