## What is already built (do not re-build)

- `clients/pwa/src/admin/adminApi.ts` (429 lines) — **every** call the administration screens make, with a header
  comment stating the three things a command carries (a written reason, `If-Match`, a caller-minted
  `Idempotency-Key`) and the one thing the surface demands (step-up, answered by the server with `403`
  `security.step-up-required`). Add functions here in the same shape; do not create a second API module.
- **Step-up is already handled centrally and must not be re-implemented.**
  `clients/pwa/src/auth/apiClient.ts` declares `STEP_UP_REQUIRED_CODE = 'security.step-up-required'` (line 113),
  a `SessionChallengeReason` of `SessionState | 'step-up'` (line 187) and `setSessionChallengeHandler`, and its own
  header says a stale proof of identity "is renewed in place" and the request retried once, with
  `challengeOnStepUp` defaulting to on (line 419). There is **no `AdminStepUp.tsx` component** — only
  `clients/pwa/src/routes/admin/AdminStepUp.test.tsx` (210 lines) and `AdminStepUp.stories.tsx`, which exercise that
  central behaviour across the admin screens. A new screen therefore gets step-up for free by calling through
  `adminApi.ts`; its obligations are not to opt out and to test that the renewal happens.
- `clients/pwa/src/admin/useAdminResource.ts` (83 lines) — the fetch hook every admin screen uses, keyed on a string
  so a changed filter refetches. `clients/pwa/src/routes/admin/AuditTrailRoute.tsx` shows the keyset-paging idiom
  (`${applied}|${cursor ?? ''}`) and why paging is a button rather than infinite scroll.
- `clients/pwa/src/routes/admin/BranchListRoute.tsx` (198 lines) and `FeatureFlagRoute.tsx` (166 lines) — the two
  closest existing shapes: a register with a create or change form, a reason, a confirmation and the three states.
  Model the retention register on them.
- `clients/pwa/src/routes/admin/AdminReasonField.tsx` — the shared reason input, with a **persistent visible label**
  and a hint saying where the words go. Use it; do not write a second reason field.
- `clients/pwa/src/routes/admin/AdminShell.tsx` (64 lines) and `clients/pwa/src/admin/adminDestinations.ts` — the
  section's navigation, whose order is deliberately fixed ("a person who finds Roles in the fourth place today must
  find it in the fourth place tomorrow — 3.2.3 Consistent Navigation"). Add the two destinations in a considered
  position and say why in the pull request.
- `clients/pwa/src/admin/RequirePermission.tsx` (45 lines) — wraps a route and renders an `EmptyState` with the
  message ids `admin.forbidden.title` / `admin.forbidden.body`. **It is not the `Forbidden` component and it never
  redirects.** Every new route is wrapped in it.
- `clients/pwa/src/admin/adminPermissions.ts` — `ADMIN_PERMISSIONS`, the one place a permission key is named on the
  client. Add the new keys there.
- `clients/pwa/src/components/states/` — `LoadingState` and `EmptyState`; `clients/pwa/src/auth/AuthProblemAlert.tsx`
  for a problem response. All three are already used by every admin route.
- `clients/pwa/src/i18n/en-IN.ts` and `ta-IN.ts`, with `MessageKey` typed from `en-IN` — a missing Tamil key is a type
  error, so both files change together. `clients/pwa/src/i18n/formatters.ts` holds the shared date and number
  formatters; a screen never calls `Intl` directly.
- **Testing**: `clients/pwa/src/routes/admin/AdminScreens.test.tsx` (415 lines) is the harness to extend —
  `MemoryRouter` + `SessionProvider` + `RequireSession` + `AppIntlProvider`, with `stubFetch`, `jsonResponse`,

- **Stories**: `clients/pwa/src/admin/testing/storyTransport.tsx` exports `storyJson`, `storyProblem`, `storyPending`,

## Out of scope

The request **decision** screen (`/admin/privacy/requests/:requestId`) is `[E14-F02-8]`; the holds register and the
exception report (`/admin/privacy/holds`, `/admin/privacy/runs`) are `[E14-F02-8b]`. The split is on those lines
because a decision screen carries a confirmation, a step-up path, an `If-Match` and an irreversible action, which is
the expensive half, and because holds and runs answer a different question — "why did this not happen" — for a
different reader. The correlation-id filter on the

`clients/pwa/src/auth/apiClient.ts`, to the service worker or to offline behaviour (#51). No Storybook **offline**
story, because `adminScreens.stories.tsx` records why admin screens deliberately have none.

## Modules, contracts and events

Client only: `clients/pwa/`. No module, no schema, no migration, no contract, no integration event. The only
generated artefacts are `clients/pwa/src/api/schema.d.ts`, regenerated from `docs/api/openapi.v1.json` with

API document.

Threat-model coverage: the client-side abuse case is "a shared counter browser retains a privacy register after the
auditor walks away". The controls are the server's `no-store` on these reads, no client-side persistence, and no
subject identifier in the URL. The customer-data threat model is scheduled by #56's children
(`docs/security/README.md` section 3.2).
