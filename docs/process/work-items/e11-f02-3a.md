Sub-issue of #48. Stage two of the two-stage dispatch: the doorstep handover that references the authorisation stage one
recorded. `docs/prd/state-transitions.md` section 4.1 fixes it — "Recipient name plus a six-digit OTP valid ten minutes
with at most five attempts, or a signature stroke, per the branch `custody.recipient_confirmation` policy; the
authorisation is unexpired and the order is not cancelled" — and `docs/prd/raci.md` row 19 names the route as `POST

returns only the comment in `CustodyPermissions.cs` that explains why `custody.recipient_confirmation` is a branch
configuration value and not a permission.

**This child is the handover record and the confirm command. The one-time code's issuance and its journey to the
customer are [E11-F02-3b].** They were split out in review for a reason that is not size: there is **no sanctioned way
today for Custody to ask Notifications to send something**. `docs/architecture/module-ownership.md` section 5.10 lists
Notifications' published read contracts as an `ITimelineSource` and the in-app notification query — no send port, no
intent port — and its consumed triggers as "Orders, Billing, Custody and Inventory **integration events**". #209's own
body says it "adds the inbox-side handlers that turn a consumed event into zero or one intent … no new publisher work
needed in those modules". A synchronous hand-off of a plaintext code, which the original single issue assumed, is
therefore a mechanism that does not exist and would need an architecture decision record before it could be merged
(`CLAUDE.md` section 8). [E11-F02-3b] carries that decision, the code lifecycle and the redaction evidence. This child
ships the table, the confirm command and the event, and it **verifies** a code without minting one.

## Acceptance criteria

- [ ] **The journey:** against a dispatched authorisation, a confirm carrying the recipient's typed name and a signature
      stroke records exactly one confirmation, moves the queue entry to `delivered`, spends the authorisation and
      publishes exactly one `custody.delivery-confirmed.v1` — over HTTP, with no direct database access in the test. The
      same confirm carrying a code whose digest the fixture wrote is accepted identically, which is the path
      [E11-F02-3b] makes reachable in production.
- [ ] The route declares a permission with branch scope, a resource scope, exactly one rate-limit policy, the audit
      filter and idempotency (ARCH-007, ARCH-008, ARCH-017, ARCH-023).
- [ ] **Negative:** a wrong code is refused and increments the attempt counter; the **sixth** attempt is refused as
      exhausted whatever the code, the live code is discarded, and the refusal says the delivery must be re-attempted
      under a new authorisation (`docs/nfr/data-classification.md` section 6). An expired code — more than ten minutes
      old — is refused identically to a wrong one, and neither refusal distinguishes "wrong" from "expired".
- [ ] **Negative:** a confirm with no recipient name, with a signature under the `Otp` policy, with a code under the
      `Signature` policy, or with a signature over 10 KB is refused with field-level problem details (CLAUDE.md section
      4 rule 3) and records nothing.
- [ ] **Negative:** a confirm against an authorisation that is expired, already spent, for a cancelled order, or whose
      custody has moved since dispatch is refused with the reason named, and the garment stays dispatched.
- [ ] **Negative:** a caller without `custody.confirm_delivery`, or from another branch, is refused and audited; the
      confirmation is never recorded by a permission check the client performed.
- [ ] **Exception — the replay the plan names:** the same confirm replayed with its original `Idempotency-Key` and
      client event UUID returns the first outcome and creates no second confirmation; a replay arriving after the
      authorisation expired surfaces a **conflict** with the current state rather than silently succeeding or silently
      failing (plan lines 2075-2076). The same client event UUID under a different actor is `409
      custody.event-conflict`.
- [ ] **Exception:** the handover is never recorded without a confirmation of one of the two kinds — no "confirmed by
      the staff member's word" path exists, and a request that omits both is refused (plan line 2072, "never skipping
      confirmation silently").
- [ ] The submitted code, the signature bytes and the recipient's name appear in no log line, no trace attribute, no
      metric and no audit payload. Proved by a test asserting the absence: the prohibition list is
      `docs/nfr/data-classification.md` **section 8**, which names customer names, recipient addresses and request
      bodies, and section 8 also describes how it is kept true — "sentinel values injected in configuration and
      telemetry tests so that a leak fails the build".
