Sub-issue of #58. #58's first implementation step is "instrument OpenTelemetry traces, structured logs and metrics" and
its first acceptance criterion is one correlation trail from user action through API and job. Neither is built:
`src/Platform/Tailor360.Platform.Observability/` is 515 lines across twelve files and declares **one** meter with no
instrument on it — `grep -rn "CreateCounter\|CreateHistogram\|ObservableGauge" src/` returns nothing, so every metric in
the deployment today comes from `AddAspNetCoreInstrumentation`, `AddHttpClientInstrumentation` and
`AddRuntimeInstrumentation`. There is no causation identifier anywhere (`grep -rn CausationId src/` is empty) and no
OTLP log exporter, so the collector's `logs` pipeline in `infra/observability/otel-collector-config.yaml` has no
producer at all. This slice builds the signal catalogue, the platform-owned instruments and the causation trail, and
nothing else.

## Acceptance criteria

- [ ] With `Observability:OtlpEndpoint` set to the compose collector, a state-changing request through the web host
      produces a trace, a metric sample and a log record that all carry the same `CorrelationId`, and the outbox
      delivery that the request caused produces a `tailor360.outbox.deliver` span and log lines carrying that same
      `CorrelationId` plus a `CausationId` equal to the outbox message id.
- [ ] Every constant in `SignalNames` appears in `docs/platform/observability.md` and every row of that document is
      either wired by this issue or names the issue that owns its producer — asserted by a test, not by reading.
- [ ] `tailor360.outbox.lag` reports the age of the oldest unprocessed message **per module schema**, and a module whose
      outbox is empty reports zero rather than being absent from the series.
- [ ] **Negative:** no instrument declares a metric attribute whose name matches `LogRedaction.IsSensitive`, and no
      instrument declares an attribute carrying a resource identifier — high-cardinality identifiers appear on spans
      only, never as metric labels (`docs/nfr/data-classification.md` section 5.18, "In logs" row). A test adds an
      offending instrument and fails.
- [ ] **Negative:** a log event whose property names are each one of the prohibited names in
      `docs/nfr/data-classification.md` section 8 is written with every value replaced by `LogRedaction.Placeholder`,
      proved with sentinel values, which is the mechanism that section 5.17 names as this issue's obligation.
- [ ] **Exception:** with `Observability:OtlpEndpoint` empty — the supported default for a single-VM deployment —
      instruments are still collected and **nothing is exported**, including logs. Note that
      `ObservabilityOptions.ExportsTelemetry` is a **computed** property (`=> !string.IsNullOrWhiteSpace(OtlpEndpoint)`,
      `ObservabilityOptions.cs:27`), not a settable flag: the Serilog sink is gated by reading it the same way
      `ConfigureOpenTelemetryTracerProvider` and `ConfigureOpenTelemetryMeterProvider` already do, and there is no
      second switch to add. No instrument throws when the store it reads is unreachable; a gauge that cannot read
      reports no measurement rather than zero, so "unknown" and "healthy" are never the same value on a dashboard.
