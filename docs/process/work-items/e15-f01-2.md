Sub-issue of #59. Nothing in this repository builds a release image. `.github/workflows/` holds exactly two files,
`ci.yml` and `pr-policy.yml`, whose triggers are `pull_request` and `push` to `main` only — and
`docs/process/workflow-demo.md` precondition **P5** records the consequence in the repository's own words: "A release
workflow exists that produces a tagged build from a merge to `main` — **Not met** — no release workflow exists." Two
more gaps sit beside it. `infra/docker/Dockerfile.cli` does not exist, although
`infra/compose/docker-compose.staging.yml` already runs its one-shot `migrate` service and its `seed` profile from
`${TAILOR360_CLI_IMAGE:?…}` (lines 214, 246 and 273) — `infra/README.md` lists it first under "Arriving later" and
`docs/dev/staging.md` section 12 item 2 calls it out as owed. And every base image in the three Dockerfiles is pinned
by **tag**, not digest: `mcr.microsoft.com/dotnet/sdk:10.0`, `mcr.microsoft.com/dotnet/aspnet:10.0` and
`node:22-alpine`, so the same commit can build two different images. This slice builds the three release images once,
from digest-pinned bases, and publishes their digests.

## What is already built (do not re-build)

- `infra/docker/Dockerfile.web` — multi-stage, repository-root context, copies the client bundle out of the PWA
  image into `wwwroot`, runs as `$APP_UID`, `DOTNET_EnableDiagnostics=0`, OCI labels including
  `org.opencontainers.image.version` and `.revision`, a `/health/ready` `HEALTHCHECK`, and `VERSION` plus
  `SOURCE_REVISION` build arguments feeding `-p:Version=` and `-p:SourceRevisionId=`. **Reuse its shape verbatim for
  the CLI image.**
- `infra/docker/Dockerfile.worker` — the same, on port 8081, `Worker__HealthPort=8081`.
- `infra/docker/Dockerfile.pwa` — `FROM scratch AS assets` holding only `/pwa/dist`, pnpm pinned to `10.33.0` through
  corepack, `pnpm install --frozen-lockfile`.
- **Container hardening is already done and is not in this issue.**
  `infra/compose/docker-compose.staging.yml` sets `read_only: true`, `security_opt: [no-new-privileges:true]`,
  `cap_drop`, `tmpfs` for the writable paths and a 50 MB × 5 `json-file` log cap through the `x-logging` anchor
  (lines 37-51 and per service). The images already run non-root. Do not re-state any of this.
- `.github/workflows/ci.yml` — its **ACTION PINNING POLICY** comment block (lines 83-92) is the rule the new workflow
  follows: every third-party action by 40-character commit SHA with the tag in a trailing comment, raised by
  `.github/dependabot.yml`. The resolved SHAs are already in that file and are copied rather than resolved again:
  `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`,
  `actions/setup-dotnet@a98b56852c35b8e3190ac28c8c2271da59106c68 # v6.0.0`,
  `actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1`. Any action this workflow needs that is
  **not** in `ci.yml` (a registry login, a build-and-push action) has its SHA resolved with the `gh api` recipe the
  policy block gives, and the resolution command is pasted in the pull request.
- `infra/compose/.env.example` — line 84 sets `TAILOR360_WEB_IMAGE=tailor360-web:local` for development; **lines 128
  to 136** are the staging block that documents `TAILOR360_WEB_IMAGE`, `TAILOR360_WORKER_IMAGE` and
  `TAILOR360_CLI_IMAGE` as required digest references, and `TAILOR360_CADDY_IMAGE` as optional. The variable names are
  fixed; this issue fills them in, it does not rename them.
  **Read line 130 before writing the workflow.** The worked example there is
  `ghcr.io/hyfib/tailor360-web@sha256:0000…`, and the namespace in it is **not** this repository's. The owner is
  `MK-AIFy`, so `${{ github.repository_owner }}` evaluates to `MK-AIFy`, and **a registry reference with an upper-case
  path segment is rejected** — `docker push ghcr.io/MK-AIFy/tailor360-web` fails with "repository name must be
  lowercase". The workflow therefore lower-cases the owner before it builds any reference (for example
  `OWNER=$(echo "${{ github.repository_owner }}" | tr '[:upper:]' '[:lower:]')`), and this pull request either updates
  line 130 to the real `ghcr.io/mk-aify/…` namespace or marks it as a deliberate placeholder in one line. Leaving the
  two disagreeing is how the first deployment pulls from a namespace that does not exist.
- `tests/Tailor360.ArchitectureTests/ComposeConfigurationTests.cs` — the pattern for a repository-shape assertion
  that reads the compose files, with negative controls. The new pinning rule is written in the same style.
- `src/Tools/Tailor360.Cli/` — `Program.cs`, `CliHost.cs` and the five commands (`migrate`, `init-reference-data`,
  `seed-synthetic`, `replay-outbox`, `flags`) with `EnvironmentGuard`/`ExitCodes`. The image wraps this project; no
  command is added.

## Acceptance criteria

- [ ] Pushing a tag produces four built images and three pushed ones (`web`, `worker`, `cli`; the PWA image is a
      build stage, not a release artefact), and the job summary carries a digest row for each.
- [ ] **How this is proved before the pull request merges, because it is the one thing about a new workflow that
      catches everybody:** a `push:` **tag** event runs the workflow file **as it exists at the tagged commit**, so
      pushing a throwaway tag (for example `v0.0.0-ci1`) at the head of this branch runs *this branch's*
      `release.yml` and is real evidence. `workflow_dispatch`, by contrast, does not appear in the Actions UI or the
      API until the workflow file is on the **default branch** — so **do not write an acceptance criterion that
      requires a dispatched run before merge**, and do not report its absence as a failure. The dispatched path is
      recorded as an Owner action to confirm after merge, and the pull request says so in one line. If this session
      cannot push a tag to this repository at all, it says that plainly and the tag run becomes the same recorded
      Owner action — it does not describe a run that did not happen.
- [ ] Every pushed image carries `org.opencontainers.image.version` equal to the tag without its `v`, and
      `org.opencontainers.image.revision` equal to the triggering commit — read back from the pushed manifest with
      `docker buildx imagetools inspect`, not from the Dockerfile.
- [ ] Building the same tag twice produces the same digest for `tailor360-cli`, proving the build is reproducible at
      least across two runs of one commit. If it does not, the pull request records which layer differed and why
      rather than asserting reproducibility it did not get.
- [ ] `docker compose -f infra/compose/docker-compose.staging.yml config --quiet` succeeds with the three
      `TAILOR360_*_IMAGE` variables set to the digests the run produced.
- [ ] `tailor360-cli` runs as a non-root user and `migrate --dry-run` inside it reaches a database and reports its
      state; the container has no writable application directory.
- [ ] **Negative:** pushing a tag whose version does not equal the root `VERSION` file fails the workflow before any
      image is pushed, with a message naming both values. A half-published release is the failure this prevents.
- [ ] **Negative:** adding an image reference to any file under `infra/` without a digest fails the architecture
      tier through the new rule, and the negative control proves the detector still catches it.
- [ ] **Exception:** a `${TAILOR360_…_IMAGE}` reference is accepted by the new rule and recorded in the exception
