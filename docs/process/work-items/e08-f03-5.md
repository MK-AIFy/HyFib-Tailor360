Sub-issue of #40. `E08-F03-4` counts; this child decides what the count **means** and writes it to the ledger. It
carries two of #40's five acceptance criteria on its own — "users cannot approve their own material variance above
configured threshold" and "stocktake never rewrites historical ledger entries" — and the invariant they come from,
**INV-STK-06** (`docs/architecture/invariants.md` line 384): "a stocktake variance is explained, approved by a
different user above the threshold, and posted as **adjustment ledger entries** — never as a direct edit of a
balance." Checked today: no `stocktake_variances` table, no approval path and no adjustment posting exists anywhere
in `src/`; the only separation-of-approval code in the tree is Billing's, named below.

## Scope

- [ ] **`StocktakeVariance` entity** in `…Inventory.Domain/Stocktakes/` — one row per count line whose **final**
      counted quantity (the recount where there is one, otherwise the first count) differs from the expected
      quantity frozen at open: the signed difference in the item's base unit, the explanation with its author and
      instant, and the approval status `NotRequired | Pending | Approved` with `ApprovedBy`, `ApprovedAt` and
      `ApprovalReason`. `CountedBy` is copied onto the variance at computation, exactly as `ReconciliationBatch`
      copies `ClosedBy`, so the same-user refusal does not depend on reading another table later.
- [ ] **Threshold as configuration, default zero.** A bound option class (`Inventory:Stocktake:` section, the shape
      of `src/Modules/Billing/Tailor360.Modules.Billing.Application/Payments/CashierOptions.cs`) decides which
      variances are `Pending` rather than `NotRequired`. Default **zero**, for the reason OD-24 records: zero records
      more, never less. **No number is written into the domain.**
- [ ] **Raise the open decision** in section 3 of `docs/prd/assumptions-and-open-decisions.md` — the
      material-variance threshold above which a second person must approve; owner: Business owner co-signed by the
      accountant; the **OD-24** entry raised by #161 as the model, word for word in structure. **Read the register
      for the next free identifier rather than hard-coding one**: it runs `OD-01` … `OD-24` today, so the next is
      OD-25, but `E08-F03-1` raises a decision on the same parent and the two may merge in either order. This is a
      decision entry, **not** a waiver: `docs/process/waivers.md` is for a gate that cannot be met, not for an
      approval nobody has given yet.
- [ ] **One migration**, `InventoryStocktakeVariances`, creating `inventory.stocktake_variances` only, with an
      append-only-after-approval trigger in the shape of
      `billing.reconciliation_batches_are_the_one_transition()`: a row may be inserted, explained once and moved to
      `Approved` exactly once, and every other `UPDATE` and every `DELETE` is refused (G-4). Expand-only; ledger row
      added to `docs/dev/migrations.md`.
- [ ] **Five endpoints, and the fifth is the one the earlier decomposition got backwards.**
      `GET /api/v1/inventory/stocktakes/{stocktakeId}/variances` (the variance sheet — expected, counted and the
      signed difference per line — on `inventory.stocktake`, which is what the **counter** holds and explains from),
      `GET /api/v1/inventory/stocktakes/{stocktakeId}/variances/for-approval` (**the same record** under
      `inventory.approve_variance`, `.RequireStepUp()`, restricted to sessions in `CountingClosed`),
      `POST …/{stocktakeId}/variances/{varianceId}/explain` (`inventory.stocktake`,
      `.Audited("inventory.stocktake_variance.explained", reasonRequired: true)`),
      `POST …/{stocktakeId}/variances/{varianceId}/approve` (`inventory.approve_variance`, `.RequireStepUp()`,
      `.Audited("inventory.stocktake_variance.approved", reasonRequired: true)`),
      `POST …/{stocktakeId}/post` (`inventory.stocktake`,
      `.Audited("inventory.stocktake.posted", reasonRequired: true)`).
      Every one: exactly one rate-limit policy (`DefaultUser` for the two reads, `Write` for the three commands),
      exactly one request timeout (`RequestTimeoutPolicies.Read` / `.Command`),
      `.ScopedToResource(InventoryResourceKinds.Stocktake, "stocktakeId")` (ARCH-023) — and on the two
      `{varianceId}` routes **also** a resource scope, or an explicit note saying the variance is reached through
      its session and the session is what the scope resolves — and `.RequireIdempotency()` on each command.
- [ ] **Why the second read exists, verified against the tree rather than reasoned about.** `inventory.stocktake` is
      granted to `branch_manager` and `inventory_clerk`
      (`src/Modules/Identity/…/Access/SystemRoles.cs:221,347`). `inventory.approve_variance` is granted to **`owner`
      and `branch_manager`** (`SystemRoles.cs:113`, matrix line 204). **The Owner therefore holds
      `approve_variance` and does NOT hold `inventory.stocktake`** — so a variance sheet published only under
      `inventory.stocktake` gives the Owner a `403` on the very sheet they are authorised to approve. That is
      **#220 Gap 1 exactly**, still an open issue, whose own words are: "an Owner who is authorized to approve a
      reconciliation gets a 403 reading the very session they're approving, and the approval screen renders no
      controls." #220 names two sanctioned approaches — widen the read's check, or "add a narrow, purpose-built read
      scoped to the approval permission itself" — and the tree shows which was taken: `ReconciliationEndpoints.cs`
      maps `GET /cashier-sessions/{sessionId}/reconciliation` under `payments.approve_reconciliation` **alone**, with
      `.RequireStepUp()` and restricted to **closed** sessions, and its own doc comment says "without this route they
      could approve a variance they could never read." Copy that precedent verbatim: same record, approval
      permission, step-up because the catalogue's flag is per permission and not per route
      (`ReconciliationEndpoints.cs:70-74`), and restricted to `CountingClosed` because an approver never needs to
      see a count still in progress. **Do not** instead grant the Owner `inventory.stocktake` — #220's third
      acceptance criterion forbids exactly that ("Neither fix grants a permission broader than 'read what this
      approval permission is specifically for'").
- [ ] **Step-up on a read, and what it costs the screen.** Because `inventory.approve_variance` is flagged
      `RequiresStepUp`, ARCH-018 forces `.RequireStepUp()` on **both** the approval read and the approve command, so
      the Owner meets a step-up demand **on arrival at the sheet**, not on pressing Approve. Say so on the route's
      `.WithDescription` and in the matrix note, and tell `E08-F03-10` — it changes where that screen renders the
      demand.
- [ ] **Posting** — in one transaction: every variance beyond the threshold is `Approved` or the post is refused;
      each variance becomes an **adjustment ledger entry** through #39's ledger command (never a balance write);
      the session moves to `Posted`; `inventory.stocktake-posted.v1` is published in the same save with its
      `docs/integration/events/` schema and example files; and each posted entry carries the variance it came from so
      the ledger row is traceable back to the count that produced it (#40: "posting as ledger adjustments linked to
      session evidence").
- [ ] **Variance metrics** on `Tailor360Diagnostics.Meter` — variance rate per posted session and a recurring-variance
      counter keyed on `(item, location)`, with low-cardinality attributes only (branch code, sign), no item
      description and no cost (`docs/nfr/data-classification.md` section 8). `E08-F03-3` establishes the naming
      scheme; follow it rather than inventing a second one.
- [ ] **Matrix and fixtures**: **five** endpoint rows in section 5 of `docs/security/permission-matrix.md` inside the
      `<!-- matrix:endpoints -->` markers, the approval read's note carrying the #220 reasoning the way matrix line
      398 carries it for Billing; and an `identifier-editing` entry for `{varianceId}` in

## Acceptance criteria

- [ ] An Inventory Clerk counts a session with one line short and one line over, explains both, a **Branch Manager**
      approves both with step-up and a reason, and the clerk posts — after which the ledger holds exactly two
      adjustment entries, each naming the variance it came from, and the balances move by exactly the signed
      differences.
- [ ] **Negative (#40 acceptance criterion 2):** the user who recorded the count is refused when approving a variance
      beyond the threshold — `403` with a stable `inventory.…-approval-by-same-user` code, in the
      `ReconciliationApprovalBySameUser` shape — even when that user holds `inventory.approve_variance` (a Branch
      Manager holds both `inventory.stocktake` and `inventory.approve_variance` in `SystemRoles.cs`, so this is a
      real path and not a hypothetical one).
- [ ] **Negative:** posting while any variance beyond the threshold is still `Pending` is refused `409` with a code
      naming the unapproved count; posting twice is refused the second time; a replayed `Idempotency-Key` returns the
      first outcome rather than posting a second set of entries.
- [ ] **Negative (#40 acceptance criterion 3):** no ledger entry written before the session existed is updated or
      deleted by posting — asserted by capturing the ledger rows before and after and comparing, and by the
      append-only trigger on the ledger refusing an `UPDATE` from the application role (INV-STK-01, G-4).
- [ ] **Negative:** approving a variance that was never beyond the threshold is refused as "not required", and
      approving an already-approved variance is refused `409`.
- [ ] **Exception:** a posting that fails part way — an adjustment the ledger refuses — leaves **no** adjustment
      entries, the session still `CountingClosed` and every approval intact, so the post can be retried after the
      cause is fixed. One transaction, proved by a test that forces the refusal.
- [ ] **An Owner holding `inventory.approve_variance` and NOT `inventory.stocktake` can read the variance sheet and
      approve from it, without a `403` on the read** — #220's first acceptance criterion, transposed to Inventory, and
      the reason the fifth route exists. Asserted with a caller that holds only the approval permission.
- [ ] Every route declares one permission, one rate-limit policy, one request timeout, a resource scope, an audit
      action on each command, and `.RequireStepUp()` exactly where the catalogue flags it — which is on **both**
      `approve_variance` routes, the read included (ARCH-018, `AuthorisationMatrix.Reconcile`);
      `AuthorisationMatrixTests` passes with the new rows.
