Sub-issue of #59. `docs/process/release-gates.md` **RG-11** makes a missing or invalid signature or provenance an
**S1 failure with no waiver**, and explains why: "The deployment model is 'build once, promote the identical digest'.
Without a verified signature, 'the identical digest' is an assumption rather than a fact." Nothing in this repository
produces either. `grep -rn "cosign\|attest\|provenance" .github/ infra/ scripts/` matches exactly twice, and both are
prose promising the thing rather than doing it: `infra/CLAUDE.md` line 134 ("Build once, promote the identical digest
**after verifying its signature and provenance**") and `infra/README.md` line 191, which assigns the verification to
#59. What does exist
is one bill of materials for the whole repository — the `sbom` job of `.github/workflows/ci.yml` (lines 1033-1184)
runs Syft `v1.51.1` through `anchore/sbom-action` and writes a single CycloneDX document,
`artifacts/sbom/tailor360.cyclonedx.json`, as the `sbom` artefact. That document describes the *source tree*, not the
three published images, and `docs/process/branch-protection.md` section 3 already says the job "produces an artefact
rather than a verdict" and that RG-11 belongs "at the release and the nightly run, not at every pull request". This
slice gives each released image its own bill of materials, a signature and a provenance attestation, and a verifier
that a deployment can run before it pulls.

## What is missing

- Per-image bills of materials. One repository-wide document cannot answer "what is in the image that is running",
  which is the question RG-11 and the nightly re-scan both ask.
- Any signature. No cosign, no key, no keyless identity, no `id-token: write` anywhere —
  `docs/process/branch-protection.md` section 8 states the current position in terms: "no Environment exists, no
  deployment secret exists, and no workflow requests `id-token`."
- Any provenance attestation, so an image's digest cannot be tied to the workflow, the commit and the builder that
  produced it.
- A verifier. `ls scripts/` returns `check-docs-links.py`, `coverage-floor.py`, `dev`, `dev.ps1`, `openapi-diff.py`
  and `sarif-gate.py`. There is nothing a deployment could run to answer "is this digest the one that was approved,
  and did this project build it".

## Acceptance criteria

- [ ] For a pushed tag, each of the three released images has, in the registry and against its digest: a CycloneDX
      bill of materials, a cosign signature and a build-provenance attestation. Proved by running the new verifier
      against each digest in a **separate job** from the one that signed, so the verification is not reading its own
      memory.
- [ ] **How this is proved before merge.** As in **E15-F01-2**: a `push:` tag event runs the workflow file at the
      tagged commit, so a throwaway tag at this branch's head exercises the real signing and attestation path, OIDC
      identity included, and the run URL is the evidence. A `workflow_dispatch` run is **not** available until
      `release.yml` is on the default branch, so the `workflow_dispatch` exception below is recorded as an Owner
      action to confirm after merge rather than demonstrated here — and the pull request says which of the two each
      piece of evidence is.
- [ ] `cosign verify` (or the verifier wrapping it) accepts the digest only when the certificate identity matches
      this repository and this workflow path. A signature made by a different workflow in the same repository is
      refused.
- [ ] The provenance attestation names the triggering commit, and the verifier refuses a digest whose provenance
      names a different commit.
- [ ] The per-image bill of materials lists the base-image packages, which the repository-wide document does not —
      demonstrated by a component count and at least one named operating-system package that appears in the image
      document and not in `artifacts/sbom/tailor360.cyclonedx.json`.
- [ ] **Negative:** `scripts/verify-artefact.py --self-test` proves the verifier rejects an unsigned digest and a
      digest whose provenance names the wrong commit, and the two failures print different messages.
- [ ] **Negative:** a Trivy image scan finding at high severity in a shipped layer fails the release job, and the
      finding is in the job summary with its severity and package. An unfixable finding is handled through
      `docs/process/waivers.md` by the security owner, exactly as the `infrastructure-scan` job's comment describes —
      not by lowering the gate. A **missing or invalid signature or provenance** is different in kind and is not
      waivable at all: it is in the "Never waivable" table of `docs/process/waivers.md` section 3, which this pull
      request quotes rather than paraphrases, beside the critical-or-high row that covers the scan findings.
- [ ] **Negative:** the verifier exits non-zero, with a message saying which tool is absent, when `cosign` is not
      installed. It must not report success, and it must not silently install anything.
- [ ] **Exception:** a release built by `workflow_dispatch` rather than by a tag push is signed by the same identity
      and is verifiable the same way; the verifier does not require a tag to exist. A tag is how a release is named,
      not how it is trusted. Because a dispatched run cannot be triggered until the workflow is on the default branch,
      this criterion is satisfied **by construction and by inspection of the identity the job requests** — the same
      job, the same `id-token` scope, no branch in the certificate subject the verifier matches on — with the live
      dispatched run recorded as the Owner's post-merge confirmation. Say which it is.
- [ ] Every action added is pinned by 40-character commit SHA with its tag in a trailing comment, per the policy
      block of `ci.yml`.
