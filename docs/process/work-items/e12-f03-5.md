Sub-issue of #52. The browser half of the parent's client-telemetry deliverable, and the fifth acceptance criterion
— "Browser/device failures produce diagnosable telemetry without sensitive data". Nothing of it exists:
`grep -rln "web-vitals\|sendBeacon" clients/pwa/src` returns nothing, and the only place the word appears in the
client today is `clients/pwa/vite.config.ts` line 61, whose comment is an instruction to this sub-issue —
"Production source maps are required to symbolicate the client error reports of **#52**". Three other
decompositions already depend on this module existing: the #36 children ship "the sink, the vocabulary and the
redaction test" for scanner metrics and say the transport is #52's, the #51 children classify the service-worker
registration outcome against it and say "the posting endpoint itself is #52's", and #58 consumes the events.

## What is missing

- Nothing collects web vitals, so `NFR-CL-01`'s field half has no instrument.
- Nothing catches an unhandled error or an unhandled promise rejection at the window level, so a failure on a
  shop-floor phone is invisible unless somebody telephones about it.
- Nothing batches, samples or posts, so **[E12-F03-4]**'s endpoint has no caller and the six generic event types
  have no producer.
- There is no client-side guard that the telemetry family writes nothing to browser storage and carries no personal
  field — which is the property that makes an always-on reporter safe to ship at all.

- [ ] Add `clients/pwa/src/telemetry/events.ts` — the closed client-side event vocabulary, one discriminated union
      with exactly the six types **[E12-F03-4]**'s allowlist accepts: unhandled error, unhandled promise rejection,
      service-worker failure, capability-detection result, web vital, navigation timing. A new type is added here
      and in the server allowlist together. The batch body is typed against the generated
      `paths['/api/v1/telemetry/client']['post']['requestBody']['content']['application/json']` of
      `clients/pwa/src/api/schema.d.ts`, so a server-side shape change fails `pnpm --dir clients/pwa typecheck`.
      That file is **[E12-F03-4]**'s to regenerate; this sub-issue consumes it and never edits it by hand.
- [ ] Add `clients/pwa/src/telemetry/redact.ts` — the client-side allowlist, applied **before** an event enters the
      buffer: per event type, the permitted attribute names and their value shapes; an error message reduced to its
      code, a stack reduced to a **hash**, a route reduced to its **name** from the route table, and every number
      bounded. Two facts about the hash a session must not discover at run time: `crypto.subtle.digest` is
      asynchronous, so the redaction step is `async` and the buffer holds the event only once it resolves; and
      `crypto.subtle` is **absent outside a secure context**. `http://127.0.0.1:8080` and `localhost` *are* secure
      contexts, so the suite and the dev stack are fine, but a shop device reached over plain `http://` on a LAN
      address is not — so the module falls back to a short, clearly non-cryptographic string hash, documented as
      such in a comment, because this is a grouping key for a stack and never a security control. Free text is never
      carried, so there is nothing to strip later. This
      is defence in depth in front of the server's allowlist, not a substitute for it.
- [ ] Add `clients/pwa/src/telemetry/buffer.ts` — the bounded in-memory buffer and the flush policy: flush on a
      size threshold, on an interval, on `visibilitychange` to hidden, and on `pagehide`; drop the oldest on
      overflow and count the drops as one event of its own. **Nothing is persisted**: no `localStorage`, no
      `sessionStorage`, no IndexedDB, no service-worker queue. A lost batch is acceptable; a telemetry queue that
      survives a shared counter device is not, and the persisted offline queue is #51's single implementation for
      **operational** commands only.
- [ ] Add `clients/pwa/src/telemetry/transport.ts` — `navigator.sendBeacon` where available, `fetch` with
      `keepalive: true` otherwise, always same-origin, never through `apiClient`, never awaited by a caller, and
      never retried on a refusal. `sendBeacon` **cannot set a header**, so the body is
      `new Blob([json], { type: 'application/json' })` — that is how the content type is declared, and it is the
      only type **[E12-F03-4]**'s endpoint accepts (a `text/plain` beacon is answered `415`). The `fetch` path sets
      the same header explicitly so the two paths are indistinguishable on the wire. A non-2xx answer, a network failure
      and a thrown exception are all the same
      outcome: the batch is discarded and a counter is incremented in memory. The module header states why
      `apiClient` is bypassed and cites lines 273 to 330 of it.
- [ ] Add `clients/pwa/src/telemetry/sampling.ts` — the sampling decision, taken **once per page load** in memory
      from `crypto.getRandomValues`, with errors and service-worker failures never sampled out and web vitals and
      navigation timings sampled. No identifier is generated, stored or reused across loads, so nothing here can
      become a device or visitor identifier.
- [ ] Add `clients/pwa/src/telemetry/install.ts` — the single entry point called once from
      `clients/pwa/src/main.tsx`: registers the `error` and `unhandledrejection` listeners, subscribes to

- [ ] Add `clients/pwa/src/telemetry/config.ts` — the flush interval, the buffer cap, the batch cap and the

- [ ] Add `clients/pwa/src/telemetry/noPersonalData.test.ts` — the family guard, in the shape of

## Acceptance criteria

- [ ] On a page load, the capability-detection result is posted once, and the Largest Contentful Paint,
      Interaction to Next Paint and Cumulative Layout Shift values arrive as web-vital events carrying the route
      **name** — the three metrics `docs/nfr/capacity-and-performance.md` section 3.3 measures in the field.
- [ ] A batch is flushed on `visibilitychange` to hidden and on `pagehide`, through `sendBeacon` where the browser
      has it and through `fetch` with `keepalive` where it does not, on all three engines.
- [ ] **Negative — no personal data:** a thrown error whose message contains a synthetic customer name, a
      navigation to a route carrying a customer identifier, and a measurement value typed into a field produce a
      posted body containing **none** of the three: a message code, a route name and a stack hash instead.
      Asserted on the body the transport was handed, not on the module's internals. The test awaits the redaction
      step, because hashing is asynchronous, and also runs once with `crypto.subtle` deleted to prove the
      non-cryptographic fallback still carries no text.
- [ ] **Negative — no storage:** a full page lifecycle including an error, a flush and a page hide writes nothing
      to `localStorage`, `sessionStorage` or IndexedDB, and sets no cookie. Asserted by spies, and asserted again
      at source level by the family guard.
- [ ] **Negative — a refusal is silent:** the endpoint answering `400`, `429` or `503`, and the network failing
      outright, each discard the batch without retrying, without logging to the console, without surfacing anything
      to the person using the screen, and **without opening the re-authentication dialog** — the last asserted by
      checking that `apiClient`'s session-challenge handler was never invoked.
- [ ] **Negative — telemetry never breaks a screen:** an exception thrown inside the telemetry module itself is
      swallowed and the application continues; demonstrated by making `redact.ts` throw in a test.
- [ ] **Exception — overflow:** filling the buffer past its cap drops the oldest entries, reports the drop count as
      one event, and never grows without bound. The buffer's memory is bounded by the cap, which is what keeps it
      inside the scan-screen memory budget `capacity-and-performance.md` section 3.3 sets.
- [ ] `grep -rn "apiRequest\|apiRequestVersioned" clients/pwa/src/telemetry` returns nothing, and
      `grep -rn "from '../telemetry" clients/pwa/src` shows exactly one importer, `main.tsx`.

No .NET module and no schema. The change set is `clients/pwa/src/telemetry/`, one line in

Threat-model coverage (DOR-05): the risk this module carries is **exfiltration through a reporter** — an
always-on, same-origin poster that gradually learns to carry more than it should. `docs/security/README.md`
section 3.2's telemetry-leak entry is the covering entry, against **#58 and #52**; the two controls named in the
pull request are the source-level family guard and the sentinel-value runtime test, and the reason they are
source-level is the one `noClientSideSecrets.test.ts` already gives: a behaviour-only test passes for a path it did
not happen to walk.

No table and no column, so no migration. What proves it: the change set contains nothing under `src/`, and
