## Scope

- [ ] **`BillingTimelineActions`** at
      `src/Modules/Billing/Tailor360.Modules.Billing.Application/Invoicing/BillingTimelineActions.cs`: the closed set
      of facts that reach a customer's timeline and their titles in the shop's words — `billing.invoice.posted`,
      `billing.invoice.cancelled`, `billing.credit_note.posted`, `billing.debit_note.posted` — with the permission
      each costs (`billing.create_invoice` for all four) and the source name constant `"billing"`. **Drafts and
      discarded drafts are deliberately absent**: nothing about a draft is authoritative
      (`InvoiceStatus.Draft`'s own remark), and putting one on a customer's history would show her a document that
      may never exist. A test asserts the deliberate absence, as `TimelineActions` does.
- [ ] **`BillingTimelineSource`** at
      `src/Modules/Billing/Tailor360.Modules.Billing.Infrastructure/Persistence/BillingTimelineSource.cs`
      implementing `ITimelineSource` with `SourceName => "billing"`. **It reads Billing's own three tables, not the
      audit trail** — and the body must carry a comment saying why: `IAuditReader.ReadEntityTrailAsync` is keyed on
      one entity, and `BillingAudit.InvoiceEntity` writes every Billing entry against the **invoice**, not the
      customer, so there is no single entity whose trail is this customer's documents. The tables, by contrast, hold
      the fact and its instant, and a posted document is immutable by trigger, so the table is the authority
      (`src/Modules/Billing/Tailor360.Modules.Billing.Application/BillingAudit.cs` line 43 is the constant to cite).
- [ ] **The union and the total order**: one entry per posted invoice (`posted_at`, keyed by the invoice id), per
      cancellation (`cancelled_at`, keyed by the cancellation id) and per note (`posted_at`, keyed by the note id),
      merged and ordered by `(OccurredAt, Id)` descending, returning at most `query.Limit` strictly older than
      `query.Before` — the same total order `TimelinePosition` defines, so the host can resume a page from any of
      the three kinds.
- [ ] **Scoping, in this order**: organisation from `query.Organisation.OrganisationId`; the invoice's
      `BranchId` must be in `query.AssignedBranches` (an invoice is branch-owned, and the timeline endpoint is
      `AssignedBranches`-scoped); `query.Permissions` must contain `billing.create_invoice`, or the source returns an
      empty list rather than throwing. **No role is ever consulted** (the port's own remark).
- [ ] **Each entry** carries `Kind` from `BillingTimelineActions`, `Title` in the shop's words, `Detail` as
      operational prose that names the document and never the customer's own data, `ReferenceType = "Invoice"` and
      `ReferenceId` = the invoice identifier so a screen can open it, `ExpandPermission = billing.create_invoice`,
      `BranchId` = the invoice's branch, and `ActorDisplayName` resolved in **one** `IUserDirectory.FindManyAsync`
      call for the whole page — never one lookup per row.
- [ ] **The reason**, where the fact carried one (a cancellation and both notes always do): set `Reason` only when
      the caller holds the reason permission and set `ReasonPermission` **whenever a reason exists**, so a screen can
      say "somebody gave a reason you may not read" rather than implying none was given. The permission is
      `CustomersPermissions.ReadNotes` — the same key `TimelineActions.ReasonPermission` already uses — because the
      reason is free text a member of staff typed about a named person, which
      `docs/nfr/data-classification.md` classifies as customer notes. State that choice in a comment; it is the one
      judgement in this slice, and it is deliberately the same judgement Customers made rather than a second one.
- [ ] **Registration** in
      `src/Modules/Billing/Tailor360.Modules.Billing.Infrastructure/BillingModuleServiceCollectionExtensions.cs`:
      `services.AddScoped<ITimelineSource, BillingTimelineSource>();` — **`AddScoped`, not `TryAddScoped`**, for the
      reason the Customers registration records. No host change at all.
- [ ] **One migration**, expand-only: the index
      `ix_invoices_organisation_customer_posted_at` on `billing.invoices (organisation_id, customer_id, posted_at)`
      filtered on `posted_at IS NOT NULL`, so a customer's posted documents are read on an index rather than by
      scanning the branch's invoices. The notes and the cancellation are reached through the invoice on their
      existing `invoice_id` indexes and need nothing.
- [ ] **Documentation**: a row in the `docs/dev/migrations.md` register in the house shape (migration, schema,

## Acceptance criteria

- [ ] A caller holding `customers.read` **and** `billing.create_invoice`, assigned to the branch that issued the
      invoice, reads `GET /api/v1/customers/{customerId}/timeline` and sees the posted invoice, its cancellation and
      each credit and debit note, newest first, each with its title, its instant, the acting member of staff's name,
      and a reference that opens the invoice.
- [ ] Paging works **across kinds**: with `limit=1`, three successive pages return the three newest facts in order,
      no fact twice and none stepped over, with the `before` cursor taken from the previous page.
- [ ] The merged timeline still contains the Customers entries for the same customer, interleaved by instant — the
      composer is not replaced, it is added to.
- [ ] **Negative:** a caller holding `customers.read` but **not** `billing.create_invoice` reads the timeline
      successfully and sees **no** Billing entry at all — not a redacted one.
- [ ] **Negative:** a caller assigned only to another branch sees none of this branch's invoice entries, and a
      caller in another organisation sees nothing; neither is told that anything was withheld.
- [ ] **Negative:** a **draft** and a **discarded** invoice produce no timeline entry, whatever the caller holds.
- [ ] **Exception:** a caller without the reason permission sees the cancellation entry with `reason` null and
      `reasonPermission` set, so the screen can say a reason exists and is not readable — never with the reason
      silently missing.
- [ ] **Exception:** when the source throws, the endpoint still answers with the other sources' entries and names
      `billing` as the failed source (the composer's existing partial-failure behaviour, asserted rather than
      re-implemented).
- [ ] The migration applies, its `Down` is executed at least once, and `dotnet ef migrations
