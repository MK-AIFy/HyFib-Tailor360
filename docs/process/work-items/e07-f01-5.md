Sub-issue of #35. The four existing children (#190, #191, #194, #197) cover identity allocation, label rendering,
resolve and reprint, and every one of them queues or consumes a print job — but **there is no print queue to queue
into**. `Platform.Abstractions.Ports.IPrintQueue` exists and its own documentation comment says "Platform owns the
queue and its table", and the only adapter is
`src/Modules/Integration/Tailor360.Modules.Integration.Infrastructure/Printing/LoggingPrintQueue.cs`, which mints a
`Guid`, writes a log line and prints nothing (ADR-0014 records it as interim). `platform.print_jobs` is named in
`docs/architecture/module-ownership.md` line 703 and in plan Section 4.4, and it does not exist: the eight entities
under `src/Platform/Tailor360.Platform.Persistence/Entities/` are `AuditEvent`, `FeatureFlag`, `IdempotencyRecord`,
`InboxMessage`, `JobLease`, `OutboxMessage`, `SequenceRow` and `WorkerHeartbeat`, and none of the five migrations in
`src/Platform/Tailor360.Platform.Persistence/Migrations/` creates a print-job table. Every receipt and invoice
printed since #169 has therefore been acknowledged and dropped.

**This slice is the persistence half only: the table, the durable queue and the port a station drains through.** The
four HTTP routes, the station permission and the content-security-policy change are **E07-F01-5b**, which follows
this one. The split is along a real seam — a row and a port here, an authorised surface there — and it exists because
one pull request carrying a new Platform table, a new permission, four routes, the matrix rows and a policy widening
is past the 1,500-line target of CLAUDE.md section 6 and past what one review can hold.

Plan Section 9 is explicit that this is #35's work and not #55's: "`IPrintBridge` (an adapter that drains
`platform.print_jobs` to a network/local bridge; **the queue and print station belong to #35**)".

## Modules, contracts and events

**Platform owns everything this issue writes.** The table is `platform.print_jobs` in the schema `PlatformDbContext`
owns (`docs/architecture/module-ownership.md` line 703); no module context maps it, so ARCH-005 and MO-2 hold
unchanged. No business module is touched: Billing keeps calling `IPrintQueue.EnqueueAsync` exactly as it does at
`DocumentArtifactHandler.cs` lines 231 and 298, and the only Integration change is deleting the interim adapter and
its registration line. Both ports are declared in `Platform.Abstractions`, so no module references another
(ARCH-004).

Published: `platform.print-job-queued.v1`. Consumed: nothing.

**The contract this issue imposes on #191, and the one thing worth a comment on #191 before it starts.** A job's
`payload_reference` is an object-storage key, because that is what both live callers pass and what 5b's document
route will stream. #191 renders labels and says nothing about persisting them, so **#191 must write its rendered
label to object storage and pass that key**; if it renders on demand instead, the station cannot print a label and
E07-F01-6 has nothing to frame. `docs/platform/print-queue.md` states the rule so the obligation is written down
rather than inferred from two call sites.

**DOR-05:** the threat model for this flow, `docs/security/threat-models/barcode-custody.md`, is the #56a backlog
row in `docs/security/README.md` line 74 and is not written yet. The abuse case this slice answers is **label
forgery** in its narrowest form: the queue stores a reference and never dereferences it, so nothing here can be made
to read an object on a caller's behalf. The reach question — who may list or resolve a job — is 5b's, where the
endpoint exists to answer it.
