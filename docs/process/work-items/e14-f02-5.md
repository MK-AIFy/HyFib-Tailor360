## What is missing

- Nothing calls `platform.verify_audit_chain`. There is no schedule, no record of a verification having happened, and
  therefore no way to say "the chain was intact as of an hour ago".
- Nothing snapshots the chain head, so a restored database cannot be proved to be the same chain.
- The trail cannot be searched by correlation id, and the column has no index, so the parent's third acceptance
  criterion — "every critical mutation has a searchable audit event **linked by correlation ID**" — is unmeetable as
  the surface stands.
- Nothing asserts at run time that an audited endpoint's entry actually carries a correlation id. ARCH-008 proves the
  filter is declared; it cannot prove the entry was written with a correlation.

## Scope

- [ ] **`platform.audit_chain_anchors`**: `id` (UUIDv7), `anchored_at`, `last_sequence`, `last_hash`,

      (nullable), `instance_name`. One row per verification run — the anchor and the verification verdict are the same
      fact and splitting them would allow an anchor with no verdict.
- [ ] **One expand-only migration**, EF name `AddAuditChainAnchors`, which also adds
      `ix_audit_events_correlation_id ON platform.audit_events (correlation_id) WHERE correlation_id IS NOT NULL`

      rewritten anchors nothing. The index is created on the partitioned parent so each partition inherits it;

- [ ] **`AuditChainVerificationService`** in `src/Hosts/Tailor360.Worker/Jobs/AuditChainVerificationService.cs`,

      start-up and then on a `PeriodicTimer`. It verifies **from the last intact anchor's `last_sequence`**, not from

- [ ] **Disagreement is the alarm, and it has two forms.** (a) `verify_audit_chain` returns a break: record the

      already covered has changed: record `Broken` with a distinct reason. Case (b) is the one a restore from an
      unexpected point produces, and it is why the anchor exists at all.

**The run-time audit-completeness sweep is out of scope and is its own child, `[E14-F02-5b]`.** It was in an earlier

## Acceptance criteria

- [ ] With the worker running, an anchor row appears for the current chain head with `outcome = Intact`, and
      `GET /api/v1/admin/audit/chain` returns it together with the current head; a second run verifies only from the
      previous anchor's sequence, proved by the recorded `verified_from_sequence`.
- [ ] `GET /api/v1/admin/audit/?correlationId=<id>` returns exactly the entries written under that request, and a
      state-changing call followed by that query joins the mutation to its audit entry with no other filter — the
      parent's third acceptance criterion, observable over HTTP.
- [ ] The new route declares a permission (ARCH-007) and exactly one rate-limit policy (ARCH-017), and declares **no**
      `.RequireStepUp()`, because `admin.audit.read` is catalogued `RequiresMfa: true` with no step-up and
      `AuthorisationMatrix.cs` line 197 checks ARCH-018 both ways. It declares no resource scope either, because it
      carries no route parameter — ARCH-023's allowed-exceptions row (`docs/architecture/architecture-rules.md`
      line 346) names exactly that case. The job declares `[WorkerJob]` (ARCH-021) and touches `IWorkerScopeFactory`
      only from the worker host (ARCH-020), both asserted by
      `BackgroundContextTests.Arch021_EveryWorkerJobDeclaresItsScope`. No route this issue adds changes state, so
      ARCH-008 is satisfied by the two existing routes keeping their declarations.
- [ ] **Negative — tampering is caught by the schedule, not only by a test that looks for it**: a row altered with the
      triggers disabled (the technique `AuditTrailTests.DetectsTamperingPerformedWithTheTriggersDisabled` already
      uses) makes the next scheduled run record `Broken` with the offending sequence and reason, turns the health
      check `Unhealthy`, and increments `audit.chain.breaks`.
- [ ] **Negative — a gap is caught**: deleting a row with the triggers disabled produces a break whose reason names
      the expected sequence, not a silent pass.
- [ ] **Negative — disagreement with the anchor is caught**: after an anchor is written, rewinding
      `audit_chain_head.last_sequence` makes the next run record `Broken` for the head-disagreement reason, which is
      the signal a restore from an unexpected point produces.
- [ ] **Negative**: a caller without `admin.audit.read` is refused `GET /api/v1/admin/audit/chain` with the `403`
      answer already defined in `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`.
- [ ] **Exception**: an anchor row cannot be updated or deleted — the append-only trigger is proved against the live
      database. Verification failing part-way leaves the previous anchor intact and records nothing half-written, so
      the next run simply repeats from the same point.
- [ ] **Exception**: `MayDetachMonth` answers **false** for a month whose covering anchor reads `Broken`, **false**
      for a month no anchor covers, and **true** only for a month whose covering anchor reads `Intact` — three unit
      assertions. It is a predicate a future detach calls, not a guard inside a path that exists today.
- [ ] Two worker instances do not both verify: the lease is proved with two concurrent scopes producing one anchor.
