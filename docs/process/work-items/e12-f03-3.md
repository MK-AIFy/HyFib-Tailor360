Sub-issue of #52. The parent's fifth implementation step — "Define capability detection/fallbacks for camera,
barcode decoding, push, clipboard/share, printing, file capture and install prompts" — and the acceptance criterion
"Missing camera/push/install/print capability has a usable documented fallback". Two of the seven are built and
five are not: `clients/pwa/src/routes/installPlatform.ts` detects the install path and is the repository's one
**contained** user-agent exception, and `clients/pwa/src/auth/CopyButton.tsx` lines 38 to 44 already probe
`navigator.clipboard` and fall back. There is no camera probe, no `BarcodeDetector` probe, no push probe, no share
probe, no file-capture probe, and **no unsupported-configuration page** — which
`docs/nfr/support-matrix.md` section 1.1 names as the behaviour for every configuration outside the matrix ("the
application refuses to run and shows the unsupported-configuration page with the upgrade path") and section 9 lists
as a per-pull-request gate. `grep -rn "BarcodeDetector" clients/pwa/src` returns nothing.

## What is already built (do not re-build)

- `clients/pwa/src/routes/installPlatform.ts` — `INSTALL_PLATFORMS` (`android`, `ios-safari`, `ios-other`,
  `desktop`, `other`), `detectInstallPlatform(probe)` and `isInstalledDisplayMode`. Read its header: user-agent
  sniffing is forbidden elsewhere, this is the documented narrow exception, **nothing there changes a layout, a
  capability or a code path**, and the functions are pure and take the probe as an argument so the matrix is
  testable without a browser. Follow that pattern exactly and do not widen the exception.
  Covered by `installPlatform.test.ts`.
- `clients/pwa/src/routes/useInstallPrompt.ts` — captures `beforeinstallprompt` and exposes `available`,
  `installed`, `busy`, `outcome` and `promptToInstall`. The install capability is therefore already detected; this
  sub-issue consumes it and does not replace it.
- `clients/pwa/src/auth/CopyButton.tsx` — the clipboard probe and its fallback, with the comment "The failure path
  matters more than the success path". The new module exposes the same fact so other screens can ask, and
  `CopyButton` keeps its own behaviour unchanged.
- `clients/pwa/src/auth/RecoveryCodes.tsx` line 44 and
  `clients/pwa/src/routes/measurements/MeasurementSheetRoute.tsx` line 151 — the two `window.print()` call sites,
  with `@media print` blocks at `src/auth/auth.css` line 229 and
  `src/routes/measurements/measurements.css` line 216. Printing already works where it is used; what is missing is
  the **probe and the documented alternative**, not the feature.
- `docs/nfr/support-matrix.md` — section 1.1 (support decided by feature detection, never user-agent sniffing, and
  the refusal behaviour), section 1.2 (the capability vocabulary), section 4 (the engine matrix and the named
  platform features the floors exist to guarantee: service workers, `getUserMedia` on a secure origin, CSS
  container queries, `:focus-visible`, `structuredClone`, ES2021 syntax and the Web Crypto API), section 4.1 (the
  WebKit constraints: no `BarcodeDetector`, install only from Safari, per-browser storage, camera released on
  backgrounding, push only for Home Screen web apps from iOS 16.4), section 6 (the capability matrix per device
  class) and section 7 (the fallback ladders that already exist, for scanning, thermal printing, document printing
  and offline). **This is the specification. Extend section 7; do not write a second document and do not restate a
  ladder that is already there.**
- `clients/pwa/src/components/states/` — `EmptyState`, `ErrorState`, `LoadingState`, `Forbidden`,
  `NetworkStatusBanner`, `OfflineBlockedAction`, `RetryableError`, `StateRegion`. The refusal page is built from
  these, not from new markup.
- `clients/pwa/src/i18n/messages/index.ts` — its header states the rule for adding a family: one file exporting
  `<family>En` and `<family>Ta`, one line added to each of the two spreads, and the type gate in `en-IN.ts` fails
  `pnpm typecheck` when a key exists in one language and not the other.
- `tests/e2e/` and its nine projects, from **[E12-F03-1b]**; the browser axe and reflow helpers, from
  **[E12-F03-2]**.
- `clients/pwa/src/main.tsx` — the mount point, 43 lines. It renders, outermost first, `StrictMode`,
  `AppIntlProvider`, `DisplayPreferencesProvider`, `SessionProvider`, then `RouterProvider`. The refusal page must
  render **inside** `AppIntlProvider` and `DisplayPreferencesProvider` — it is built from message ids and a person
  who needs the 150% text size or the high-contrast theme needs it most on a page that refuses to start — and
  **outside** `SessionProvider` and the router. Saying "before `SessionProvider`" is not the same as "before the
  intl provider", and getting that wrong renders raw message ids.

## What is missing

- One place that answers "does this device have X". Each consumer would otherwise probe for itself, which is how a
  fallback ladder becomes five different ladders.
- Probes for the camera **API** (`navigator.mediaDevices.getUserMedia` on a secure origin) and for a camera
  **device** (an enumerable video input), barcode decoding (`BarcodeDetector` and its supported formats), push
  (`PushManager` and `Notification.permission`), share (`navigator.share` / `canShare`), file capture
  (`<input type="file" capture>` and `showOpenFilePicker`), and printing (`window.print`).
- The unsupported-configuration page. Today a device missing a required platform feature gets a blank screen or a
  runtime error, because `clients/pwa/src/main.tsx` mounts the router unconditionally.
- Fallback ladders in `support-matrix.md` section 7 for camera and media capture, clipboard and share, push, and
  file capture. Scanning, thermal printing, document printing and offline already have theirs.
- The lint rule `support-matrix.md` section 1.1 proposes — `navigator.userAgent` restricted outside the advisory
  and telemetry modules — which is what keeps the `installPlatform.ts` exception narrow.

## Scope

- [ ] Add `clients/pwa/src/app/capabilities.ts` — one pure, **synchronous** `detectCapabilities(probe)` over an
      injected probe object, in `installPlatform.ts`'s style, returning a closed record for **fourteen** keys:
      `serviceWorker`, `cameraApi`, `cameraDevice`, `barcodeDetector` (with the formats reported), `push`,
      `clipboardWrite`, `share`, `print`, `fileCapture`, `secureContext`, `containerQueries`, `focusVisible`,
      `structuredClone` and `webCrypto`. Each value is one of `'available' | 'unavailable' | 'blocked'` —
      `blocked` is the case a permission was refused, which is not the same fact as absence and must not be
      collapsed into it. No `navigator.userAgent` is read anywhere in this file.
- [ ] **Split the camera in two, because `support-matrix.md` section 4 and section 6 disagree if you do not.**
      Section 4 lists "`getUserMedia` on a secure origin" among the platform features the operating-system floors
      exist to guarantee, so the **API** is required; section 6 says camera scanning is `Fallback` on a desktop
      without a webcam, so the **device** is optional. `cameraApi` is therefore a required capability (the method
      exists on a secure origin) and `cameraDevice` is an optional one (a video input is enumerable, or the
      permission state already says so). Collapsing them either refuses every back-office desktop without a webcam
      or never checks the feature the floor was chosen for.
- [ ] Resolve the permission state **asynchronously and separately**. `navigator.permissions.query` returns a
      promise, so it cannot take part in a synchronous first-paint decision: the synchronous record decides the
      refusal, and a second, awaited pass upgrades `cameraDevice` or `push` from `unavailable` to `blocked` for the
      About rows only. That is why the About section has a genuine pending state and the refusal page does not.
- [ ] Add `clients/pwa/src/app/CapabilityProvider.tsx` and `useCapabilities()` — the synchronous detection runs
      **once**, at mount, the result is read from context, and the asynchronous permission pass updates the same
      context when it settles. Camera and push are probed without prompting: the module reports whether the API
      exists and what `navigator.permissions.query` already says, and **never** calls `getUserMedia` or
      `requestPermission` on its own. Asking for the camera is the scanner's job (#36), on a screen where the
      person has asked to scan. A browser with no `navigator.permissions` at all leaves the value as the
      synchronous answer and the About row says the state is unknown rather than inventing `blocked`.
- [ ] Add `clients/pwa/src/app/UnsupportedConfiguration.tsx` — the refusal page. It is rendered by
      `clients/pwa/src/main.tsx` **instead of** `SessionProvider` and the router, and **inside** `AppIntlProvider`
      and `DisplayPreferencesProvider`, when a **required** capability is unavailable — before any request is made.
      The required set is exactly the platform features `support-matrix.md` section 4's version-policy notes name as
      "present without a polyfill": service workers, `getUserMedia` on a secure origin (`cameraApi`), CSS container
      queries, `:focus-visible`, `structuredClone` and the Web Crypto API — six detectable ones, plus the secure
      context they all assume. ES2021 syntax is the seventh and is **not** detectable from inside a bundle that
      already failed to parse, so the page cannot catch that case and the body says so rather than pretending.
      The optional capabilities (`cameraDevice`, barcode decoding, push, share, file capture, clipboard, print)
      never refuse the application, because every one of them has a ladder that ends in something a member of
      staff can do.
- [ ] The refusal page says three things and nothing else: which capability is missing, which supported
      configuration to move to (the browser and operating-system floors of section 4, by name), and that the
      matrix is the source. It carries no telemetry call of its own — that is **[E12-F03-5]** — and no link into
      the application, because the application is what has refused to start.
- [ ] Add a **Device and capabilities** section to the existing `clients/pwa/src/routes/AboutRoute.tsx` (161
      lines): one row per capability with its state and, where it is unavailable, the alternative in one sentence
      and a link to the matrix section. This is where a support call looks, and it keeps the change to two screens.
- [ ] Add `clients/pwa/src/i18n/messages/capabilities.ts` with `capabilitiesEn` and `capabilitiesTa`, registered
      in both spreads of `messages/index.ts`. Every string on the refusal page and in the About section is a
      message id; the type gate proves the Tamil catalogue is complete.
- [ ] Extend `docs/nfr/support-matrix.md` section 7 with the four missing ladders — **7.5 camera and media capture**
      (the camera used to *photograph material*, which is #189's journey; it cross-references 7.1 for the camera
      used to *scan* and must not restate that ladder), **7.6 clipboard and share**, **7.7 push** and **7.8 file
      capture** — each in the shape sections 7.1 to 7.4 already use, each ending in something a member of staff can
      do, and each marked proposed where it states anything numeric. Push's ladder records what section 4.1 already
      decided: **v1 does not rely on web
      push for anything operational**, so its fallback is the in-app notification centre and the messaging
      adapters, and its absence is never a refusal.
- [ ] Add the lint rule section 1.1 proposes. Section 1.1 suggests `no-restricted-globals`, which **cannot express
      it**: `userAgent` is a property of `navigator`, not a global. Use `no-restricted-properties` with
      `{ object: 'navigator', property: 'userAgent' }` and the same for `platform`, in
      `clients/pwa/eslint.config.js`, with a second configuration object whose `files` is
      `['src/routes/installPlatform.ts']` turning the rule off — the single named exception, beside a comment citing
      section 1.1 and naming the substitution and why. Mark it in the comment as **proposed, to be confirmed**, because
      that is the
      status section 1.1 gives it.
- [ ] Add `tests/e2e/specs/capabilities.spec.ts`, tagged `@capability`: the About section reports the real
      capabilities of each engine, and — with a required capability deleted by a Playwright
      `addInitScript` before the bundle loads — the refusal page appears and the router does not mount. This is the
      "feature-detection test asserts the refusal page appears" row of section 9. It runs on the three
      pull-request projects **[E12-F03-2]** fixes, plus `firefox-desktop`, because Gecko is the engine whose
      `barcodeDetector` answer the matrix most depends on being `unavailable`.
- [ ] Record the required-capability set in `docs/nfr/support-matrix.md` section 9 beside its existing

## Acceptance criteria

- [ ] On each project the spec runs, the About screen's capability section reports the engine's real answers —
      `barcodeDetector` available on Chromium and unavailable on WebKit and Firefox, which is the fact
      `support-matrix.md` section 4.1 is built on. No row reads "unknown" **except** a permission row on a browser
      with no `navigator.permissions`, which is a real answer and says so.
- [ ] **Negative:** with a **required** capability removed before the bundle loads, the refusal page renders, names
      the missing capability and the supported configuration, and the router never mounts — no request is made and
      no session is opened. Asserted on all three engines.
- [ ] **Negative:** with an **optional** capability removed (`BarcodeDetector`, `navigator.share`, `PushManager`,
      or every video input), the application starts normally, the About section shows it unavailable with its
      alternative, and nothing is refused. In particular a desktop with **no webcam** is supported: `cameraApi` is
      available and `cameraDevice` is not, and that combination never reaches the refusal page.
- [ ] **Exception:** a camera permission already refused reports `blocked`, not `unavailable`, and the About row
      says how to re-grant it; the application does not prompt for the camera at start-up, which is proved by the
      absence of a permission prompt in the capability spec. The upgrade from `unavailable` to `blocked` arrives
      after the first paint, and the About row shows its own pending state until it does — asserted, not tolerated.
- [ ] `detectCapabilities` is pure **and synchronous**: its unit tests pass every state of all fourteen
      capabilities through the probe argument with no global stubbing, the way `installPlatform.test.ts` does, and
      the asynchronous permission pass is tested separately through its own injected resolver.
- [ ] `grep -rn "navigator.userAgent" clients/pwa/src` returns only `src/routes/installPlatform.ts`, and the new
      lint rule fails when a second file reads it. Demonstrated and reverted.
- [ ] The refusal page and the About section pass the browser axe run and `expectNoHorizontalOverflow` at its
      default widths and zooms, and carry no hard-coded English: the pseudo-locale story shows accented text
      throughout.
