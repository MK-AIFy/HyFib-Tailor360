Sub-issue of #48. Stage one of the two-stage dispatch plan Section 6.2 note 2 assigns to this issue: "#48 adds the
partial-delivery policy and the two-stage dispatch (online receive scan records a dispatch authorisation; the doorstep
confirmation references it)". Nothing of it exists. `grep -rn "dispatch_authorisation" src/` returns nothing;
`CustodyEndpoints.cs` maps an empty group, so `POST /custody/dispatch` — the route `docs/prd/raci.md` row 19 names — is
not there either. The Billing half **is** merged: `IDispatchEligibilityQuery` with `GetDispatchEligibilityAsync` and
`ConsumeExceptionAsync` shipped with #164 (closed), and its own summary says "Custody's dispatch scan (#37) is not built
yet, so this has no live caller". This issue is that caller.

## What is already built (do not re-build)

- `src/Modules/Billing/Tailor360.Modules.Billing.Contracts/Payments/IDispatchEligibilityQuery.cs` — **merged**.
  `GetDispatchEligibilityAsync(Guid orderId, IReadOnlyCollection<Guid> jobIds, Guid organisationId, CancellationToken)`
  returns `DispatchEligibilityResult(string Reason, string PolicyVersion, Guid? DispatchExceptionId)`. **`Reason` is a
  `string`, not an enum** — `DispatchEligibilityQuery.cs:50` produces it as `DispatchEligibilityReason.ToString()`, so
  the six legal values are the exact PascalCase member names `Paid`, `PartialAboveThreshold`, `PartialBelowThreshold`,
  `Unpaid`, `ApprovedException`, `NotEvaluated`. Map all six explicitly and **refuse any other string, including an
  empty one**, so a seventh reason added in Billing cannot default to allow. **The result carries no amount**:
  `amount_outstanding_at_authorisation` comes from a second call to `IFinancialTotalsQuery.GetOrderBalanceAsync(orderId,
  organisationId, ct)`, whose `Outstanding` is a `decimal` beside a `string Currency`. `ConsumeExceptionAsync` returns
  `Tailor360.Platform.Abstractions.Results.Result` — check it and refuse the scan when it fails, rather than treating a
  non-throwing call as success. Its own summary says it "fails closed — an order Billing has not heard of, or one with
  no posted invoice, answers `NotEvaluated`", and `ConsumeExceptionAsync(dispatchExceptionId, orderId, jobIds,
  dispatcherId, organisationId)` spends an approved exception exactly once and re-validates the balance, the job set,
  the policy version, the expiry **and that the dispatcher is not the approver**. Call it; do not re-check any of that
  here, and never read `billing.dispatch_exceptions` (ARCH-010, MO-2).
- `src/Modules/Billing/Tailor360.Modules.Billing.Domain/Payments/DispatchEligibility.cs` — `DispatchEligibilityReason`
  and the pure `DispatchEligibilityRule`. Read for the semantics; it is Billing's and is not referenced from Custody.
- `src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Orders/IOrderSnapshotQuery.cs` — `GetJobsAsync` "exists for the
  door", because `deliver_together` membership is re-read at the moment it matters (SQ-07/08/09). `GetAsync` gives the
  order state, so a cancelled order is recognised without reading `orders.*`.
- `src/Modules/Identity/Tailor360.Modules.Identity.Contracts/Directory/IBranchDirectory.cs` —
  `BranchSummary.TimeZoneId`, the only lawful source for "expiry = branch end of day".
- `src/Modules/Billing/Tailor360.Modules.Billing.Api/Payments/DispatchExceptionEndpoints.cs` and `PaymentEndpoints.cs` —
  the command-endpoint idiom: `.RequirePermission(key, BranchScope.CurrentBranch)`, `.ScopedToResource(kind,
  "routeParam")`, `.Audited("module.action")`, `.RequireIdempotency()`, `.RequireRateLimiting(...)`,
  `.WithRequestTimeout(...)`. `IdempotencyHeaders.Key` is how the client key is read.
- `src/Platform/Tailor360.Platform.Security/Endpoints/RateLimitPolicyNames.cs` — `ScanBurst` ("barcode scanning, which
  arrives in bursts as a rack is worked through") is the policy for both scans here.
- `src/Platform/Tailor360.Platform.Security/Permissions/CustodyPermissions.cs` — `Receive`, `Dispatch` and
  `RecordDeliveryOutcome` already exist with their flags; `docs/security/permission-matrix.md` lines 169 and 175 already
  carry `custody.dispatch` ("Fails closed: an unevaluated payment answer blocks the scan and the attempt is audited")
  and `custody.receive` ("The receive scan is what evaluates the dispatch gate"). **No permission is added by this
  issue.**
- `src/Platform/Tailor360.Platform.Abstractions/Time/IClock.cs` and `Identifiers/IIdGenerator.cs` — ARCH-014 and
  ARCH-015 mean every timestamp and identifier comes from these.

## Scope

- [ ] **`custody.dispatch_authorisations`** on `CustodyDbContext`, one expand-only migration — `dotnet ef migrations add
      DispatchAuthorisations`, which the scaffolder names `<timestamp>_DispatchAuthorisations`; the plan's
      `<issue>_<slug>` form (`48_dispatch_authorisations`) is recorded in the new row of `docs/dev/migrations.md` and is
      not a legal type name. Columns: id, order id, branch, organisation, the job set (a child table
      `dispatch_authorisation_jobs` so the set is queryable rather than a JSON blob), `eligibility_reason`,
      `billing_policy_version` and `custody_policy_version`, `amount_outstanding_at_authorisation` with its currency,
      `dispatch_exception_id` (nullable), `approver_user_id` (nullable — set only on the exception path),
      `authorised_by`, `authorised_at`, `expires_at`, `state` (`authorised`/`dispatched`/`spent`/`expired`), `spent_at`,
      `xmin`. Unique: at most one `authorised` row per garment job, enforced by a partial unique index on the child
      table.
- [ ] **`POST /api/v1/custody/orders/{orderId}/delivery-receive`** — the delivery-team receive scan at the branch, the
      one place the payment rule blocks (`docs/prd/state-transitions.md` section 4.1, row "With QC → Delivery team
      receive scan at the branch"). **The order is in the path on purpose**: a body-only route has no route parameter,
      so `.ScopedToResource` has nothing to bind to and ARCH-023 cannot be satisfied positively. Body: the scanned
      identities or the job set, the client event UUID, an optional `dispatchExceptionId`, an optional reason. It
      re-reads the parcel through `IOrderSnapshotQuery.GetJobsAsync`, applies `DeliveryDispatchPolicy` from #E11-F02-1,
      calls `GetDispatchEligibilityAsync`, and on `Paid`, `PartialAboveThreshold` or `ApprovedException` records the
      authorisation, calling `ConsumeExceptionAsync` in the same transaction on the exception path. `custody.receive`,
      `BranchScope.CurrentBranch`, `.ScopedToResource(CustodyResourceKinds.Order, "orderId")`,
      `.Audited("custody.receive")`, `.RequireIdempotency()`, `RateLimitPolicyNames.ScanBurst`,
      `.WithRequestTimeout(RequestTimeoutPolicies.Command)`.
- [ ] **It is a scan, so it records a scan event — through [E07-F03-1], never beside it.** Section 4.1's output for
      this row is a `dispatch_authorisation` **and** the custody move to the delivery team, and `docs/prd/raci.md`
      **row 17** routes the delivery-custody handover through `POST /custody/scans` with action `RECEIVE`, which is
      [E07-F03-1]'s endpoint and [E07-F03-2]'s transfer. This issue therefore calls those application services from
      inside its own transaction and **adds no second way to write `custody.scan_events` or `custody_transfers`**; two
      scan paths in one module is how a custody chain acquires rows nobody can explain. Row 19 names
      `POST /custody/dispatch`, which is below, and names no route for the gate itself — so the pull request adds a
      one-line note to `docs/prd/raci.md` row 19 recording the route it took, as the deviation it is.
- [ ] **The refusal, in full.** `Unpaid`, `PartialBelowThreshold` and `NotEvaluated` are refused with an RFC 9457
      problem whose code is `custody.dispatch-blocked` (EX-10, verbatim), carrying the eligibility reason, the policy
      version and the two documented ways out — take the balance, or obtain a single-use exception approved by someone
      other than the dispatcher. The attempt is audited whether it succeeds or fails. A garment that failed QC, is on
      hold or is in the wrong custody has **no** exception path and is refused on the policy outcome before Billing is
      asked at all (`docs/prd/state-transitions.md` section 9.2). A handover that would split a live `deliver_together`
      parcel is refused with `orders.delivery-would-split-parcel` — the code section 9.1 fixes; its prefix names the
      rule's owner, not the refusing module, and it is used as written rather than re-coined.
- [ ] **Expiry = branch end of day**, computed from `BranchSummary.TimeZoneId` through `IClock` (never `DateTime.Now`,
      ARCH-014). Section 4.1 fixes the rule; no duration is invented.
- [ ] **`POST /api/v1/custody/dispatch`** — the dispatch scan, **irreversible** (section 7 of `state-transitions.md`).
      Requires an `authorised` authorisation that has not expired, moves it to `dispatched`, records the custody
      transfer out to the delivery team through **[E07-F03-2]**'s transfer mechanism — called, not reimplemented — and
      writes `custody.dispatch-recorded.v1` to the Custody outbox in the same transaction. `custody.dispatch`,
      `BranchScope.CurrentBranch`, `.Audited("custody.dispatch")`, `.RequireIdempotency()`, `ScanBurst`,
      `.WithRequestTimeout(RequestTimeoutPolicies.Command)`. The route is the one `docs/prd/raci.md` row 19 names and
      carries the authorisation in its **body**, so it has no route parameter and **ARCH-023 does not engage**; the
      branch is evaluated server-side against the authorisation's own `branch_id`, and a caller from another branch gets
      the same answer as a caller naming an authorisation that does not exist.
- [ ] **`GET /api/v1/custody/dispatch-authorisations/{authorisationId}`** — what the doorstep screen reads before it can
      confirm: state, expiry, the job set, the eligibility reason and the policy version. `custody.dispatch`,
      `BranchScope.CurrentBranch`, `.ScopedToResource(CustodyResourceKinds.DispatchAuthorisation, "authorisationId")`,
      `DefaultUser`, `Read`. **No amount is returned at all.** The stored figure is evidence of what was outstanding
      when dispatch was allowed, read by an Auditor through a custody export; it is not a balance for a screen, and the
      doorstep screen needs no figure to complete a handover. A conditional "unless the caller holds a Billing read"
      would be a masking rule this repository does not have — `IOrderSnapshotQuery.GetPricedAsync`'s
      `TotalsIncluded` remarks record why the mask is declared and not yet applied — so do not invent one.
- [ ] **Custody event contract** `custody.dispatch-recorded.v1` in `Custody.Contracts`, versioned, carrying order, job
      set, authorisation id, actor, branch and server time — and **no customer identifier, no amount and no recipient**.
      Already named in `docs/architecture/module-ownership.md` section 5.6, so no document amendment is needed for it.
- [ ] **The event's documentation is part of the build, not an afterthought.**
      `tests/Tailor360.ContractTests/IntegrationEventTests.cs` fails until
      `docs/integration/events/custody.dispatch-recorded.v1.schema.json` and `.example.json` exist and describe
      **exactly** the properties the record serialises — no more and no fewer — and until a row is added to
      `docs/integration/events/README.md`. The same tests hold the wire name to `<module>.<event-name>.v<major>`, hold
      `SchemaVersion` to the major in the name, require the type to live in `Custody.Contracts`, and refuse a property
      whose **name** looks like personal data. Read a merged pair first — `billing.dispatch-exception-approved.v1.*` is
      the closest — and copy its shape. `README.md` is a single-writer file.
- [ ] Payloads in `Custody.Api` (ARCH-013); registration in `AddCustodyModule`; the three operations regenerated into
      `docs/api/openapi.v1.json` and `clients/pwa/src/api/schema.d.ts`.

## Acceptance criteria

- [ ] **Paid path:** Delivery Staff scans an order whose invoice is settled; an authorisation is recorded with the
      Billing policy version, the outstanding amount at the time, the job set and an expiry at the branch's end of day;
      a subsequent dispatch scan succeeds once and publishes exactly one `custody.dispatch-recorded.v1`.
- [ ] Every route declares a permission with branch scope, exactly one rate-limit policy, a resource scope or a recorded
      justification, and — for the two commands — the audit filter and idempotency (ARCH-007, ARCH-008, ARCH-017,
      ARCH-023).
- [ ] **Negative — the control itself:** each of `Unpaid`, `PartialBelowThreshold` and `NotEvaluated` refuses the
      receive scan with `custody.dispatch-blocked`, records no authorisation, and writes an audit row naming the actor,
      the order and the reason. An order Billing has never heard of is `NotEvaluated` and is therefore blocked, not
      allowed.
- [ ] **Negative:** a failed-QC, held or wrong-custody garment is refused with its own blocking reason and is **not**
      offered the exception path, even when a live approved exception exists for the order.
- [ ] **Negative:** a dispatch scan with no authorisation, with an expired one, or with one for a different job set is
      refused; the garment stays with the delivery team and nothing is published.
- [ ] **Exception:** the `ApprovedException` path consumes the exception exactly once — a second receive scan with the
      same `dispatchExceptionId` is refused by Billing's own re-validation and records no second authorisation; an
      exception approved by the person now dispatching is refused.
- [ ] **Exception:** a retried receive scan with the same `Idempotency-Key` returns the first outcome and creates no
      second authorisation; the same client event UUID under a different actor is `409 custody.event-conflict`, never a
      replay (plan Section 4.4).
- [ ] Command latency meets `docs/nfr/slo.md` section 5 row "Command latency (S3)", `p95 < 800 ms`; the scan round trip
      belongs to the client issue and its figure is not claimed here.
