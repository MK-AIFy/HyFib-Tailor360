Sub-issue of #33. The workflow engine has no data model at all. `src/Modules/Orders/Tailor360.Modules.Orders.Domain/`
holds 35 files and not one of them mentions a phase, a transition or a workflow version; the only migration,
`20260911141153_InitialOrdersSchema`, creates twelve tables and none of them is `workflow_definitions`,
`workflow_versions` or `workflow_version_phases`, which
[`docs/architecture/module-ownership.md`](../../architecture/module-ownership.md) line 407 assigns to the `orders`
schema. Yet `GarmentJob` already carries `WorkflowDefinitionId` and a nullable `WorkflowVersionId`
(`Jobs/GarmentJob.cs:168,177`) and refuses to re-pin one — so the job side of the contract exists and the thing it
points at does not. This slice builds that thing and nothing else: the configuration records, the graph rules, and
the store. No endpoint, no phase instance, no assignment.

## Scope

- [ ] `Domain/Workflows/WorkflowDefinition.cs` — the named process: code, name, description, active flag,
      organisation. Codes follow the catalogue code rules already used by `CatalogCode.cs` in the Catalog module;
      mirror the shape, do not reference it (ARCH-004).
- [ ] `Domain/Workflows/WorkflowVersion.cs` — a draft → published → retired record per D8, with `version_number`
      per definition, the phase set, the transition graph, the category mapping and the publication metadata. A
      published version is immutable: every mutator refuses unless the status is `Draft`.
- [ ] `Domain/Workflows/WorkflowPhase.cs` — code, display name, ordinal, `required_role_keys`,
      `requires_evidence`, `expected_duration`, `sla`, `is_optional`, `is_skippable`, `is_terminal`.
- [ ] `Domain/Workflows/PhaseTransition.cs` and `Domain/Workflows/WorkflowGraph.cs` — the graph and the six checks
      plan Section 8 (#33, "Administration") names: exactly one start phase; at least one terminal phase; every
      phase reachable from the start; no phase without an outbound transition unless it is terminal; no phase whose
      `required_role_keys` is empty; unique phase codes. Each check returns a stable dotted code and the phase code
      it is about, in the shape `Catalog.Contracts.Catalogue.CatalogFinding` uses, so the report renders the same
      way the catalogue's does.
- [ ] `Domain/Workflows/WorkflowVersionStatus.cs` — `Draft`, `Published`, `Retired`, with the same "no delete"
      discipline `GarmentJobStatus.cs` documents.
- [ ] `Application/Abstractions/IWorkflowDefinitionStore.cs` and
      `Infrastructure/Persistence/WorkflowDefinitionStore.cs` — load a definition whole with its versions, add,
      `EntityTagOf` for `If-Match`, and `SaveAsync` returning `OrdersWriteFailures`-mapped results the way
      `OrderStore.cs` does. Plus `FindPublishedVersionAsync(definitionId, at)`, which is what start-production will
      call in E06-F02-4.
- [ ] Three `DbSet`s and their mappings in `OrdersDbContext.cs`, inside the `orders` schema only (ARCH-005, MO-2),
      every table carrying `id`, `organisation_id`, `created_at/by`, `updated_at/by` and `xmin` per
      `src/Modules/CLAUDE.md` section 5. `workflow_version_phases` is a child table; the transition graph and the
      category mapping are `jsonb` columns on `workflow_versions`, because `module-ownership.md` line 407 enumerates
      exactly three tables for this area and plan Section 8 puts "transitions graph, category mapping" on the
      version.
- [ ] One migration, `33_workflow_definitions`, expand-only. Partial unique index on
      `(definition_id) WHERE status = 'Published'` so a definition can never have two published versions at once,
      and unique `(definition_id, version_number)`.
- [ ] Registration in `OrdersModuleServiceCollectionExtensions.cs`: the store only. **Configuration, not code**
      (DOR-11, NFR-MQ-05): phases and their order are versioned data in these tables, seeded by
      `init-reference-data` in E06-F02-3, never a C# enumeration.

## Acceptance criteria

- [ ] A draft version carrying the six phases of `docs/prd/workflows/blouse.md` section 2.1 and their transitions
      round-trips through `WorkflowDefinitionStore` and reads back identical — phase order, roles, durations, the
      graph and the category mapping — with `xmin` serving as the `If-Match` token.
- [ ] `WorkflowGraph` validation returns one finding per defect, all of them in a single report, for a version with
      an unreachable phase, a non-terminal dead end, no start phase, two start phases, **no terminal phase at
      all**, a duplicated phase code and a phase with no permitted role. That is seven defects exercising the six
      checks, because "no start phase" and "two start phases" are both failures of the one-start-phase check. The
      report names the offending phase code in `Target`, and is null on `Target` for a finding about the version
      as a whole — the shape `CatalogFinding` documents.
- [ ] **Negative:** every mutator on a version whose status is `Published` or `Retired` is refused with a conflict
      result naming the status, and the row is unchanged — asserted by reading the row back, not by trusting the
      return value.
- [ ] **Negative:** two concurrent attempts to publish a second version of one definition cannot both succeed; the
      partial unique index refuses the loser and the refusal surfaces as a named result from `SaveAsync`, never as a
      raw `PostgresException`.
- [ ] **Exception:** a retired version stays readable for ever, because a garment job may be pinned to it
      (INV-JOB-02). There is no delete, and `Down` on the migration drops the tables only.
- [ ] `dotnet run --project src/Tools/Tailor360.Cli -- migrate --dry-run` then `migrate` apply cleanly, and `Down`
      has been executed once (`src/Modules/CLAUDE.md` section 6 rule 4).

## Data and classification

Every field below is operational configuration, not a record about a person or a customer, which is why the whole
table reads Internal. The grant metadata names staff, which is 5.15.

| Item | Class | Purpose | Retention | Who may read it | Logs, telemetry, export |
| --- | --- | --- | --- | --- | --- |
| `orders.workflow_definitions.code`, `.name`, `.description` | Internal (`docs/nfr/data-classification.md` 5.7) | Name the process a category is made by | Business record; no routine deletion (5.7) | `catalog.workflows.edit` holders; `orders.read` holders see the pinned version's phases | Codes may appear in logs and as telemetry attributes; names may not be a metric dimension |
| `orders.workflow_versions.status`, `.version_number`, `.published_at`, `.retired_at` | Internal | The immutable published record a job is pinned to | As above | As above | Safe, low cardinality |
| `orders.workflow_versions.transitions` (jsonb), `.category_mapping` (jsonb) | Internal | The graph and which categories use it | As above | As above | Phase codes only; never the whole document in a log line |
| `orders.workflow_version_phases.required_role_keys` | Internal | Which roles may work a phase | As above | As above | Role keys are safe; they are not a person |
| `orders.workflow_versions.published_by`, `.created_by`, `.updated_by` | Personal (5.15) | Who drafted and who published | As the row | `admin.users` for administration; the audit trail otherwise | Identifier only. Never a display name in a log, a metric or a trace attribute |

No new integration event, no new log field, no media, no credential and no secret in this slice.
