Sub-issue of #45. Plan Section 8 (#45) lists `customer_retention` — "new vs repeat customers per period, repeat
interval, category mix" — among this feature's projections, and it is the only one of them whose grain is the
customer rather than the garment. Nothing of it exists: Reporting has no schema before #183 and no projection before
E10-F02-1, and `grep -rn "retention" src/Modules/Reporting` returns nothing. It is split out because it is the one
slice that brings a customer identifier into Reporting, which is a classification decision of its own, and because
it is the only one that has to survive a customer merge.

## Scope

- [ ] **`reporting.projections_customer_order_history`** — one row per customer per branch:
      `organisation_id`, `branch_id`, `customer_id`, `first_order_confirmed_at`, `last_order_confirmed_at`,
      `orders_confirmed`, `orders_cancelled`, `garments_confirmed`, `days_since_previous_order` (the most recent
      interval), `interval_days_total` (for a mean over intervals), `merged_into_customer_id`, `last_event_at`. The
      row is a derived fact about ordering behaviour and carries **no name, no telephone number, no address and no
      measurement**.
- [ ] **`reporting.projections_customer_retention_period`** — `organisation_id`, `branch_id`, `period_start`,
      `period_grain` (`Day`, `Week`, `Month`, in the branch timezone), `new_customers`, `repeat_customers`,
      `orders_confirmed`, `garments_confirmed`, `mean_interval_days`, `last_event_at`. **No category dimension on
      this table**: the decision is taken here rather than left to the session, because two grains on one table is
      the mistake that makes a total disagree with its own breakdown.
- [ ] **`reporting.projections_customer_category_mix_period`** — the category mix as its own table at its own grain:
      `organisation_id`, `branch_id`, `period_start`, `period_grain`, `category_key`, `garments_confirmed`,
      `orders_confirmed`, `last_event_at`. The period table above holds the totals, this one holds the breakdown, and
      the acceptance criterion that the breakdown sums to the total is a join between them rather than a
      self-consistency check inside one row.
- [ ] **Handlers** `reporting.retention-on-order-confirmed`, `-on-order-cancelled` and `-on-customer-merged`,
      following `OrderFactHandlers.cs`: unique `HandlerName` each, `Schema = ReportingDbContext.SchemaName`, writes
      staged and never saved, safe to call twice.
- [ ] **The merge case, as a first-class requirement.** On `customers.customer-merged.v1` the merged customer's
      history is folded into the survivor's — orders summed, `first_order_confirmed_at` taken as the earlier, the
      intervals recomputed — and `merged_into_customer_id` is stamped so the fold is visible and idempotent. A
      chain (A into B, then B into C) resolves transitively, which is what the event's own remarks require.
- [ ] **`GET /api/v1/reporting/retention`** — per period and branch: new customers, repeat customers, the repeat
      rate with its numerator and denominator, orders and garments per customer, the mean interval in days and the
      category mix. **Aggregate figures only**: no row names or identifies a customer, which is what keeps the
      response Internal and the route readable by a Branch Manager without `customers.read`.
- [ ] **The route declares** `RequirePermission(ReportingPermissions.Read, BranchScope.AssignedBranches)`
      (ARCH-007), exactly one rate-limit policy — `RateLimitPolicyNames.DefaultUser` (ARCH-017) — and
      `RequestTimeoutPolicies.Report`. No `.Audited(...)`, because the response carries no personal data; the
      **projection** holds Personal data and the response deliberately does not.
- [ ] **Payload types in the `Api` project** (ARCH-013). No response view: every response field is `Operational`.
- [ ] **One migration**, `CustomerRetentionProjection`, on the `ReportingDbContext` chain, scaffolded with the
      command in `src/Modules/CLAUDE.md` section 6.
- [ ] **Metric dictionary** entries in `docs/reports/metrics.md` for `new_customers`, `repeat_customers`,
      `repeat_rate`, `mean_order_interval_days` and `category_mix_share`, each naming its formula, its source
      events, its denominator, the merge rule, the cancellation rule and the period basis. A customer new in one
      branch and returning in another is the definitional case: state which reading the entry takes and why.
      `docs/reports/` does not exist in the working copy; the scaffold is #183's and E10-F02-1 extends it first.
      Check whether #183 shipped a seeding path for its `metric_definitions` table (`grep -rn "metric_definitions"
      src/ docs/`); if it did, add these rows there too, and if it did not, the document is the dictionary and the
      table stays empty.

## Acceptance criteria

- [ ] Over a synthetic stream of confirmations — two customers ordering once, one ordering three times across two
      months, one order cancelled — `GET /api/v1/reporting/retention` reports the new and repeat counts, the repeat
      rate with its denominator, and the mean interval, and the cancelled order is excluded per the metric
      dictionary rather than silently counted.
- [ ] The category mix shares sum to 100% of the period's garments within the stated rounding, and
      `projections_customer_retention_period.garments_confirmed` equals the sum of
      `projections_customer_category_mix_period.garments_confirmed` for the same branch, period start and grain —
      asserted as a join, so the breakdown can never disagree with its own total.
- [ ] **Exception — a customer merge:** after `customers.customer-merged.v1`, the survivor carries the union of both
      histories, the earlier `first_order_confirmed_at`, and a repeat count that treats the two records as one
      person; the merged row is retained with `merged_into_customer_id` set rather than deleted, so the fold is
      auditable and replaying the event changes nothing.
- [ ] **Exception — a merge chain:** A merged into B and then B into C leaves one history on C and none on A or B,
      whichever order the two events are delivered in.
- [ ] **Negative — another branch:** a caller assigned to branch A receives no branch-B figure, and the response
      states which branches it covered.
- [ ] **Negative — no permission:** a caller without `reports.read` is answered `403` `security.forbidden`.
- [ ] **Negative — no customer is nameable:** a test asserts the payload type has no property carrying a customer
      identifier, name, telephone number or address, and that a single-customer period is still reported as a count
      (the response must not become identifying by being narrow enough).
- [ ] **Rebuild equals live:** `rebuild-projection` reproduces all three tables, including the merge folds.

## Migration and rollback

One expand-only migration, `CustomerRetentionProjection`, creating **three** tables in `reporting` — the history
table, the period table and the category-mix period table — and altering nothing existing. The previous release
tolerates it because the tables are new and unread. `Down` drops them and is executed at least once before the pull
request opens. Rollback is redeploying the previous tag with the tables unused. A row is added to the migration
register of `docs/dev/migrations.md`, and because the history table holds a Personal column, the classification row
above is part of the same pull request (`src/Modules/CLAUDE.md` section 6).
