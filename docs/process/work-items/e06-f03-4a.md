## Adding an integration event, and the six tests that will fail you

`tests/Tailor360.ContractTests/IntegrationEventTests.cs` enforces the whole chain. Read it before writing the
first record.

- `EveryEventIsDocumentedByASchemaAndAnExample` — both `docs/integration/events/<wire-name>.schema.json` and
  `<wire-name>.example.json` must exist. For size: `orders.job-held.v1.schema.json` is 72 lines and its example
  12, so budget about 84 lines per event for the JSON alone.
- `EverySchemaDescribesExactlyWhatTheEventPutsOnTheWire` — the schema's `properties` must be **exactly** the set
  the record serialises, `required` must be non-empty and must name nothing the record lacks, and
  `additionalProperties` must be present and `true` (`docs/integration/events/README.md` section 2: a closed
  schema would make every additive change breaking).
- `EveryExampleMatchesItsSchemaAndNamesItsOwnEvent` — the example carries the same property set and its
  `eventType` is the wire name.
- `EveryEventVersionsItsNameAndItsPayloadTheSameWay` — `SchemaVersion` agrees with the `.vN` in the wire name.
- `EveryEventIsDeclaredInItsOwnModulesPublishedSurface` — the record lives in `Orders.Contracts` and the wire name
  appears in the **Publishes — integration events** list of `docs/architecture/module-ownership.md` section 5.5.
  If it does not, amend that list in the same pull request; section 9 of that document requires it.
- `NoPayloadCarriesAFieldNamedLikePersonalData` — `IntegrationEventInventory.PersonalFieldWords` rejects a
  serialised property whose whole name, **or any camel-cased word inside it**, is one of `name`, `firstname`,
  `lastname`, `fullname`, `displayname`, `nativename`, `phone`, `telephone`, `mobile`, `msisdn`, `email`,
  `address`, `postcode`, `pincode` and the rest of that list. So no `checklistName`, no `defectName`, no
  `criterionName`, no `inspectorName`, no `roleName` — codes, keys, identifiers, statuses, amounts and timestamps
  only. The register `IntegrationEventInventory.PersonalFieldExemptions` exists but using it needs the approval
  `docs/nfr/data-classification.md` section 5.3 describes, which this issue does not have.

Two shapes to copy rather than invent: the payloads are **flat** — no `payload` wrapper — as
`orders.job-held.v1.schema.json` shows (`eventId`, `occurredAt`, `aggregateId`, `organisationId`, `branchId`,
`orderId`, `garmentJobNumber`, `reasonCode`, `eventType`, `schemaVersion`); and the `$comment` those schemas carry
states that a property added within `v1` is optional forever. Add the event's row to the table in
`docs/integration/events/README.md` as well — one row per event, with links to both files.
