## Acceptance criteria

- [ ] An Admin records a deletion request for a customer over HTTP; an Owner who is not the requester approves it
      with step-up and a reason; `GET /api/v1/admin/privacy/requests/{requestId}` shows `Approved`, the approver, the
      decision instant and the reason, and the register lists it under a status filter. No direct database access.
- [ ] Every route this issue adds declares a permission (ARCH-007), exactly one rate-limit policy (ARCH-017), and
      each `POST` carries `.Audited(...)` with a mandatory reason (ARCH-008).
      **ARCH-018 binds per endpoint, on that endpoint's own permission — get this the right way round.** The
      **create** route carries `customers.request_deletion`, which `CustomersPermissions.cs` line 97 catalogues
      `RequiresStepUp: true`, so **the create route must declare `.RequireStepUp()`** or
      `AuthorisationMatrix.cs` line 197 fails it. The **approval** route carries
      `admin.privacy.approve_erasure`, which this issue declares, so it must be catalogued `RequiresStepUp: true`
      for its `.RequireStepUp()` to be legal — ARCH-018's check runs both ways, and
      `tests/Tailor360.UnitTests/Security/StepUpRequirementTests.cs` is where the pairing is reasoned about. The two
      reads use `admin.privacy.read`, which is catalogued `RequiresStepUp: false`, so **they must not declare it**.
      **ARCH-023 is not the reason for `TouchesNoBranchOwnedResource` here**: its allowed-exceptions row
      (`docs/architecture/architecture-rules.md` line 346) puts organisation-scoped routes outside the rule, and
      `EndpointAuthorisationInspector.UnscopedIdentifierComplaints` yields nothing for `BranchScope.Organisation`.
      Declare it anyway, as `MapExport` and `FeatureFlagAdminEndpoints` do, so the matrix's `Resource` cell reads
      `—` the way their rows do.
- [ ] **Negative**: the person who recorded the request cannot approve it — `409 privacy.approval-by-requester`, and
      the request is still `Requested` afterwards. A unit test asserts the aggregate refuses it even when called
      directly, so the rule is not only in the endpoint.
- [ ] **Negative**: approving a request that is already `Refused` is refused with a named code and changes nothing;
      approving with a stale `If-Match` returns `409` carrying the current version, per
      `ConcurrencyResults.VersionConflict` and the behaviour
      `tests/Tailor360.IntegrationTests/Platform/ConcurrencyContractTests.cs` already pins. **The `ETag` the detail
      read emits is the one this issue makes work**: the `GET .../{requestId}` route calls
      `HttpResponse.SetEntityTag(RowVersion.EntityTagOf(context, request))` and the two commands declare
      `.RequireIfMatch()`, so the criterion rests on an endpoint this pull request builds rather than on one that
      might not support it. A caller holding
      `customers.request_deletion` but not `admin.privacy.approve_erasure` is refused the approval with the `403`
      answer already defined in `matrix.yaml`.
- [ ] **Negative**: a replayed `Idempotency-Key` on the create route returns the first request rather than recording
      a second; the same key with a different body is refused `422 idempotency.key-reused`.
- [ ] **Exception**: a refusal is terminal and keeps everything — the requester, the reason asked for, the reason
      refused — and a new request for the same subject may be recorded afterwards and is a distinct row. A refused
      request never reads as "not found".
- [ ] **Exception**: a request of type `Export` records `related_export_id` pointing at the export the existing
      `POST /api/v1/customers/{customerId}/export` produced, and does not itself generate a document.
- [ ] The detail payload names the subject by identifier only; a contract test asserts no payload field carries a
      customer name, phone number or email.
