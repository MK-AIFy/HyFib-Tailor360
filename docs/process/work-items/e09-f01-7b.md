Sub-issue of #41. Putting a price in force: the publication checks read **before** a publish, and the publish itself
— step-up, a reason, and the two races another administrator can win. E09-F01-7 ships the price-list version editor
up to the last save and deliberately carries no validate control and no publish control; this issue adds them, and
reuses the findings list E09-F01-5b built rather than writing a second one.

It is split from E09-F01-7 because one session cannot carry both under the 1,500-line target of CLAUDE.md section 6,
and because this half is where the second permission key, the step-up renewal, the mandatory reason, **two** distinct
conflict codes and the severity distinction **OD-19** turns on all live. It is also the slice that genuinely needs a
**published tax configuration**, which is why E09-F01-5b blocks it and E09-F01-7 does not.

## Acceptance criteria

- [ ] An Owner opens a draft version holding an item whose tax code the published tax configuration carries, runs
      the validation, sees it report nothing to fix, publishes with a reason, and sees the version move to
      `Published` with the version it superseded named — no deployment, no database access.
- [ ] **Negative, the publication check:** a draft holding an item whose tax code no published tax configuration
      carries is refused at publish with `billing.tax-code-unknown` against that item, and a draft with items while
      **no** tax configuration is published is refused with `billing.tax-configuration-missing` — both rendered as
      sentences against their target, with **every** finding listed, not just the first. The second refusal's
      sentence names publishing a tax configuration as the way out and links to `/admin/tax-configuration`.
- [ ] **Negative, severity is not flattened:** a draft with no item at all publishes, and the warning
      `billing.no-items` is shown as a warning rather than as a failure; a version leaving a branch unpriced
      publishes with `billing.branch-left-unpriced` shown the same way, naming the branch. A screen that showed a
      warning as a failure would teach an administrator to ignore the report.
- [ ] **Negative, two different races:** when another administrator has already published a version of this list the
      publish answers `billing.publish-conflict`; when another **list's** version pricing one of the same branches
      was published in the same moment it answers `billing.branch-publish-conflict` — **two different sentences**,
      the second naming the branch. Either way the screen re-reads the version and shows its new status rather than
      leaving a stale `Draft` on screen. This is the client half of the parent's "concurrent effective-version
      publish" verification, whose server half is
      `TheDatabaseRefusesTwoPublishedVersionsPricingOneBranchWhateverTheChecksSaw`.
- [ ] **Negative, authorisation:** a holder of `billing.manage_price_lists` without `billing.publish_price_list` sees
      no publish control and a `Forbidden` region naming who may publish; a holder of neither meets
      `RequirePermission`'s `EmptyState`, never a redirect. The test also asserts the screen handles the **server's**
      refusal of a publish, because the claim list from `GET /me` can be minutes old.
- [ ] **Exception path, step-up:** when the publish answers `403 security.step-up-required`, the transport renews the
      proof of identity in place and replays the identical request with the **same** `Idempotency-Key`; the screen
      shows no challenge of its own and exactly one publication results.
- [ ] **Negative, the reason:** a publish submitted with no reason is refused with `billing.reason-required` as a
      field error on the reason field, and the dialog stays open with the typed reason intact.
- [ ] **Negative, the stale report:** a write made after a validation run marks the report stale and says so; the
      publish control does not read a stale report as permission to publish.
- [ ] **Offline:** the validate and publish controls render `OfflineBlockedAction` — "Needs connection — this will
      not be queued", word for word.

## Data and classification

Nothing is persisted client-side: component state only, no `localStorage`, no service-worker cache, and **no rate,
amount or reason in any telemetry attribute**.

| Item | Class | Purpose | Retention | Who may read it | Logs, telemetry, export |
| --- | --- | --- | --- | --- | --- |
| `BillingValidationReport` and each `BillingFinding` — severity, code, message, target | **Internal** | To say why a publication would be refused, and what it warned about | None client-side | Holders of `billing.manage_price_lists`; `owner` today | The server's sentence is rendered; the code is never shown to a person and never logged by the client. A finding names an item code or a branch, never a rate — `docs/security/permission-matrix.md` line 423 makes the same point about the tax checks |
| `PriceListPublication` — the published version with its items and rules, the superseded version, the findings | **Confidential** (it carries `baseRate` and the rule bounds) / **Internal** (the identifiers) | To show what was published and what it replaced | None client-side | As above | "Price-list rates and discounts" is the Confidential row of `docs/nfr/data-classification.md` line 52. The published payload carries the whole version, so the screen must not log it, export it or put any part of it in telemetry |
| The publish **reason** the administrator types | **Internal** — evidentiary | The audit trail of a publication that changes what every future order is quoted at | Server-side, per `docs/nfr/data-classification.md` section 5.16 | `auditor`, `owner` | Sent in the body, stored on the audit event by `.Audited(..., reasonRequired: true)`. The client keeps it only until the request succeeds, and **never** in `localStorage` |

No new field is unclassified and no retention period is invented.

## Migration and rollback

No schema change: no table, no column, no `DbContext`, no migration. Proof is
`dotnet run --project src/Tools/Tailor360.Cli -- migrate --dry-run` reporting nothing outstanding, pasted in the
pull request. Rollback is redeploying the previous client bundle — but note what rollback does **not** undo: a
version published through this screen stays published, its rows are frozen by trigger, and it retired the version it
superseded in the same transaction. Say so in the pull request; it is the one place in this family where a client
change has an irreversible consequence.
