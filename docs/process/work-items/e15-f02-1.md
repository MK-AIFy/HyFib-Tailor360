Sub-issue of #60. The first slice of the parent: the database half of the backup chain. The design is already
decided, so this slice implements it rather than choosing it — plan D18 (`docs/IMPLEMENTATION_PLAN.md` line 140),
`docs/architecture/deployment.md` section 7 and `docs/nfr/slo.md` section 6 fix the mechanism, the destination and
the retention. Nothing of it is built: `ls infra/backup` fails, `infra/docker/` holds only `Dockerfile.pwa`,
`Dockerfile.web` and `Dockerfile.worker`, `grep -rni pgbackrest infra/ src/ scripts/` returns nothing, and the
`postgres` service at `infra/compose/docker-compose.staging.yml:292` runs the stock `postgres:16.13-alpine` image
with `max_connections` and `log_min_duration_statement` as its only settings — no `archive_mode`, no
`archive_command`, no repository. There is therefore no recovery point of any kind today.

- `tests/Tailor360.ArchitectureTests/NegativeControlTests.cs` (212 lines) — **where a negative control goes.**
  `docs/architecture/architecture-rules.md` line 442 is explicit: "Every source-scan rule ships a control in

- `docs/nfr/slo.md` section 6 — RPO, RTO, destination, key custody, retention and restore cadence per hosting

- `docs/platform/secrets.md` — secret classes, the file-per-key convention and rotation. Line 57 already says a

## What is missing

- No `infra/backup/` directory, so nothing schedules a backup and nothing configures a repository.

      **The default development path must not change, and this is the one way this slice can break every other
      developer.** `archive_mode` and the custom image are both *unconditional* properties of the `postgres`
      service — a compose profile cannot switch another service's image or command — so writing `archive_mode=on`

      `./scripts/dev up`, `./scripts/dev reset`, `./scripts/dev status` and every integration-test container run.
      Two consequences, both real:

      1. With archiving on and no repository reachable (the ordinary case, because the profile is off),
         `archive_command` fails on every segment, PostgreSQL **retains every WAL file it could not archive**, and
         `pg_wal` grows until the volume fills and the cluster stops accepting writes. That is the exact failure
         this issue's own "Rolling the chain forward after an outage" note describes, inflicted on every laptop.
      2. A `build:` stanza on `postgres` makes `docker compose up` build a custom PostgreSQL image before the
         backing services start, so `up`, `reset` and the integration tier all acquire a Docker **build** dependency
         they do not have today.

## Acceptance criteria

- [ ] On a machine with a Docker daemon, after `docker build -f infra/docker/Dockerfile.postgres -t
      tailor360-postgres:local .` and with `TAILOR360_POSTGRES_IMAGE`, `POSTGRES_ARCHIVE_MODE` and
      `POSTGRES_ARCHIVE_COMMAND` exported as `docs/platform/backups.md` documents them,
      `docker compose -f infra/compose/docker-compose.yml --profile backup up -d --wait` brings up a PostgreSQL whose
      `SHOW archive_mode` is `on`, and `pgbackrest --stanza=tailor360 info` reports a completed full backup and
      archived WAL in the MinIO repository.
- [ ] **Negative — the default development stack is unchanged.** With none of those three variables set,
      `docker compose -f infra/compose/docker-compose.yml up -d --wait` starts the **stock** `postgres:16.13-alpine`,
      `SHOW archive_mode` is `off`, no image is built, and `./scripts/dev status` reports the five components up. This
      is the criterion that protects every other developer and every integration-test run, and it is asserted in
      `BackupConfigurationTests` as well as run by hand.
- [ ] `pgbackrest --stanza=tailor360 check` passes, which is the assertion that the `archive_command` PostgreSQL
      actually runs reaches the repository — not that the configuration file parses.
- [ ] Every object the chain writes is encrypted at rest by pgBackRest itself: reading a repository object with `mc
      cat` yields ciphertext, and the passphrase is in a mounted file, not in the configuration, the image, the
      environment block or the repository.
- [ ] The scheduler writes `backup-status.json` with the seven properties named in Scope after both a successful and
      a failed attempt, and writes no database content, object key or credential into it.
- [ ] **Negative — retention cannot be issued as a command:** `grep -rn "pgbackrest expire\|repo1-retention" infra/`
      finds nothing, and the new architecture test fails when either is reintroduced (proved by its negative
      control).
- [ ] **Negative — no secret is committed:** the architecture test fails on a cipher passphrase, access key or
      secret key literal placed in `infra/backup/**` or in a compose `environment:` block, and the `security` job's
      gitleaks scan passes on the branch.
- [ ] **Negative — the staging stack refuses to run an unarchived database:** with `TAILOR360_POSTGRES_IMAGE`
      unset, `docker compose -f infra/compose/docker-compose.staging.yml config` fails with the variable's own
      message, in the same way the existing `TAILOR360_WEB_IMAGE` does.
- [ ] **Exception — a failed backup is loud and leaves the chain intact:** with the repository endpoint pointed at a
      closed port, the scheduler exits non-zero for that attempt, records `lastExitCode` and leaves `lastSuccessAt`
      at its previous value; it never deletes, truncates or re-creates the stanza to recover, and the next
      successful attempt continues the same chain rather than starting a new one.
- [ ] `./scripts/dev test architecture` passes, including the new file's negative controls, and
      `dotnet format --verify-no-changes` is clean.

## Migration and rollback

No database table, column, index or trigger changes, so no EF Core migration is added. What proves it:
`dotnet run --project src/Tools/Tailor360.Cli -- migrate --dry-run` prints "The database is up to date with this
build." and the `migration-check` job of `.github/workflows/ci.yml` reports no model change.

Two rollbacks matter instead, and both belong in `docs/platform/backups.md`:

1. **Rolling the image back.** `archive_mode` is a start-up parameter, so reverting `TAILOR360_POSTGRES_IMAGE` to
   the stock digest stops archiving at the next restart and leaves the repository intact but frozen. The previous
   release tolerates it because nothing in `src/` reads the repository.
2. **Rolling the chain forward after an outage.** PostgreSQL retains WAL it could not archive until `pg_wal` fills,
   at which point the cluster stops writing. The document must say this plainly, say which alert catches it
   (`docs/nfr/security-operations-targets.md` line 273, "no WAL archived for 15 minutes"), and say that the
   recovery is to restore archiving, never to delete WAL by hand.
