Sub-issue of #56. The W5 half of this parent owes an "automated security regression suite" over eleven abuse-case
families (plan Section 8), split across seven sibling sub-issues. **This sub-issue takes exactly one family, and it is
the largest: `ABF-05` invoice or payment tampering.** It is one family rather than three because it is the only family
whose whole surface is **already live** — thirteen migrations, thirty-nine tables and **sixty-five endpoint
registrations** of money-handling code are in `main` today — so it is the one family a session can cover completely
and verifiably at W5 entry, and the one whose failure would cost real money. `ABF-06` stock manipulation and `ABF-08`
export leakage are the immediately following sibling: both depend on surfaces that do not exist yet (#39 and #40 for
the stock ledger, #183 to #186 for the reporting exports), so pairing them with `ABF-05` would have made a session
that could not finish until three other parents had landed.

The gap is checkable today: `ls tests/Tailor360.IntegrationTests/Billing` returns eighteen files that test Billing's
**happy and refusal paths per endpoint** (`InvoiceEndpointTests.cs`, `PaymentEndpointTests.cs`,
`RefundEndpointTests.cs`, `ReconciliationEndpointTests.cs`, `CashierSessionEndpointTests.cs`, and so on) and
`ls tests/Tailor360.IntegrationTests/Security` returns five files, **none about money**. Nothing tests a tampering
**sequence**, and the parent's third acceptance criterion — business rules cannot be bypassed through direct API
calls — is unevidenced for payments.

## What is missing

- No test performs a money **sequence**: post an invoice and then edit it; allocate a payment twice; reverse a
  payment and then allocate the original; close a cashier session and then record a payment into it; approve a
  variance as the person who recorded it.
- Nothing asserts posted-document immutability **as an attack**: that a posted invoice cannot be edited, that a
  reversal cannot mutate the row it reverses, and that a closed cashier session cannot be reopened. Each is an
  invariant in `docs/architecture/invariants.md` and none of them fails a test today if it stops holding.

## Acceptance criteria

- [ ] `./scripts/dev test integration` runs the new class, and the suite can also be run alone by its family
      trait. Every test carries `[Trait("Category", "Integration")]`.
- [ ] For every money-moving route in the published endpoint inventory — every route that creates, posts, cancels,
      allocates, reverses, refunds or receipts an amount, or opens or closes a cashier session — a case exists in this
      suite, and `AbuseCaseCoverage` **fails when a new such route has none**, listing them by name.
- [ ] **Negative case shape**: every refusal is asserted on the exact response — status, RFC 9457 problem type, and
      the absence of any detail that distinguishes a forbidden resource from a missing one — and on the audit row it
      produced. A test that asserts only "not 200" does not count.
- [ ] **Negative case, immutability**: each of the three immutable things — a posted invoice, a recorded payment, a
      closed cashier session — is proved immutable by attempting the mutation through **every** route that could
      plausibly reach it, not only the obvious one. With sixty-five registrations live, "the obvious one" is not a
      defence, and the pull request lists the routes tried per target.
- [ ] **Negative case, arithmetic is not re-tested but tampering is**: a client-supplied amount, tax figure, place of
      supply, price or discount is shown to be **ignored or rejected**, and the resulting stored figure is compared
      against what the server computes — so the test fails if the server ever starts trusting the input, without
      duplicating `pricing-golden-master.json`.
- [ ] **Exception case**: each sanctioned way out is tested as *working*, not only as refused — an adjustment note
      corrects a posted invoice; a reversal with a reason succeeds and is audited and leaves the original row intact; a
      manual allocation with a reason succeeds; a reconciliation approved by a **second** person succeeds
      (`INV-CSH-04`); an approved dispatch exception lets dispatch through and is audited. A suite that only proves
      refusals would pass against a system that refuses everything.
- [ ] The suite is **stable**: it passes twice in a row in different orders (CLAUDE.md section 5), and the pull request
      reports the integration tier's duration before and after against the 15-minute pull-request pipeline budget
      (plan Section 8).
- [ ] Every new test names the `ABF-nn` family and the flow model's `AB-nn`/`CTL-nn` identifier it proves, and
      `docs/security/abuse-cases.md` names the test class in return.
- [ ] Any finding is either fixed here or is an open issue number in a skip reason. Nothing is silently removed.
- [ ] `dotnet format --verify-no-changes` is clean and the other tiers still pass.

## Migration and rollback

No table, no column, no migration; `migrate --dry-run` reports no outstanding change. If a production fix found here

after, making a silent loss of coverage visible.
