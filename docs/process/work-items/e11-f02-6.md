Sub-issue of #48. The parent's last implementation step — "Emit delivery confirmation for receipt, notification, reports
and feedback request" — on the Notifications side, and the half of plan Section 6.2 note 4 that is not the status page:
"#48 adds the `status` link purpose, **delivery templates and `Templates/delivery.*`**; neither modifies the #47
service, adapters or existing templates, and the second PR to merge rebases and re-runs the #47 routing tests." Nothing
exists: the Notifications module is seven files of scaffolding (`NotificationsEndpoints.cs` maps an empty group,
`AddNotificationsModule` returns `services` unchanged), so there is no template, no routing rule and no consumer of any
Custody event anywhere in `src/`.

**A boundary with #209 that has to be said out loud.** #209's own body claims the general case — it "adds the inbox-side
handlers that turn a consumed event into zero or one intent" — while plan Section 6.2 note 4 and the #47 blueprint both
assign the delivery rules to #48: "#40 (low stock), #48 (delivery) and #49 (feedback follow-up, service-recovery
closure) **register their own routing rules and templates in their PRs** without changing the routing engine". The line
is drawn by what exists when #209 merges: #209 owns the gate, the `notification_intents` table and the consent,
preference, quiet-hours and de-duplication decisions, plus handlers for the events that exist at its merge time. The
four Custody delivery events **do not exist until [E11-F02-2], [E11-F02-3a] and [E11-F02-4] merge**, so #209 cannot have
written their handlers. State that in the pull request, and if #209 has somehow added one, extend it rather than adding
a second handler for the same event — the inbox de-duplicates on `HandlerName`, so two handlers with one name silently
become one and two with different names deliberately both run.

## Scope

- [ ] **Four routing rules** under `src/Modules/Notifications/Tailor360.Modules.Notifications.Infrastructure/Routing/`,
      each one `IOutboxMessageHandler` with its own `HandlerName` and `Schema = NotificationsDbContext.SchemaName`,
      named `Delivery*` so they sit beside #40's `Inventory*` without colliding: `custody.dispatch-recorded.v1` → a
      dispatch message; `custody.delivery-confirmed.v1` → a handover confirmation; `custody.delivery-failed.v1` and
      `custody.delivery-returned.v1` → the failed-attempt message EX-12 requires. **`custody.delivery-confirmed.v1` will
      have a second handler**: #49's `[E11-F03-5]` consumes the same event for the feedback invitation. That is legal
      and intended — the inbox de-duplicates per `HandlerName` — so pick a name that cannot collide with theirs, and say
      in the pull request which two handlers now run on that event. Each raises a **notification intent** through the
      mechanism #209 delivers and lets that mechanism decide consent, preference, quiet hours and de-duplication; none
      of them sends anything itself and none calls a provider adapter.
- [ ] **`Templates/delivery.*`** — `delivery.dispatched`, `delivery.confirmed`, `delivery.failed` (which serves the
      **returned** outcome too, through a declared variable naming the outcome, because EX-12 asks for one message —
      "explaining the failed attempt and offering a new slot" — and two bodies saying the same thing in two languages
      are two things to keep in step) and `delivery.status-link`, each as a template with a published version per
      channel in **`en-IN` and `ta-IN`**, rendered in safe mode from a declared variable allowlist (#208's mechanism).
      The allowlist per template is the minimum that makes the message useful — order display number, branch name,
      promised date, the status link where one exists — and **never** a measurement, a design, an amount, a recipient
      name, a one-time password, a free-text reason or a staff name. Seeded as versioned configuration through `dotnet
      run --project src/Tools/Tailor360.Cli -- init-reference-data`, which is what DOR-11 asks about; no template body
      is compiled into code. **Two mechanical facts about that command**: it resolves one `I…ReferenceDataSeeder` per
      module **by hand** in `src/Tools/Tailor360.Cli/Commands/InitReferenceDataCommand.cs`, so this adds a line there —
      a single-writer file — and `src/Tools/Tailor360.Cli/CliHost.cs` composes Identity, Customers, Catalog, Media,
      Orders and Billing and **not Notifications**, so it needs `AddNotificationsModule` before the seeder can be
      resolved at all. Check whether #208 has already added both, and say which in the pull request.
- [ ] **The mint, which moved here from #E11-F02-5 in review.** Each rule calls #211's
      `ICustomerLinkIssuer.Issue("status", orderId, ttl)` for the order and passes the resulting URL as a template
      variable. The time-to-live is `Notifications:CustomerStatus:LinkTtl`, and **it has no default**: with no
      configured value **no link is minted**, the template renders its no-link variant, and the omission is recorded —
      fail-closed, because **OD-08** has sourced no expiry and a guessed expiry is a guessed disclosure window. The
      message still goes out. The decision of *when* to mint belongs with the thing that sends, which is why it is here
      and not on the page; #E11-F02-5 owns the page and the amount policy and calls `ICustomerLinkIssuer` nowhere.
- [ ] **De-duplication and ordering.** One message per event per recipient: the intent's de-duplication key is derived
      from the event identifier, so a redelivered outbox message produces no second message, and the inbox row commits
      with the intent. A delivery that was confirmed and then disputed does not retract the confirmation message; the
      dispute is staff-facing and is not a customer message here.
- [ ] **The lost-link reissue path, end to end for `status`**: when support reissues a link under #211's
      `notifications.manage_customer_links`, the new link is sent on the consented channel using `delivery.status-link`.
      This is the "lost-link/reissue flow" the parent issue names; the permission, the revocation and the endpoint are
      #211's and are used unchanged.
- [ ] **No change to #47's service, adapters or existing templates** — plan Section 6.2 note 4, quoted verbatim in the
      pull request description. The only files touched under `Notifications` are new `Routing/Delivery*` and
      `Templates/delivery.*` files plus their registrations. **The second pull request of the W4 Notifications group to
      merge rebases and re-runs the #47 routing tests**, as that note instructs.

- [ ] A published `custody.dispatch-recorded.v1` produces exactly one notification intent for the order's customer,
      carrying the `delivery.dispatched` template version, the customer's locale and a status link where one is
      configured — with the intent recorded and the inbox row committed in the same transaction.
- [ ] The same for `custody.delivery-confirmed.v1`, `custody.delivery-failed.v1` and `custody.delivery-returned.v1`,

- [ ] Every template has a published version in **both** `en-IN` and `ta-IN`; a missing language is a failing test, not
      a runtime fallback to English.
- [ ] **Negative:** a redelivered event produces **no** second intent and no second inbox row; four deliveries of the
      same event produce one message.
- [ ] **Negative:** a customer with no consent or no channel for the `transactional_messages` purpose produces a
      **suppression** with its reason rather than a send, and the suppression is audited — the behaviour
      `docs/architecture/module-ownership.md` section 5.10 and #209 define. No message is ever sent outside consent by
      this issue's rules.
- [ ] **Negative — EX-10's rule:** no rule reacts to a *blocked* dispatch attempt, so no message can imply a garment is
      on its way while it is blocked. Asserted by a test that publishes nothing on a refused receive scan and by the
      absence of any handler for a blocked-attempt event.
- [ ] **Negative:** no rendered body, recipient address, template variable or `/c/**` path appears in any log line,
      trace attribute or metric. The class is `docs/nfr/data-classification.md` section 5.13; **the absolute prohibition
      list is section 8**, whose rows include "rendered notification bodies and template variable values" and
      "customer-link tokens and `/c/**` paths". Asserted by a test over captured output.
- [ ] **Exception:** with `LinkTtl` unset, each message still sends, renders its no-link variant, and records that no
      link was minted; nothing guesses an expiry.
- [ ] **Exception:** a reissued `status` link sends `delivery.status-link` on the consented channel and the superseded
      token answers as not found (#211's behaviour, exercised here end to end).
- [ ] Hand-off to the provider meets `docs/nfr/slo.md` section 5 row "Notification hand-off (S10)", `p95 < 60 s` for
      transactional messages, and the outbox lag row (S7) `p95 < 30 s`; both figures are cited, not set here.

## Modules, contracts and events

Notifications is the only module whose schema is written (MO-1, MO-2, ARCH-005). Four **Custody** integration events are
consumed through the transactional inbox — the second sanctioned mechanism of `docs/architecture/module-ownership.md`
section 1 — and their payload types are read from `Custody.Contracts` (ARCH-004). One Notifications-owned port is called
in-process for the link mint (#E11-F02-5's path over #211's `ICustomerLinkIssuer`). **No Custody, Orders or Billing
table is read**, and no event is published by this issue: `notifications.notification-delivered.v1` and its siblings
belong to #210. ARCH-009 holds because no provider SDK is referenced here — the adapters stay in
`Integration.Infrastructure` behind #210's ports. DOR-05: the threat model is the customer-messaging set #56a owns; the
abuse cases covered above are sending outside consent, sending a misleading message on a blocked dispatch, leaking a
token through a log, and duplicate messages from a redelivered event.
