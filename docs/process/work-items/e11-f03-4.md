## Scope

- [ ] `POST /api/v1/notifications/feedback/cases/{caseId:guid}/assign` — body `{ ownerUserId, reason }`. Reassigns
      an open case. `RequirePermission(feedback.manage_cases, BranchScope.CurrentBranch)`,
      `ScopedToResource("notifications.service_recovery_case", "caseId")`, `RateLimitPolicyNames.Write`,
      `.Audited("notifications.service_recovery.assigned")`, `.RequireIdempotency()`, `RequestTimeoutPolicies.Command`.
      The assignee must be a user of the case's branch — checked server-side, never by trusting the request
      (`CLAUDE.md` security rule 2: "a caller's claims say what to check, not what to allow"). **The contract
      exists and is registered**, verified:
      `src/Modules/Identity/Tailor360.Modules.Identity.Contracts/Directory/IUserDirectory.cs` declares
      `Task<StaffMember?> FindAsync(Guid userId, ct)`,
      `Task<IReadOnlyList<StaffMember>> FindManyAsync(IReadOnlyCollection<Guid>, ct)` and

      would produce a job nobody can pick up" — which is precisely the mistake to avoid on a case with a due time.
- [ ] `POST /api/v1/notifications/feedback/cases/{caseId:guid}/contact` — body

      decorations, audit action `notifications.service_recovery.contact_recorded`.
      `exceptions.md` section 4.4 requires that "the case notes must record how the customer was reached", which is
      what `channelCode` and `note` are for.
- [ ] `POST /api/v1/notifications/feedback/cases/{caseId:guid}/close` — body
      `{ resolutionCode, acceptAlteration, alterationGarmentJobId, alterationReasonCode, reason }`. Closes through
      #213's operation, which publishes `notifications.service-recovery-closed.v1` in the same transaction. Audit

      AlterationSource.Feedback, caseId, feedbackId)` and store `AlterationRequestId` and the nullable
      `GarmentJobId` on the case. A failed `Result` from Orders refuses the whole close — the case stays open, which
      is the only answer that keeps TR-50 true.

      until #34 merges. An `acceptAlteration` close with none registered is refused with a stable problem code

      works normally. This is deliberately the opposite of plan Section 6.2 note 10's "confirmation succeeds and the
      job card shows label not yet available": a label can be printed later, whereas a case closed claiming an
      alteration nobody will work is exactly the forgotten alteration TR-50 exists to prevent. State the choice in
      the pull request.
- [ ] `GET /api/v1/notifications/feedback/service-recovery-policy` — the calling branch's policy row: rating
      threshold, automatic-case-on-alteration-request flag, owning role key, due time in business hours, the

      `ConcurrencyResults.SetEntityTag(response, tag)` (`Platform.Security/Endpoints/ConcurrencyEndpoints.cs:39`).

## Acceptance criteria

- [ ] A Branch Manager assigns an open case to a colleague of the same branch, records two contact attempts and
      closes it with a configured resolution code — all over HTTP, with a reason on every call, and the case detail
      afterwards shows the owner, both attempts, the resolution and the closing instant.
- [ ] Rule-level: all five routes declare a permission with a branch scope (ARCH-007), exactly one rate-limit policy
      (ARCH-017), and the three case commands and the policy edit carry `.Audited(…)` (ARCH-008). ARCH-023 — "a
      branch-scoped permissioned endpoint **with a route parameter** declares a resource scope, or records why it
      names no branch-owned row" — binds the **three** routes carrying `{caseId}`, which declare `ScopedToResource`.
      The two policy routes take no route parameter, so ARCH-023 does not reach them; they declare
      `TouchesNoBranchOwnedResource` regardless, because the matrix's Resource column needs a value and saying it
      out loud costs less than a reviewer deducing it. (An earlier draft of this body counted "four routes with
      `{caseId}`"; there are three — assign, contact, close — plus two policy routes, which is the five.) None
      declares both a permission and an anonymous justification (ARCH-022); none accepts a second authentication
      scheme (ARCH-019); none declares `.RequireStepUp()`, which ARCH-018 permits because neither permission is
      catalogued `RequiresStepUp` — verified in `NotificationsPermissions.cs`, where `ManageCases` carries
      `RequiresReason: true` and nothing else, and `ReadFeedback` carries no flag at all. A row per route is added to
      the `<!-- matrix:endpoints -->` block (lines 311–512).
- [ ] Accepting an alteration on close records the alteration request against the case and passes
      `AlterationSource.Feedback`, the case identifier and the feedback identifier — and passes **no free text**: a
      test asserts the customer's comment string never appears in the arguments handed to `IAlterationRequests`.
- [ ] Negative: a caller holding `feedback.read` but not `feedback.manage_cases` is refused `403
      security.forbidden` on all three commands and on the policy edit; a command with no reason is refused with a
      field error on `reason`, because the permission is catalogued `RequiresReason`.
- [ ] Negative: a case of another branch answers `404`, and the same command replayed with the same
      `Idempotency-Key` returns the first outcome rather than appending a second contact attempt or closing twice
      (`CLAUDE.md` security rule 4). "Same key, different body" and "duplicate while in flight" both behave as
      `IdempotencyContract` defines.
- [ ] Negative: closing an already-closed case is refused with a stable code and changes nothing; assigning a
      closed case likewise.
- [ ] Negative: a `PUT` of the policy with no `If-Match` is refused through `ConcurrencyResults.PreconditionMissing`
      and one with a stale tag through `ConcurrencyResults.VersionConflict` — two distinct answers, not one, because
      "you forgot the precondition" and "somebody changed it since you read it" need different remedies from the
      person at the screen. Both leave the row untouched.
- [ ] Exception: an `acceptAlteration` close while no `IAlterationRequests` implementation is registered is refused
      with `notifications.alteration-hand-off-unavailable`, the case stays open, and a close without an alteration
      on the same case then succeeds. Both arms are tested — one with a fake implementation registered, one with
      none.
- [ ] Exception: a close whose `Result` from Orders is a refusal leaves the case open and writes no closing audit
      event, proving the hand-off and the closure commit together.
