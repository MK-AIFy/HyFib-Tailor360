Sub-issue of #48. The delivery queue is the first of the three areas plan Section 8 row #48 names (Custody queue,
Notifications links, PWA delivery), and it has to exist before anything can be dispatched from it. The Custody module is
a five-project stub today — `ls src/Modules/Custody/*/` is seven files, `Api/CustodyEndpoints.cs` maps an empty group at
`/api/v1/custody`, `CustodyModuleServiceCollectionExtensions.cs:14` declares the schema name as a constant and there is
no `DbContext`, no migration and no entity anywhere under the module. So `custody.delivery_queue_entries`
(`docs/architecture/module-ownership.md` section 5.6) does not exist, and nothing in `src/` consumes
`orders.job-ready-for-delivery.v1`, which is the event that puts a garment on the queue.

## What is already built (do not re-build)

- `src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Events/GarmentJobReadyForDelivery.cs` — the queue's source
  event, `orders.job-ready-for-delivery.v1`, merged and documented. **Read its remarks before writing the handler**: it
  is raised only on the not-ready→ready transition, there is deliberately **no** not-ready event, and
  `BoundWithGarmentJobIds` is "the parcel as the gate saw it … and never durable membership". It carries `OrderId`,
  `GarmentJobNumber`, `DueDate`, `EvaluatedAt` and `BranchId`.
- `src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Orders/IOrderSnapshotQuery.cs` — `GetAsync`, `GetJobAsync`,
  `GetJobsAsync(garmentJobIds)` and `GetPricedAsync`. `GetJobsAsync`'s own remarks say it "exists for the door" and that
  "#48's delivery queue re-read the whole parcel at the moment it matters". `GarmentJobSnapshot` carries `State`,
  `IsReadyForDelivery`, `ReadyStateComputedAt`, `ReadyStateBlocks`, `DueDate`, `HoldReasonCode` and
  `CancellationReasonCode` — and **no money and no personal data**, by design.
- `src/Modules/Billing/Tailor360.Modules.Billing.Contracts/Payments/IFinancialTotalsQuery.cs` —
  `GetOrderBalanceAsync(orderId, organisationId)` returning `OrderBalanceSummary` (charges, credits, allocated,
  `UnappliedAdvances`, `Outstanding`, currency). Merged with #162. **Custody displays this and computes nothing**
  (`docs/architecture/module-ownership.md` section 5.6: "Custody **never computes a customer balance**").
- `src/Modules/Identity/Tailor360.Modules.Identity.Contracts/Directory/IBranchDirectory.cs` — `FindAsync` /
  `FindManyAsync` returning `BranchSummary` with `Code`, `Name`, `TimeZoneId`. The only lawful source of the branch
  timezone a due/ready age is computed against.
- `src/Platform/Tailor360.Platform.Persistence/Outbox/IOutboxMessageHandler.cs` — `EventType`, `HandlerName`, `Schema`,
  `HandleAsync`. Its remarks are binding: **stage writes, never call `SaveChangesAsync`** — the dispatcher commits the
  handler's writes with the inbox row. The worked precedent is
  `src/Modules/Billing/Tailor360.Modules.Billing.Infrastructure/Invoicing/OrderFactHandlers.cs` with its registrations
  at `BillingModuleServiceCollectionExtensions.cs:114-118`.
- `src/Modules/Billing/Tailor360.Modules.Billing.Application/Payments/DispatchPolicyOptions.cs` — the house pattern for

  reading of every knob … so that nothing here loosens dispatch". Copy that shape.
- `src/Platform/Tailor360.Platform.Security/Permissions/CustodyPermissions.cs` — seventeen keys including `Scan`,

## Acceptance criteria

- [ ] A Delivery Staff principal holding `custody.read_delivery_queue` reads the branch's queue over HTTP and sees, for
      a confirmed order whose gate has opened, the order number, the promised date, every garment job, the live
      outstanding balance and `Dispatchable` under the default `WholeOrder` policy — with no direct database access in
      the test.
- [ ] Both routes declare a permission with branch scope, exactly one rate-limit policy and — for the route with
      `{orderId}` — a resource scope (ARCH-007, ARCH-017, ARCH-023). Neither is state-changing, so ARCH-008 does not
      apply and the issue says so rather than adding an audit filter.
- [ ] **Negative:** a caller without `custody.read_delivery_queue` is refused `403` with an RFC 9457 problem and an
      `authz.denied` audit row; a caller from another branch reads the first route as an empty queue and the `{orderId}`
      route as `404`, never as another branch's rows.
- [ ] **Negative:** under `WholeOrder`, an order with one garment still in production shows **every** garment as
      blocked, each naming the sibling garment job number that is holding the order back; under `PerJob` the ready
      garments show as dispatchable and the unready one keeps its own block. The same fixture, two configurations, two
      answers. **The whole-order block is Custody's own reason code and not `ReadyBlockReason.DependenciesMet`** —
      that member belongs to Orders' ready gate and means a declared `deliver_together` prerequisite, which is a
      different fact from "the branch policy ships the order in one piece". `ReadyStateBlock` is an Orders type with a
      private constructor and a validating `Of` factory; Custody reads them and constructs none.
- [ ] **Negative:** a garment whose gate has closed again — held after it was queued — reads as blocked with the hold
      reason code on the next queue read, although no event told the queue so, because the read re-reads
      `IOrderSnapshotQuery`.
- [ ] **Exception:** a redelivered `orders.job-ready-for-delivery.v1` writes no second row and no second entry in the
      inbox; an event carrying an `EvaluatedAt` earlier than the stored one changes nothing (CI-03).
- [ ] **Exception:** a cancelled garment job or a cancelled order closes its queue entries with a reason code and leaves
      the rows in place; nothing is deleted.
- [ ] The queue read meets the published read objective — `p95 < 400 ms`, `docs/nfr/slo.md` section 5 row "Read latency
      (S2)" — at the load of `docs/nfr/capacity-and-performance.md` section 2.4. The figure is cited, not set here.
