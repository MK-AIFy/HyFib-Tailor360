Sub-issue of #48. The parent's third acceptance criterion — "Customer-status links expire, can be revoked and expose no

leaves the table and port unchanged; **#48 adds the `status` purpose and page**, #49 the `feedback` purpose, without

**The page is built in `src/Hosts/Tailor360.Web`, not in the Notifications module, and that is not a detail.** #211's

balance, which no single module owns, so the composer is the host — the fourth of the five sanctioned mechanisms in

## What is already built (do not re-build)

  ProductionStartedAt, DeliveredAt, CancelledAt, Jobs)` and each `GarmentJobSnapshot` carries `GarmentJobNumber`,
  `State` (`Confirmed`, `InProduction`, `OnHold`, `Ready`, `Delivered`, `Closed`, `Cancelled`), `DueDate` and
  `IsReadyForDelivery`. Its remarks are load-bearing here: "**It carries no personal data at all** … There is no

  customer-facing page needs, and it is why this page composes this contract rather than reading anything else.

- `src/Hosts/Tailor360.Web/Timeline/CustomerTimelineComposer.cs` — the house precedent for BFF composition: the host
  merges several modules' contributions behind one route and no module learns another's tables. The status page uses the

  modules".
- `src/Modules/Billing/Tailor360.Modules.Billing.Api/Payments/ReceiptEndpoints.cs` — `ResolveReceiptBarcode`, the
  existing "reads alike as not found" discipline #211 names as the model for indistinguishable refusals.
- `docs/nfr/data-classification.md` **section 8** — the absolute prohibition list, whose last rows are

## Acceptance criteria

- [ ] A `status` token minted for a confirmed order resolves to a page that names the order number, the promised date
      and one progress step per garment, in English and in Tamil, with no script executed and no request to any origin
      but this one.
- [ ] **Negative — the whole point of the criterion:** an expired token, a revoked token, a token minted for a different
      purpose and a random 128-bit guess all produce the **same** response — indistinguishable in status, in body and in
      timing (the discipline #211 builds and this page must not break by rendering a different shell for one of them).
- [ ] **Negative:** the page exposes no other customer's or order's data under any input: changing the language, the
      casing of the token, or any header reaches the same order or nothing. There is no identifier on the page that can
      be altered to reach another order, because there is no identifier on the page.
- [ ] **Negative:** with `AmountDisplay = None` no figure, no currency symbol and no balance wording appears in the
      rendered HTML — asserted against the markup, not against a helper's return value.
- [ ] **Exception:** the page is reachable only by a token, so there is **nothing on it to mint** — the `LinkTtl`
      fail-closed rule is asserted by **#E11-F02-6**, which owns the mint. Stated here so a reviewer does not look for
      it.
- [ ] **Exception:** a revoked-and-reissued link gives the new token a page and the old token the indistinguishable
      not-found answer.
- [ ] The token appears in no log line, no trace attribute, no metric, no access log and no database dump of anything
      but the hash — the `/c/**` prohibition of `docs/nfr/data-classification.md` **section 8**, restated in section
      5.14's own "In logs: **Never**" row, asserted by a test.
- [ ] **One Lighthouse mobile-profile run is pasted, and no numeric gate is claimed.** Plan line 2083 asks for a "light
      bundle tested with the Lighthouse mobile profile", which is the obligation. The nearest published figure is the
      **Largest Contentful Paint** row of `docs/nfr/capacity-and-performance.md` **section 3.3** — `p75 ≤ 2.5 s, cold
      cache` — and that row names "scan, workboard, order-intake, billing routes", not a `/c/**` page outside the client
      shell, and section 3.3's own preamble says "**every target below is proposed, to be confirmed**". So report the
      numbers, compare them to that row, and claim no gate. The continuous budget is #52's.
