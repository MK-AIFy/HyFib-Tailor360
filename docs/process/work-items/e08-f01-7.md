      reload returns to the choose phase rather than re-posting anything.
- [ ] **The outcome report** — every row's outcome, never only the first failure: the row number, the SKU as the file

      rows reachable without stepping through every cell (A11Y-LF-05). Nothing is committed by previewing.
- [ ] **Commit** — a separate, explicit act that applies **only the previewed, unchanged batch** (#195's
      acceptance criterion: "the commit step only ever applies exactly the previewed batch"): send back whatever
      token, hash or preview identifier the preview returned. The double-apply guarantee rests on two things, and
      the body names both because #195's scope declares `Idempotency-Key` explicitly only on **create**: first, the
      preview token, which the server will not honour twice; second, the **same** `Idempotency-Key` minted at the
      commit click and held across a retry, sent if the commit operation declares the header in the generated
      schema. If it declares neither the header nor a single-use token, that is a defect raised on #195 — a bulk

      server no longer recognises is refused, and the screen says so and offers a fresh preview rather than

- [ ] **Entry point**: a link or button to the import screen on `ItemListRoute.tsx`, shown only to a caller holding

- [ ] Five states plus the four phases, each with a Storybook story through

- [ ] DOR-11: no configuration is added. The 10 MB figure is cited from plan Section 5.2 in a comment, not chosen

## Out of scope

A downloadable error report. Making a cell safe to open in a spreadsheet — the `'` prefix and quoting of plan
Section 5.2, behind NFR-FI-07 — is a server rule on a server export path, and producing a CSV in the browser would
put it in the one place it is not tested; a downloadable report is a new operation on #195's surface and is raised
there. Also out of scope: importing suppliers, locations or reorder rules (nothing in #38 asks for it); a
progress bar for a long-running server-side import (#195's endpoints are synchronous preview and commit; an
asynchronous job would be a different design and a different issue); editing a failed row in place and re-previewing
it (the person fixes the file — the file is the record of what they intended); and the item editor itself
(`E08-F01-6`).

## Acceptance criteria

- [ ] An Inventory Clerk chooses a synthetic CSV of 20 item rows of which 3 duplicate an existing SKU and 2 are
      invalid, previews it, reads every row's outcome with its row number, and commits — and exactly the previewed
      batch is applied. Proved by a Vitest journey against the stubbed transport.
- [ ] **Nothing is committed by previewing**: the preview request is the only request the preview phase makes, and
      leaving the screen after a preview changes nothing (asserted against the stub's recorded calls).
- [ ] A file over 10 MB is refused **before** it is read or posted, in plain words naming the limit, with the limit
      cited from plan Section 5.2 — not a number invented in the component.
- [ ] A server refusal of the whole file — a control character, a malformed row, more rows than the cap — is shown
      as the server's words with the row it concerns where the server gives one, and never as a code or a stack.
- [ ] Committing twice (a double click, or a retry after a network failure) applies the batch **once**: the same
      `Idempotency-Key` is reused and the replayed outcome is what is shown.
- [ ] A preview the server no longer recognises at commit time is refused with a sentence and an offer to preview
      again; the person's file selection is not lost.
- [ ] A caller without `inventory.manage_items` sees the sentence and who to ask — and the entry point is not shown
      to them on the item list.
- [ ] The report's counts and the empty case are announced through the polite live region, not by silence and not by
      a toast.
