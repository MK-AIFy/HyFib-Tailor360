## Scope

- [ ] **`TransferScopeRequirement`** in `src/Platform/Tailor360.Platform.Security/Authorisation/`, with its
      authorisation handler, admitting a caller who (a) holds the endpoint's permission, (b) is assigned to the
      transfer's `to_branch_id`, and (c) names a transfer that is **still `pending`** — and admitting them for
      **exactly** the receive, reject and resolve actions on that transfer's jobs and nothing else (INV-CDY-04,
      BR-8). The grant ends the moment the transfer is accepted, rejected or expired; it is re-evaluated per
      request and never cached beyond it.
- [ ] **`ITransferGrantSource`** beside it — a platform port (`CLAUDE.md` section 3 mechanism 5) the requirement
      asks, because the platform never queries a module's tables (the rule `IResourceScopeResolver`'s own remarks
      state). It answers identifiers only: the transfer's state, its `to_branch_id` and its job set. Implemented
      by `Custody.Infrastructure` as one indexed read and registered in `AddCustodyModule`.
- [ ] **Apply it to exactly three routes**, by adding `.WithinPendingTransferScope()` beside the existing
      `.RequirePermission(...)` on E07-F03-2's receive (`POST /custody/transfers/{transferId}/receive`) and reject
      (`…/reject`), and on **E07-F03-3b's** correction route (`POST /custody/cases/{caseId}/corrections`) — which is
      what BR-8's "resolve" means and is why **E07-F03-3b, not E07-F03-3, is the dependency**: E07-F03-3 has no
      correction route to decorate. The case **approval** is deliberately left out, so a destination-branch user may
      propose the repair and never sign it off. The
      ordinary branch-scope check remains and the new requirement **widens nothing else**: the transfer-out route,
      the case approval, the queue reads and every other custody route keep plain branch scope.
- [ ] **After acceptance, custody moves branch.** `job_custody_state.current_custody_branch_id` becomes the
      destination on accept, so ordinary branch scope then admits the destination and excludes the origin for
      custody actions — while order and billing ownership stay with the originating branch, which this slice never
      touches (plan Section 8, #37, "Cross-branch transfers").
- [ ] **`CustodyTransferSlaOptions`** bound to `Custody:TransferSla`, a map of transfer type to duration plus a
      `PolicyVersion`, with an `IValidateOptions<>` validator. **Default: empty.** An unconfigured transfer type
      gets `expires_at = null` and never goes overdue and never expires, because **FBH-03** says in terms "No
      numeric default is asserted here". Transfer-out writes `expires_at` from the configured duration evaluated
      in the branch timezone from `IBranchDirectory` through `IClock`.
- [ ] **`CustodyTransferOverdueService`** in `src/Hosts/Tailor360.Worker/Jobs/`,
      `[WorkerJob("custody.transfer_overdue", WorkerBranchScope.None)]`, under a lease with a fixed batch size,
      modelled on `DispatchExceptionExpiryService`. Two passes in one job: a `pending` transfer past its overdue
      mark publishes `custody.custody-transfer-overdue.v1` **exactly once** (the once-only guard is an
      `overdue_notified_at` column this slice adds), and a `pending` transfer past `expires_at` moves to
      `expired`, appends no scan event and **leaves custody with the sender**.
- [ ] **Decide the expiry's case type with the reviewer, do not invent one.** `state-transitions.md` section 4.1
      sends both a rejection and an expiry to "Reconciliation case open", but EX-13's six types — `mismatch`,
      `duplicate`, `stale`, `unknown location`, `lost`, `disputed` — have **no member for an expiry**, and
      E07-F03-3 opens a case only for the types it found written down. Default in force: the expiry publishes the
      overdue event and opens **no** case. If the reviewer wants one, EX-13 gains the type in this same pull
      request with the reason (`CLAUDE.md` section 8: a document change, never an invented value).
- [ ] **`Contracts/Events/CustodyTransferOverdue.cs`** — wire name `custody.custody-transfer-overdue.v1` carrying
      transfer id, job ids, age, branch code and server time per `barcode-handoff.md` section 5, and **no customer
      identifier**; a `.schema.json` **and** a `.example.json` under
      `docs/integration/events/`, plus the row in the catalogue table of `docs/integration/events/README.md`

- [ ] **Documentation in the same pull request**: the `TransferScopeRequirement` row of
      `docs/security/permission-matrix.md` section on branch scope, the BR-8 row of

## Out of scope

Any widening of branch reach beyond the three named actions on a pending transfer — that is what the IDOR tests
exist to prove. The delivery-team receive scan and the dispatch authorisation (#48). The notification the overdue
event triggers: Notifications owns routing and templates (#47, and `Routing/` additions are that issue's), so this
slice publishes the event and adds no template. The overdue **screen** — E07-F03-8. A numeric SLA — **FBH-03** and
**OD-06** are open and the default is "no SLA configured, nothing expires".

## Acceptance criteria

- [ ] A user assigned only to branch B, holding `custody.receive`, accepts a transfer sent from branch A to branch
      B while it is `pending`; after acceptance `job_custody_state.current_custody_branch_id` is B, and the same
      user can then scan the job under ordinary branch scope.
- [ ] **Negative — the grant is exactly three actions.** The same user, on the same job, is refused
      transfer-out, the case approval, the label reprint and the job timeline — each audited as `authz.denied`
      (INV-CDY-04: "and nothing else"). The answer is `404 security.resource-not-found`, `matrix.yaml`'s
      `holder-other-branch: out-of-reach`, not `403`: the requirement widens reach for three actions and the other
      routes therefore answer exactly as they do for a row that does not exist.
- [ ] **Negative — the grant ends with the transfer.** After the transfer is accepted, rejected or expired, a
      destination-branch user who is no longer the custodian's branch is refused receive, reject and resolve on
      that transfer; nothing is served from a cached scope.
- [ ] **Negative — IDOR.** A destination-branch user naming a **different** transfer of branch A, or a foreign
      `{transferId}`, gets the same answer as for a transfer that does not exist, per `matrix.yaml`'s
      `identifier-editing` dimension.
- [ ] **Negative — no permission.** A destination-branch user **without** `custody.receive` is
      `403 security.forbidden` even while the transfer is pending — `non-holder-own-branch`, because the refusal is
      about the permission and not about reach: the requirement widens reach, never permission (deny by default,
      `CLAUDE.md` section 4 rule 1). This is the one custody refusal that is a 403 rather than a 404, and the
      matrix dimension is what says so.
- [ ] **Exception — overdue and expiry.** With an SLA configured, a pending transfer past its mark publishes
      `custody.custody-transfer-overdue.v1` exactly once across repeated passes, and one past `expires_at` becomes
      `expired` with custody **still the sender's**; with no SLA configured, neither happens and no row changes.
- [ ] A second worker instance running the same pass does no duplicate work, proved by the lease log.
