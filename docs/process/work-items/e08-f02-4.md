Sub-issue of #39. The parent's second implementation step is "purchase order/receipt basics with supplier, quantity,
unit, cost, tax reference, lot/batch where enabled, receiving location and evidence", and
`docs/architecture/module-ownership.md` section 5.7 assigns `purchase_orders`, `purchase_order_lines`,
`purchase_receipts` and `purchase_receipt_lines` to this module. None of the four exists: the Inventory module has no
`DbContext` at all today. This child builds the **intent to buy** only — it posts no ledger entry and moves no
balance, which is why it is separable from the receipt (`E08-F02-5`) and why it can be reviewed without the ledger in
the diff.

## Scope

- [ ] **`inventory.purchase_orders`** — `id` (UUIDv7), `organisation_id`, `branch_id`, `supplier_id` (foreign key
      inside the schema), `status` stored as a name in `character varying(20)` — `Draft`, `Placed`, `Closed`,
      `Cancelled` — `expected_receiving_location_id`, `expected_at` nullable, `currency` left out (the system is
      single-currency — `docs/architecture/conventions.md` section 1.1: "The organisation is a single Indian legal
      entity trading in INR only (assumption A1)", money `decimal`/`numeric(18,2)`, a unit rate `numeric(18,4)`),
      `notes_code` for a commercial note **code** rather than free text, `placed_at`, `closed_at`, `cancelled_at`,
      `cancellation_reason_code`, `created_by_user_id`, `client_request_key`.
- [ ] **`inventory.purchase_order_lines`** — `id`, `purchase_order_id`, `item_id`, `ordered_quantity numeric(18,4)`
      with `ordered_unit_code`, the **base-unit equivalent** computed and stored at entry time through #195's
      conversion graph (INV-STK-02: conversion happens on entry, never in a report), `unit_cost numeric(18,4)`,
      `hsn_code` and `tax_code_reference` copied from the item at entry, `line_index`, and a unique index on
      `(purchase_order_id, line_index)`.
- [ ] **The status machine** — `Draft → Placed → Closed`, and `Draft → Cancelled`, `Placed → Cancelled`. A `Placed`
      order's lines are frozen; a `Closed` or `Cancelled` order accepts no change at all. `Closed` is reached only by
      `E08-F02-5` when the receipts cover the ordered quantity, so this child implements the transition and leaves the
      caller to it.
- [ ] **Validation** — the supplier must exist in the caller's organisation and be `active`; a `draft`, `suspended` or
      `retired` supplier is refused with `inventory.supplier-not-selectable` while remaining fully readable on an
      existing order (#193's rule, exercised here for the first time). Every item must be `active` (a retired item is
      refused with `inventory.item-not-selectable` — #195's status guard, enforced again here because a purchase is a
      new selection). The receiving location must belong to the caller's branch. At least one line; no duplicate item
      within an order unless the units differ; a non-positive quantity or a negative unit cost is refused naming the
      field.
- [ ] **Endpoints** — **five**, all under `/api/v1/inventory/purchase-orders` (three commands and two reads; the
      acceptance criteria and the matrix rows both count five):
  - `POST` create a draft with its lines. `.RequireIdempotency()`, `.Audited("inventory.purchase_order.created")`,
    `RateLimitPolicyNames.Write`, `.TouchesNoBranchOwnedResource(reason, "#39")`.
  - `POST /{purchaseOrderId}/placement` place a draft. `.RequireIdempotency()`,
    `.Audited("inventory.purchase_order.placed")`, `.ScopedToResource(InventoryResourceKinds.PurchaseOrder,
    "purchaseOrderId")`.
  - `POST /{purchaseOrderId}/cancellation` cancel with a reason code. `.RequireIdempotency()`,
    `.Audited("inventory.purchase_order.cancelled")`, resource scope as above. **`reasonRequired` stays at its default
    `false`**, because the new permission below is declared `RequiresReason: false` and
    `PermissionMatrixDocumentTests.cs:84` asserts the matrix's Reason column equals the catalogue flag — the
    cancellation's reason code is a validated body field, not the audit-reason contract. The handler writes the code
    onto the audit entry through `IInventoryAuditWriter` regardless; no filter writes anything
    (`AuditedEndpointMetadata.cs:5-6`).
  - `GET /{purchaseOrderId}` and `GET /`. The collection shape is fixed by `docs/api/conventions.md` section 4.2 and
    not invented: `items`, an opaque `nextCursor`, `hasMore`, **no `totalCount`**, `filter[status]` and
    `filter[supplierId]`, `sort` with a leading `-` for descending, and `limit` **clamped** to the endpoint's bound
    rather than refused — take the bound #193's Inventory list endpoints set rather than choosing a second number. An
    undeclared `filter[...]` is **400**, never ignored (same section). `RateLimitPolicyNames.DefaultUser`,
    `RequestTimeoutPolicies.Read`, resource scope on the single read; another branch's order reads **404**
    (`matrix.yaml`'s `out-of-reach`: 404 `security.resource-not-found`).
- [ ] **A new permission key** — `inventory.manage_purchase_orders`. Five edits, all in this pull request, and the
      first two are the ones a session forgets:
  1. the `public const string ManagePurchaseOrders = "inventory.manage_purchase_orders";` constant in
     `src/Platform/Tailor360.Platform.Security/Permissions/InventoryPermissions.cs`, beside the existing ten; **and**
     an entry in that file's `All` collection (`:46-65`) — `new(ManagePurchaseOrders, "…",
     PermissionModules.Inventory)`, which takes `PermissionScope.Branch`, `RequiresMfa`, `RequiresStepUp` and
     `RequiresReason` at their defaults (`Permission.cs:25-31`). A constant that is not in `All` is invisible to
     `PermissionCatalogue`, and the route then fails assertion 13 of `docs/security/permission-matrix.md` section 8.1
     — "every permission a route demands is in the catalogue and has a row in section 4" — which closes the route to
     everybody.
  2. a row in `docs/security/permission-matrix.md` section 4 whose Module, Scope, MFA, Step-up and Reason cells match
     the catalogue entry exactly, because `tests/Tailor360.UnitTests/Security/PermissionMatrixDocumentTests.cs:70-85`
     compares all five.
  3. the five route rows in section 5's `<!-- matrix:endpoints -->` block, hand-written per
     `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`'s "How to extend it when you add an endpoint".
  4. the grant to `branch_manager` and `inventory_clerk` in
     `src/Modules/Identity/Tailor360.Modules.Identity.Application/Access/SystemRoles.cs`, in both roles' permission
     lists, beside the four existing `InventoryPermissions.Manage*` entries.
  5. the `identifier-editing` entry for `{purchaseOrderId}` in `matrix.yaml`.

## Out of scope

Receipts, lot references, receiving evidence and every ledger effect — `E08-F02-5`, which also closes an order it
covers. A supplier-facing purchase-order document or PDF, and any notification to a supplier: nothing in #39 sends a
message, and Notifications is #47. An approval workflow above a value threshold: no threshold has a source
(`docs/prd/assumptions-and-open-decisions.md`), and inventing one would be inventing a control. Open purchase quantity
counting towards the low-stock threshold is #40's alert policy, which reads these rows. The purchase-order entry
screen is `E08-F02-10`.

## Acceptance criteria

- [ ] An Inventory Clerk holding `inventory.manage_purchase_orders` creates a draft order with three lines in two
      different purchase units over HTTP, places it, and reads it back with each line's base-unit equivalent already
      computed; `GET /` lists it for the caller's branch and not for another's.
- [ ] **No ledger effect:** after create, place and cancel, `inventory.ledger_entries` has no new row and every
      balance is unchanged — asserted directly, because this is the claim that separates this child from `E08-F02-5`.
- [ ] A suspended or retired supplier cannot be selected on a new order (`inventory.supplier-not-selectable`) and
      **remains readable on an order that already names it** — #193's history rule, proved here.
- [ ] A retired item cannot be added to an order; an order created before the item was retired still reads in full.
- [ ] **Negative:** a caller without `inventory.manage_purchase_orders` is refused 403 and audited; another branch's
      `{purchaseOrderId}` reads 404; an empty line list, a zero quantity and a negative unit cost are each refused
      with an RFC 9457 problem naming the field, never a database error; a replayed `Idempotency-Key` returns the
      first order rather than creating a second.
- [ ] **Exception:** placing an already-placed order, cancelling a closed order and editing a placed order are each
      refused with a stable `inventory.purchase-order-not-<state>` code, and the cancellation records its reason code
      and its actor in the audit trail — history is appended, never rewritten.
- [ ] Every route declares exactly one permission and one rate-limit policy, each command carries the audit filter and
      idempotency, and each `{purchaseOrderId}` route declares a resource scope (ARCH-007, ARCH-008, ARCH-017,
      ARCH-023).
- [ ] `./scripts/dev test contract` passes with the regenerated `docs/api/openapi.v1.json` committed, and
      `./scripts/dev test architecture` passes with no new exception row.
