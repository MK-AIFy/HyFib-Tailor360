## The one design question this slice must not guess at, and its answer

**Two open siblings of #47 say different things about where a feedback token lives, and a session that picks
wrongly rewrites this contract.** Read this before the scope list.

- #211 (open) ships `notifications.customer_links` with `feedback` in its purpose enumeration, and a
  `/c/{purpose}/{token}` route that resolves through `ICustomerLinkResolver` and dispatches per purpose.
- #213 (open) ships `feedback_tokens` as "its own table, since its semantics — one-time submission, one edit
  window, bound to a delivered order — differ from a purpose-bound informational link".
- `docs/architecture/module-ownership.md` section 5.10 (lines 635–637) lists **both**: `customer_links`
  ("`SHA-256(token)`, purpose, subject ids, expiry, revocation, use count, rate-limit counters") **and**
  `feedback_tokens, feedback_responses` ("One-time feedback capture with a single edit window").
- `docs/IMPLEMENTATION_PLAN.md` line 2095 says the invitation carries "a `purpose = feedback` token on the shared
  customer-link store", and Section 6.2 note 9 (line 653) says #49 adds the purpose "without changing the port".

**Default in force — the reconciling reading, because it is the only one under which no document has to be
amended** (the same test OD-13's recorded default applied): `customer_links` is the **credential** — the hash, the
purpose, the expiry, the revocation and the rate-limit counters, all #211's — and `feedback_tokens` carries the
**capture state** keyed on that row: how many times it has been submitted, when the edit window closes, and the
order and garment the response is bound to. Every document above stays true, #211's dispatcher works unchanged, and
both tables module-ownership 5.10 lists have a job.

**So that this slice does not have to be rewritten if #213 merged the other reading**, the contract below takes an
**opaque token**, not #211's resolved-link value, and every resolution happens inside
`Notifications.Application`. Under the default in force the handler calls `ICustomerLinkResolver.Resolve(token)`
and then loads the `feedback_tokens` row; if #213 shipped a self-contained `feedback_tokens` with its own hash and
no `customer_links` row, the handler calls #213's own resolve operation instead — **one private method changes and
no public type moves**. If #211's dispatcher insists on handing a content provider a resolved link as well, the
registration adapter passes the token through and discards the rest, which is one line.

Whichever way it lands, say in the pull-request description which reading #213 merged, and — if it is not the
default above — raise a one-line documentation fix against plan line 2095 and Section 6.2 note 9, because the
authority on table ownership is `module-ownership.md` and it must not be left disagreeing with the plan.

## What is missing

- No `Notifications.Contracts` type describes what the `/c/feedback/{token}` page must render or accept, so #211's
  per-purpose dispatcher has nothing to dispatch to for `feedback`.
- No handler turns a resolved feedback token into a `feedback_responses` row, and nothing calls #213's
  policy evaluation, so the EX-11 promise ("exactly one case per low rating or alteration request",
  `docs/prd/exceptions.md:48`) is unreachable from a customer action.

## Scope

- [ ] `Tailor360.Modules.Notifications.Contracts/Feedback/FeedbackLinkToken.cs` — a `readonly record struct`
      wrapping the opaque token string, with `ToString()` overridden to return `"[redacted]"` and no public
      property exposing the value outside the assembly that resolves it. The token is **Credentials and secrets**
      (`data-classification.md` 5.14) and security rule 7 forbids it from reaching a log, a trace or a problem
      detail; a type that cannot be interpolated into a message is how that is made true by construction rather
      than by care at every call site. A unit test asserts `$"{token}"` does not contain the value.
- [ ] `Tailor360.Modules.Notifications.Contracts/Feedback/IFeedbackCapture.cs` — the per-purpose content and
      submission contract #211's dispatcher calls, taking the **opaque token and not a resolved link**, for the
      reason given above: `GetFormAsync(FeedbackLinkToken token, CancellationToken)`,
      `SubmitAsync(FeedbackLinkToken token, FeedbackSubmission submission, CancellationToken)` and
      `UpdateAsync(FeedbackLinkToken token, FeedbackSubmission submission, CancellationToken)`, each returning
      `Result<T>`. Contracts may reference `Platform.Abstractions` and nothing else (ARCH-002, ARCH-004).
- [ ] `Contracts/Feedback/FeedbackForm.cs` — what the page renders: the order display number, the delivery date,
      the garment list (`GarmentJobId`, `GarmentJobNumber`, `CategoryLabel`, `ServiceTypeLabel`), the locale to
      render in, the five rating prompts as stable keys, and the state — `AwaitingResponse`, `EditWindowOpen`
      (with the instant it closes) or `Closed`. No customer name, no address, no amount: the token holder needs
      none of them to answer five questions.
- [ ] `Contracts/Feedback/FeedbackSubmission.cs` — `Overall`, `Fit`, `StitchingQuality`, `DesignMatch`,
      `Timeliness` (each 1–5, the five dimensions `docs/prd/glossary.md:242` names), `Comment` (optional),
      `ContactRequested`, `AlterationRequested` and `AlterationGarmentJobId` (required when
      `AlterationRequested`). Validate every field server-side (`CLAUDE.md` security rule 3); a rating outside
      1–5, a garment that is not on the order, or an alteration request naming no garment is a refusal with field
      errors, never a clamp. The comment's length bound is the one #213 gives `feedback_responses.comment` — read
      it, refuse above it, and do not introduce a second number here.
- [ ] `Tailor360.Modules.Notifications.Application/Feedback/FeedbackCaptureHandler.cs` — resolve, validate, write,
      evaluate, all in one transaction: the response row through #213's store, then #213's policy evaluation, so
      that a low rating or an explicit alteration request has opened exactly one case by the time the customer sees
      the thank-you. `notifications.feedback-received.v1` is published by #213's operation inside the same
      transaction; this handler does not publish it a second time.
- [ ] The eligibility rule, evaluated **again at submission and not only at issue**: `IOrderSnapshotQuery.GetAsync`
      must answer an order whose `DeliveredAt` is set (or, for a per-garment handover, a `Jobs` entry whose
      `DeliveredAt` is set), in the branch the link was issued for. Anything else reads as not found, with the same
      body and the same status as an expired token (#211's "reads alike as not found" discipline).
- [ ] Registration in `NotificationsModuleServiceCollectionExtensions.AddNotificationsModule` — `IFeedbackCapture`
      and its handler, plus whatever per-purpose registration #211's dispatcher reads for `feedback`. Today
      `AddNotificationsModule` is `return services;` (verified), so this is the module's first registration of a
      contract implementation. Registration extension only; the host composes (ARCH-006). **That file is a
      single-session file** shared with every other Notifications slice — rebase, never merge.
- [ ] Configuration, not code (DOR-11). Two numbers this slice needs and must not invent:
      **the edit window's closing instant** — read it from the token record #213 resolves (the field its own scope
      calls "a single edit window") and compare it against `IClock.UtcNow`; this slice writes no window length
      anywhere. **The invitation's time-to-live** — not this slice's at all; it is set where the link is minted,
      which is [E11-F03-5]. If #213 merged with neither an edit-window instant on the token nor a field
      for it on `service_recovery_policies`, **that is a gap to file against #213 before this slice starts** — a

## Acceptance criteria

- [ ] A customer holding a valid `feedback` link for a delivered order submits overall 4, fit 5, stitching quality
      4, design match 5, timeliness 3 and a comment, through `IFeedbackCapture`, and a `feedback_responses` row
      exists with those five values, the order and garment references and the locale — with no direct database
      write anywhere in the test.
- [ ] The same token submits once more inside the edit window and the row is **updated in place**, keeping its
      identifier, its `feedback_responses` created instant and its case link; a third attempt, and any attempt
      after the window has closed, is refused with a stable problem code and changes nothing.
- [ ] A rating at or below the branch policy threshold, **or** `AlterationRequested` at any rating, leaves exactly
      one `service_recovery_cases` row for that feedback identifier — still exactly one when the submission is
      replayed and when the evaluation runs twice (EX-11, `docs/prd/exceptions.md:48`). **On what the idempotency is
      keyed, two sources disagree and the default is recorded below**: `exceptions.md` section 4.4 (line 160) and
      plan line 2101 both say "idempotent on the feedback id", while #213's own acceptance criterion says
      "idempotent on the order/garment-job reference". This slice asserts the *observable* rule — one case, however
      many times the evaluation runs — so the test passes under either key, and the body's open-decisions table
      names which one #213 must settle on.
- [ ] Negative: a token for an order that is not delivered, a token for another branch, a revoked token, an expired
      token and a random 128-bit guess all answer identically — the same status and the same body, with nothing
      that distinguishes "wrong purpose" from "never existed".
- [ ] Negative: an alteration request naming a garment that is not on the order is refused with a field error on
      `alterationGarmentJobId`, and no case and no response row is written.
- [ ] Exception: feedback never mutates anything outside `notifications`. An integration test asserts that a full
      submission leaves the `customers`, `orders` and `catalog` schemas byte-identical — the EX-11 clause "feedback
      rows are read-only after the edit window and never mutate measurements, design or job history".
- [ ] Rule-level: this slice adds no HTTP route, so ARCH-007, ARCH-017, ARCH-008 and ARCH-023 have nothing to
      bind to here; the architecture tier stays green and `docs/api/openapi.v1.json` is unchanged.
