Sub-issue of #50. The #50 blueprint in `docs/IMPLEMENTATION_PLAN.md` section 8 is explicit that display preferences
— "theme system/light/dark/high-contrast for sunlight; text size 100/125/150%" — are "stored server-side in
`identity.user_preferences` and applied at login so shared devices do not leak or lose settings". Half of that
exists: `src/Modules/Identity/Tailor360.Modules.Identity.Domain/Users/UserPreferences.cs` holds `Locale`,
`TimeZoneId`, `Theme`, `Density`, `ReducedMotion` and `LandingRoute`, and `GET /api/v1/me` returns them. The other
half does not: there is **no text-size field** on the record, and **no endpoint that writes preferences at all** —
searching the `Api` project for "preferences" finds only the read in `Me/MeEndpoints.cs` and the payload that
serialises it. The client says the same thing from its side: `clients/pwa/src/app/preferences.ts` lines 15-35
document the requirement, define the two-method `DisplayPreferencesStore` interface the server implementation is
meant to drop into, and ship a `localStorage` stub as the only implementation. This slice is the server half only.

  maps `user_preferences`: key `UserId`, `Locale` (16), `TimeZoneId` (64), `Theme` and `Density` as strings

  an endpoint may declare itself, with `RequireSignedInHolder(justification, reviewedIn)` as the level for
  an act on the caller's own account that is not credential material. It satisfies ARCH-007 through
  `SelfServiceMetadata`, which `tests/Tailor360.ContractTests/EndpointPolicyTests.cs` and
  `EndpointReviewCitationTests.cs` both read.
- `src/Platform/Tailor360.Platform.Security/Endpoints/RateLimitPolicyNames.cs:44` — `Write = "write"`.
  `EndpointAuthorisationExtensions.Audited(...)`
  (`src/Platform/Tailor360.Platform.Security/Endpoints/EndpointAuthorisationExtensions.cs:44`) is the
  audit filter ARCH-008 asserts.
- **`src/Platform/Tailor360.Platform.Security/Endpoints/EnumText.cs` — `EnumText.TryRead<TEnum>(text,
  out value)` is how an enumeration member arrives from a request, and the only way it may.** Do not
  write `Enum.TryParse`: issue #90 was exactly that defect — `Enum.TryParse` accepts `"99"`, `"-1"`
  and `"Millimetre, Count"`, each of which then reaches storage as a value no member names. `TryRead`
  matches the declared names and refuses numbers, which is also what makes `"textSize": "200"` a
  field error rather than a stored value.
- `src/Modules/Identity/Tailor360.Modules.Identity.Api/IdentityApiErrors.cs` — the Api-level error
  catalogue the new recognition errors belong in, beside `StatusNotRecognised` (line 48),
  `RoleReachNotRecognised` (54) and `FactorNotRecognised` (79). The shape is
  `Error.Validation("identity.<kebab-code>", "<what to send instead>", "<field name>")`, and the
  field name in the third argument is what puts the message under the right key in the RFC 9457
  `errors` object. `Problems.From(error, context)` is the call that renders it —
  `UserAdminEndpoints.cs:117-120` is the pattern to copy verbatim.
- `docs/security/permission-matrix.md` — the endpoint table, whose rows live **inside the
  `<!-- matrix:endpoints -->` markers** (lines 311-512) and are what `AuthorisationMatrixTests`
  reads; the four-value `Declaration` vocabulary is defined at line 284-289, and
  `self-service:<level>` takes `live-session`, `sign-in-complete` or `second-factor-satisfied`.
  Read two rows before writing the new one. The `GET /api/v1/me/` row at line 500 is declared
  **`self-service:live-session`**, not `sign-in-complete` — it is deliberately the weaker level,
  because the challenge screen has to be able to paint. The rows in the level this endpoint uses are
  `POST /api/v1/auth/logout-all` (line 350), `GET /api/v1/auth/passkeys` (355) and
  `DELETE /api/v1/sessions/{sessionId}` (502); copy the shape of those. The table is in route order,
  so the new row goes immediately after line 500. Columns, in order: `Method`, `Route`,
  `Declaration`, `Permission`, `Branch scope`, `Resource`, `Audited as`, `What it is for` — the four
  middle cells are `—` for a self-service route.

## What is missing

- A text size on the record. `UserPreferences` has no equivalent of the client's
  `TEXT_SIZE_PREFERENCES = ['100', '125', '150']`
  (`clients/pwa/src/design-system/foundations/types.ts:55`), so the one preference a person with
  presbyopia actually switches on (checklist item **A11Y-72**, which names 100 / 125 / 150%) cannot be
  stored at all.
- Any write path. `MeEndpoints.MapMeEndpoints` maps one `GET`. A person can be shown their preferences and
  cannot change them; the shell's `DisplayPreferencesPanel` writes to `localStorage` on the device, which
  is exactly the leak on a shared counter tablet that the blueprint names.
- A domain way to materialise preferences for an account that has none.
