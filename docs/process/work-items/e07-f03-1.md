## Acceptance criteria

- [ ] A Reception user holding `custody.scan` records an intake-received scan over HTTP against a confirmed
      garment job and the response names the new custodian; one `scan_events` row and one `job_custody_state` row
      exist, with the server timestamp, not the client's, ordering the chain (INV-CDY-08).
- [ ] The route declares one permission, one rate-limit policy, the audit filter and its no-resource
      justification, and the contract tests that enforce ARCH-007, ARCH-008, ARCH-017 and ARCH-023 pass unchanged.
- [ ] **Negative — replay.** The same `Idempotency-Key` replays the first outcome byte for byte; a different body
      under that key is `422 idempotency.key-reused`; the same `clientEventUuid` under the same actor returns the
      original outcome without a second row; the same `clientEventUuid` under a **different** actor is `409
      custody.event-conflict` (INV-CDY-02).
- [ ] **Negative — wrong branch, and it is a 404.** Two arms, and they answer differently, because
      `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml` fixes both:
      a caller who does not hold `custody.scan`, or whose session carries no branch, is
      `403 security.forbidden` (the `non-holder-own-branch` dimension); a caller who **holds** `custody.scan` in
      branch A and names a job whose `current_custody_branch_id` is branch B gets
      `404 security.resource-not-found` — the `holder-other-branch: out-of-reach` dimension — **indistinguishable
      from a job that does not exist**, because a 403 here would make the endpoint an oracle for which garment jobs
      live at which branch. Both are audited as `authz.denied` and write no event. Note in the pull request that
      `docs/architecture/sequences/barcode-handoff.md` section 6's "Actor is outside the job's branch scope → 403"
      row describes the first arm only; `matrix.yaml` is the machine-checked authority for the second.
- [ ] **Negative — manual without the permission.** `source = manual` without `custody.manual_lookup` or without a
      reason is refused and writes no event; with both, the event carries `source = manual` and the reason.
- [ ] **Exception — mismatch.** A scan contradicting the recorded custodian is **refused**
      (`custody.custodian-mismatch`) and the event is nevertheless persisted with its `exception_reason`; the
      custodian does not change. A stale event is refused `custody.stale-event` with the same treatment.
- [ ] `UPDATE` and `DELETE` on `custody.scan_events` are refused by the database, not only by the application.
- [ ] An action this release does not accept is refused `custody.action-not-available` naming the issue that
      brings it, rather than silently succeeding.
