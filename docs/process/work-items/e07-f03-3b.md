## Scope

- [ ] **`ReconciliationCase.RecordCorrection` and `ReconciliationCase.Approve`** on the domain type E07-F03-3
      created — pure, no I/O, so every arm is a unit test. `RecordCorrection` refuses on a `resolved` or
      `withdrawn` case. `Approve` refuses when the approver **is** the recorder (INV-CDY-07) and when the case is
      not `awaiting_approval`. The approval rule is a pure predicate over the recorder, the approver and the
      correction's shape.
- [ ] **`CustodyReconciliationOptions`** bound to `Custody:Reconciliation`, with a `PolicyVersion` stamped on every
      case resolution, `AlwaysRequireApproval` defaulting to **true**, and an `IValidateOptions<>` validator.
      `true` is the strictest reading of a threshold **IOD-05 has not set**, it invents no number, and it is the
      justification `DispatchPolicyOptions` already records for the same situation. A **branch change**, a **phase
      skip** and a **dispatch reversal** are hard-coded as always requiring approval whatever the configuration
      says, because `state-transitions.md` line 293 and EX-13 both fix those three by name.
- [ ] **`POST /api/v1/custody/cases/{caseId}/corrections`** — the repair. Body: the resulting custodian kind and id
      or `locationId`, the corrected `scanEventId`, a reason code, reason text, an optional note and a
      `clientEventUuid`. Appends a `Correction` scan event through E07-F03-1's handler in one transaction, linked
      to both the corrected event and the case; sets `job_custody_state` **only when approval is not required**,
      otherwise leaves the case `awaiting_approval` with the correction recorded and custody unmoved.
      `CustodyPermissions.Reconcile`, `BranchScope.CurrentBranch`,
      `.ScopedToResource(CustodyResourceKinds.ReconciliationCase, "caseId")` (ARCH-023),
      `.RequireIdempotency()`, `RateLimitPolicyNames.Write`, `.Audited("custody.reconcile", reasonRequired: true)`,
      `RequestTimeoutPolicies.Command`.
- [ ] **`POST /api/v1/custody/cases/{caseId}/approvals`** — the second approver: applies the recorded correction,
      moves `job_custody_state` and resolves the case, stamping `PolicyVersion`.
      `CustodyPermissions.ApproveReconciliation`, the same resource scope, **`.RequireStepUp()`** (ARCH-018 demands
      it, because the permission is flagged `RequiresStepUp`), `.RequireIdempotency()`, `RateLimitPolicyNames.Write`,
      `.Audited("custody.approve_reconciliation", reasonRequired: true)`, `RequestTimeoutPolicies.Command`.
      Refused `custody.approver-is-recorder` when the approver recorded the correction.
- [ ] **Turn `ScanAction.Correction` live** in E07-F03-1's guard table — the one edit this slice makes to that
      file — so a `Correction` event may only be appended by these two routes and never by `POST /custody/scans`
      directly. A `Correction` presented to the scan route stays refused `custody.action-not-available`, now naming
      the correction route instead of an issue, which is itself an acceptance criterion.
- [ ] Payload types in `Custody.Api` (ARCH-013, no domain type returned); **two** rows in the
      `<!-- matrix:endpoints -->` block of `docs/security/permission-matrix.md`; the two routes and their
      `identifier-editing` answers for `{caseId}` in `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`,
      plus the **step-up dimension** for the approval (`flagged-stale-step-up: step-up`,
      `flagged-fresh-step-up: allowed` — both already defined, so no new dimension is needed);
      `docs/api/openapi.v1.json` and `clients/pwa/src/api/schema.d.ts` regenerated
      (`pnpm --dir clients/pwa generate:api`).

## Acceptance criteria

- [ ] A Branch Manager records a correction on an open `mismatch` case naming the resulting custodian; the case
      becomes `awaiting_approval`, the `Correction` scan event exists linked to both the corrected event and the
      case, and `job_custody_state` has **not** moved. An Owner then approves under step-up;
      `job_custody_state` names the corrected custodian, the case is `resolved` with `approved_by` set, and
      **both** the corrected event and the `Correction` event are still readable — history is never edited
      (INV-CDY-01).
- [ ] Both routes declare one permission, one rate-limit policy, the audit filter with a reason and the `{caseId}`
      resource scope; the approval declares step-up (ARCH-007, ARCH-008, ARCH-017, ARCH-018, ARCH-023).
- [ ] **Negative — self-approval.** The user who recorded the correction cannot approve it:
      `custody.approver-is-recorder`, the case stays `awaiting_approval`, custody does not move, and the refusal is
      audited (INV-CDY-07).
- [ ] **Negative — no reason.** A correction or an approval without a reason is refused and writes nothing; both
      permissions are `RequiresReason: true` in `CustodyPermissions.All`.
- [ ] **Negative — stale step-up.** An approval from a session whose last strong authentication is older than
      `Security:StepUp:Freshness` is `403 security.step-up-required` and writes nothing; the same session, having
      re-authenticated inside the window, completes — `matrix.yaml`'s `flagged-stale-step-up` and
      `flagged-fresh-step-up` dimensions, asserted and not re-invented.
- [ ] **Negative — other branch.** A case whose `branch_id` is another branch answers
      `404 security.resource-not-found` for the correction and for the approval — `matrix.yaml`'s
      `holder-other-branch: out-of-reach`, the same answer as a case that does not exist, so `{caseId}` cannot be
      used to enumerate cases. A caller lacking the permission gets `403 security.forbidden`.
- [ ] **Negative — wrong state.** A correction on a `resolved` or `withdrawn` case, and an approval on a case that
      is not `awaiting_approval`, are both refused `custody.case-not-open` with the current status named, and write
      nothing.
- [ ] **Exception — the three always-approve shapes.** With `AlwaysRequireApproval = false` in configuration, a
      correction that changes the custody **branch**, skips a **phase**, or reverses a **dispatch** still requires
      the second approver; an ordinary custodian correction does not. Three tests, one per shape.
- [ ] A `Correction` presented to `POST /custody/scans` is still refused, naming the correction route.
