`src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Events/` holds **ten files** today and not one is about QC,
rework or alteration (`ls` it), while `src/Modules/Orders/Tailor360.Modules.Orders.Domain/Jobs/` has `ReadyGate.cs`

## Scope

- [ ] **`reporting.projections_job_quality`** — one row per garment job: `organisation_id`, `branch_id`,
      `garment_job_id`, `category_key`, `service_type_key`, `qc_attempts`, `qc_passes`, `qc_failures`, `first_pass`
      (true when the first recorded QC outcome was a pass), `rework_cycles`, `rework_open`,
      `last_failure_reason_code`, `alteration_requested`, `alteration_accepted`, `alteration_completed`,
      `reopened_count`, `reached_qc` (false for a garment whose pinned workflow version has no QC phase, which is
      what keeps it out of every denominator rather than silently at zero), `first_qc_at`, `last_qc_at`,
      `last_event_at`.
- [ ] **`reporting.projections_quality_reason_daily`** — `organisation_id`, `branch_id`, `business_date` (the
      branch's own day), `category_key`, `phase_code`, `failure_reason_code`, `failures`, `rework_opened`,
      `rework_completed`, `alterations_requested`, `last_event_at`. The grain the Pareto of failure reasons and the
      trend are read from.
- [ ] **Handlers** `reporting.quality-on-qc-recorded`, `-on-rework-opened`, `-on-rework-completed`,
      `-on-alteration-requested`, `-on-alteration-decided`, `-on-alteration-completed` and `-on-job-reopened`,
      following `OrderFactHandlers.cs`: unique `HandlerName` each, `Schema = ReportingDbContext.SchemaName`, writes
      staged and never saved, safe to call twice.
- [ ] **Out-of-order and duplicate delivery are the normal case.** A rework completion may arrive before its
      opening; the row is created by whichever event arrives first and the counters are recomputed rather than
      incremented blindly. The inbox row, not a guard in the projector, is what makes a redelivery a no-op.
- [ ] **No attribution to a named person anywhere in this slice.** Neither table carries an actor column, and the
      events carry the actor's role at most. 5.15 restricts figures about a named person to three roles and DC-11's
      proposed position forbids a shop-floor ranking; a quality projection that named tailors would be exactly the
      "misleading staff ranking without adequate context" the parent's fifth implementation step rules out.
      Per-assignee figures live only behind `reports.read_workload` in E10-F02-3b.
- [ ] **No media.** QC evidence photographs are Media's, are **Confidential** under 5.5, and are reachable only
      through Media's authorised streaming endpoint: no storage key, no identifier and no URL enters this projection
      (security rule 9).
- [ ] **One migration**, `QualityOutcomeProjection`, on the `ReportingDbContext` chain, scaffolded with the command
      in `src/Modules/CLAUDE.md` section 6, producing `<timestamp>_QualityOutcomeProjection`. Expand-only: two new
      tables, nothing altered.
- [ ] **Registration** of the handlers and the projection in `ReportingModuleServiceCollectionExtensions.cs`
      (ARCH-006).
- [ ] **Metric dictionary** entries in `docs/reports/metrics.md` for `first_pass_rate`, `qc_failure_rate`,
      `rework_rate`, `rework_cycles`, `alteration_rate` and `reason_share`, each stating its formula, its source
      events, its denominator (**garments that reached QC**, not every garment), its exclusions (cancelled garments,
      and garments whose workflow version has no QC phase) and the rework-time treatment plan Section 8 (#45) fixes:
      **counted in production time, reported separately as cycles**. `docs/reports/` does not exist in the working
      copy; the scaffold is #183's and E10-F02-1 extends it first. Check whether #183 shipped a seeding path for its
      `metric_definitions` table (`grep -rn "metric_definitions" src/ docs/`); if it did, add these rows there too,
      and if it did not, the document is the dictionary and the table stays empty.

## Acceptance criteria

- [ ] Over a synthetic stream where one garment fails QC twice with different reason codes, is reworked twice and
      then passes, `projections_job_quality` shows `qc_attempts = 3`, `qc_failures = 2`, `first_pass = false`,
      `rework_cycles = 2`, `rework_open = false` and `reached_qc = true`, and
      `projections_quality_reason_daily` carries one failure row per reason code per day.
- [ ] A garment whose pinned workflow version has no QC phase ends with `reached_qc = false` and zeroed QC counters,
      so E10-F02-4b can exclude it from a denominator rather than counting it as a pass or a failure.
- [ ] **Negative — redelivery:** dispatching the same stream twice changes no row and leaves the checkpoint unmoved
      on the second pass.
- [ ] **Negative — out of order:** a rework completion delivered before its opening ends with the same row as the
      forward order, with `rework_cycles` counted once and `rework_open` false.
- [ ] **Negative — no person is nameable:** a test asserts neither projection table has a column resolving to a user
      identifier or a display name. This is a test because it is the parent's "avoid misleading staff ranking"
      criterion, and a prose promise cannot fail a build.
- [ ] **Exception — a reopened garment:** `orders.job-reopened.v1` after delivery adds a QC cycle to the existing row
      rather than creating a second garment row, the earlier outcomes are not rewritten, and the reason the row
      changed is visible as `reopened_count`.
- [ ] **Exception — an unknown reason code:** a code the vocabulary does not yet contain is counted under its own
      value, never dropped and never mapped to "other", because **OD-10** is open and the projection fixes no
      vocabulary.
- [ ] **Rebuild equals live:** `rebuild-projection` reproduces both tables row for row, including the daily roll-up.
- [ ] `ReportingDbContext` maps nothing outside `reporting` (ARCH-005); no Reporting project references
      `Orders.Infrastructure` or `Orders.Api` (ARCH-011).
