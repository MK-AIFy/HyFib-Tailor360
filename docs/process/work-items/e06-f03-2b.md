## Adding an integration event, and the six tests that will fail you

`tests/Tailor360.ContractTests/IntegrationEventTests.cs` enforces the whole chain. Read it before writing the
first record.

- `EveryEventIsDocumentedByASchemaAndAnExample` — both `docs/integration/events/<wire-name>.schema.json` and
  `<wire-name>.example.json` must exist. For size: `orders.job-held.v1.schema.json` is 72 lines and its example
  12, so budget about 84 lines per event for the JSON alone.
- `EverySchemaDescribesExactlyWhatTheEventPutsOnTheWire` — the schema's `properties` must be **exactly** the set
  the record serialises, `required` must be non-empty and must name nothing the record lacks, and
  `additionalProperties` must be present and `true` (`docs/integration/events/README.md` section 2: a closed
  schema would make every additive change breaking).
- `EveryExampleMatchesItsSchemaAndNamesItsOwnEvent` — the example carries the same property set and its
  `eventType` is the wire name.
- `EveryEventVersionsItsNameAndItsPayloadTheSameWay` — `SchemaVersion` agrees with the `.vN` in the wire name.
- `EveryEventIsDeclaredInItsOwnModulesPublishedSurface` — the record lives in `Orders.Contracts` and the wire name
  appears in the **Publishes — integration events** list of `docs/architecture/module-ownership.md` section 5.5.
  If it does not, amend that list in the same pull request; section 9 of that document requires it.
- `NoPayloadCarriesAFieldNamedLikePersonalData` — `IntegrationEventInventory.PersonalFieldWords` rejects a
  serialised property whose whole name, **or any camel-cased word inside it**, is one of `name`, `firstname`,
  `lastname`, `fullname`, `displayname`, `nativename`, `phone`, `telephone`, `mobile`, `msisdn`, `email`,
  `address`, `postcode`, `pincode` and the rest of that list. So no `checklistName`, no `defectName`, no
  `criterionName`, no `inspectorName`, no `roleName` — codes, keys, identifiers, statuses, amounts and timestamps
  only. The register `IntegrationEventInventory.PersonalFieldExemptions` exists but using it needs the approval
  `docs/nfr/data-classification.md` section 5.3 describes, which this issue does not have.

Two shapes to copy rather than invent: the payloads are **flat** — no `payload` wrapper — as
`orders.job-held.v1.schema.json` shows (`eventId`, `occurredAt`, `aggregateId`, `organisationId`, `branchId`,
`orderId`, `garmentJobNumber`, `reasonCode`, `eventType`, `schemaVersion`); and the `$comment` those schemas carry
states that a property added within `v1` is optional forever. Add the event's row to the table in
`docs/integration/events/README.md` as well — one row per event, with links to both files.

## Out of scope

**Returning the garment to the phase.** This slice records that a rework is open and what phase it returns to; the
`job_phases` row that actually reopens the phase is #33's `orders.phase_transition` command, and a rework does not
call it. Say so in the pull request as a known limitation: a rework opened here is visible to the gate (it blocks) and
to the dashboard (E06-F03-6), and the phase itself is moved by the workboard. The ready-gate recomputation a rework
causes — E06-F03-5, the only writer of `garment_jobs.is_ready_for_delivery` (INV-JOB-07); this slice leaves the
recomputation port un-called and says so. Holds and cancellation — E06-F03-3. Alterations — E06-F03-4a, 4b. The
repeated-rework dashboard read — E06-F03-6. Any screen — E06-F03-7. Evidence media — as E06-F03-2a records, stored as
a reference and never resolved (#187, #188).

## Acceptance criteria

- [ ] A Tailor Master records a failing QC result, opens a rework against it naming a phase of the pinned workflow
      version with a reason code and a reason, completes the rework, and records a **new** QC result. All three QC
      rows and the one rework row remain readable with their actors and timestamps, and nothing is overwritten —
      **this is #34's acceptance criterion "Rework cycles preserve each QC result, actor, defect and resolution"**,
      completed with E06-F03-2a.
- [ ] Both routes declare a permission and a resource scope (ARCH-007, ARCH-023), exactly one rate-limit policy
      (ARCH-017), a request timeout, and the audit filter **with a reason** (ARCH-008); the endpoint-inventory
      contract test shows it, and the audit row carries the reason.
- [ ] **Negative**: a rework opened against a **passing** latest result is refused with a named problem code; a
      second rework opened while one is already open is refused by the partial unique index **and** by the handler,
      so the answer is a problem detail and not a database error; completing an already-completed rework is refused;
      a `return_to_phase_code` the pinned workflow version does not contain is refused with the code named; a caller
      without `orders.open_rework` receives `403` `security.forbidden`; a caller whose branch does not reach the job
      receives the same answer as for a job that does not exist; a replayed `Idempotency-Key` returns the first
      outcome; a command with no reason is refused by validation.
- [ ] **Exception**: a rework opened against a result that is not the **latest** is refused, because INV-JOB-06 is
      about the latest result and a rework against a superseded one would block the gate on a fact nobody can clear.
- [ ] **Exception**: deleting the parent order cascades through `rework_tasks` without a `restrict_violation`,
      asserted beside `OrdersCascadeTests`.
