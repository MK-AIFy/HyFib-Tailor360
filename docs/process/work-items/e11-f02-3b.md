Sub-issue of #48, split out of [E11-F02-3] in review. [E11-F02-3a] ships the doorstep handover record and the confirm
command, which **verifies** a six-digit code against a stored digest. Nothing mints one, and nothing can get one to the
customer, because **no sanctioned mechanism exists today for Custody to ask Notifications to send something**. This
child is that mechanism, the code's lifecycle, and the one design decision the parent cannot avoid.

`docs/prd/state-transitions.md` section 4.1 fixes the rule — "Recipient name plus a six-digit OTP valid ten minutes with
at most five attempts … per the branch `custody.recipient_confirmation` policy" — and `docs/nfr/a11y-checklist.md`
**A11Y-78** makes the typed-name-plus-code path required outright, which is why the feature is not optional and why #48
cannot close without it.

## The decision this issue carries, stated before the scope

`docs/architecture/module-ownership.md` section 5.10 lists what Notifications publishes: an `ITimelineSource` and the
in-app notification query. **There is no send port and no intent port**, and its consumed triggers are "Orders, Billing,
Custody and Inventory **integration events**". #209's own body confirms it: it "adds the inbox-side handlers that turn a
consumed event into zero or one intent … no new publisher work needed in those modules". So the four candidate designs
are these, and the pull request states which it took and why:

1. **Rejected — a synchronous call from Custody into Notifications.** The contract does not exist. Inventing one is a
   new cross-module mechanism, which `CLAUDE.md` section 8 and `module-ownership.md` section 1 both route through an
   architecture decision record **before** merge. If the reviewer wants this, it is an ADR and a re-scope, not a quiet
   addition.
2. **Rejected — the plaintext code in the event payload.** `/admin/outbox` renders payloads, the relay of #56 copies
   them, and `docs/nfr/data-classification.md` section 6.3 forbids a credential being a log field; an outbox row is
   worse than a log line because it is durable and replayable.
3. **Rejected — a sender inside Custody.** It would bypass #209's consent gate, duplicate what ARCH-009 keeps in
   `Integration.Infrastructure`, and is the failure plan Section 6.2 note 7 warns about.
4. **Taken — a read contract, which is the first of the five sanctioned mechanisms.** Custody mints the code, stores a
   digest for verification and a Data-Protection-ring-protected copy for one read, and publishes
   `custody.delivery-confirmation-code-issued.v1` **carrying no code**. Notifications' rule ([E11-F02-6b]) raises its
   intent from that event, and the renderer pulls the plaintext **once** through a new Custody read contract at render
   time. The protected copy is cleared by that read. The code therefore exists in the mint response's absence, in one
   protected column, and in the rendered body — and nowhere else.

`docs/nfr/data-classification.md` section 6.2's register is the precedent for the protected column: **TOTP MFA secrets**
are held "encrypted with the Data Protection ring", and the ring itself arrived with #21. The register's own row,
**Delivery one-time passwords**, requires only "short-lived, single-use, bound to the dispatch authorisation" — it does
not require hash-only, which is the stricter rule the register states for **recovery codes**, and which this design
still keeps for *verification*.

## Scope

- [ ] **One expand-only migration** — `dotnet ef migrations add DeliveryConfirmationCode`, giving
      `<timestamp>_DeliveryConfirmationCode` (the plan's `<issue>_<slug>` form, `48_delivery_confirmation_code`, goes in
      the `docs/dev/migrations.md` row, not in the type name) — adding to `custody.delivery_confirmations`:
      `code_protected` (bytes, nullable, ring-protected, cleared after one read), `code_issued_at`, `code_taken_at`,
      `code_issue_count`. Every column nullable or defaulted, so the previous release keeps working against the same
      table.
- [ ] **`POST /api/v1/custody/deliveries/{authorisationId}/confirmation-code`** — mint. Six digits from
      `RandomNumberGenerator`, valid **ten minutes** from the mint, at most **five attempts per delivery attempt**,
      bound to the authorisation, the order, the job set and the dispatching user (`docs/prd/state-transitions.md`
      section 4.1; plan lines 2069-2070). Stores the digest and the protected copy, publishes the event, and **returns
      the expiry and the attempts remaining and never the code** — a mint response carrying the code would hand the
      dispatcher both factors and void the control. `custody.confirm_delivery`, `BranchScope.CurrentBranch`,
      `.ScopedToResource(CustodyResourceKinds.DispatchAuthorisation, "authorisationId")`,
      `.Audited("custody.confirmation_code_issued")`, `.RequireIdempotency()`, `RateLimitPolicyNames.Write`,
      `.WithRequestTimeout(RequestTimeoutPolicies.Command)`.
- [ ] **A re-issue replaces the live code and resets nothing else.** `code_issue_count` increments, the previous digest
      and protected copy are overwritten, and `code_attempt_count` is **not** cleared: the five attempts belong to the
      delivery attempt, not to the code, so re-minting is not a way to buy five more guesses. A re-issue after the
      authorisation is spent or expired is refused.
- [ ] **`Custody.Contracts.Delivery.IDeliveryConfirmationCodeReader`** with one member —
      `Task<string?> TakeAsync(Guid dispatchAuthorisationId, Guid organisationId, CancellationToken)` — which unprotects
      the copy, clears it in the same save, and returns null for anything else: already taken, expired, spent, unknown,
      or another organisation's. **Exactly-once by construction, and the only way the plaintext leaves the module.** Its
      XML remarks carry the rule a caller must not break: the value is rendered into a message body and is never logged,
      never stored by the caller and never returned to a staff surface.
- [ ] **`custody.delivery-confirmation-code-issued.v1`** in `Custody.Contracts`, carrying the authorisation, the order,
      the branch, the organisation, the actor, the expiry and the server time — and **no code, no digest, no recipient
      and no amount**. It is the trigger, not the carrier.
- [ ] **Amend `docs/architecture/module-ownership.md` section 5.6 in this pull request**: add the event to Custody's
      published integration events and `IDeliveryConfirmationCodeReader` to its published read contracts, and add
      Notifications to the consumers of the event. Section 9 of that document requires the amendment to travel with the
      change, and `CLAUDE.md` section 3 says a published name that is not in the ownership document does not exist.
- [ ] **The event's documentation**: `docs/integration/events/custody.delivery-confirmation-code-issued.v1.schema.json`,
      its `.example.json`, and a row in that directory's `README.md` — `tests/Tailor360.ContractTests/
      IntegrationEventTests.cs` fails until all three exist and the schema describes exactly the serialised properties.
      `README.md` is a single-writer file.
- [ ] **Move `CustodyDispatchOptions.RecipientConfirmation`'s interim default from `Signature` to `Otp`**, now that a
      code can actually be sent, and update the question recorded against **OD-04** in
      `docs/prd/assumptions-and-open-decisions.md` to say so. `Otp` is the strictest of the three values and the one
      A11Y-78 requires to exist whatever a branch chooses.
- [ ] **The ten minutes must survive an asynchronous send, and the body says why it does.** The outbox lag objective is
      `p95 < 30 s` (S7) and the notification hand-off `p95 < 60 s` (S10), both in `docs/nfr/slo.md` section 5, so a
      ten-minute code has an order of magnitude of headroom. The expiry runs from the **mint**, the mint response
      returns it so the screen can show it, and a code that expires before it arrives is re-requested — never silently
      extended.
- [ ] Payloads in `Custody.Api` (ARCH-013); registration in `AddCustodyModule`; the one operation regenerated into
      `docs/api/openapi.v1.json` and `clients/pwa/src/api/schema.d.ts`.

## Acceptance criteria

- [ ] **The journey:** against a dispatched authorisation, Delivery Staff mints a code; the response carries the expiry
      and the attempts remaining and **no code**; exactly one `custody.delivery-confirmation-code-issued.v1` is
      published carrying no code; a single call to `IDeliveryConfirmationCodeReader.TakeAsync` returns the plaintext;
      and [E11-F02-3a]'s confirm accepts that plaintext and records the handover. Over HTTP, with the contract called
      in-process, and no direct database access in the test.
- [ ] The route declares a permission with branch scope, a resource scope, exactly one rate-limit policy, the audit
      filter and idempotency (ARCH-007, ARCH-008, ARCH-017, ARCH-023).
- [ ] **Negative — the exactly-once property:** a second `TakeAsync` for the same authorisation returns null, and two
      concurrent calls return the plaintext to exactly one of them. Asserted under real PostgreSQL with two connections,
      not with a mock.
- [ ] **Negative:** `TakeAsync` returns null for an expired code, a spent authorisation, an unknown authorisation and an
      authorisation in another organisation — one indistinguishable answer, so the contract cannot be used to probe.
- [ ] **Negative:** a re-issue does not reset `code_attempt_count`; after five wrong attempts a freshly minted code is
      still refused and the refusal says the delivery must be re-attempted under a new authorisation
      (`docs/nfr/data-classification.md` section 6.2's "on compromise" column says exactly that).
- [ ] **Negative:** a mint against an authorisation that is not `dispatched`, or is expired or spent, or whose order is
      cancelled, is refused with an RFC 9457 problem naming the state, and records nothing.
- [ ] **Negative:** a caller without `custody.confirm_delivery`, or from another branch, is refused and audited.
- [ ] **Exception:** a replayed mint with its original `Idempotency-Key` returns the first outcome, publishes no second
      event and does not overwrite the live code.
- [ ] **Exception — the redaction that is the whole point:** a mint and a take run with logging, tracing and the audit
      writer captured, asserting the six digits appear in **no** log line, trace attribute, metric, audit payload,
      problem detail or outbox payload. The prohibition list is `docs/nfr/data-classification.md` **section 8**; section
      8 also describes the sentinel technique that keeps it true. This is the single piece of evidence a reviewer cannot
      reconstruct later.
- [ ] Command latency meets `docs/nfr/slo.md` section 5 row "Command latency (S3)", `p95 < 800 ms`; the figure is cited,
      not set here.
