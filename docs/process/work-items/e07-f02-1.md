- [ ] **`clients/pwa/src/scanning/scannerSource.ts`** — the `ScannerSource` abstraction named in plan Section 4.4:
      `start(onResult)`, `stop()`, an `availability` descriptor and a `source` discriminator, so a screen is written

      **extend it in place and delete the duplicate** rather than adding a second one — the #33 blueprint's
      **Screens** paragraph (plan line 1585 today) says the interface is defined there and plan Section 4.4 says #36
      implements it.
- [ ] **`clients/pwa/src/scanning/barcodePayload.ts`** — normalise and classify a payload against plan **D9**
      (the D9 row of the plan's decision table): namespace letter, then a twelve-character Crockford base32 body of
      eleven random characters and one Damm-style check character; decoding upper-cases and folds the `I`/`L` → `1`
      and `O` → `0` confusables. Returns `checksumValid` without throwing. The Damm quasigroup table and the test
      vectors are **copied from `docs/architecture/identifiers.md`**, which #190 publishes; this file reproduces
      them and its test asserts every published vector.
- [ ] **Classify the symbology before the namespace, and never refuse a GS1 payload locally.** #35's blueprint
      fixes the order — "the parser classifies symbologies before namespace checks" — and #194's own scope says an
      **EAN-8, EAN-13 or UPC-A digit string** validates the **GS1 check digit** and resolves against a stock item's
      `supplier_ean` within branch scope. A client that treated a digit string as `barcode.malformed` would refuse
      a label the server accepts, which is the opposite of the rule in `barcode-handoff.md` section 2. So
      `BarcodeNamespace` carries a `'gs1'` member beside `garment | stock | invoice | receipt`, a digit string of
      8, 12 or 13 digits classifies as `gs1` with the GS1 modulo-10 check digit verified locally for feedback only,
      and the **server** decides what it resolves to. A `product` member is **not** invented: nothing in the
      repository names one.
- [ ] **`clients/pwa/src/scanning/scanDebounce.ts`** — a same-payload debounce window so a camera that decodes the
      same label thirty times a second yields one result. The window length is **configuration, not a product
      number**: a module constant with the plan's rationale quoted, exported so a test can drive it.
- [ ] **`clients/pwa/src/scanning/KeyboardWedgeSource.ts`** plus **`useKeyboardWedge.ts`** — buffers `keydown`
      until a terminator (`Enter`, and `Tab` configurable) and emits one `ScanResult` with `source: 'wedge'`. It is

      `select` or anything `isContentEditable`, which is what checklist item **A11Y-SC-03** asks and what keeps
      E07-F01-6's Verify field working. Per `docs/nfr/support-matrix.md` section 7.1, Web Serial, WebHID and WebUSB
      are **not** used.
- [ ] **Mount the wedge listener once in the app shell** — `clients/pwa/src/App.tsx` (24 lines today) renders
      `AppShell` around the router `Outlet`; the hook is mounted there so a hardware scan works from the work queue
      or a job card, per plan Section 8 for #36. It publishes nothing by itself: a screen subscribes.
- [ ] **`clients/pwa/src/scanning/scannerTelemetry.ts`** — an in-memory sink with a named event vocabulary

## Acceptance criteria

- [ ] Every test vector published in `docs/architecture/identifiers.md` by #190 parses to the same `namespace`,
      `id` and `checksumValid` as the server's own test asserts — the vectors are read from that document, not
      invented here.
- [ ] A payload typed in lower case, or with `l`, `I` or `O` substituted for `1`, `1` and `0`, normalises to the
      same `normalised` value as the canonical form, and `raw` still carries what arrived.
- [ ] **Negative:** a payload with a corrupted check character returns `checksumValid: false` and is still returned
      as a result — the parser never throws and never decides the outcome, because the server re-validates
      (`barcode-handoff.md` section 2, INV-BID-07).
- [ ] **Negative:** an `S-`, `I-` or `R-` payload classifies as `stock`, `invoice` or `receipt` and never as
      `garment`, so a caller asking for a garment can refuse it locally before any request is made.
- [ ] **Negative:** an EAN-8, EAN-13 or UPC-A digit string classifies as `gs1` with its GS1 check digit verified,
      and is **not** classified malformed — the local classifier must not refuse a payload #194's parser accepts. A
      digit string with a broken GS1 check digit still classifies as `gs1` with `checksumValid: false`, because the
      server is the authority (INV-BID-07).
- [ ] **Negative:** with focus in a text input, a scripted wedge burst ending in `Enter` leaves the field's value
      exactly as typed and emits **no** `ScanResult` (A11Y-SC-03).
- [ ] The same payload delivered twice inside the debounce window yields one `ScanResult`; delivered twice either
      side of it, two.
- [ ] **Exception:** an unterminated wedge buffer — the scanner is configured with the wrong terminator — is
      abandoned rather than emitted, records a `decode.failure` with reason `wedge-unterminated`, and leaves the
      next scan working.
- [ ] No telemetry event produced anywhere in this issue contains a payload, a job number, a customer reference or
      typed text, asserted by a test over the sink rather than by review.
