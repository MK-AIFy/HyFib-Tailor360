## Scope

- [ ] **`GET /api/v1/inventory/items/{itemId}/balances`** — every balance for that item at the locations of the
      caller's branch: `onHand`, `reserved`, `available` (derived, never stored), `inTransit`, the location's
      identifier and name, and `asOf` from `IClock`. Plus the item's **consumed** figure for the branch, folded from
      `Consumption` entries, because the parent asks for consumed beside the other four.
      `RequirePermission("inventory.view_reports", BranchScope.CurrentBranch)`, `RateLimitPolicyNames.DefaultUser`,
      `RequestTimeoutPolicies.Read`, and — since an item is organisation-owned rather than branch-owned and has no
      branch a resolver could answer — `.TouchesNoBranchOwnedResource("An item belongs to the organisation; the
      balances answered are only those at the caller's own branch's locations.", "#39")` (ARCH-023's recorded-why
      arm). An item of another organisation reads **404** (`matrix.yaml`'s `out-of-reach`: 404
      `security.resource-not-found`). **`BranchScope.CurrentBranch` on a read, not `AssignedBranches`** — both idioms
      exist (`PaymentEndpoints.cs:128` uses `CurrentBranch` on a read of branch-owned money; `CustomerEndpoints.cs:24`
      explains why a customer record, which is organisation-wide, uses `AssignedBranches`), and stock is branch-owned
      like money, so this module follows Billing on every route. Say so once in `InventoryEndpoints` rather than
      deciding it three times.
- [ ] **`GET /api/v1/inventory/items/{itemId}/ledger`** — the transaction timeline: cursor-paginated entries newest
      first, each with type, signed base quantity, location, garment job, phase, reason code, actor, `postedAt`,
      `correctsEntryId` and the entry that corrects it where one exists. `filter[locationId]`, `filter[type]`,
      `filter[postedAfter]`, `filter[postedBefore]`; an unknown filter is **400**, never ignored. Same permission,
      rate-limit policy and scope justification as above.
- [ ] **`GET /api/v1/inventory/ledger`** — the same timeline for the caller's branch rather than for one item, so the
      ledger browser has something to page: cursor-paginated, newest first, with `filter[itemId]`,
      `filter[locationId]`, `filter[type]`, `filter[postedAfter]` and `filter[postedBefore]`, the same payload type
      and the same cost gate as the per-item read. Same permission and rate-limit policy;
      `.TouchesNoBranchOwnedResource("The listing is bounded to the caller's own branch and names no resource.",
      "#39")`. It shares one query and one payload with the route above — this is a third route, not a second
      implementation.
- [ ] **The cost gate** — `unitCost` appears on a ledger entry in the timeline **only** when the caller holds
      `inventory.view_valuation`, with `costIncluded` on the payload so a withheld figure is distinguishable from an
      absent one, exactly as `PricedOrderSnapshot.TotalsIncluded` does it. The property is nullable, because a
      withheld field must have a value to send. `docs/nfr/data-classification.md` section 5.9: "Cost, valuation and
      margin figures are Confidential and are not shown on shop-floor screens."
- [ ] **`Inventory.Contracts.IStockBalanceQuery`** — the first of the two read contracts `module-ownership.md` section
      5.7 publishes: one method answering on-hand, reserved, available and in-transit for an item and location, and
      one answering them for an item across a branch, with the caller's permission keys passed in and cost answered by
      neither. It is the **only** way another module reads stock, and nothing in this child consumes it (Reporting's
      reconciliation is #44 and #46).
- [ ] **`StockBalanceReconciliationService`** in `src/Hosts/Tailor360.Worker/Jobs/` —
      `[WorkerJob("inventory.balance_reconciliation", WorkerBranchScope.Organisation,
      InventoryPermissions.ViewReports)]`, under a lease named by the job, a fixed batch size, and a fixed interval.
      Per `(item, location)` it compares the materialised balance with `BalanceRebuild`'s fold and, on any difference,
      logs at error level with the item, the location, both figures and the correlation identifier, and increments a
      counter metric. **The ledger is authoritative; the job changes nothing** (`stock-reservation.md` section 7: "the
      reconciliation job reports the difference and alerts; the ledger is authoritative … The drift is a defect, not a
      correction").
- [ ] **No table, no new column, and no notification.** Routing the drift to a person is the alert machinery of #40
      and the delivery engine of #47; `module-ownership.md` section 5.7 lists no reconciliation-run table, so none is
      invented and the log plus the metric is the alert until #40 lands. Say so in the job's own documentation
      comment.
- [ ] Matrix rows for the three routes in `docs/security/permission-matrix.md` section 5, the `{itemId}`
      `identifier-editing` entries in `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`, the regenerated
      `docs/api/openapi.v1.json`, and `pnpm --dir clients/pwa generate:api` so `clients/pwa/src/api/schema.d.ts`
      carries the three operations the client children consume.

## Acceptance criteria

- [ ] An Inventory Clerk holding `inventory.view_reports` reads an item's balances for their branch over HTTP and gets
      on-hand, reserved, available, in-transit and consumed, with `available` equal to `onHand - reserved` and
      `inTransit` zero; locations of another branch are absent from the answer rather than refused.
- [ ] The same caller reads the item's ledger timeline, pages it with `nextCursor`, filters by location, by type and
      by a date window, and gets entries newest first with no `totalCount`; an unknown `filter[...]` is 400.
- [ ] The branch-wide `GET /api/v1/inventory/ledger` pages the same entries for the caller's branch, filters by item,
      location, type and date window, and never returns an entry from another branch even when another branch's
      `filter[itemId]` is supplied.
- [ ] **The cost gate:** the timeline read by a caller **without** `inventory.view_valuation` carries `costIncluded:
      false` and no `unitCost` on any entry; the same read by a caller **with** it carries the figure. Proved over
      HTTP for both callers, and a payload test asserts the property is nullable.
- [ ] **Reconciliation:** with a balance row deliberately corrupted directly in SQL, one pass of
      `StockBalanceReconciliationService` logs an error naming the item, the location and both figures, increments its
      counter, and **leaves the balance row exactly as it found it**. With no drift, a pass logs no error and changes
      nothing.
- [ ] The job takes its lease: with the lease already held, a second instance's pass does no work and says so, and a
      released lease lets the next pass run (the `DispatchExceptionExpiryService` pattern).
- [ ] `IStockBalanceQuery` answers the same figures as the HTTP read for the same item and location, and carries no
      cost field at all — asserted by a test, because the contract is what three other modules will read.
- [ ] **Negative:** a caller without `inventory.view_reports` is refused 403; an item of another organisation reads
      404; another branch's location identifier used as `filter[locationId]` returns an empty page rather than that
      branch's entries.
- [ ] All three routes declare exactly one permission and one rate-limit policy and record why they name no resource
      scope (ARCH-007, ARCH-017, ARCH-023); neither is a state change, so neither carries the audit filter and
      ARCH-008 does not apply — except that **a read of cost data is audited explicitly** (CLAUDE.md security rule 5:
      "a read is audited explicitly when the read itself is sensitive"), so the timeline read writes
      `inventory.ledger.cost_read` when, and only when, it includes cost.
- [ ] The worker job declares `[WorkerJob]` with its permissions and branch scope (ARCH-021), and nothing outside the
      worker and command-line hosts references `IWorkerScopeFactory` (ARCH-020).
