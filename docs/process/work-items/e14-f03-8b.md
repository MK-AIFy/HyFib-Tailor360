Sub-issue of #58, and the second half of child 8. Child 8 founds `tests/load/`, its `lib/` harness, the thresholds
module, the registry, the README, the `load` tier in both `scripts/dev` and `scripts/dev.ps1`, the `doctor` row, the CI
smoke job and `docs/nfr/performance-report.md`, and proves the whole chain with one scenario — the MFA challenge. This
issue adds the two scenarios that need a **route mix** rather than a single route: **S1-partial** (counter peak) and
**S7** (soak).

It is split from child 8 on size and on risk order. Founding a new test tier — a sign-in and anti-forgery helper, a
per-virtual-user client-keying scheme, a thresholds module that cites every `docs/nfr/` row, two shell scripts, a CI job
and a new document — is a session. Writing a 15-minute mixed-load scenario and an 8-hour soak over it, and interpreting
the numbers, is another.

## Acceptance criteria

- [ ] **S1-partial passes** at 20 requests per second for 15 minutes: every section 3.3 budget held for the routes it
      drives, an HTTP **5xx rate of zero**, an error rate under **0.1%**, and database connections inside the section 4
      budget — with the excluded routes of `docs/nfr/slo.md` section 5.1 measured separately rather than folded in.
- [ ] **S7 passes** at a shortened duration with **no** memory growth trend in web or worker, **no** connection leak,
      and no table growth outside section 2.6 — each read from the server-side series, not from k6's client-side
      numbers. The committed scenario is the full 8 hours and the pull request says which duration it ran.
- [ ] Every new threshold cites the `docs/nfr/` row it came from, and the registry lists S1 and S7 as implemented with
      their absent legs named.
- [ ] **Negative:** S1-partial produces **no** rate-limit rejections for authenticated staff traffic, and a run with the
      per-virtual-user keying removed **does** produce them. Without the contrast, a green run may mean nothing more
      than that the rate limiter answered quickly.
- [ ] **Negative:** a deliberately tightened threshold fails the run **and** the CI job, so the gate is proved able to
      fail. A performance gate that has never failed is not a gate.
- [ ] **Negative — the honest-failure case:** if a budget is **not** met, the pull request reports the measured figure
      against the proposed target and opens the question, rather than loosening the threshold to make the run green.
      Loosening a `docs/nfr/` number is a change to the product and belongs in that document with a reason, not in
      `thresholds.js`.
- [ ] **Exception:** the suite refuses to run against a non-development environment, honouring the rule
      `src/Tools/Tailor360.Cli/Commands/EnvironmentGuard.cs` applies to `reset` — refused by the tool, not by a
      convention.
- [ ] **Exception:** with k6 absent, `./scripts/dev test load` and `.\scripts\dev.ps1 test load` both warn by name and
      exit **0**, and `doctor` reports the tier SKIPPED with the reason — the behaviour child 8 established for the
      `e2e` tier, unchanged.

## Migration and rollback

No database change; the `migrate --dry-run` output proves it. The bootstrap creates rows through the API in a
development or load environment and is refused against Production by the environment guard. Rollback is reverting the
commit and removing the smoke step; no production behaviour changes. One caution for the release: a failing smoke step
blocks a pull request, so it is introduced with its thresholds at the **published** targets and not tightened in the
same change.
