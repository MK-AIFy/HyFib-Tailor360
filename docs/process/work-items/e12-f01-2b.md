Sub-issue of #50. The account's **locale** is stored, returned and ignored. `UserPreferences.Locale` holds `en-IN`
or `ta-IN`, `GET /api/v1/me` returns it as `AccountPreferences.locale`
(`clients/pwa/src/auth/types.ts:101-108`), and e12-f01-1 lets its holder write it — but the client never reads it:
`clients/pwa/src/i18n/IntlProvider.tsx:31-36` resolves the locale from `window.localStorage` and
`window.navigator.language` and from nothing else, so an administrator who sets a person's language on their account
changes nothing they see, and a shared counter tablet keeps whatever the last person's browser asked for. This slice
is that one connection: the account's locale reaches `AppIntlProvider` and `<html lang>` when a session resolves,
and the device default returns at sign-out.

It is split out of **e12-f01-2** on purpose. It is a different subsystem (`src/i18n/`), it carries the one real
provider-composition decision in #50's client work, and appending it to the display-preferences slice is what would
have made that session overrun.

## What is already built (do not re-build)

- `clients/pwa/src/i18n/IntlProvider.tsx` — `AppIntlProvider({ children, locale })`. It already computes
  `active = locale ?? resolveLocale(readStoredPreference() ?? window.navigator.language)`, already sets
  `document.documentElement.lang = active` in an effect (line 59), and already renders exactly one
  `IntlProvider` with `defaultLocale={DEFAULT_LOCALE}` and the catalogue from `catalogueFor(active)`. The
  `locale` prop is documented as the override "used by tests, stories and the language switcher" and **must keep
  winning**, because every test and story passes it.
- `clients/pwa/src/i18n/locales.ts` — `SUPPORTED_LOCALES` (`en-IN`, `ta-IN`), `DEFAULT_LOCALE`,
  `isSupportedLocale`, `resolveLocale(preference)` (exact match, then language subtag, then `en-IN`) and
  `LOCALE_STORAGE_KEY = 'tailor360.locale'`. No React in it, on purpose. `resolveLocale` is the only place a
  locale string is interpreted; do not add a second.
- `clients/pwa/src/i18n/pseudo.ts` — `PSEUDO_LOCALE` and `pseudoCatalogue()`. It is deliberately **not** in
  `SUPPORTED_LOCALES` and is never offered to staff; `RenderableLocale` is the union that includes it.
- `clients/pwa/src/auth/SessionProvider.tsx:58-67` — `rememberUser(next)`, the **single** choke point through
  which every `setUser` goes. Its own comment says it is written beside every `setUser` rather than synchronised
  in an effect, precisely so that a derived fact cannot go stale. That is the one line this slice hooks.
- `clients/pwa/src/i18n/messages/` — fifteen family files, each holding both languages, with `MessageCatalogue` in
  `en-IN.ts` failing the type check when a key exists in one language and not the other.
- `clients/pwa/src/auth/testing/fixtures.ts` — `stubFetch`, `jsonResponse`, `problemResponse`, `aCurrentUser`. The
  harness pattern is `clients/pwa/src/auth/RequireSession.test.tsx`: `AppIntlProvider` + `MemoryRouter` +
  `SessionProvider` over a stubbed `fetch`. `design-system/testing/renderWithProviders.tsx` supplies no session
  and no router and cannot be used here.
- `clients/pwa/src/App.test.tsx:101` already asserts `document.documentElement.lang === 'en-IN'`. Keep that
  assertion true for the anonymous case.

## What is missing

- Any read of `AccountPreferences.locale`. `rg -n "preferences.locale" clients/pwa/src` returns nothing.
- Any way for a value known inside `SessionProvider` to reach a provider **above** it.
  `SessionProvider` renders `ReauthenticationDialog`, which uses `FormattedMessage`, so it must stay inside
  `AppIntlProvider`; the locale therefore cannot be passed down by nesting.
- Any write of `LOCALE_STORAGE_KEY`. `rg -n "LOCALE_STORAGE_KEY" clients/pwa/src` returns the declaration and the
  one read, so there is no language selection of any kind today — which is correct, and stays correct: this slice
  applies a locale, it does not offer a choice.

## Scope

- [ ] `clients/pwa/src/i18n/accountLocale.ts` — a tiny subscribable module with no React import:
      `setAccountLocale(locale: string | null)`, `getAccountLocale(): SupportedLocale | null`,
      `subscribeAccountLocale(listener): () => void`. It stores the resolved locale (through `resolveLocale`) or
      `null`, notifies on change only, and **never touches `localStorage`** — a shared device must not keep one
      person's language after they leave. Unit-tested on its own, because it is the whole of the mechanism.
- [ ] `AppIntlProvider` subscribes to it with `useSyncExternalStore(subscribeAccountLocale, getAccountLocale)`
      and computes `active = locale ?? account ?? resolveLocale(readStoredPreference() ?? navigator.language)`.
      The explicit `locale` prop still wins, so every existing test and story is unaffected; the account wins over
      the device; the device is the anonymous fallback. This is the required shape — do not add a provider above
      `AppIntlProvider` and do not move `AppIntlProvider` below `SessionProvider`.
- [ ] One line in `SessionProvider.rememberUser`: `setAccountLocale(next?.preferences.locale ?? null)`. That is
      the only call site, which is why `rememberUser` is the hook point — sign-in, refresh, re-authentication and
      every sign-out path already go through it.
- [ ] Correct the now-false comment on `LOCALE_STORAGE_KEY` in `clients/pwa/src/i18n/locales.ts:15-21`, which
      says the key is "where the locale preference lives until the identity module exists". It is now the
      **anonymous** device fallback only; say that, and say that the durable home is `identity.user_preferences`
      applied at sign-in.
- [ ] Correct the matching bullet in `clients/pwa/CLAUDE.md` section 6 (line 156-157): "The locale preference
      lives there only until the identity module gives it a durable home on the user record". One line, naming
      what is true after this slice. **Do not touch the other bullets of that section** — the TanStack Query
      sentence is e12-f01-4's to correct, and two children editing the same bullet is a merge conflict for no
      gain.
- [ ] No new message id and no new screen. If the type check reveals a missing `ta-IN` key anywhere, that is a
      pre-existing defect: fix it and name it in the pull request rather than folding it into this scope silently.

## Out of scope

A **language picker**, and anything that lets a person choose Tamil for themselves. `ta-IN` becomes a selectable
interface language only when the eight criteria of the Tamil enablement gate in
`docs/nfr/accessibility-localisation.md` section 10.3 pass; `clients/pwa/src/i18n/ta-IN.ts` says in its own header
that the catalogue awaits native-speaker review, and no Tamil feature flag exists in `src/` today. Applying a locale
that is already on the account is a different act from offering the choice, and only the first is in scope.
Administering somebody else's locale is #25. Document and label rendering in Tamil is NFR-LO-05, scheduled against
#32a and #35. The four display preferences are **e12-f01-2**, which merges first.

## Acceptance criteria

- [ ] An account whose stored locale is `ta-IN` signs in, and the interface renders from the Tamil catalogue with
      `document.documentElement.lang === 'ta-IN'` — asserted on the rendered document, not on the module's state.
- [ ] The same person signs out; `lang` returns to the resolved device locale and the catalogue returns with it.
      The next person to sign in on that device gets **their** account's locale and never the previous person's.
      This is the criterion the slice exists for.
- [ ] An anonymous visitor at `/install`, `/about` or `/settings/display` renders in the device locale exactly as
      today, and `clients/pwa/src/App.test.tsx:101` still passes untouched.
- [ ] Negative: the account's locale is `fr-FR` — something no endpoint will store today, but the client must not
      assume that — `resolveLocale` answers `en-IN`, the shell renders, and nothing throws.
- [ ] Negative: the account's locale is absent, empty or `null` in the payload; the device locale is used and the
      shell renders.
- [ ] Negative: a story or test that passes `locale` explicitly is unaffected by a set account locale. Assert it
      once, because the opposite would silently break the pseudo-locale and `ta-IN` toolbar stories.
- [ ] Exception: the session resolves to `unavailable` (`GET /me` failed) — the device locale stays in force and
      the shell still renders. A failed session must not blank the interface.
- [ ] Nothing is written to `localStorage` for a signed-in person: asserted, because a shared tablet keeping the
      last person's language is the defect this slice removes.
