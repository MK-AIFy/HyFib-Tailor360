#216 records that `billingApi.listOutstandingBalances` is a client-side fan-out standing in for a server-side
aggregate, and its fourth acceptance criterion asks for a decision on it; this is that decision taken the fixing way.
The stand-in is at `clients/pwa/src/billing/billingApi.ts` lines 149 to 203: it walks every page of `GET
/api/v1/billing/invoices?status=Posted&limit=50` and then calls `GET /api/v1/billing/orders/{orderId}/balance` once per
invoice on the page, so a branch with 120 posted invoices costs 123 requests to render one table. Its own comment
already says "a true aggregate read is a reasonable follow-up", and `clients/pwa/src/i18n/messages/billing.ts` lines 113
and 430 already carry `billing.outstanding.loadMore: 'Show more'` in both catalogues, referenced from nowhere in `src/`
— the paged control was planned with the screen and never wired.

**No server route answers the question today.** Verified two ways, not by a keyword grep — `Outstanding` is all over
Billing as a *property* of `InvoiceBalance` and `DispatchEligibility`: (a)
`src/Modules/Billing/Tailor360.Modules.Billing.Api/BillingEndpoints.cs` composes twelve endpoint groups and none of
them maps a branch-wide list; (b) the `<!-- matrix:endpoints -->` block of `docs/security/permission-matrix.md` carries
no such route. `IFinancialTotalsQuery` answers **one invoice or one order**, which is exactly why the client had to
fan out.

## Scope

- [ ] `src/Modules/Billing/Tailor360.Modules.Billing.Application/Payments/OutstandingBalanceQuery.cs` — one Application
      query taking `(organisationId, branchId, cursor, limit)`, running inside `IPaymentStore.ReadConsistentlyAsync`.
      Per **source page**: `IInvoiceStore.ListAsync` for one page of `InvoiceStatus.Posted` at
      `InvoiceListQuery.MaximumLimit`, then one `AllocatedByInvoiceAsync` and one `RefundedByInvoiceAsync` over that
      page's identifiers, then `InvoiceBalance.Of` per invoice, keeping only rows whose `Outstanding` is above zero.
      Three queries per source page, whatever the size. No new formula, no caching.

      **It must fill the page, not filter one page.** The balance is not a column — `InvoiceBalance.Of` needs the
      invoice, its allocations and its refunds, so the filter can only happen after the rows are read, and a page of
      posted invoices that are all settled yields **no rows**. If the query returned that as-is, a branch with four
      pages of settled invoices and one unpaid invoice on the fifth would show the reader four empty tables with a
      *Show more* button under each, and a branch with nothing outstanding at all would never reach its empty state.
      So the query **loops source pages until it has `limit` rows or the source cursor is null**, and returns the
      source cursor it stopped at. `nextCursor` is then null only when the branch's posted invoices are exhausted,
      which is what makes the screen's empty state honest. This is strictly less total work than today: the client
      already walks every page, over HTTP, one request per invoice on top.
- [ ] A declared bound on that loop, in the same file:
      `private const int MaximumSourcePagesPerRequest = 10;` — at most 500 invoices and 30 queries scanned before the
      request hands a cursor back, with a comment naming the read-budget row it protects (`API p95, reads`,
      `docs/nfr/capacity-and-performance.md` section 3.3, line 220). This is an **engineering bound on one request's
      work, not a product number**: it changes no user-visible rule, only how much scanning one request may do before
      returning a cursor, so `CLAUDE.md` section 8's "do not invent a number" does not engage and no open decision is
      needed. At the bound the query returns the rows it has — possibly fewer than `limit`, possibly none — with a
      **non-null** cursor, which is the one case a short or empty page can still occur and is the exception case below.
- [ ] Registered in `BillingModuleServiceCollectionExtensions.cs` beside `FinancialTotalsQuery`.
- [ ] `OutstandingBalancePayload` and `OutstandingBalancePagePayload` in
      `src/Modules/Billing/Tailor360.Modules.Billing.Api/Payloads/PaymentPayloads.cs`, fields exactly as the client's
      `OutstandingBalanceRow` plus `nextCursor` — ARCH-013, a payload type declared in the `Api` project and no `Domain`
      type returned.
- [ ] `src/Modules/Billing/Tailor360.Modules.Billing.Api/Payments/OutstandingBalanceEndpoints.cs` mapping `GET
      /api/v1/billing/outstanding-balances?cursor=&limit=`, registered from `BillingEndpoints.MapBillingEndpoints`.
      `limit` clamped with `Math.Clamp(limit, 1, InvoiceListQuery.MaximumLimit)` and defaulted to
      `InvoiceListQuery.DefaultLimit` — reusing the invoice list's own bounds rather than inventing a page size.
      `.RequirePermission(BillingPermissions.CreateInvoice, BranchScope.CurrentBranch)` (ARCH-007), the `DefaultUser`
      rate-limit policy (ARCH-017) and the `Read` request timeout. No audit filter: ARCH-008 applies to state-changing
      routes, and this is a safe `GET`. No resource scope: the route takes no identifier, so ARCH-023 does not engage —
      the same position `ListInvoices` holds.
- [ ] A row in the `<!-- matrix:endpoints -->` block of `docs/security/permission-matrix.md`. The header comment of
      `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml` is explicit: until the route is in that block,
      `AuthorisationMatrixTests` fails and names it.
- [ ] `docs/api/openapi.v1.json` regenerated, and `clients/pwa/src/api/schema.d.ts` with it. Generated files; excluded

## Acceptance criteria

- [ ] A Cashier at a branch with two posted invoices — one part-paid, one settled in full — loads `/billing/outstanding`
      and sees exactly the part-paid invoice, with the same outstanding figure `GET
      /api/v1/billing/orders/{orderId}/balance` reports for it, over HTTP and the screen only, with no direct database
      access.
- [ ] Rendering that screen issues exactly **one** request to `/api/v1/billing/**` per page, asserted in the client test
      by counting the stubbed transport's calls to that prefix (the session and antiforgery reads are not counted). The
      previous behaviour — one request per invoice — fails that assertion.
- [ ] The route declares `billing.create_invoice` with `current-branch` scope and one rate-limit policy from the
      catalogue, and appears in the `<!-- matrix:endpoints -->` block; `EndpointPolicyTests`, `EndpointRateLimitTests`,
      `EndpointInventoryTests` and `AuthorisationMatrixTests` all pass unchanged in intent.
- [ ] **Negative:** a caller holding no billing permission is answered `403` with problem code `security.forbidden`, and
      a caller with no branch on the session is answered the `Required("branch")` problem — the same two refusals
      `ListInvoices` gives. An invoice of another branch never appears in any page, asserted by a second seeded branch.
- [ ] **Negative:** `limit=500` is clamped to 50 rather than honoured or refused, and `limit=0` is clamped to 1. A
      cursor this endpoint never issued is **ignored and the first page returned** — that is what
      `InvoiceStore.Decode` (line 241) already does: it catches a bad base64 or a bad pair and returns `Guid.Empty`,
      which the `Where` clause at line 127 then skips. Assert that behaviour rather than a 400 or a 500, because it is
      the behaviour `ListInvoices` already has and this route must not differ from it.
- [ ] **Exception:** a branch with more than `MaximumSourcePagesPerRequest × 50` posted invoices, none of them
      outstanding, is answered with an empty `rows` array and a **non-null** `nextCursor`; the screen keeps its *Show
      more* control rather than showing the empty state, because "none found so far" is not "nothing outstanding". The
      empty state is shown only when `rows` is empty **and** `nextCursor` is null. Asserted at the integration tier by
      seeding past the bound, and at the client tier by stubbing that answer directly.
- [ ] Reads stay inside the published read budget — `docs/nfr/capacity-and-performance.md` section 3.3, row **API p95,
      reads** — measured at the load that row states. No new number is introduced here.
