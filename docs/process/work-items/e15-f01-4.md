Sub-issue of #59. #59's acceptance criterion "Production cannot deploy an unapproved or different artifact" has no
mechanism today. `docs/process/branch-protection.md` section 8 states the position in terms: "**no Environment
exists, no deployment secret exists, and no workflow requests `id-token`**", and names what must change — "Every
Environment that can reach a real system has **required reviewers**; `production` additionally has a wait timer and a
deployment-branch rule limiting it to tags | Environment settings, **applied with the release workflow of #59**".
`docs/process/release-gates.md` **RG-14** is the same requirement from the other end: it checks "That the GitHub
Release for the tag carries the complete evidence set, **and that the deployment workflow refuses to run without
it**" — and it is S1 with no waiver. `docs/process/release-evidence.md` is the sixteen-row form, written for a human
to fill in, with no machine reading it. Section 3 of that form is where the promoted digests go and it is blank.
This slice makes the approval real: one promote workflow, two Environments, a machine-checked release record, and
protection on the branches and tags a release may come from.

- `docs/process/branch-protection.md` — sections 3 (the twelve required check names and the two deliberate

  repository settings), 8 (Environments and workflow tokens), 9 (how the settings are verified, with the exact

  **`main` is already fully specified.** This issue adds `release/*` and the tag rule, and changes nothing about
  `main` except where a new required check is named.
- `docs/process/waivers.md` — sections 1 to 3, including the never-waivable list and the statement that RG-14 "reads
  this register and fails the release when any waiver applying to it has passed its expiry date". The checker
  implements that read. **Read section 4 carefully before writing the parser, because the document contains two
  tables a reader could mistake for each other:**
  - **section 4.2's register** is the one the checker reads. Its columns are fixed by section 4.1 (`ID`, `Gate`,
    `Scope`, `Reason`, `Risk`, `Risk owner`, `Approved by`, `Granted`, `Expires`, `Review date`,
    `Corrective issue`, `Status`), identifiers are `WV-nnn`, dates are `YYYY-MM-DD`, and **today it holds exactly one
    row, `_(none)_`**. So the parser's normal case is "no waivers", and that must pass.
  - immediately below it, **"Known gaps that will need a row here at the first release"** is a *different* table with
    *different* columns (`Gap`, `Recorded as`, `Owner`, `Corrective issue`, `Gate it would be waived against`), four
    populated rows, no identifier and **no expiry date at all**. The document says in terms that "these are not
    waivers yet". A parser that walks every Markdown table under section 4 will read those four rows as waivers with
    a missing expiry and **fail every release from the day it is merged**. Anchor on the section 4.2 register's
    heading and on its column set, and make "the known-gaps table is not read" an explicit assertion in the
    self-test.
  - section 4.3 is labelled "Worked example — illustrative only" and is a third table. It is not read either.
- `.github/workflows/pr-policy.yml` — already resolves a linked issue number against the API and fails on a closed
  issue, a non-existent issue or a pull-request number. Its parsing approach is the model for reading a release body.
- `scripts/sarif-gate.py`, `scripts/openapi-diff.py`, `scripts/check-docs-links.py`, `scripts/coverage-floor.py` —
  the house style for a gate script: a `--self-test`, a `--label`, a job summary, one clear failure line. Follow it.
- `.github/CODEOWNERS` — exists. `docs/process/branch-protection.md` section 5.2 records that the rule on `/.github/`

- **E15-F01-3**'s `scripts/verify-artefact.py` — the signature and provenance verifier. The promote workflow calls

## Acceptance criteria

- [ ] A tag whose GitHub Release carries all sixteen items promotes: the checker passes, the verifier passes for all
      three digests, and the promotion record names the tag, the three digests, the commit and the target
      environment.
- [ ] **Positive, and it is the one the repository is in today:** a release record whose waiver list is empty passes,
      because the section 4.2 register holds no row. The checker does not require a waiver to exist, and it does not
      read the four "known gaps" rows below the register as waivers.
- [ ] **How the workflow half is proved before merge.** A `push:` tag event runs the workflow at the tagged commit, so
      a throwaway tag at this branch's head exercises the checker, the verifier and the promote job for real. The
      successful case needs a **GitHub Release** on that tag carrying a synthetic but complete sixteen-item record;
      creating it is a repository write. If this session can create it, it does and pastes it; if it cannot, it runs
      `scripts/release-record.py` against a **local fixture** of the same body, says that is what it did, and the live
      run becomes an Owner action. Either way the pull request distinguishes the two — a fixture run described as a
      workflow run is the failure this criterion exists to prevent.
- [ ] **Negative:** a tag whose Release omits item 11 (the migration dry-run output, the rollback note and the
      recorded recovery target) fails before the promote job reaches the Environment, and the failure message names
      item 11 by its number and its title. Nothing is promoted.
- [ ] **Negative:** a tag whose Release carries item 9 as the bare word "yes" fails, with a message distinguishing
      "missing" from "present but not evidence" — the distinction `docs/process/release-evidence.md` section 2 rule 2
      exists to draw.
- [ ] **Negative:** a release carrying a waiver whose expiry date has passed fails RG-14 through the checker, naming
      the waiver and its expiry. A waiver with a future expiry passes and is listed in the job summary, which is
      checklist item 13.
- [ ] **Negative:** a digest that is not in the digest manifest for this tag — a digest from a different tag, or a
      locally built one pushed to the same repository — is refused by the verifier, and the promote job stops. This
      is the criterion "production cannot deploy a **different** artifact".
- [ ] **Negative:** a `workflow_dispatch` promote aimed at `production` from a branch rather than a tag is refused by
      the Environment's deployment-branch rule, and the refusal is visible in the run rather than only in a setting.
- [ ] **Exception:** a release that touches neither the financial surface nor go-live passes with items 15 and 16
      marked `n/a` plus a one-line reason, and **fails** when they are simply absent. Deleting a row and marking it
      `n/a` must not be the same outcome.
- [ ] **Exception:** during the single-maintainer period the same person may approve their own promotion **only**
      when the promotion record carries the written self-confirmation and what was re-checked, per
      `docs/process/branch-protection.md` section 5.1. The checker requires that text to be present, so the exception
      leaves a trace rather than being silent.
- [ ] `gh api repos/MK-AIFy/HyFib-Tailor360/environments/production` read-back shows required reviewers, the wait
      timer and the tag-only deployment rule; the pull request records a `404` honestly, with section 6's reading of
      what a `404` means, if the account's plan cannot enforce it.
