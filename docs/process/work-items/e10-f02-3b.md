Sub-issue of #45. E10-F02-3a fills two workload projections and publishes no route, so nothing can read them. This
slice is the read surface, and it carries the one genuinely cross-cutting security decision in #45: **who may see a
figure about a named member of staff**. It is split from the projection because together they measure over 1,400
production lines at this repository's rates, and because this half can be reviewed as a security change on its own.

There is a contradiction in the merged code that this slice has to settle, and it is the reason the permission work
lives here rather than being waved at:
`src/Platform/Tailor360.Platform.Security/FieldVisibility/OrdersResponseViews.cs` lines 119 to 123 already declare
`assigneeThroughput` with `FieldClassification.StaffPerformance` gated on **`ReportingPermissions.Read`** — a key
five roles hold, including `admin` and `auditor` — while its own comment cites DC-11, whose proposed position is
"No — visible to Tailor Master, Branch Manager and Owner **only**". Both cannot be true. This slice makes them
agree.

## Scope

- [ ] **`reports.read_workload`**, a new permission, declared in `ReportingPermissions.cs` beside `Read` and
      `Export`: branch scope, no MFA, no step-up, no reason. It exists because `reports.read` reaches five roles
      while 5.15 and DC-11's proposed position restrict a figure about a named person to three, and a role list is
      not an enforcement mechanism. The precedent is `customers.read_contact`, which the matrix records as "split
      from `customers.read` because contact data is classified separately".
- [ ] **Granted to `owner`, `branch_manager` and `tailor_master` in `SystemRoles.cs`** — the three roles 5.15 names
      — and added as one row to the `<!-- matrix:permissions -->` block with that reason in its own words.
      Deliberately **not** granted to `admin` or `auditor`; the negative test below is what makes that real.
- [ ] **Re-gate the existing field.** Change `OrdersResponseViews`' `assigneeThroughput` from
      `ReportingPermissions.Read` to the new key, so the catalogue gives one answer rather than two. It is safe and
      it is verified safe: `orders.work_queue` is not in `ResponseViewPayloadTests.ServedViews`, so no payload and no
      endpoint is held to it yet. Regenerate the `matrix:fields` and `matrix:role-fields` blocks of
      `docs/security/field-visibility.md`, whose per-role derivation changes for that field. Say in the pull request
      that this is a correction of a contradiction and not a widening.
- [ ] **`ReportingResponseViews.cs`** in `src/Platform/Tailor360.Platform.Security/FieldVisibility/`, declaring
      `reporting.workload` on **`ViewSurface.Workshop`** — the only existing surface whose forbidden set permits
      `StaffPerformance` while still withholding `Pricing`, `PaymentState`, `CustomerContact` and `CustomerNotes`.
      The view requires `ReportingPermissions.Read`; the open-work fields (`assigneeUserId`, `displayName`,
      `isActive`, `openPhases`, `oldestQueueAgeHours`, the phase and category breakdown) are `Operational` except
      `displayName`, which is `CustomerIdentity`-like staff identity and is declared `StaffPerformance` only if it

      caller who may see the row may see whose row it is. The **throughput** fields (`phasesCompleted`,
      `phasesCompletedOnTime`, `onTimeRate`) are `FieldClassification.StaffPerformance` gated on

      of `docs/security/field-visibility.md`. **Adding a third `ViewSurface` is out of scope**:
      `SurfaceRules.ForbiddenOn` throws for an unknown surface on purpose, and a new surface is a new decision about
      what may never appear on it — a decision this issue has no source for.
- [ ] **`GET /api/v1/reporting/workload`** — one row per assignee in the requested branches: open phases grouped by
      phase code and category, the oldest queue age among them, the completed and on-time counts over the requested

## Acceptance criteria

- [ ] A Tailor Master holding `reports.read` and `reports.read_workload` reads `GET /api/v1/reporting/workload` over
      HTTP for their branch and receives one row per assignee with open phases, oldest queue age and the period's
      completions, plus the unassigned row, with every display name resolved through `IUserDirectory` and no name
      read from a projection column.
- [ ] **Negative — the permission split bites:** a caller holding `reports.read` but **not** `reports.read_workload`
      receives the open-work columns and **no throughput column at all** — absent from the payload, withheld by the
      view rather than blanked by the handler — and an `auditor`, who holds `reports.read` and is not granted the new
      key, is exactly such a caller. An `admin` is the second.
- [ ] **Negative — the contradiction is gone:** a test asserts that `orders.work_queue`'s `assigneeThroughput` now
      requires `reports.read_workload`, so the two declarations of "who may see staff throughput" agree; the
      regenerated `matrix:role-fields` block shows `admin` and `auditor` losing it.
- [ ] **Negative — another branch:** an assignee who works only in branch B does not appear for a caller assigned
      only to branch A, and filtering for branch B returns no row rather than an error; the response states which
      branches it covered, so a narrowed answer is never mistaken for the whole shop.
- [ ] **Negative — no permission at all:** a Tailor is answered `403` `security.forbidden`
      (`AuthorisationProblemResultHandler.ForbiddenCode`).
- [ ] **Negative — no ranking:** a test asserts there is no sort or order parameter whose value is a throughput
      field, and that the default order is by open work.
- [ ] **Negative — a malformed filter:** an unknown phase code, a reversed date range or a limit above the cap is
      answered with RFC 9457 problem details naming the field, never a stack trace; the limit is clamped as
      `ListInvoices` clamps it and the response states the limit it applied.
- [ ] **Exception — a deactivated member of staff:** somebody who has left still carries completed work in a past
      period and is still attributable; their row is returned with the inactive flag from `IUserDirectory`, and
      their identifier is never replaced by a name the directory no longer has — nor is the row dropped, which would
      silently change a historical total.
- [ ] **Exception — an empty branch:** a branch with nobody assigned returns the unassigned row and zeroed counts
      with the `asOf` instant, not a 404.
- [ ] **Rule-level:** both routes declare a permission (ARCH-007), exactly one rate-limit policy (ARCH-017) and the
      audit filter; the audit entry names the action, the actor and the branches read and carries **no figure and no
      assignee name or identifier**. The contract tier proves the first three.
