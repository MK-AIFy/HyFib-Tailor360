Sub-issue of #35. Follows E07-F01-5, which creates `platform.print_jobs`, the durable `IPrintQueue` and the
`IPrintStationQueue` port. **This issue is the authorised surface over that port: the four routes a branch print
station drains through, the permission they demand, the resource scope that proves a job belongs to the caller's
branch, and the one content-security-policy directive that makes a browser-dialog print possible at all.** Without
it the queue fills and nothing can read it, and the screens of E07-F01-6 and E07-F01-7 have no server to talk to.

The two halves are separate pull requests because a new Platform table, a new permission, four routes, the
permission-matrix rows, the `matrix.yaml` dimensions, a policy widening and a regenerated OpenAPI document in one
branch is past the 1,500-line target of CLAUDE.md section 6 and past what one review can hold. The seam is the HTTP
boundary: E07-F01-5 ends at a port, this issue starts at a route.

## What is missing

- **A way to read the queue over HTTP.** Nothing exposes `IPrintStationQueue`, so a station screen has nothing to
  call and #55's bridge has no surface either.
- **Somewhere for the artefact to be fetched from.** Billing streams a receipt through
  `GET /api/v1/billing/receipts/{receiptId}/document` under `billing.print_receipt`; a station draining labels,
  receipts, invoices and measurement sheets cannot hold one permission per kind.
- **A content-security policy that allows a same-origin print frame.** `frame-src 'none'` makes a browser-dialog
  print impossible today.

## Scope

- [ ] **Four routes, in `src/Hosts/Tailor360.Web/Endpoints/PrintStationEndpoints.cs`** with payload types under
      `src/Hosts/Tailor360.Web/PrintStation/`, mapped from `Program.cs` beside `MapCustomerTimelineEndpoint()`
      (line 177), tagged `Printing` with a description added to `ApiDocumentTransformer.TagDescriptions`:
  - `GET /api/v1/print-station/jobs` — `RateLimitPolicyNames.DefaultUser`, `RequestTimeoutPolicies.Read`; `queued`
    first, paged by a `limit` whose default and cap are typed options with `ValidateOnStart`, never literals.
  - `GET /api/v1/print-station/jobs/{jobId:guid}/document` — `DefaultUser`, `Read`; streams
    `IObjectStorage.OpenReadAsync(payload_reference)` with `Cache-Control: no-store`, never a URL and never the key
    (CLAUDE.md section 4 item 9), and audits the access as `platform.print_job.fetched`.
  - `POST /api/v1/print-station/jobs/{jobId:guid}/printed` — `RateLimitPolicyNames.Write`,
    `RequestTimeoutPolicies.Command`, `.RequireIdempotency()`, `.Audited(...)`.
  - `POST /api/v1/print-station/jobs/{jobId:guid}/failed` — the same four, with the reason required and validated
    server-side before the port is reached.

- [ ] **The branch decision is taken in the handler, and the body must not pretend the declaration takes it.**
      `.RequirePermission(key, BranchScope.CurrentBranch)` establishes that the caller is working in a branch; the
      **list** route then passes `caller.Context.BranchId` into `ListQueuedAsync`, exactly as the timeline route
      passes `caller.AssignedBranches` into its composer. `docs/security/permission-matrix.md` section 7 is explicit
      that there is no scoped-query port behind a collection — "a list, a search, an export, a bulk command … reaches
      its handler with no branch decision taken at all" — so the filter is the handler's own work and the
      cross-branch test below is what proves it. A null `Context.BranchId` is refused, not widened.
- [ ] **`print.station`, one new permission.** Branch scope, no second factor, no step-up, no reason. Declared in
      `PlatformPermissions` with `PermissionModules.Platform`, granted in `SystemRoles.cs`, given one section 4 row
      and four section 5 rows in `docs/security/permission-matrix.md`. **The spelling is not invented: it is the one
      already published** in `docs/nfr/support-matrix.md` section 3 line 92, which describes the print station's
      operator as "any role with `print.station` in the branch". Two things make that legal rather than a new
      convention: `PermissionModules`' own documentation says "a permission's module is the module that owns the
      action, which is not always the module whose name the key starts with … `admin.` is a vocabulary rather than an
      owner", and `payments.session` is the precedent for a key that names a thing rather than a verb. **Do not
      spell it `platform.print_station`**: no key in the catalogue uses a `platform.` prefix — every Platform-owned
      key today is `admin.*` or `audit.export` — and inventing a sixteenth vocabulary to fit a convention that does
      not exist is the kind of change a reviewer is right to stop.
- [ ] **Grants, and why these three.** `branch_manager`, `reception`, `cashier` — exactly the union of the roles
      that hold `custody.print_label` (matrix line 174) and `billing.print_receipt` (matrix line 147) today, so the
      station opens to the people who already queue work into it and **nobody gains reach they did not already
      have**. Assertion 7 of `docs/security/permission-matrix.md` section 8 means the key **cannot** be declared and
      left ungranted pending the owner: "every permission is granted to at least one role" is a unit test, so a
      pull request that declares the key and defers the grant fails the unit tier. Assertion 6 compares the
      `Granted to` column with what `init-reference-data` writes, so the document and `SystemRoles.cs` move in the
      same commit. See **Open decisions in force** for what a reviewer is being asked to settle.
- [ ] **`PlatformResourceKinds`** in `src/Platform/Tailor360.Platform.Security/Authorisation/` — new, holding
      `PrintJob = "platform.print_job"`, in the same `"<module>.<thing>"` shape as `BillingResourceKinds`. It goes
      in `Platform.Security` because both the host and the resolver already reference that project, and
      `IResourceScopeResolver` lives there.
- [ ] **`PrintJobScopeResolver`** in `src/Platform/Tailor360.Platform.Persistence/Printing/`, reading
      `PlatformDbContext` for the job's `branch_id`, registered by `PlatformServiceCollectionExtensions` as
      `AddScoped<IResourceScopeResolver, PrintJobScopeResolver>()`. The three routes taking `{jobId}` declare
      `.ScopedToResource(PlatformResourceKinds.PrintJob, "jobId")` and so satisfy ARCH-023 by resolving, not by
      claiming they touch nothing branch-owned. A foreign job and a job that does not exist must answer alike —
      `404 security.resource-not-found`, the answer `matrix.yaml` already defines as `out-of-reach`.
- [ ] **Three rows in the `identifier-editing` block of
      `tests/Tailor360.IntegrationTests/Authorization/matrix.yaml`**, one per `{jobId}` route, each with the
      `because` the file asks for: a print job identifier is a UUIDv7 a caller could type instead of follow, and a
      distinguishable answer would let one branch's station enumerate another's queue. The file's own header makes

- [ ] **`frame-src 'self'`** in `SecurityHeadersMiddleware.StaticDirectives`, with the `ContentSecurityPolicyTests`

      directions, not by inspection.
- [ ] **Negative:** a caller without `print.station` is refused with an RFC 9457 problem and the refusal is audited;

- [ ] **Exception:** two stations resolving the same job race and exactly one wins — the loser receives

**DOR-05:** the threat model for this flow, `docs/security/threat-models/barcode-custody.md`, is the #56a backlog
row in `docs/security/README.md` line 74 and is not written yet. The abuse cases this slice must answer are **label
forgery** (a caller fetching another branch's artefact — answered by the permission, the branch filter and the
resource resolver) and **barcode enumeration** (the document route takes a job identifier, never a payload, and
answers alike for another branch's job and a job that does not exist). The authorisation threat model itself is
#32a's, per `docs/security/permission-matrix.md` section 7.
