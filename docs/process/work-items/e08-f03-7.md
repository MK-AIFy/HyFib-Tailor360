## Scope

- [ ] **`ValuationMethod`** — `WeightedAverage` (the default) and `Fifo`, as a domain enumeration, with the method
      **recorded on every run** (INV-STK-08). The method in force is configuration, not a request parameter a caller
      can vary per run; a run may be asked for explicitly in the other method for comparison, and then records that
      it was.
- [ ] **The valuation engine**, pure, in `…Inventory.Domain/Valuation/` — over the ledger entries up to the cut-off
      and the **immutable source costs** on the purchase receipt lines they came from (#39): weighted average as a
      running cost per `(item, location)`; FIFO as a consumption of cost layers in receipt order. Both follow
      `conventions.md` section 1.2 exactly: four decimal places throughout, one rounding step half away from zero to
      paise at the end, sums never re-rounded. **Customer-supplied material is excluded by construction**
      (INV-STK-07), not by a filter somebody can forget.
- [ ] **`valuation_runs` and `valuation_lines`** — the run records method, configuration version, cut-off instant,
      branch, actor, totals and the instant it completed; the lines record quantity, unit cost and value per
      `(item, location)`. Both **append-only by database trigger** (G-4, INV-STK-08), reusing the shape of
      `billing.financial_records_are_append_only()`.
- [ ] **One migration**, `InventoryValuationRuns`, creating exactly those two tables and their trigger. Expand-only;
      ledger row added to `docs/dev/migrations.md`.
- [ ] **`Inventory.Contracts.IValuationQuery`** — value per `(item, location)` at a cut-off, answering from the
      nearest completed run at or before that cut-off and saying which run answered, so a caller can never receive a
      figure whose provenance it cannot name. This is the contract #46 consumes; it returns Contracts types only and
      no `Domain` type (ARCH-013), and it is the **only** way another module may learn a valuation
      (`module-ownership.md` section 5.7: "Reporting valuation figures come from `IValuationQuery` and Inventory
      events, never from a join on `inventory.ledger_entries`").
- [ ] **Four endpoints**, all `RequirePermission(InventoryPermissions.ViewValuation, BranchScope.CurrentBranch)`:
      `POST /api/v1/inventory/valuation/runs` (run at a cut-off; `RateLimitPolicyNames.ExportHeavy` because a run is
      expensive per call; `.Audited("inventory.valuation_run.completed")`; `.RequireIdempotency()`),
      `GET /api/v1/inventory/valuation/runs` (list, `DefaultUser`),
      `GET /api/v1/inventory/valuation/runs/{runId}` (the run with its lines, `DefaultUser`,
      `.ScopedToResource(InventoryResourceKinds.ValuationRun, "runId")` per ARCH-023), and
      `GET /api/v1/inventory/valuation/runs/{runId}/export` (`ExportHeavy`,
      `.Audited("inventory.valuation_run.exported", reasonRequired: true)` per `data-classification.md` section 10,
      the same resource scope) — **and the export route alone declares
      `RequirePermission(ReportingPermissions.Export, BranchScope.CurrentBranch)` rather than `view_valuation`**,
      because `docs/nfr/data-classification.md` section 5.9's "In exports" row names that key verbatim for "Stock,
      **valuation** and profitability exports". `reports.export` is flagged `RequiresMfa` and `RequiresReason` and is
      granted to `owner`, `branch_manager` and `auditor` (matrix line 245), so a download of cost figures demands a
      second factor and a reason, which is what the classification document intends for this class of file. Reuse the
      decision and the wording `E08-F03-6` recorded; do **not** re-argue it. Every route declares exactly one request
      timeout (`RequestTimeoutPolicies.Read` for the two reads, `.Export` for the export, `.Report` for the run
      command). None declares `.RequireStepUp()` — neither `inventory.view_valuation` nor `reports.export` is flagged
      `RequiresStepUp`, and `AuthorisationMatrix.Reconcile` fails an endpoint that declares step-up for an unflagged
      key (`DetectsStepUpDeclaredForAPermissionThatIsNotFlaggedForIt`, ARCH-018).
      **Say in the pull request** why running a valuation sits on `view_valuation`: the catalogue has no
      `inventory.run_valuation` key, the run exists only to produce the read, and matrix line 212 already attributes
      `view_valuation` to #40. If the reviewer disagrees, adding a key is a matrix change, not a code workaround.
- [ ] **`docs/inventory/valuation.md`** — the document the accountant signs: the two methods with a worked example
      each; the treatment of **supplier returns, wastage, approved stocktake adjustments and transfers** (the cases
      #40 asks to document explicitly); the rounding rule, quoted from `conventions.md` section 1.2 rather than
      restated; the exclusion of customer material; and what a figure means at a cut-off when a receipt is recorded
      late. **Link it from `docs/architecture/module-ownership.md` section 5.7's Inventory record**, whose
      `valuation_runs` / `valuation_lines` row already reads "Immutable valuation at a cut-off using the configured
      method" and is the one place a reader will look — that document's own section 9 governs how it is edited, so
      follow it and say in the pull request that you did. `./scripts/dev docs` checks that every relative link
      **resolves**, not that every file is reachable, so a document nothing links to passes the check and is still
      lost; add the link deliberately.
- [ ] **Golden fixtures** at `tests/fixtures/inventory/valuation/*.json`, one file per scenario, covering exactly the
      cases the blueprint names: differing purchase costs, supplier returns, wastage, adjustments, transfers and

## Acceptance criteria

- [ ] A run at a cut-off over the committed golden fixtures reproduces the expected value per `(item, location)` and
      the expected total to the paise, for **weighted average and FIFO**, including the differing-cost, return,
      wastage, adjustment, transfer and rounding scenarios — the golden-master comparison is the test, not a
      tolerance. **Note what this criterion is and is not.** #40's fifth acceptance criterion reads "Valuation
      methodology and rounding pass **accountant-approved** scenarios", and an approval is a human signature, not
      something a coding session can produce. This child's criterion is the golden-master comparison against
      fixtures **it authored from its own document**, marked in the file as pending sign-off; #40's AC5 itself closes
      in **`E08-F03-13`**, the evidence child that carries the accountant's review. Say so in the pull request, so
      nobody ticks AC5 on the strength of a green test.
- [ ] Re-running the same cut-off produces a **new immutable run** whose figures match the first; neither run is
      edited, and `IValuationQuery` at that cut-off names which run answered it.
- [ ] Customer-supplied material recorded through `customer_material_custody` (#198) contributes **zero** to every
      figure, asserted by a test that values a branch holding customer cloth (INV-STK-07).
- [ ] **Negative:** a caller holding `inventory.view_reports` but **not** `inventory.view_valuation` gets
      `matrix.yaml`'s `not-permitted` answer — `403` with `security.forbidden` — on all four routes: the separation
      the matrix's own note for line 212 gives as the reason the key exists.
- [ ] **Negative:** a caller holding `inventory.view_valuation` but **not** `reports.export` can run and read a
      valuation and is refused the **export**; a caller holding `reports.export` whose second factor is not satisfied
      is answered `second-factor` (`403`, `security.second-factor-required`), which is a different answer from
      `not-permitted` and has its own row in `matrix.yaml`.
- [ ] **Negative:** a caller at another branch pasting a `{runId}` is answered `404`; an `UPDATE` or `DELETE` against
      `valuation_runs` or `valuation_lines` is refused by the database trigger even for the application role.
- [ ] **Negative:** a cut-off in the future is refused with a field-level problem detail; a replayed
      `Idempotency-Key` returns the first run rather than computing a second.
- [ ] **Exception:** a receipt recorded **after** a run for a cut-off before it does not alter that run; the next run
      at the same cut-off shows the new figure and the two runs stand side by side, which is what makes a valuation
      auditable rather than a moving number. `docs/inventory/valuation.md` says this in words and a test asserts it.
- [ ] No log line, metric or trace carries a unit cost or a valuation (`data-classification.md` section 5.9),
      asserted by a redaction test over the new code paths.
