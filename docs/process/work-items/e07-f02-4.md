Sub-issue of #36. Follows E07-F02-3 and **E07-F02-3b**, which together build `/scan` in **single** mode — one
decode, one resolve, one confirmation card or one undo window, one action. **This issue adds continuous mode**: the
viewfinder stays open, every decode is validated through the resolve endpoint and appended to a running list with a
per-item status, items can be removed before anything is sent, and one **Commit N** action submits N commands
sequentially, each with its own client event UUID and `Idempotency-Key`.

The split exists because the two modes are two different state machines over the same viewfinder, and plan Section 8
for #36 defines them separately — single for sensitive transitions, continuous for "everything else: receive, phase
start and complete, transfer accept, stocktake count and material issue" (the #36 blueprint's **Scan modes**
paragraph). Putting both in one pull request puts the
list, the batch driver and the per-item idempotency underneath a route that is already most of a session
(`clients/pwa/src/routes/catalog/CatalogVersionEditorRoute.tsx` is 978 production lines for one route, as this
repository's calibration note records). The gap is checkable: after E07-F02-3b merges,
`clients/pwa/src/scanning/scanModes.ts` declares `ScanMode = 'single' | 'continuous'` and only `single` is
implemented; nothing in `clients/pwa/src/` holds a list of pending scans, and `grep -rn "Commit" clients/pwa/src/`
finds nothing of the kind.

## Scope

Target: about 700 production lines plus tests. No new route: this extends `ScanRoute.tsx` and adds modules beside
it.

- [ ] **`clients/pwa/src/scanning/scanBatch.ts`** — the reducer over the running list. An item is
      `{ key, result, status, resolved?, problem?, clientEventId?, idempotencyKey? }` with
      `status: 'resolving' | 'ready' | 'rejected' | 'duplicate' | 'submitting' | 'submitted' | 'failed'`. Pure,
      exhaustively tested, no React.
- [ ] **Duplicate detection within the list** — a payload already present is appended as `duplicate` rather than
      silently dropped, because the operator is holding a garment and needs to be told it is already on the list;
      a `duplicate` item is **never** submitted and is excluded from the commit count.
- [ ] **`clients/pwa/src/scanning/useScanBatch.ts`** — the hook that wires the reducer to `resolveBarcode()`:
      each decode appends a `resolving` item, the resolve moves it to `ready` or `rejected` with the problem code,
      and the viewfinder **stays open** throughout. Concurrent resolves are tracked per item, and an `AbortSignal`
      cancels them on unmount.
- [ ] **Removal before commit** — a named per-row control, keyboard reachable and ≥ 48 × 48 px, that drops an item
      while nothing has been sent. After a commit starts, `submitted` items cannot be removed, because an append-only
      `scan_events` row cannot be un-appended; the row says so rather than disabling the control without a reason.
- [ ] **`clients/pwa/src/scanning/commitScanBatch.ts`** — the sequential driver over E07-F02-3b's
      `ScanCommandSubmitter`. Each `ready` item gets its **own** `clientEventId` and `Idempotency-Key`, minted with
      `crypto.randomUUID()` **when the person presses Commit** and **held across retries of that item**, never
      re-minted. Items are submitted **one at a time, in list order**, never in parallel: the `scan-burst` policy is
      sized from the scenario S3 shape of `docs/nfr/capacity-and-performance.md`, and a fan-out of N parallel
      requests from one device is not what it was sized for.
- [ ] **Mid-batch failure behaviour, stated in the code's doc comment rather than inferred**: the driver
      **continues** through the remaining items and reports a per-item outcome; it never rolls anything back. Two
      documented facts force this — `scan_events` and `custody_transfers` are append-only with a database trigger
      (the #37 blueprint, `barcode-handoff.md` section 4), and a batch abandoned half-way would leave the operator
      not knowing which garments moved. A `failed` item keeps its key so **Retry** is a replay, which the server
      answers with the original outcome.
- [ ] **One exception to "continue": a rate-limit refusal stops the batch.** A `429` from the `scan-burst` policy
      means the budget the policy protects is already spent, so the driver **halts**, marks the remaining items
      still `ready` rather than `failed`, says how many were sent and how many were not, and offers the operator the
      choice to continue. It does **not** retry automatically and it does **not** keep submitting into a refusal.
      The same rule applies to a `401` or `403`: stop, because every remaining item would be refused identically.
- [ ] **In-memory retry only, with a visible pending state.** Plan Section 6.2 **dependency note 8** is explicit:
      "#37 retries scan submissions in memory; #51 is the only implementation of encrypted local drafts and the
      persisted offline scan queue." Nothing in this issue writes to `localStorage`, `IndexedDB` or a service
      worker. A commit attempted while offline shows `OfflineBlockedAction` — "needs connection, this will not be
      queued" — and the list survives only as long as the screen does, which the copy says plainly.
- [ ] **The mode switch** on `ScanRoute.tsx` — a named control, with the default mode chosen from E07-F02-3b's
      `CONFIRM_BEFORE_COMMIT`: an action in that set opens in **single** mode, everything else in **continuous**.
      The continuous set — receive, phase start, phase complete, transfer accept, stocktake count, material issue —
      is **already** the derived complement in `scanModes.ts`; import it, and do not restate it here as a second
      list that can drift from the first.
- [ ] **Counts announced**: the list's own count when it loads and when it changes (**A11Y-LF-01**), and the
      pending or failed count outside the list when it changes (**A11Y-46**), once per change and not on every
      re-render (**A11Y-43**).
- [ ] **Messages** added to `clients/pwa/src/i18n/messages/scanning.ts` in both `scanningEn` and `scanningTa`,
      including a plural-aware `Commit {count}` and one string per item status.
- [ ] **Stories** added to `clients/pwa/src/routes/scanning/scanningScreens.stories.tsx` through
      `withAdminApi` / `StoryRoutes` / `storyJson` / `storyProblem` / `storyPending` from
      `clients/pwa/src/admin/testing/storyTransport.tsx`: an empty list, a mixed list (ready, rejected, duplicate),
      a commit in progress, and a partly failed batch. **No offline story**, per the reason recorded in
      `clients/pwa/src/routes/catalog/catalogScreens.stories.tsx`.

## Acceptance criteria

- [ ] A Tailor in continuous mode scans ten synthetic payloads without the viewfinder closing; the list shows ten
      rows with per-item status; **Commit 10** submits ten commands **sequentially** and reports ten outcomes —
      asserted against a fake submitter that records call order and concurrency.
- [ ] Each submitted item carries a **distinct** `clientEventId` and a **distinct** `Idempotency-Key`, and a retry
      of one item reuses **that item's** key rather than minting a new one.
- [ ] **Negative:** the same payload scanned twice outside the debounce window appears once as `ready` and once as
      `duplicate`; the duplicate is excluded from the commit count and is never submitted. Inside the window it
      appears once, because E07-F02-1's debounce already collapsed it.
- [ ] **Negative:** an `S-`, `I-` or `R-` payload is appended as `rejected` with `barcode.wrong-namespace`, stays
      visible in the list so the operator can see which label was wrong, and is never submitted.
- [ ] **Negative:** pressing Commit while offline submits nothing and shows `OfflineBlockedAction`; no entry is
      written to `localStorage` or `IndexedDB` — asserted by a test that fails if either is touched.
- [ ] **Exception:** when item 4 of 10 fails, items 5 to 10 are still attempted, item 4 is `failed` with its problem
      rendered through `problemDetails.ts`, and **Retry** on item 4 replays the same key. Nothing is rolled back and
      no `submitted` item changes state.
- [ ] **Exception:** while the real submitter is absent — #37 has not merged — Commit shows the named unavailable
      state once for the batch, records `fallback.used`, and leaves every item `ready` rather than `failed`.
- [ ] **Exception:** a `429` on item 3 of 10 halts the batch: items 1 and 2 stay `submitted`, items 3 to 10 stay
      `ready`, the screen says "2 of 10 sent" and names why, and no further request is made without the operator
      asking. A `403` behaves the same way.
- [ ] An item already `submitted` cannot be removed, and the row says why.
- [ ] The list count is announced on load and on change (**A11Y-LF-01**); the failed count is announced when it
      changes (**A11Y-46**); neither repeats on re-render (**A11Y-43**).
- [ ] No axe violation in any state; no horizontal overflow at `expectNoHorizontalOverflow`'s default widths and
      zoom levels, including a ten-row list at 320 px.
