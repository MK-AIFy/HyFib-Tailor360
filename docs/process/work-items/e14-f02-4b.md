## Scope

- [ ] **`PrivacyLifecycleService`** in `src/Hosts/Tailor360.Worker/Jobs/PrivacyLifecycleService.cs`, declared
      `[WorkerJob("platform.privacy_lifecycle", WorkerBranchScope.Organisation)]`, leased under that same name, run at
      start-up and then on a `PeriodicTimer`. **The interval and the lease duration are bound, validated configuration
      values with defaults, never literals in the loop** — follow whatever `AuditPartitionMaintenanceService` and
      `CustomerExportPurgeService` do for their own options class, and put the defaults in that class with a doc
      comment citing this issue, not in `appsettings`.
- [ ] **One loop, two subject selectors.** The execution pass selects `data_subject_requests` in status `Approved`.
      The sweep pass selects subjects whose resolved policy period has elapsed. Both then run the **same** participant
      loop, hold check, audit and run-recording code, because two copies of this logic is two places for a record to
      be deleted under a hold.
- [ ] **The hold check comes first and is per `(subject, DataClass)` pair**, through `IRetentionHolds` — the predicate
      and its five unit assertions already landed with the fourth child, so this job consumes it and does not restate
      it. A held pair is skipped, counted, and written into `exceptions` **on every run it is skipped**, not only the
      first (`docs/nfr/data-classification.md` section 7 item 4, and the same criterion #192 states for media holds).
- [ ] **A `Pending` retention decision is a skip, never a default.** Where `IRetentionPolicies` answers `Pending`, the
      sweep records reason code `pending_decision` with the decision id (`OD-05`, `OD-08`, `DC-09`, `OD-14`) and
      erases nothing. This is how the open owner decisions stay out of the code path rather than being papered over
      with a fallback. Eighteen of the twenty seeded classes resolve `Pending` on a freshly seeded database, so this
      is the **ordinary** path and not an edge: a first run on seeded reference data erases nothing at all and says
      why, eighteen times.
- [ ] **Statutory exclusions are enforced here, not hoped for.** The classes `invoices_and_notes`,
      `payments_and_refunds`, `receipts_and_cash`, `barcode_and_scans` and `audit_events` are **never offered to a
      participant** whatever their policy says; they are recorded in `exceptions` with reason `statutory_retention` so
      the requester's answer can explain the exclusion. The list is a `static readonly` set in this file with the
      section 7 and section 8 citations in its doc comment, and a unit test pins its membership so a class cannot be
      dropped from it by accident. `docs/nfr/security-operations-targets.md` section 8 row "Scan events, custody
      transfers, ledger entries, posted invoices, payments, receipts" is the source.
- [ ] **Request state advances honestly.** A request moves `Approved` → `Executing` → `Executed` when every offered
      class succeeded, or `PartiallyExecuted` when any was skipped or a participant failed, with `executed_classes`,
      `skipped_classes` and `executed_at` written from the run through `IDataSubjectRequestAdministration`. A
      participant throwing does **not** fail the run: it is caught, recorded as `participant_error`, and retried with
      bounded backoff on the next run.
- [ ] **One transaction per subject, and the run row completed once.** Each subject's participants run inside one
      transaction so a half-erased subject is impossible; the run row is inserted with `finished_at` null and
      completed by the single `UPDATE` the `retention_runs_append_only` trigger permits.
- [ ] **Idempotence is a criterion, not a hope.** A second run against the same data erases nothing further, writes no
      second audit event, and records a run whose `erased` count is zero. The participants are already idempotent;
      this job must not defeat that by re-offering an `Executed` request.
- [ ] **Signals**: counters on `Tailor360Diagnostics.Meter` — `privacy.runs`, `privacy.erased`, `privacy.skipped`
      (dimensioned by reason code and run kind **only**, never by subject) and `privacy.participant_errors`; a
      `NonEssential`-tagged `IHealthCheck` reporting `Degraded` when the last run failed or when no run has completed
      within twice the configured interval; one structured log record per run carrying the counts and the correlation
      id and **no subject identifier beyond the identifier itself**.
- [ ] **Documentation**: add the job to the background-job list of plan decision D12 where the other five are
      described (`docs/platform/`), and record in `docs/nfr/data-classification.md` section 7 that the backup
      consequence — "deleted data persists until backup expiry, and a restore replays the requests executed after the
      restore point" — is carried by **#60**'s restore runbook and is **not** implemented here.

## Acceptance criteria

- [ ] An approved deletion request for a synthetic customer is executed end to end by the job: the request reaches
      `Executed`, `executed_classes` lists the classes the Customers participant erased, the customer row is
      pseudonymised, and a run row records the counts. Driven through the worker and the API, with **no direct
      database writes** in the test.
- [ ] The job declares `[WorkerJob("platform.privacy_lifecycle", WorkerBranchScope.Organisation)]` (ARCH-021) and
      reaches `IWorkerScopeFactory` only from the worker host (ARCH-020), both asserted by the architecture tier —
      `BackgroundContextTests.Arch021_EveryWorkerJobDeclaresItsScope` is the test that fails otherwise.
- [ ] **Negative — the criterion this child exists for**: a subject under an open legal hold is **not** erased; the
      request ends `PartiallyExecuted`; the skip appears in `exceptions` with reason `hold`; and it appears **again**
      on the next run and the run after that, not only the first.
- [ ] **Negative**: releasing the hold lets the next run erase the held classes and move the request to `Executed`,
      and the earlier `PartiallyExecuted` runs remain readable.
- [ ] **Negative**: a class whose policy resolves `Pending` is never erased by the sweep; the run records
      `pending_decision` naming the decision id. A test asserts the job substitutes no period of its own, and a second
      test runs the sweep against a **freshly seeded** register and asserts `erased = 0` with eighteen
      `pending_decision` entries.
- [ ] **Negative**: a participant that throws does not abort the run — the remaining participants still run, the
      failure is recorded as `participant_error`, the request ends `PartiallyExecuted`, and the health check reports
      `Degraded` rather than the readiness probe failing.
- [ ] **Exception**: the job is idempotent — running it twice over the same data produces zero additional erasures and
      zero additional audit events, asserted by comparing `platform.audit_chain_head.last_sequence` before and after
      the second run.
- [ ] **Exception**: two worker instances running at once do not both execute a request — the lease is proved by
      starting two scopes and asserting one run row, the way the existing job tests prove theirs.
- [ ] **Exception**: posted invoices, payments, receipts, ledger entries, scan events and audit events are untouched
      by any pass, asserted by row-hash comparison, and their classes appear in `exceptions` with
      `statutory_retention`.
- [ ] **Exception**: a run interrupted part-way — the process stopped between two subjects — leaves the completed
      subjects erased, the run row with `finished_at` null, and the next run recording a fresh row rather than trying
      to complete the abandoned one.

## Migration and rollback

`dotnet run --project src/Tools/Tailor360.Cli -- migrate --dry-run` reporting no outstanding change and

`docs/nfr/data-classification.md` section 7: the data survives in backups until they expire, and a restore replays the
requests executed after the restore point before the environment is opened — owned by **#60**, referenced here, not
