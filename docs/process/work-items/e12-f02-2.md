Sub-issue of #51. The compatibility handshake exists on both sides and nothing joins them up. The server answers
`426` with `client.upgrade-required` (`src/Hosts/Tailor360.Web/Middleware/ClientVersionMiddleware.cs`), the client
declares `X-Client-Version` on every request (`clients/pwa/src/app/clientVersion.ts`) and already carries the refusal
back as a typed failure (`clients/pwa/src/auth/apiClient.ts` line 122, `UPGRADE_REQUIRED_CODE`, tested at
`apiClient.test.ts:471` — "carries a 426 back with the versions the update prompt is written from"). **Nothing writes
that prompt.** `grep -rn "UPGRADE_REQUIRED_CODE" clients/pwa/src` finds the constant and its tests and no consumer.
This sub-issue builds the update path: detect, tell the person, activate only when they consent, and refuse to keep
working against a server this build cannot talk to.

## What is already built (do not re-build)

- `clients/pwa/src/app/version.ts` — `VERSION_ENDPOINT = '/api/version'`, `fetchVersion()` which **validates** the
  payload rather than trusting it, `useVersion()`, `VersionInfo` with `minimumClient`, `current`, `api`,
  `environment` and `schemaVersion`, and `isProductionEnvironment()`. Use `fetchVersion`; `clients/pwa/CLAUDE.md`
  section 6 says "Do not build a second data-fetching path".
- `clients/pwa/src/app/clientVersion.ts` — `CLIENT_VERSION` (compiled from `package.json` through
  `define.__CLIENT_VERSION__`) and `CLIENT_VERSION_HEADER`. An unknown version is sent as nothing at all; keep that
  behaviour.
- `clients/pwa/src/auth/apiClient.ts` — **read the shapes before writing a line against them.** `ApiError` carries
  `status`, `problem` and `sessionState`, with `code` as a getter over `problem?.code`; `minimumClient` and `current`
  live on the **problem**, not on the error. So it is `failure.problem?.minimumClient`, never
  `failure.minimumClient` — the `ApiProblem` interface declares them at lines 50-53 and the existing test asserts
  them as `failure.problem?.minimumClient` / `failure.problem?.current`. `exactOptionalPropertyTypes` and `strict`
  are both on, so the wrong spelling is a `typecheck` failure rather than a runtime surprise, but do not spend the
  session discovering that. `setSessionChallengeHandler` (line 204) and `runSessionChallenge` (line 209) are the
  single-flight pattern to **copy** for the upgrade latch rather than inventing a second one. And note the existing
  test "does not retry a 426, because only a reload fixes it" — the latch must not reintroduce a retry.
- `clients/pwa/src/components/primitives/Alert.tsx` (tone, title, `onDismiss`, `live`) and
  `clients/pwa/src/components/dialogs/` (`Dialog`, `ConfirmDialog`, `BottomSheet`, `Drawer`). The update prompt is a
  persistent `Alert`, never a toast: `docs/nfr/accessibility-localisation.md` section 6 forbids toasts for sync state
  and actionable errors, and `docs/nfr/a11y-checklist.md` **A11Y-42** is the question asked on the device.
- `clients/pwa/src/components/layout/AppShell.tsx` lines 118-134 — `ShellStatusProvider`, the skip link,
  `RouteAnnouncer` and `TrainingBanner`, in that order. `TrainingBanner` is the precedent for a shell-wide persistent
  notice.
- `clients/pwa/src/offline/registerServiceWorker.ts` from **#E12-F02-1** — the registration handle, and the worker's
  `{ type: 'SKIP_WAITING' }` message listener. This issue sends that message; it does not edit `sw.ts`.
- `clients/pwa/src/i18n/messages/` — one file per family holding both languages, both added to the two spreads in
  `index.ts`; the type gate in `clients/pwa/src/i18n/en-IN.ts` fails `typecheck` if a key exists in one language and
  not the other. The rules are at the top of `messages/shell.ts`.

## What is missing

- No update detection: nothing listens for `updatefound`, `registration.waiting` or `controllerchange`.
- No consumer of `UPGRADE_REQUIRED_CODE`, so a build the server has stopped supporting shows a generic failure on
  whichever screen the person happened to be using.
- No "what changed" surface. `clients/pwa/src/routes/AboutRoute.tsx` shows the running version and nothing about it.

## Scope

- [ ] **`clients/pwa/src/offline/clientUpdate.ts`** — the state machine, framework-free and unit tested:
      `current` (nothing to do), `available` (a waiting worker, or `/api/version` reports a `current` different from
      `CLIENT_VERSION`), `required` (this build is at or below `minimumClient`, or a `426` has been seen),
      `activating`. One exported `applyUpdate()` which posts `{ type: 'SKIP_WAITING' }` to the waiting worker and
      reloads **once** on `controllerchange`, guarded against the reload loop by a module flag.
- [ ] **When it checks.** On start, on `visibilitychange` to visible, and on the `online` event —
      `registration.update()` plus `fetchVersion()`. **No polling interval is invented**: a timer would be a number
      with no source, and `docs/nfr/slo.md` fixes none. Say so in the module comment.
- [ ] **`clients/pwa/src/offline/UpdatePrompt.tsx`** — a persistent `Alert`
      (`clients/pwa/src/components/primitives/Alert.tsx`, whose `live` prop takes `'off' | 'polite' | 'assertive'`
      and defaults to `'off'`) mounted in `clients/pwa/src/components/layout/AppShell.tsx` immediately after
      `<TrainingBanner />` (line 126, inside `ShellStatusProvider` and before the three shell layouts). `available`
      offers "Update now" and stays until taken; `required` is
      **non-dismissable**, states that this device cannot save anything until it updates, and offers only "Update
      now". Both announce through the region they are rendered in, not through a toast (A11Y-40, A11Y-42).
- [ ] **The `426` latch in `clients/pwa/src/auth/apiClient.ts`** — `setUpgradeRequiredHandler(handler)` in the shape
      of `setSessionChallengeHandler`, invoked once when a response carries `UPGRADE_REQUIRED_CODE`; afterwards every
      **unsafe** method (`POST`, `PUT`, `PATCH`, `DELETE`) fails fast with the same `ApiError` without reaching the
      network, while `GET` and `HEAD` continue so the person can still read and finish what they were looking at.
      This is the one change to a single-writer file in this issue; keep it to one exported function and one latch.
- [ ] **`clients/pwa/src/offline/WhatChangedSheet.tsx`** — a `BottomSheet` shown **once per version** after an update
      has taken effect, in the person's language, from `clients/pwa/src/i18n/messages/update.ts`
      (`update.whatChanged.<version>` when a release note exists for that version, otherwise one general sentence).
      "Seen" is a version string in `localStorage` — permitted: `clients/pwa/CLAUDE.md` section 6 forbids anything
      *sensitive* there, and a build number is Public.
- [ ] **`clients/pwa/src/i18n/messages/update.ts`** with `updateEn` and `updateTa`, both added to the two spreads in
      `messages/index.ts` — the prompt, the required-update wording, the blocked-save sentence and the sheet. Tamil
      strings that are not yet translated carry the English text and the
      `// not translated — awaiting native-speaker review` comment, as `messages/shell.ts` requires. A separate family
      from `clients/pwa/src/i18n/messages/offline.ts`, which **#E12-F02-1 creates**; do not create or rename that
      file here, and do not move update strings into it.
- [ ] **Stories** in `clients/pwa/src/offline/updatePrompt.stories.tsx`: available, required, activating, and the
      sheet, each in the pseudo-locale (`clients/pwa/src/i18n/pseudo.ts`, `PSEUDO_LOCALE`, 40% growth). These are
      component stories, so `renderWithProviders`-style wrapping is enough; they are not route stories and need no
      `withAdminApi`.

## Out of scope

Registration, the precache, the cache policy and `sw.ts` itself (**#E12-F02-1**) — including the activation-time
cache cleanup, which lives in the worker. "No unsaved work" as an alternative trigger for `skipWaiting`: this issue
activates **only** on explicit consent, because an unsaved-work registry is a second mechanism and the plan's own
wording allows either. Say so in the pull request. The offline queue's effect on an update — a pending queue is a
reason not to reload, and #E12-F02-5a adds that guard once the queue exists. Release-note authoring and the pipeline
that would generate `update.whatChanged.<version>` from a changelog: out, with one general sentence as the default
(#59 owns release packaging). Client telemetry for service-worker failures (#52).

## Acceptance criteria

- [ ] With a second build deployed, the running client shows the update prompt without being reloaded by hand, and
      taking it activates the new worker and reloads once — not twice, and not in a loop.
- [ ] Declining the prompt leaves the application entirely usable on the old build, and the prompt is still on
      screen; nothing has reloaded and no typed input was lost.
- [ ] When `GET /api/version` reports a `minimumClient` newer than `CLIENT_VERSION`, the prompt is in its `required`
      form, cannot be dismissed, and every state-changing action is refused in the client with the upgrade sentence
      rather than being sent and refused by the server.
- [ ] **Negative:** a `426` on any request latches the `required` state, and a subsequent `POST` fails **without a
      network call**, while a `GET` still succeeds. A named test asserts the `fetch` stub saw no second `POST`.
- [ ] **Negative:** `GET /api/version` failing or answering an unexpected payload leaves the state `current` and
      shows **no** prompt — `fetchVersion` already validates, and a wrong update prompt is as bad as a missing one
      (`clients/pwa/CLAUDE.md` section 6: "The client never asserts what the server has not confirmed").
- [ ] **Exception:** rollback. After the previous asset build is republished with the same minimum client, a client
      that had taken the newer build is told to update again, takes it, and lands on the older build without a
      reload loop and without a stranded `required` latch.
- [ ] The what-changed sheet appears once per version: reloading does not show it again, and a second update shows it
      again for the new version. It is dismissable, focus-trapped by `BottomSheet`, and never blocks work.
- [ ] Accessibility: the prompt is a persistent region, announced politely for `available` and assertively for
      `required`; no horizontal overflow at 320, 360, 768, 1024 and 1280 px at 100% and 200% zoom, using
      `clients/pwa/src/design-system/testing/expectNoHorizontalOverflow.ts` with its own defaults (do not narrow the
      list); `expectNoAccessibilityViolations` from `clients/pwa/src/design-system/testing/axe.ts` clean.
- [ ] **A11Y-OF-08** (`docs/nfr/a11y-checklist.md` section 5.8) is this issue's checklist item, and it is the item
      the whole sub-issue exists to answer: "Is the 'client too old' update prompt announced with plain-language
      instructions and a keyboard-reachable action?" Answer it with a Pass/Fail, the device and the screen reader.
      Section 3.7 names how the state is forced — "a pinned old client build, or an `X-Client-Version` override that
      provokes the 426 response", owner technical reviewer "with #53" — so the fixture already has a documented
      route and you are not inventing one. **A11Y-42** (persistent, never a toast) and **A11Y-43** (announced once)
      also apply.
