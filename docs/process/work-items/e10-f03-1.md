## What is already built (do not re-build)

Everything below exists or is delivered by a named dependency. Re-creating any of it is the failure this section
exists to prevent.

- `src/Platform/Tailor360.Platform.Persistence/Outbox/IOutboxMessageHandler.cs` — the at-least-once delivery
  mechanism, with `EventType`, `HandlerName` (the inbox de-duplication key) and `Schema`. Its doc comment states the
  rule this child must obey: **stage writes, never call `SaveChangesAsync`** — the dispatcher commits the handler's
  writes and the inbox row in one transaction.
- `src/Modules/Billing/Tailor360.Modules.Billing.Infrastructure/Invoicing/OrderFactHandlers.cs` — the worked example
  of one module projecting another module's events: an abstract handler plus one sealed handler per event type, each
  reading the payload into an owned fact and handing it to a projector. Copy this shape.
- `src/Platform/Tailor360.Platform.Persistence/Conventions/ModuleDbContext.cs` — gives a module its own
  `outbox_messages`/`inbox_messages` tables by construction.
- `src/Modules/Inventory/Tailor360.Modules.Inventory.Contracts` — `IStockBalanceQuery` (#39) and `IValuationQuery`
  (#40) are the **only** ways stock figures leave Inventory: `docs/architecture/module-ownership.md` section 5.7 says
  "Reporting valuation figures come from `IValuationQuery` and Inventory events, never from a join on
  `inventory.ledger_entries`". The seven published Inventory events are listed there too.
- `src/Modules/Orders/Tailor360.Modules.Orders.Contracts/Events/GarmentJobCreated.cs` —
  `orders.garment-job-created.v1` carries `OrganisationId`, `BranchId`, `OrderId`, `CategoryKey` and `ServiceTypeKey`.
  It is the category/service dimension source; **do not call Orders for it at read time.**
- `src/Modules/Identity/Tailor360.Modules.Identity.Contracts/Directory/IBranchDirectory.cs` —
  `FindAsync`/`FindManyAsync` answering `BranchSummary` with `Code` and `TimeZoneId`. The branch day boundary comes
  from here, never from a hard-coded zone.
- `src/Platform/Tailor360.Platform.Security/Background/WorkerJobAttribute.cs` — the attribute **and** the
  `WorkerBranchScope` enum, both in that one file (`None = 0`, `OneBranch = 1`, `AssignedBranches = 2`, `Organisation
  = 3`). A worker job declares `[WorkerJob(name, WorkerBranchScope.…, permissions)]` (ARCH-021) and only the worker
  and command-line hosts may reference `IWorkerScopeFactory` (ARCH-020).
  `src/Hosts/Tailor360.Worker/Jobs/DispatchExceptionExpiryService.cs` is the lease-and-interval shape to copy, over
  `src/Platform/Tailor360.Platform.Abstractions/Scheduling/IJobLease.cs`. The attribute's own doc comment states the
  rule this child relies on: the declared permissions are the job's **ceiling**, not a grant, so declaring a key the
  job turns out not to need costs nothing and declaring one it needs and has not got fails loudly.
- `tests/Tailor360.ArchitectureTests/ModuleBoundaryTests.cs` — already asserts ARCH-011
  (`Arch011_ReportingReferencesOnlyContractsOfOtherModules`), so a reach into `Inventory.Infrastructure` fails on the
  first run.

## Scope

- [ ] **`projections_stock_movements`** — one row per projected movement: organisation, branch, location, item,
      movement kind, signed base quantity, unit cost **only where the source event carries one**, occurred-at
      (instant) plus the branch-local date, source reference (`purchase_receipt_id`, `ledger_entry_id`,
      `garment_job_id`), category key and service-type key where a garment job is named, and the event id the row came
      from. Append-only for the projection's own writes; a rebuild truncates and replays (#183).
- [ ] **`projections_stock_position_daily`** — one row per organisation × branch × location × item × branch-local
      date, carrying on-hand, available, reserved and in-transit base quantities as `IStockBalanceQuery` answered them
      at that branch day's close, the instant the snapshot was taken, and the branch timezone identifier the boundary
      was computed in.
- [ ] **Four projection handlers**, one per consumed event, each with its own `HandlerName`:
      `inventory.purchase-received.v1`, `inventory.stock-consumed.v1`, `inventory.stock-reserved.v1`,
      `inventory.stock-released.v1`. A fifth handler consumes `orders.garment-job-created.v1` and maintains the job →
      (category, service type, branch) dimension this child stores on its movement rows; it must tolerate a
      consumption arriving before the job-created event (`docs/adr/0011-reporting-read-models.md` section 4.2:
      projections tolerate events from different aggregates in any relative order) by leaving the dimension null and
      back-filling on arrival.
- [ ] **`reporting.stock_position_snapshot` worker job** — `[WorkerJob("reporting.stock_position_snapshot",
      WorkerBranchScope.Organisation, ReportingPermissions.Read, InventoryPermissions.ViewReports)]`. A pass that
      snapshots every branch is organisation-wide, and `WorkerBranchScope.Organisation` is the member whose principal
      carries `admin.organisation.read_all_branches` (the enum's own doc comment). It declares
      `inventory.view_reports` and **not** `inventory.view_valuation`, because it reads quantities only and this table
      has no cost column at all. It runs under a lease in the shape of `DispatchExceptionExpiryService`, reads each
      branch's `TimeZoneId` from `IBranchDirectory`, and at the branch day's close writes the position rows from
      `IStockBalanceQuery`. Idempotent per (branch, date): a second pass for a date already written replaces nothing
      and writes nothing.
- [ ] **One quantity reconciliation** registered against #183's `reconciliation_runs`/`reconciliation_findings`:
      projected on-hand per item × location at a cut-off compared with `IStockBalanceQuery` at the same cut-off,
      recording source total, projected total, delta and status, and raising
      `reporting.report-reconciliation-mismatch.v1` on a non-zero delta. No new table — #183 owns both.
- [ ] **Metric-dictionary entries** in `docs/reports/metrics.md` for on-hand, available, reserved, in-transit,
      purchase quantity, purchase value and consumption quantity: definition, source event or contract, the cut-off
      and timezone rule, and the limitation each carries. Versioned configuration only — no seeded numbers (DOR-11).
- [ ] **One expand-only migration** scaffolded as `dotnet ef migrations add StockMovementProjections`, plus its row in
      the ledger table of `docs/dev/migrations.md`.
- [ ] Register the handlers and the projector in `ReportingModuleServiceCollectionExtensions`, and the worker job in
      `src/Hosts/Tailor360.Worker`.

## Acceptance criteria

- [ ] Replaying the four Inventory events and `orders.garment-job-created.v1` into a scratch database produces the
      movement rows with their category dimension, and `rebuild-projection` (#183) reproduces them byte-identically.
- [ ] Delivering the same event twice writes one row: the inbox row committed with the handler's writes is what makes
      the second delivery a no-op, and the test asserts the row count and the unchanged checkpoint.
- [ ] A consumption whose `orders.garment-job-created.v1` has not arrived yet is projected with a null category and is
      back-filled when that event arrives — no row is dropped and no handler throws.
- [ ] The position snapshot for a branch is written at that branch's own day boundary, read from
      `IBranchDirectory.TimeZoneId`; a branch in a different zone gets a different boundary in the same pass.
- [ ] **Negative:** a reconciliation run whose projected on-hand differs from `IStockBalanceQuery` at the cut-off
      records a finding with the delta and raises `reporting.report-reconciliation-mismatch.v1`; it does **not**
      correct the projection (ADR-0011: hand-correcting projection rows is never permitted — the fix is a rebuild).
- [ ] **Exception:** `IStockBalanceQuery` unavailable or answering nothing for a cut-off leaves the previous position
      rows untouched, records the run as failed with the reason, and the next pass retries; no partially written day
      is left behind.
- [ ] `ReportingDbContext` maps no table outside `reporting.*` (ARCH-005) and no Reporting project references another
      module's `Infrastructure` or `Api` (ARCH-011).

## Modules, contracts and events

Reporting owns every table here (`docs/architecture/module-ownership.md` section 5.9, `reporting` schema). Inputs
cross the boundary through two of the five sanctioned mechanisms only (CLAUDE.md section 3): **versioned integration
events** through the transactional outbox (`inventory.*`, `orders.garment-job-created.v1`) and **published read
contracts** (`Inventory.Contracts.IStockBalanceQuery`, `Identity.Contracts.Directory.IBranchDirectory`). No
`inventory.*`, `orders.*` or `identity.*` table is read (ARCH-005), and no Reporting project references another
module's `Infrastructure` or `Api` (ARCH-011). Reporting publishes only `reporting.report-reconciliation-mismatch.v1`
and `reporting.report-freshness-breached.v1` (module-ownership section 5.9) and exposes no read contract to any
module. DOR-05: the threat model covering reporting and export abuse is the backlog entry in `docs/security/README.md`
section 3.2 carried by **#56a** — the plan's label (Section 6.2 note 5) for a **not-yet-filed** W2 child of open issue
**#56**, with **ADR-0011 section 4.4** standing in; this child adds no new attack surface because it adds no route.
