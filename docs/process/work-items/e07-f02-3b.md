Sub-issue of #36. Follows E07-F02-3, which ships `/scan` in single mode up to the point of commit: decode, resolve,
feedback, rejections. **This issue adds the commit path** — the set of transitions that need a confirmation card, the
card itself, the three-second undo on everything else, and the `ScanCommandSubmitter` port that #37 fills. It is the
half of single mode that decides whether a garment actually moves, which is why it is reviewed on its own rather than
underneath a viewfinder.

It is sequenced before the endpoint it will call, and that is deliberate rather than an oversight: plan Section 6.2's
W3 row is `#41 → #32a → #32b → (#33 ∥ #35) → (#34 ∥ #36) → #37`, so **#36 precedes #37**, while every commit is a
#37 command. The resolution is a port with a **fail-visible** default: this issue defines the seam and proves the
decision logic against a fake, and #37 registers the real submitter. No acceptance criterion below needs #37.

## Scope

Target: about 550 production lines plus tests. No route, no new message family, no dependency.

- [ ] **`clients/pwa/src/scanning/scanModes.ts`** — `ScanMode = 'single' | 'continuous'` and the
      `CONFIRM_BEFORE_COMMIT` constant holding exactly the five actions FBH-02 proposes: **dispatch, delivery
      confirmed, QC result, cross-branch transfer-out, correction**. The doc comment names **FBH-02**
      (`docs/architecture/sequences/barcode-handoff.md` section 8), states that the real list is branch configuration
      `Scanning:ConfirmBeforeCommit` which the server will serve, and states that this constant is the **default in
      force until it does**. The complementary continuous set — receive, phase start, phase complete, transfer
      accept, stocktake count, material issue — is derived from it as the complement and written **once**, so the two
      lists cannot drift. Nothing is added to either list and nothing removed.
- [ ] **`clients/pwa/src/scanning/scanCommand.ts`** — the `ScanCommandSubmitter` port a screen commits through:
      `submit({ action, jobId, clientEventId, idempotencyKey, source, manualReason? })` returning the outcome or
      throwing an `ApiError`. Its only implementation here is a **fail-visible default** that records
      `fallback.used`, surfaces a named "this action is not available yet" state, and **never claims success**: the
      `POST /api/v1/custody/scans` endpoint is **#37's**. A registration seam (a module-level setter, the shape
      `setScannerTelemetryTransport` already uses) lets #37 register the real one without touching this file's
      callers. Tests drive a fake.
- [ ] **`clientEventId` and `Idempotency-Key` minted at the moment of commitment** with `crypto.randomUUID()`, held
      across every retry of that same command, and never re-minted on a retry — the rule `apiClient.ts` states.
      They are two distinct values with two distinct jobs: the key makes a retry a replay, the client event UUID is
      what #37 deduplicates per actor.
- [ ] **The confirmation card** — job number, current state and the expected action — shown before committing any
      action in `CONFIRM_BEFORE_COMMIT`, rendered through `ConfirmDialog` at the `confirm` tier resolved by
      `resolveConfirmTier(…, shellKind)`, with the refusal rendered **inside** the dialog. It is the screen's amber
      "needs confirmation" state; `ScanOutcome` in `shellStatus.ts` stays `'accepted' | 'rejected'` and is **not**
      widened, because that type belongs to #50's design system.
- [ ] **The undo window for everything else** — a non-sensitive action is sent **after** `UNDO_WINDOW_MS` elapses,
      with `UndoBar` visible and `useUndoWindow` driving it, so an undo inside the window means **nothing was ever
      submitted**. The copy says that plainly: this is a delay before sending, not a compensating action afterwards,
      because `scan_events` is append-only (`barcode-handoff.md` section 4) and nothing can be un-appended.
- [ ] **Offline and the absent endpoint, told apart.** A commit attempted offline shows `OfflineBlockedAction` —
      "needs connection, this will not be queued" — because the persisted queue is **#51** (plan Section 6.2
      dependency note 8) and this screen must not imply one exists. A commit attempted while the real submitter is
      absent shows the **named unavailable** state instead. The two are different sentences and different message
      ids.
- [ ] **Messages** added to `clients/pwa/src/i18n/messages/scanning.ts` under `scanning.commit.*` in **both**
      `scanningEn` and `scanningTa`.
- [ ] **Stories** added to `clients/pwa/src/routes/scanning/scanningScreens.stories.tsx` through `withAdminApi` /
      `StoryRoutes` / `storyJson` / `storyProblem` / `storyPending`: the confirmation card open, the undo bar
      running, a refused commit with the problem inside the dialog, and the unavailable state. **No offline story**
      (`clients/pwa/src/routes/catalog/catalogScreens.stories.tsx` lines 27-33 record why).

Versioned configuration (DOR-11): `CONFIRM_BEFORE_COMMIT` is **configuration in waiting** — a named constant with
FBH-02 quoted, replaced by branch configuration when the server serves it — and the undo duration is the existing
`UNDO_WINDOW_MS`. No number is invented here.

## Acceptance criteria

- [ ] A sensitive action — each of the five in `CONFIRM_BEFORE_COMMIT`, table-driven — **cannot** be committed until
      the confirmation card is answered: the test drives the primary action and asserts the fake submitter was not
      called, then answers the card and asserts exactly one call.
- [ ] The card names the **job number, the current state and the expected action**, taken from the resolve response,
      and that text is announced when it opens (**A11Y-39**).
- [ ] A non-sensitive action is submitted only **after** `UNDO_WINDOW_MS`, with `UndoBar` visible throughout.
- [ ] **Negative:** an undo inside the window results in **zero** calls to the submitter — not a call followed by a
      compensating one.
- [ ] **Negative:** a commit attempted offline calls the submitter **not at all** and shows `OfflineBlockedAction`
      with copy that does not promise a queue; nothing is written to `localStorage` or `IndexedDB`, asserted by a
      test that fails if either is touched.
- [ ] **Negative:** cancelling the card leaves the resolved result on screen and re-readable (**A11Y-SC-11**), and
      does not clear the scan.
- [ ] **Exception:** while the real submitter is absent, committing shows the **named unavailable** state, records
      `fallback.used`, does not throw, does not leave a spinner running and does not claim success. This state is
      visibly different from the offline state.
- [ ] **Exception:** a refused commit renders the `ApiError` through the dialog's own `failure` prop — inside the
      modal, not behind it — and a retry of that same command reuses the **same** `Idempotency-Key` and the **same**
      `clientEventId`, asserted on the fake submitter's recorded calls.
- [ ] Two different commands mint two different key pairs; the same command retried mints none.
- [ ] No axe violation with the card open, with the undo bar running, and in the unavailable state; no horizontal
      overflow at `expectNoHorizontalOverflow`'s **default** widths and zoom levels; every control ≥ 48 × 48 px.
