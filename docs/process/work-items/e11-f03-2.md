Sub-issue of #49. The customer-facing feedback page does not exist, and neither does any route under `/c/`:
`grep -rn "/c/" src/Hosts/Tailor360.Web --include=*.cs` returns nothing today. Plan Section 4.4 (line 393) fixes
what the page must be — "served under `/c/{purpose}/{token}` by a minimal server-rendered page outside the PWA shell
and service-worker scope with its own strict CSP, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`,
rendered in the customer's language" — and #211 builds that mechanism for the `estimate` purpose. This slice adds the
`feedback` purpose's page to it: the form a customer fills in, and the POST that hands it to the
`IFeedbackCapture` contract [E11-F03-1] ships. It is the only slice of #49 that touches
`src/Hosts/Tailor360.Web`, and it adds exactly two routes.

## What is already built (do not re-build)

- `src/Hosts/Tailor360.Web/Endpoints/AppShellEndpoints.cs` — the pattern for serving a nonce-stamped HTML document
  from the host under the enforcing policy of #53: the document is split at the tags needing the attribute and
  rejoined per request, never served from disk, always `Cache-Control: no-store`. Read it before writing a renderer;
  the feedback page has the same constraint and must not re-solve it differently.
- `src/Hosts/Tailor360.Web/Middleware/SecurityHeadersMiddleware.cs` — `PolicyFor(nonce)` and the
  `StaticDirectives` constant (line 54) which already carries `style-src 'self'`, `form-action 'self'`,
  `frame-ancestors 'none'` and `object-src 'none'`. **Do not edit `StaticDirectives`**: it is one of the
  single-session contended constants, and a policy change needs its own review.
- `src/Modules/Identity/Tailor360.Modules.Identity.Api/Recovery/RecoveryEndpoints.cs` — the `POST /recovery` and
  `POST /recovery/confirm` maps are the precedent for an **anonymous, state-changing, audited** endpoint:
  `AllowAnonymousWithJustification(justification, reviewedIn)` + `RequireRateLimiting(...)` +
  `Audited(handler.Action)`. Verified in the working copy. ARCH-007, ARCH-017 and ARCH-008 are all satisfied on a
  route with no session, and this is how.
- `src/Platform/Tailor360.Platform.Security/Endpoints/RateLimitPolicyNames.cs` — the closed catalogue. `DefaultIp`
  is "ordinary unauthenticated requests that are not credential endpoints"; per-token limiting is #211's counters on
  `notifications.customer_links`, not a new policy name.
- `src/Platform/Tailor360.Platform.Security/Antiforgery/` — all verified by reading the files.
  `AntiforgeryEnforcementMiddleware` validates every unsafe method that has no `AntiforgeryExemptionMetadata` by
  calling the framework's `IAntiforgery.ValidateRequestAsync`, which accepts **either** the header **or** the form
  field; its `ErrorCode` constant is `"security.antiforgery-token-invalid"` and the refusal is
  **`403`, not `400`**. `SecurityServiceCollectionExtensions.AddCrossSiteDefences` (lines 84–100) sets
  `options.Cookie.Name = AntiforgeryDefaults.CookieName` (`"__Host-t360.csrf"`, `HttpOnly`, `SameSite = Lax`,
  `Path = "/"`, so it is carried at `/c/`) and `options.HeaderName = AntiforgeryDefaults.HeaderName`
  (`"X-CSRF-Token"`), and **does not set `FormFieldName`**, which therefore stays at the framework default
  `__RequestVerificationToken`.
  **The consequence a session must not discover the hard way**: the cookie is `HttpOnly`, so the page cannot read
  the request token from it. The GET handler calls `IAntiforgery.GetAndStoreTokens(httpContext)` and writes
  `tokens.RequestToken` into a hidden `<input name="__RequestVerificationToken">`; that call is also what sets the
  cookie half on the GET response. No client script is involved, and none may be (`script-src` admits only a
  nonced script and this page has none).
- `src/Hosts/Tailor360.Web/Endpoints/VersionEndpoints.cs` and `AntiForgeryEndpoints.cs` — the `.InternalEndpoint(…)`
  idiom that keeps a non-API route out of `docs/api/openapi.v1.json`. The feedback page is markup, not an
  operation, so it uses it and this slice therefore does **not** regenerate the OpenAPI document or
  `clients/pwa/src/api/schema.d.ts`.
- #211's `/c/{purpose}/{token}` route group, its resolver call, its per-purpose dispatch, its page chrome, its
  language handling and however it serves the page's stylesheet under `style-src 'self'`. **Read all of it first.**
  This slice extends that mechanism with one purpose and one POST; it never stands up a second page mechanism. If
  #211's merged file names differ from the ones guessed below, #211 wins.
- **[E11-F03-1]**'s `Notifications.Contracts.Feedback.IFeedbackCapture` —
  `GetFormAsync(FeedbackLinkToken, ct)`, `SubmitAsync(FeedbackLinkToken, FeedbackSubmission, ct)` and
  `UpdateAsync(FeedbackLinkToken, FeedbackSubmission, ct)` — and `FeedbackForm` carrying the order display number,
  the delivery date, the garment list, the locale and the state (`AwaitingResponse`, `EditWindowOpen`, `Closed`).
  The page renders that record and validates nothing the contract already validates.

## What the page must NOT do, and why it matters here more than anywhere else

**The page never resolves the token itself.** It takes the route value, wraps it in `FeedbackLinkToken` and hands it
to `IFeedbackCapture`. [E11-F03-1]'s body explains why at length: two open siblings of #47 disagree about
whether a feedback token is a `customer_links` row with a `feedback` purpose (#211) or its own `feedback_tokens` row
(#213), `module-ownership.md` 5.10 lists both tables, and the contract is deliberately shaped so that the answer is
a private method inside `Notifications.Application` rather than something this page knows. **Do not call
`ICustomerLinkResolver` from the host**, even though #211's dispatcher does for other purposes: the feedback token's
one-time-plus-one-edit state does not live on the `customer_links` row, and a host that resolved the link itself
would have to go and find that state, which is exactly the cross-module reach `IFeedbackCapture` exists to prevent.
If #211's dispatcher hands a content provider an already-resolved link, the `feedback` provider discards it and
passes the token through — one line, noted in the pull request.

## Scope

- [ ] `GET /c/feedback/{token}` — resolves through #211's dispatcher, calls `GetFormAsync`, renders the form in the
      customer's language. `AllowAnonymousWithJustification` (ARCH-007), `RequireRateLimiting(DefaultIp)`
      (ARCH-017), `InternalEndpoint`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`.
- [ ] `POST /c/feedback/{token}` — one route for both the first submission and the in-window edit: the handler
      already knows which, so the page does not decide. Calls `SubmitAsync` or `UpdateAsync` and re-renders with
      either the thank-you state or the field errors. `AllowAnonymousWithJustification`,
      `RequireRateLimiting(DefaultIp)`, `.Audited("notifications.feedback.submitted")` (ARCH-008), anti-forgery
      validated through the hidden field, `InternalEndpoint`.
- [ ] The markup: one `<form method="post">` with a fieldset per rating dimension as a 1–5 radio group (never a
      hover-only star control), a labelled `<textarea>` for the comment, two checkboxes (contact requested,
      alteration requested) and, when alteration is ticked, a garment `<select>` built from `FeedbackForm`'s garment
      list. No inline script, no inline style, no third-party asset, no web font from another origin.
- [ ] Accessibility, to `docs/nfr/a11y-checklist.md`: every control labelled; the radio groups in a `fieldset` with
      a `legend`; errors summarised at the top of the form, linked to the first invalid control and announced; a
      visible focus ring; 44 px touch targets; readable at 320 px and at 200% zoom; `lang` set to the rendered
      locale. The page is the only screen in the system a customer ever sees, so it carries the checklist in full.
- [ ] Localisation: English and Tamil, the two locales `clients/pwa/src/i18n/` already ships, rendered server-side
      from the same per-locale string set #211's page uses. Do **not** import the client's `react-intl` catalogue:
      it is a different runtime. A locale the page cannot render falls back the way #211's page falls back.
- [ ] The three closed states, each a page and not an error: already submitted and the window has closed; expired or
      revoked or unknown (one body for all three); and the thank-you after a successful submission, which says
      whether somebody will be in touch when contact or an alteration was requested.

## Acceptance criteria

- [ ] A customer opens a valid `feedback` link on a phone-width viewport, fills in five ratings and a comment, and
      posts the form; the response is recorded and the thank-you page is returned — walked end to end over HTTP,
      with no direct database access.
- [ ] Rule-level: both routes declare an anonymous justification with its review reference (ARCH-007), exactly one
      rate-limit policy from `RateLimitPolicyNames` (ARCH-017), and the POST carries `.Audited(…)` (ARCH-008).
      Neither declares a permission as well as a justification (ARCH-022) and neither accepts a second
      authentication scheme (ARCH-019). The contract tier's endpoint inventory shows both as `anonymous`.
- [ ] Negative: a POST with no anti-forgery field is refused by the middleware with **`403`** and
      `security.antiforgery-token-invalid` (`AntiforgeryEnforcementMiddleware.ErrorCode`) and writes nothing. A POST
      carrying the header instead of the hidden field also passes, because `ValidateRequestAsync` accepts either —
      assert the form-field path, since that is the one the page depends on.
- [ ] Negative: a rating of 0 or 6, or an alteration ticked with no garment chosen, re-renders the form with a
      field error, the customer's other answers still in the controls, and no row written.
- [ ] Negative: an expired token, a revoked token and a random 128-bit guess return byte-identical pages, and the
      token appears in no log line, no trace attribute and no `Referer` — asserted, not assumed.
- [ ] Exception: opening the link again after a successful submission shows the edit affordance while the window is
      open and the closed page afterwards; the closed page never says "not found", because the customer did answer.
- [ ] The page renders with no content-security-policy violation under the enforcing policy, and
      `docs/api/openapi.v1.json` is unchanged (both routes are `InternalEndpoint`).

## Modules, contracts and events

The routes live in `src/Hosts/Tailor360.Web` and reach Notifications only through
`Notifications.Contracts.Feedback.IFeedbackCapture` — composition in the web host, the fourth of the five
sanctioned mechanisms (`CLAUDE.md` section 3), and the same arrangement #211 uses so that "Notifications itself
never reads an Orders or Billing table to render the page". The host may reference a module's `Api`,
`Infrastructure` or `Contracts` (ARCH-006) and nothing here reaches past that. No event is published or consumed.
Threat model: the customer-link model #211 owns covers this route's trust boundary — an unauthenticated caller
holding a bearer string — and this slice adds the form-submission arm to it.
